# Hook 0.10.2 正式灰度交付

状态：发布候选。0.10.2 的 Windows 包、后端与运营后台必须从同一冻结提交构建；完成的步骤及证据以 `deliverables/releases/0.10.2/` 为准。此前的 [0.10.1 流程](HOOK-GRAY-0.10.1.md)保留为历史基线。

## 发布目标与环境

- 纳入灰度分支上连续两次已审修复：`7fbb5ff` 隐藏 Worker 启动黑窗并保留失败提示；`07ed0af` 在健康心跳后解除已恢复的连接等待，不自动把暂停或其他故障改成接单中。
- Worker、运营后台、后端包与 `contracts/c2_contract_v3.json` 的合同修订、`contracts/hook_contract_v1.json` 的产品版本统一为 **0.10.2**。Hook 协议结构号 `hook-v1`、C2 结构号 3 不因产品升版而改变。
- 正式环境沿用 `https://jiangsuchejin.com/api`、Docker Compose 和 PostgreSQL 15；Windows 现有已激活的微信 3.9.10.16 x86 与原 Hook DLL 不随本次 Worker 更新替换。

## 发布前检查与备份

1. 核对远端 `gray-release-0.10.x` 最新提交包含两次修复及本次升版；确认工作树没有混入未审代码、密钥或本地证据。
2. 先查看服务器磁盘、Docker 空间、旧发布包和日志。只清理明确过期且与当前/回退版本无关的发布缓存；不动 PostgreSQL、知识库、账号、Worker 绑定、消息或在途状态。
3. 查看 Worker 心跳、接单/任务/未知结果与迁移状态。切换后端前让正在工作的 Worker 按原暂停、排空、正常退出流程处理；不能删记录或强制踢下线来过门禁。
4. 保存现有 Compose 配置、镜像摘要、前端静态文件清单、数据库快照与迁移版本。备份文件须能读取、列出和校验；在不覆盖生产业务事实的前提下保留可恢复的 0.10.1 版本。

## 构建与发布步骤

1. 只执行版本/合同一致性、改动相关的启动器与连接等待测试，以及正式构建工具门禁；复用工程师已通过的其他定向测试证据，不重复全量回归。
2. 在 `gray-release-0.10.x` 上取得匹配当前提交的原生源码证据和发布工具证据，人工触发 `.github/workflows/hook-windows-build.yml`。Windows runner 生成签名候选包并封存清单、摘要和构建运行号；检查工具失败时保留已构建包，按原 SOP 对同包复验。
3. 仅在成品摘要、签名、通道、版本、文件清单与当前源码一致后上传正式下载位置。生产后端及运营后台用相同提交构建，执行迁移并切换，核对镜像与静态资源摘要；客户端更新入口保持人工受控，不擅自开放按钮升级。
4. 现有 Windows 采用保留数据更新：正常退出 Worker，保留 `%LOCALAPPDATA%\CheJinWorkerHook`、原微信进程、Hook DLL、激活与账号。新包的 `Setup-CheJin-Hook.cmd` 只在需要生成/刷新快捷方式时使用；旧 `CheJin Worker` 快捷方式必须重新生成才会隐藏黑窗。配置不一致时停止，不覆盖原绑定。

## 验证、风险与回退

- 服务器：`/healthz`、`/api/openapi.json` 与后台页面显示 0.10.2；后端 `/openapi.json` 的版本和合同文件一致；登录会话、知识库及原账号/Worker 绑定仍在。观察应用、PostgreSQL、Nginx 日志及 Worker 心跳。
- Windows：必须在实机点击重新生成的两个快捷方式，核对微信进程路径、工作目录、`StartPort=<配置端口> ConnectType=http RecvType=0`、DLL 加载、端口归属和 Worker 环境检查；确认黑窗不再常驻、连接恢复后能解除旧等待，暂停状态仍不自动接单。未完成这项实机验证不得标记完整交付通过。
- 失败时停止扩大灰度，保留当前数据库、客户端数据与未知结果；先恢复已验的同 Hook 通道镜像、前端与包，按迁移兼容性决定是否需要单独恢复数据库，不直接用旧备份覆盖新增业务事实。任何回退都验证登录、知识库、Worker 身份、心跳及暂停状态。
- 风险点：本轮改动涉及启动器和 Worker 接单门禁；后台/后端代码未改业务逻辑但产品合同必须同步。旧已创建的快捷方式不自动更新；当前已运行的微信无需因这两项修复重启。
