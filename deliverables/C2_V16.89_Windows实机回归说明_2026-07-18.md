# C2 V16.89 Windows 实机回归说明

## 一、回归版本

```text
客户端：V16.89
压缩包：chejin-worker-client-20260718-v16.89.zip
SHA256：0ae48a51bf6614cb634463ef409a58e186bb49ebfd2911bf1cecfc2c866ad17c
后端：http://192.168.2.106:8000/api
```

本版本只修复 V16.88 实机证明确认的语音转写绑定问题，尚未取得 C2 最终通过结论。

## 二、本次根因

V16.88 点击最下面 customer `6"` 后，微信已经成功展开转写正文，但点击后的 OCR 临时把同一气泡时长识别成 `9 (c`。旧代码把时长数字作为硬身份，因 `6 != 9` 拒绝了角色、局部行和上下结构均唯一匹配的转写结果，将该 anchor 记为失败。Worker 只上报 anchor 已绑定的 voice，因此遗漏了这条真实转写；sidecar 同时错误返回 `voice_transcribe_completed`，没有暴露失败。

## 三、V16.89 改动

1. 时长 OCR 改为辅助证据，不再单独否决语音身份。
2. 时长冲突时，只有同行头像角色、左右 lane、点击局部行和展开文字结构共同指向唯一候选，才允许绑定。
3. 同一区域存在多个候选时继续拒绝，禁止因放宽时长产生跨语音串绑。
4. 被动重拍期间使用同一结构规则重新绑定，不重复物理右键或点击。
5. 每条已绑定 voice 增加 `voice_anchor_binding_evidence`，记录前后时长、候选数、采用策略和接受原因。
6. 只要存在 `failed_voice_anchor_keys`，本轮必须返回 `voice_transcribe_partial`，不得返回 `completed`。
7. Worker 的 V3 安全门不变：仍然只上报 sidecar 已可靠绑定的 voice；后端合同不变。

## 四、重点回归

1. 当前屏幕准备至少两条 customer 语音和一条 self 语音，覆盖相同时长、不同长度正文和上下多个候选。
2. 确认从下到上逐条处理，每条只进行一次物理转写操作。
3. 重点确认最下面 customer 转写后即使时长 OCR 短暂抖动，仍能通过唯一结构绑定并上报。
4. 确认顶部 customer 与右侧 self 均不遗漏，角色分别为 `customer`、`self`。
5. 确认没有重复右键、头像菜单、Esc、主动滚动和微信窗口隐藏。
6. 查看 `voice_transcribe_review.json`：唯一容错应记录 `strategy=unique_structure_with_duration_conflict`、`accepted=true`、`structural_candidate_count=1`。
7. 人为存在多条相邻同侧语音时不得串绑；不能唯一确认的项必须是 `partial`，且成功项仍可正常上报。

```powershell

Expand-Archive -Force .\chejin-worker-client-20260718-v16.89.zip .\chejin-worker-client-20260718-v16.89
cd .\chejin-worker-client-20260718-v16.89\worker-client
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
$env:CHEJIN_API_BASE_URL="http://192.168.2.106:8000/api"

```
