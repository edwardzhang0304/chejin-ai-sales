# P0 运营后台验收标准

> 项目：AI 智能客服售前跟进系统  
> 模块：运营后台 P0 - 线索导入与分配  
> 日期：2026-06-02  
> 验收基准：PRD v0.1、测试交接说明 v0.1、静态稿 `website/ops-admin.html`、Vite 前端 `http://127.0.0.1:5173/`、后端 API `http://127.0.0.1:8000/api`

## 1. 结论

P0 运营后台验收标准为：**真实业务链路可闭环、接口状态可追溯、静态稿一致性满足约定、P0 缺陷清零、性能达到本地基准、UAT 场景通过后，方可判定通过。**

若出现以下任一情况，P0 不得验收通过：

| 阻塞项 | 判定 |
|---|---|
| 人工新增客户失败，或成功后列表/详情不可见 | 不通过 |
| 重复手机号创建了新的有效线索 | 不通过 |
| 重复手机号保存返回 500 或错误结构不可识别 | 不通过 |
| 自动轮询分配不可用，且无失败原因和重试入口 | 不通过 |
| 标记无效、恢复有效、重新分配任一 P0 状态流转错误 | 不通过 |
| 手机号明文查看无审计原因或无审计记录 | 不通过 |
| 静态稿要求的 P0 页面在约定数据和视口下明显不一致 | 不通过 |
| P0 接口存在 5xx、数据错乱、权限绕过或敏感信息泄露 | 不通过 |

## 6. 接口验收标准

| 编号 | 接口 / 链路 | 通过标准 |
|---|---|---|
| P0-API-001 | `GET /readyz` | 返回 API 和数据库健康状态 |
| P0-API-002 | `GET /api/leads` | 支持分页、状态筛选、关键字筛选，返回统一结构 |
| P0-API-003 | `GET /api/leads/stats` | 今日新增、已分配、未分配、重复记录统计准确 |
| P0-API-004 | `POST /api/leads` | 正常新增返回 `OK`，包含新线索和分配结果 |
| P0-API-005 | `POST /api/leads` 重复手机号 | 返回 `409`，错误码 `LEAD_PHONE_DUPLICATED`，`data.created=false` |
| P0-API-006 | `GET /api/leads/{id}` | 返回基础信息、联系方式、备注、分配、重复记录 |
| P0-API-007 | 标记无效接口 | 记录 `invalid_reason`、`invalid_remark`、`invalid_at`、`invalid_by` |
| P0-API-008 | 恢复有效接口 | 按 PRD 规则恢复为 `assigned` 或 `unassigned` |
| P0-API-009 | 重新分配接口 | 未分配线索可重试分配，失败时返回明确原因 |
| P0-API-010 | `GET /api/sales` | 返回销售启用、轮询、排序、名下线索数 |
| P0-API-011 | 销售配置接口 | 启用、停用、轮询、排序变更持久化并影响分配 |
| P0-API-012 | `GET /api/operation-logs` | 明文查看、无效、恢复、导出等关键操作可审计 |

统一响应要求：

| 类型 | 标准 |
|---|---|
| 成功响应 | `code=OK`，`message=success`，`data` 为结构化对象 |
| 业务错误 | 使用稳定 `code`，不得只返回“未知错误” |
| 系统错误 | P0 场景不得出现 500；如出现必须定位并回归 |
| 时间字段 | 返回 ISO 字符串，不得出现 JSON 序列化异常 |
| 敏感字段 | 默认手机号脱敏，明文仅在授权审计场景返回 |

### 7.2 像素级一致性前提

| 前提 | 标准 |
|---|---|
| 数据一致 | 必须使用与静态稿一致的 mock/seed 数据，否则文字内容差异不计为布局通过 |
| 默认选中态一致 | 静态稿默认“已选 2 条”时，Vite 若要求完全一致也必须复现同状态 |
| 详情对象一致 | 静态稿详情为固定客户时，Vite 验收截图需切到同等数据状态 |
| 图标、颜色、圆角、字号 | 必须与静态稿 token 一致 |
| 横向溢出 | 桌面和移动端页面不得产生非预期横向溢出 |

### 7.3 移动端

| 项目 | 通过标准 |
|---|---|
| 页面宽度 | 375px、390px、414px 视口无整体横向溢出 |

## 9. 性能验收标准

当前 P0 为本地 Docker 验收基准，正式生产容量需另行确认【待确认】。

| 指标 | P0 本地通过标准 | 说明 |
|---|---:|---|
| 并发用户数 | 20 | 本地轻量压测 |
| 核心接口 | `GET /api/leads?page=1&page_size=20` | 列表为运营高频入口 |
| QPS | ≥ 150 | 本地 Docker 基准 |
| 平均响应时间 | ≤ 150ms | 不含浏览器渲染 |
| P95 响应时间 | ≤ 300ms | 短时压测 |
| P99 响应时间 | ≤ 500ms | 短时压测 |
| 错误率 | ≤ 0.5% | 业务错误不计入压测错误，5xx 计入 |
| API CPU | 无持续打满 | 观察 `docker stats` |
| API 内存 | 无持续增长 | 观察 `docker stats` |
| 数据库连接 | 无连接耗尽 | 观察数据库连接数 |
| 慢 SQL | 无持续慢查询 | 需后续接入慢 SQL 日志【待确认】 |

压测模型：

| 模型 | 通过标准 |
|---|---|
| 阶梯加压 | 1、5、10、20 并发均无 5xx |
| 稳定性压测 | 20 并发持续 15 分钟，错误率 ≤ 0.5% |
| 峰值压测 | 30 并发 5 分钟，P95 ≤ 500ms【待确认】 |
| 突发流量 | 1 秒内突增到 20 并发，无服务崩溃【待确认】 |

## 10. 缺陷分级与通过规则

| 等级 | 定义 | 验收规则 |
|---|---|---|
| S1 阻塞 | 主链路不可用、数据错误、敏感信息泄露、5xx、重复手机号创建有效线索 | 必须修复并回归通过 |
| S2 严重 | P0 功能局部失败，但有明确人工绕行，不造成数据错乱 | 原则上修复；如遗留需项目负责人签字确认 |
| S3 一般 | 文案、轻微样式、非 P0 体验问题 | 可进入遗留清单 |
| S4 建议 | 优化项或后续能力 | 不阻塞 P0 |

P0 通过条件：

| 条件 | 标准 |
|---|---|
| P0 功能用例 | 100% 通过 |
| P0 API 用例 | 100% 通过 |
| UAT 场景 | 核心 6 条通过，或失败项均非 P0 且签字确认 |
| S1 缺陷 | 0 个 |
| S2 缺陷 | 0 个，或有条件通过并明确责任人和修复日期 |
| 性能基准 | 达到第 9 节标准 |
| UI 静态稿一致性 | 达到第 7 节标准 |
| 验收证据 | 截图、接口响应、测试报告、缺陷记录齐全 |
