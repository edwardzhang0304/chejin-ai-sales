# V16.107 之后问题根因与修复简表

口径：

- `V16.107` 是当前 Windows 已通过基线。
- 下表是之后的 C2-C3 开发内容，尚未升级版本、尚未打新包。
- 只记根因，不重复记录同一根因造成的不同现象。

| 问题 | 根因 | 修复 |
|---|---|---|
| 图片有两套入口 | 旧图片流程没有删干净 | 只保留新版 Vision；图片只在内存处理 |
| 图片、语音会重复操作 | 操作前没统一查本地账本 | 先查稳定消息身份；旧消息不再右键或识图 |
| 文字、语音、图片顺序错 | 三种消息分开追加 | 最终画面统一排槽位，再从上到下上报 |
| 重启后历史消息重复入库 | 新旧版本消息身份不兼容 | Worker 做身份迁移；后端唯一键最终去重 |
| 入库失败后重复操作微信 | 处理结果和入库结果绑在一起 | 增加 Outbox；只重传 JSON，不重做 RPA/Vision |
| Brain 任务卡住或被抢 | 普通任务线程和 C2 都能领回复 | 回复只由当前 C2 会话流程领取；支持恢复和失败收口 |
| 等 Brain 后没有权限发送 | 普通读取授权不能覆盖 `ai_active` | 后端签发只属于当前批次的续行票 |
| 旧 Outbox 抢走新回复 | 旧请求也能推动状态机 | 旧事实可补录；没有正确批次票就不能触发 Brain |
| Brain 超时仍在后台运行 | 线程超时不能真正停止请求 | Brain/Vision 改成独立子进程；超时或停止时直接终止 |
| Brain 配置互相冲突 | 同时保留两套模型配置 | 正式环境只保留一套模型、地址和协议 |
| AI 回复会被当成人工销售 | 只看右侧 `self` 和相同文字 | 记录 AI 新气泡稳定身份；后端再标记 `ai/human` 来源 |
| 回复可能没发出却报成功 | 按 Enter 或点击后没有证明结果 | 找真实输入框和发送按钮；必须看到输入框清空和新增右侧气泡 |
| 会删除销售草稿 | 不区分人工草稿和程序文字 | 发现未知草稿立即停止；只允许清理已证明属于本次程序的文字 |
| 转人工后又被 AI 激活 | 状态、开关和转人工记录各算一套 | 未关闭的 HandoffEvent 成为唯一人工接管门禁 |
| `pause/no_action/recall` 状态错 | Brain 非发送结果没有完整合同 | 三种结果明确映射，并恢复正确会话状态 |
| 停止监听后长动作还继续 | Vision、Brain、发送只在开始前检查 | 长动作中持续续租和检查授权；停止后终止子进程/RPA |
| 重复截图、菜单污染 | 每个小步骤各自截图，异常未统一收口 | 复用同一有效画面；菜单异常统一关闭且不用 `Esc` |
| 历史销售消息误解除新接管 | 把“本次扫描时间”当成“消息发送时间” | 只认真实消息时间；无法证明就保持人工接管 |
| 真实销售回复无法解除接管 | OmniAuto 没有逐条消息时间，后端却只认时间 | 无时间时比较最终画面的稳定消息身份和上下顺序 |
| 刷新后客户插入新消息仍发送旧回复 | 最终读取结果没有传到发送动作 | 传递消息序列指纹；输入前、点击前都不一致就停止 |
| UI 锁续租失败后仍操作微信 | 续租线程失败后静默退出 | 记录 `lease_lost`；所有长动作共用取消门禁 |
| 加好友丢锁后仍操作微信 | C1 没把停止和锁状态传给 sidecar | 加好友共用取消门禁；丢锁立即终止 sidecar |
| 旧代码容易被误接回 | 已退役入口和无用参数仍留在正式代码 | 删除四段无调用代码和 `locate_payload` |
| OCR 顺序被当成真实上下关系 | 有些消息没有气泡坐标，程序仍拿 OCR 返回顺序解除人工接管 | 只有全屏消息都有真实气泡坐标时，才允许顺序影响状态；否则只排序，不做业务决定 |
| 缺少会话身份时 Worker 自己造一个 | Sidecar 没给 `rpa_session_key` 时，用标题和行号拼了临时身份 | 缺少真实会话身份就排除并记录原因，禁止点击、授权和读取 |
| Worker 再猜消息类型和发送方 | 正式字段缺失时，用时长、内容或旧别名猜成语音、文字、客户或销售 | 只接受 OmniAuto 正式值；缺失或旧别名统一为 `unknown` 并触发安全门禁 |
| 同一服务端任务可能被两个客户端继续执行 | 任务只有 `running`，没有所有者、到期时间和防旧票编号 | 增加任务租约、定时续租和 fencing token；旧进程不能继续改任务或点微信 |
| 任务线程会把 C2 正在使用的微信动作领成失败 | “微信是否空闲”和“拉取任务”不是一个原子步骤 | 拉任务前后共用调度锁并再次检查 UI 锁；忙时任务继续留在后端排队 |
| 历史销售消息会解除新人工接管 | 有时间字段时忽略了最终画面的真实上下顺序 | 最终画面顺序优先；销售在触发消息上方时绝不解除，可靠微信时间只作降级证据 |
| 延迟历史消息会把最近消息时间改早 | 后端直接用本次消息覆盖会话最近时间 | 最近客户、我方和销售回复时间统一只增不减 |
| C1 停止被记成 C2 授权失败 | Sidecar 取消路径写死了 C2 错误码 | 取消回调透传真实原因；Worker 停止、任务租约和 UI 锁分别记录 |
| 超大入库请求仍可能先占满内存 | 只检查可伪造或缺失的 `Content-Length` | ASGI 接收数据块时实时累计，超过上限立即 413 |
| C2 正在发送回复但心跳显示空闲 | C2 领取 `chat_reply` 后只启动租约，没有设置心跳读取的 `current_task` | 领取后立即标记任务；所有出口统一清理任务和租约 |
| 两个请求可能同时领取同一任务 | 后端先普通查询 `pending` 再修改，没有锁任务行 | 领取改为 `SELECT ... FOR UPDATE`；只有一个请求能签发租约 |
| 没调用 Vision 的图片被永久判失败 | 历史断层和真正模型失败共用同一个 `failed` 终态 | 上下文不安全时只延期且不写终态；门禁解除后允许处理一次 |
| 一条语音失败时 Brain 仍会回复 | 失败语音只记在 Worker 本地，没有进入正式 V3 事实，后端拿不到角色和位置 | 成功语音照常入库；客户和销售失败语音都形成 failed voice，按最终画面顺序阻断 Brain 或确认销售介入 |
| 客户失败语音下面已有销售回复却再次转人工 | 语音门禁只有错误码，没有最终画面位置，后端无法证明销售回复在后 | failed voice 携带 `screen_order + failed_voice_visual_top`；后续销售消息可按可靠顺序解除门禁 |
| 失败语音账本一直显示等待上报 | partial 与成功消息同批返回结果时，只确认成功消息的 source key | 后端 200 接受门禁后同步确认 `failed_voice_source_keys`，本地状态改为 `confirmed` |
| 未通过好友挤掉真实客户 | 所有 `friend_request_sent` 都进入最高优先级队列，最后又只保留 20 个 | 只有最近 90 秒在首屏真实出现的好友短码才进入激活队列 |
| 回复失败却显示本轮成功 | 最终结果只检查消息有没有入库，没有检查 Brain、领任务和发送是否完成 | 分开记录事实入库和会话闭环；技术失败明确返回失败，人工接管等正常终态仍算完成 |
| 任务线程与 C2 偶发抢 UI 锁 | “没有任务”和“取得 UI 锁”之间没有共用同一把协调锁 | 检查任务和取得 UI 锁改为一个原子区间；后来的任务继续排队 |
| 转写期间新到语音被永久判失败 | 最终画面里的所有未转写语音都被并入本轮失败集合，没有区分动作开始前后 | 只有动作前候选可进入本轮终态；处理中新增语音不入库、不进 Brain，下一轮处理 |
| Outbox 重传会重新打开已经解除的门禁 | 后端遇到重复消息直接跳过，也跳过了已入库销售来源和顺序证据 | 重传时从已入库事实恢复 `ai/human` 来源，只复现原门禁结论，不重复触发 Brain |
| 授权过期后失败语音事实丢失 | 旧 Outbox 放弃后账本仍禁止右键，但新授权流程不会重新组装失败事实 | 从失败账本恢复同一 V3 failed voice，用新授权只重传结构化事实，不再操作微信 |
| 用户停止被写成语音永久失败 | “本轮取消”和“业务转写失败”共用失败终态 | 停止或授权撤销只中断本轮，不写失败账本；恢复后按新画面重新判断 |
| 语音全部失败后同屏消息要等下一轮 | 把“语音动作失败”误写成“整个会话流程结束”，并把错误行为固定进测试 | 只结束失败语音动作；仍复核最终画面，把失败语音、文字、图片和销售消息同批上报 |
| AI 输入失败后留下草稿 | 输入已发生但 OCR 未确认时直接退出，没有执行程序草稿清理 | 只有“本次确实输入过 + UIA 内容与本次 AI 原文完全一致”才清空；否则保留并转人工 |
| 暂停接单后 C2 仍扫描微信 | C2 后台线程和长动作没有统一检查本地 `run_status` | 所有微信 UI 动作共用一个暂停门禁；心跳和已保存 Outbox 仍可继续 |
| Vision 缺配置后整个会话不再读取 | 把“图片能力暂停”误写成“会话暂停” | 只延期图片并阻断 Brain；同屏和后续文字、语音、销售消息照常入库 |
| AI 气泡停机一天后被当成人工销售 | 本地和后端都按 24 小时删除发送凭证 | 凭证保留到该稳定气泡得到后端 `ingested/duplicated` 确认后再消费 |
| 开始/暂停显示与后端不一致 | 先改本地状态，再请求后端，失败后没有一致的补偿 | 开始必须后端确认后生效；暂停先本地停 UI，再自动重试后端并显示同步失败 |
| 文字、语音、图片各自判断角色可信度 | 相同规则散落在 Worker 和 Vision 多处硬编码 | 唯一规则从 `c2_contract_v3.json` 读取；各流程只调用公共校验函数 |
| Vision 暂停请求被后端 409 拒绝 | Worker 自创了合同不认识的位置来源 | 临时能力门禁统一由合同构建，使用真实槽位位置；不可重试的 4xx 会终止旧 Outbox |
| Vision 缺配置后永久转人工 | 临时能力暂停和真实识图失败共用普通 flow gate | 临时门禁只阻止 Brain，不创建 handoff；文字、语音照常入库，配置恢复后补图并恢复批次 |
| AI 已发出但回执失败后被当人工销售 | sent_ack Outbox 与 C2 扫描没有先后屏障 | sent_ack 未确认时禁止 C2 扫描；后端把合法 `sending` 凭证标记为 `ai_pending_ack` |
| 转写期间新增语音被拆到下一轮 | 最终画面发现新语音后直接释放当前会话 | 保持当前会话和 UI 锁；只要待处理集合有变化就继续，明确无进展或失败才结束 |
| AI 可能已发出但确认失败后被当人工销售 | 点击发送前没有可靠保存“这条气泡可能来自 AI” | 物理发送前保存 `possible_ai_send`；下一轮只把第一条匹配的新稳定气泡标记为 `ai_unreconciled`，不得关闭人工接管 |
| 前一条语音失败后不再处理后来语音 | 失败状态错误地阻断了整个待转语音集合 | 失败语音只进入本轮排除集合；当前屏其他新语音继续逐条处理 |
| 语音失败后图片也不识别 | Brain 安全门禁和图片操作门禁共用一个总开关 | 语音失败只阻断 Brain；只有历史断层或身份冲突才禁止图片操作 |
| 一条坏 Outbox 永久堵住所有会话 | Worker 不知道后端错误是否值得重试 | 后端统一返回 `data.retryable`；不可重试数据进入 dead-letter 并报警，其他会话继续 |
| 超过 20 个目标后部分会话永远轮不到 | `read-targets` 每次固定截取相同的前 20 条 | 按 `last_read_dispatched_at` 公平轮询；长动作只复核当前会话轻量授权，不受队列轮换影响 |
| 点过发送后界面空白却按失败处理 | 后续 OCR 结果覆盖了“发送按钮已经点击”这个不可逆事实 | Sidecar 明确返回 `physical_send_triggered`；点过后任何不确定都只能是 `SEND_RESULT_UNKNOWN`，AI 保护不得删除 |
| 后续新增语音的失败结果会消失 | 循环只返回最后一轮结果，失败锚点又被加入排除集合 | 失败来源和角色全程只增不减；调用方使用并集，后一轮不能覆盖前一轮 |
| 坏 Outbox 隔离后每轮又重新生成 | Outbox 已是 `abandoned`，对应消息 ledger 仍是 `waiting` | 永久结构错误同步隔离 ledger；授权过期保留事实，等新授权重新组装 |
| 本机状态丢失后未知 AI 气泡被当成人工销售 | AI 气泡保护只存本机，后端未利用已有的未知发送记录 | 后端对一条未消费的 `unknown_send_result + 同文` 气泡做保守保护；标记待对账 AI，不关闭人工接管，后续同文仍可按人工判断 |
