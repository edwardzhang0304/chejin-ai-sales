# C2 图片流程唯一状态机与三层整改说明

日期：2026-07-30
状态：三层运行代码与机器合同已按本文整改，待 Windows UAT
适用范围：OmniAuto、车金 Worker、车金后端、Windows UAT

## 1. 本次收口结论

图片不是独立任务，而是 C2-C3 单会话串行事务中的一种消息类型。一个会话一旦进入最终画面处理，当前屏内每条可信的新图片必须在本次 Flow 内形成明确终态，不允许留下由下一轮继续接管的图片业务 `pending/deferred`。

唯一口径：

```text
启动 C2 前：
Vision 配置完整 -> 允许进入 C2
Vision 配置缺失 -> C2 全局 not_ready，不扫描、不打开会话

进入单会话后：
不在最终画面 -> 本轮不存在该槽位，不处理、不门禁
最终画面存在但角色不可信 -> ignored，不调用 Vision
最终画面存在且角色可信 -> NEW_IMAGE
NEW_IMAGE -> completed / failed
OLD_COMPLETED / OLD_FAILED -> 不重复右键、不重复 Vision
OUTBOX_WAITING -> 只重传原 JSON
```

`C2_IMAGE_PROCESSING_DEFERRED` 从目标架构删除。它不能作为图片业务状态、Brain 门禁或跨轮恢复协议。

## 2. 为什么删除 deferred

旧方案允许先保存同屏文字，再把未处理图片标成 `deferred`，后端不创建 Brain 批次。该方案没有定义图片被顶出屏幕后由谁解除门禁，也没有定义已经入库的文字如何重新触发 Brain，可能导致客户事实已入库但永远没有回复。

本次恢复最初的简单不变量：

```text
一个最终画面中的新消息，在离开当前会话前必须全部收口。
```

不能唯一定位、不能复制、模型失败或结果非法，都属于明确的图片处理失败，不是等待下一轮的理由。

## 3. 最终画面边界

1. 语音处理完成后建立 `final_read`。
2. 只有 `final_read` 中仍可见的消息才建立槽位。
3. 被语音展开或新消息顶出最终屏幕的图片，本轮不处理、不上滚、不从旧截图恢复。
4. 图片动作前页面再次变化时，先重新读取完整当前画面并重建最终槽位。
5. 重建后图片已经不在屏幕，删除本轮旧候选，不产生 failed 或门禁。
6. 重建后图片仍在屏幕但无法唯一匹配原稳定身份，形成 `item_state=failed + C2_IMAGE_SLOT_RECONFIRM_FAILED`。

## 4. 单张图片状态机

| 当前状态 | 条件 | 结果 | 是否允许再次自动处理 |
|---|---|---|---|
| 未进入 C2 | API Key、模型或地址缺失 | Worker 全局 `vision_not_ready` | 配置修复后重新启动/预检 |
| 不在 final_read | 图片已被顶出最终屏幕 | 本轮无该槽位 | 后续自然可见时按新一轮观察 |
| `NEW_IMAGE` | 同行头像角色不可信 | `ignored` | 否 |
| `NEW_IMAGE` | 动作前重建画面后不再可见 | 从本轮候选移除 | 后续自然可见时重新观察 |
| `NEW_IMAGE` | 仍可见但稳定身份无法唯一确认 | `failed` | 否 |
| `NEW_IMAGE` | 右键、菜单或复制明确失败 | `failed` | 否 |
| `NEW_IMAGE` | 复制已触发但结果无法确认 | `failed + IMAGE_PROCESS_RESULT_UNKNOWN` | 否 |
| `NEW_IMAGE` | Vision 超时、异常或结果非法 | `failed` | 否 |
| `NEW_IMAGE` | Vision 成功且合同合法 | `completed` | 否 |
| `OLD_COMPLETED/OLD_FAILED` | 本地 ledger 命中终态 | 使用缓存事实 | 否 |
| `OUTBOX_WAITING` | 后端尚未确认 | 原样重传 JSON | 不重复图片动作 |

允许在同一个 Flow、同一张内存图片上进行一次受控的模型网络重试；不得重新右键、重新复制，也不得跨轮重复 Vision。

## 5. 三层唯一分工

### OmniAuto

- 看当前微信画面，发现图片矩形。
- 执行重新截图、重新定位、右键、菜单 OCR、复制和剪贴板读取。
- 返回实际物理 `visual_side`、指纹、邻近锚点和动作证据。
- 不决定 `customer/self`，不生成跨轮消息身份，不决定 Brain 门禁。

### Worker

- 在 C2 启动前完成 Vision 全局能力预检。
- 使用统一同行头像规则确定图片 `sender_role`。
- 建立最终槽位、`screen_order`、`source_message_key` 和本地 ledger。
- 决定 NEW/OLD/OUTBOX，并保证每个当前屏 NEW_IMAGE 收口为 `completed/failed/ignored`。
- 将文字、语音、图片按最终顺序一次性提交现有 `messages/ingest`。

### 后端

- 校验授权、短码、private、V3 合同和幂等键。
- 持久化 completed/failed 图片事实，执行数据库最终去重。
- customer 图片失败时按确定性业务门禁阻断 Brain，并进入既有 handoff 状态；不创建“人工修图片消息”的任务。
- 完整批次可用时创建 `message_batch`，调用回复 Brain/Guard，并通过任务中心下发发送动作。
- 不承担 Worker 本地图片 pending 队列，也不提供图片专用上传接口。

## 6. 唯一角色和物理证据

```text
sender_role = C2 同行头像规则的业务结论
visual_side = OmniAuto 当前截图观察到的物理左右侧
visual_side_consistent = sender_role 与 visual_side 是否一致
```

`visual_side` 只能用于诊断和点击证据，不得参与：

- customer/self 定案；
- 图片跨轮身份；
- 相同图片出现次数分组；
- 是否允许调用 Vision；
- 后端状态机。

相同图片的出现序号必须使用 C2 已确认角色和稳定邻近锚点生成，不能使用 Vision 几何侧作为隐藏分组条件。

图片动作前重新截图时，必须再次运行同一个 C2 同行头像规则。初始
`sender_role` 与刷新后的 `sender_role` 必须相同且均为
`customer/self`；不同或刷新后为 `unknown` 时零点击并形成
`C2_IMAGE_SLOT_RECONFIRM_FAILED`。`visual_side` 即使与两次 C2 角色冲突，
也只记录诊断，不参与这项业务判断。

图片观察结果使用失败关闭规则：

```text
检测成功 + 0 张图片 = 正常零图片
检测器/物理锚点异常 = C2_IMAGE_OBSERVATION_FAILED
```

第二种情况必须作为结构化 observation contract error 交给 Worker，在任何
语音、图片动作、消息入库和 Brain 前阻断，禁止用空图片列表吞掉异常。

## 7. 接口收口

继续使用：

```text
POST /api/workers/{worker_id}/wechat/messages/ingest
```

允许入库：

```text
image + item_state=completed
image + item_state=failed + content=null + error_code/reason
```

不允许入库：

```text
image + pending
image + deferred
image + discovered
原图/Base64/image_local_path
```

删除目标：

- `C2_IMAGE_PROCESSING_DEFERRED`
- `unresolved_new_source_keys` 跨轮业务语义
- 图片临时 Brain 门禁
- “文字先入库、图片以后补、再唤醒原文字”的补偿链路

后端通用 `capability_paused` 只保留给请求级合同、版本或 schema 不兼容，不再表示 Vision 配置缺失或单张图片未处理。

## 8. 一次性整改范围

### 客户端工程师

1. 增加 C2 启动前 Vision 全局预检，缺配置时不进入扫描循环。
2. 删除单会话图片 `deferred` 和对应临时 Brain 门禁。
3. 页面变化时重新建立 final_read；已出屏图片从本轮删除，仍可见但无法唯一确认则 failed。
4. 修正相同图片 occurrence 分组，不允许 `visual_side` 间接参与业务身份。
5. 修正 `sender_role/visual_side/visual_side_consistent` 字段含义。
6. 门禁详情按完整语义去重，不能只按 `error_code` 删除不同角色证据。
7. 不改回车金已有短码、private、角色、语音、去重、停止、Outbox、单会话串行和发送约束。

### 后端工程师

1. 新合同不再接受 `C2_IMAGE_PROCESSING_DEFERRED`。
2. failed 图片继续作为消息事实入库，customer failed 确定性阻断 Brain。
3. 删除图片临时门禁下“保存文字但不建批次”的新路径。
4. 保留通用 Outbox `retry / refresh_and_rebuild / capability_paused`，但不得与图片业务状态混用。

### 测试工程师

必须按状态转换矩阵测试，不再只测单个修复案例：

1. 单张 customer/self 图片成功。
2. 单张图片模型失败。
3. 图片动作前被顶出屏幕。
4. 图片仍可见但重新定位不唯一。
5. 两张相同图片、不同角色。
6. 两张相同图片且 Vision 几何侧与 C2 角色冲突。
7. 图片处理期间新增文字、语音和图片。
8. 崩溃发生在右键前、复制后、Vision 返回后、入库前。
9. 重启后不重复右键、不重复 Vision、不重复入库。
10. 图片失败时同屏文字和语音仍入库，但不错误触发 Brain。

## 9. 发布顺序

1. 先修改 Worker/OmniAuto 与自动化测试。
2. 同步修改后端合同和处理逻辑。

## 10. 当前代码状态

- OmniAuto、Worker、后端与 `contracts/c2_contract_v3.json` 已在同一轮整改中升级。
- 图片业务状态已删除 `pending/deferred`；旧
  `C2_IMAGE_PROCESSING_DEFERRED` 和
  `C2_VISION_CAPABILITY_PAUSED` 仅保留在机器合同的退役错误码清单中，
  后端收到旧请求会拒绝且不会保存部分事实。
- Vision 配置已在 C2 扫描和打开会话前执行全局预检；缺配置时 C2
  为 `not_ready`，不会进行微信 UI 操作。
- 当前屏图片统一收口为 `completed/failed/ignored`；动作前已出屏图片从
  本轮候选移除，不产生门禁。
- `visual_side` 仅保留为物理诊断证据，图片角色和出现次数分组使用 C2
  同行头像角色。
- 图片动作前会用统一同行头像规则重新确认角色；两次 C2 角色不一致或
  刷新角色为 `unknown` 时保持 `not_attempted`，不右键、不复制、不调用
  Vision。
- 图片检测成功为零与图片观察异常已使用不同合同结果；观察异常返回
  `C2_IMAGE_OBSERVATION_FAILED` 并在 Worker 入库和 Brain 前阻断。
- 自动化已覆盖三层合同、旧门禁拒绝、角色冲突、图片移出当前屏、
  重新定位失败、图片后新增消息和 Brain 阻断。
- 图片阶段统计改为按 `source_message_key` 唯一累计，多轮刷新和历史缓存
  不再覆盖或重复计算本轮结果。
- Worker 只上报图片 `completed/failed/ignored` 事实；客户失败图片是否
  阻断 Brain 由后端根据已入库事实统一决定，Worker 不再维护第二套图片
  业务门禁。
- 图片处理前后仍各自基于当时的权威画面重建增量计划，但消息排序、角色
  可信度和门禁投影共用同一组纯函数，不再复制规则。
- `C2_VISION_CAPABILITY_PAUSED` 和 `C2_IMAGE_PROCESSING_DEFERRED`
  只存在于未正式发布的中间开发包，正式产品不承担其本地 Outbox 迁移。
  Windows UAT 前由测试准备步骤清理中间开发版 SQLite；后端继续拒绝
  退役错误码，防止旧请求混入新合同。
- 已删除无生产调用者的旧图片匹配包装函数和无效窗口状态字段，避免后续
  工程师误接回第二套路径。
- 当前尚未生成新的 Windows 包；完成 Windows 图文语音混合 UAT 后，
  才能作为正式发布基线。
