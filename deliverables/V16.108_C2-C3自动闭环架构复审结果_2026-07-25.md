接管客户，属于会话业务状态；它不等于让人到后台修 Outbox 或 sent_ack。

## 二、正式闭环口径

1. 消息事实只有后端确认 `ingested/duplicated` 后，Worker 才能开始新的微信 UI 动作。
2. 语音或图片识别失败以 `item_state=failed + error_code` 走原
   `messages/ingest` 入库；后端仍返回 `ingested`，但不把残缺上下文交给 Brain。
3. 网络和服务端临时故障按有上限的指数退避间隔自动重试，不按固定次数放弃原事实。
4. 授权失效只刷新授权外壳，消息身份、正文和证据不变。
5. 请求级合同、身份或版本整体不兼容时进入 `capability_paused`，冻结原 Outbox，
   阻断新 UI 动作并自动探测恢复；不建立人工消息处理队列。
6. `sent_ack` 的 `sent/failed/unknown` 都是后端可确认的正式终态。
7. `unknown` 表示物理发送可能发生；后端确认后结束原回复动作，禁止自动补发。
8. sent_ack 网络失败时只重传原回执，不再次点击发送，不进入 `abandoned`。
9. Worker 的 C2 扫描和任务中心领取 `add_friend/chat_reply` 必须共用同一个全局事务门。

## 三、代码审计发现与整改结果

### P0-1 任务中心绕过消息 Outbox 门禁

心跳线程在领取任务前只恢复 sent_ack，没有检查 C2 消息 Outbox。消息尚未交给后端时，
任务中心仍可能领取并执行 `add_friend`。

整改：建立唯一 `worker_transaction_barrier`，由 C2 循环、心跳任务领取和恢复线程共同调用。
门禁未清空时不得领取或执行任何新的微信 UI 任务。

状态：**已完成**。心跳领取、任务领取、首屏扫描、会话读取均调用同一事务门；
已增加“消息 Outbox 未确认时不得领取 add_friend”反例测试。

### P0-2 Worker 仍会丢弃 quarantined 消息链路

机器合同仍定义 `quarantine -> quarantined`，网络最多重试 20 次。达到上限或遇到合同
错误后，Worker 隔离 Outbox 和 ledger，并允许后续会话继续。该行为与自动闭环口径冲突。

整改：

- 机器合同改为 `retry / refresh_and_rebuild / capability_paused`。
- 删除固定次数后放弃事实的转换。
- 增加 `next_attempt_at` 和指数退避。
- `capability_paused` 保留原 Outbox，并通过后台健康检查自动恢复。
- 消息级失败由后端作为 failed 事实接收，不使用请求级 `capability_paused`。

状态：**已完成**。机器合同升级为 `3.6.0`，固定 20 次和固定刷新次数上限已删除；
连续失败 25 次后原 JSON、错误和尝试次数仍完整保留。

### P0-3 sent_ack 仍存在 abandoned 放行

Worker 收到不可重试响应后会把 sent_ack 标记为 `abandoned`，随后恢复函数将其视为已经
收口并解除门禁。物理消息可能已经发送，但后端可能没有收到 Worker 的正式回执。

整改：

- 删除生产链路中的 `abandoned`。
- 网络失败持续按退避周期重传原 sent_ack。
- 请求结构异常进入 `capability_paused`，不得放行新 UI 动作。
- 后端对 `sent/failed/unknown` 核心结果先持久化；辅助证据异常只记 warning。
- 后端已经因 stale sending 自动进入 `unknown_send_result` 时，Worker 后续查询或重传
  必须得到幂等的“终态已确认”，不能再收到普通 claim conflict。

状态：**已完成**。sent_ack 不再进入 `abandoned`；网络失败按
`1/2/5/10/30/60` 秒退避。后端已进入 `unknown_send_result` 时，
晚到回执只做幂等对账，不改变终态、不允许补发。

### P1-1 缺少旧本地状态自动迁移

已经安装过旧版本的 Worker 可能存在 `quarantined` 消息 Outbox 和 `abandoned` sent_ack。
新版本如果只修改新写入逻辑，旧记录仍会被静默跳过。

整改：

- 启动迁移把保留完整 payload 的 `quarantined` 转为 `capability_paused`。
- 把具有完整 ack payload 的 `abandoned` 转回待重传状态。
- 迁移必须幂等，并保留原错误、尝试次数和动作证据。

状态：**已完成**。SQLite 启动迁移已覆盖旧消息 Outbox、ledger 和 sent_ack，
并有原 payload、错误和次数不丢失测试。

### P1-2 重试没有调度时间

当前 C2 循环约每秒调用一次 Outbox 恢复，没有 `next_attempt_at`。后端短时故障会形成
高频请求，并快速耗尽旧的 20 次限制。

整改：增加可持久化的 `next_attempt_at`，建议间隔按
`1s -> 2s -> 5s -> 10s -> 30s -> 60s` 增长，最大间隔保持 60 秒，恢复后自动继续。

状态：**已完成**。C2 消息 Outbox 与 sent_ack Outbox 均持久化
`next_attempt_at`；退避期间仍保持全局事务门，不会每秒请求或提前放行。

### P1-3 后端仍使用“需人工确认”技术文案

后端已经能把 `unknown` 持久化为 `unknown_send_result` 并自动转入销售接管状态，这是
可复用的正确主体逻辑；但任务备注仍写“需人工确认”，容易让实现再次生成不存在的后台
处理流程。

整改：改为“发送结果未知，原动作已终结且禁止补发；会话转销售正常接管”。不创建技术
消息待办，不要求人工修 sent_ack。

状态：**已完成**。普通 unknown、stale sending 和晚到回执共用同一终态语义。

### P2-1 机器合同仍是旧口径

`contracts/c2_contract_v3.json` 仍包含 `quarantine/quarantined/manual_recovery/max_retry_attempts=20`。
Worker 和后端都从该文件派生行为，因此必须先改机器合同，再改两端代码和生成测试，不能
只修改一侧。

状态：**已完成**。机器合同、Worker 分类器、后端错误外壳和生成的 OmniAuto
observation schema 已同步；schema 过期检查通过。

### 2026-07-25 最终工程收口

- Worker 增加 `c2_outbox_lock`，任务线程和 C2 线程同时恢复时只会发起一次请求。
- 合同升级为 `3.7.0`，永久错误不再统一塞入 `capability_paused`。
- 请求过大按同一 `read_run_id` 原子拆批，最后一片完成前不启动 Brain。
- 后端拒绝无效媒体时返回具体 `source_message_key`；Worker 只重建坏的那一条，
  同批成功语音和图片不受影响。
- 解绑/短码失效终结目标；身份或映射冲突由后端先持久化技术终态，再终结会话
  Outbox；未知错误仍保守暂停。
- 发送失败与结果未知的说明统一为“自动发送已终止，会话转销售正常接管，
  禁止自动补发”。
- 通用 `VALIDATION_ERROR` 改为 `capability_paused`；后端未保存消息事实时不再
  返回终态确认，Worker 保留原 Outbox 和 ledger。
- 终态保留期清理已覆盖 `confirmed / split_completed / payload_terminated /
  target_terminated / conversation_terminated`，不会清理仍需恢复的记录。

最终 Mac 验证：Worker `416 passed, 29 skipped`；OmniAuto compatibility
`187/187`，其余专项 `44/44`；后端 `194 passed, 1 skipped`。跳过项为本机
缺少 PostgreSQL 并发环境的行锁测试，不代表已完成 Windows 微信 UAT。

## 四、已经正确的部分

1. 失败语音和失败图片可以作为 `item_state=failed` 消息事实入库。
2. 后端接受 `sent/failed/unknown` 三种发送结果，并能持久化
   `unknown_send_result`。
3. `trigger_attempted` 后结果不明不会被自动改成普通 failed，也不会自动补发。
4. 回复文本 hash 冲突发生在可能发送之后时，后端会保守改成 unknown。
5. add_friend 仍以最终“确定”按钮物理点击成功作为 `invite_sent`，没有增加不存在的
   页面成功状态。
6. private + 短码准入、统一 sender_role、文字/语音/图片消息身份和后端最终去重方向
   未发现被本轮异常恢复代码改坏。

## 五、必须新增的自动化测试

1. 存在待确认 C2 消息 Outbox 时，心跳不得调用 `pull_task`。
2. 待确认 Outbox 同时阻断 C2 扫描、`add_friend` 和恢复型 `chat_reply`。
3. 后端连续不可用超过旧的 20 次限制后，原事实仍保留并继续退避重试。
4. `capability_paused` 恢复健康后自动转回 waiting，并重传同一 Outbox。
5. 旧 `quarantined/abandoned` 数据启动后自动迁移且不会丢 payload。
6. sent_ack 网络失败、Worker 重启后只重传回执，不再次发送微信消息。
7. 后端先进入 `unknown_send_result` 后，Worker 重传得到幂等确认而不是 claim conflict。
8. 辅助证据异常不拒绝可信核心消息或核心 sent_ack。
9. failed 语音/图片入库后不调用 Brain，并自动进入既定销售接管状态。

全部测试通过后，再打 Windows 包验证断网恢复、进程重启、unknown 发送对账和任务中心
全局门禁。
