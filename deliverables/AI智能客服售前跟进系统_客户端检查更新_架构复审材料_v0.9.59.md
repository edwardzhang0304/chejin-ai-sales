## 2. 已实现范围

### 2.1 后端发布权威

- 新增不依赖 Worker 绑定的 `GET /api/client-releases/latest`。
- 新增 `worker_client_releases` 发布权威表和单一 Alembic head `20260901_0031`。
- `channel + platform + version` 唯一，状态限定为 `draft / published / withdrawn`。
- 只向客户端返回 `published + windows-x64 + gray + rollback_safe=true` 的更高版本，禁止自动降级。
- 发布描述通过 Ed25519 公钥验证后登记；同版本签名事实不可改写，撤回只改变状态。
- 签名中的发布时间统一为 UTC 固定六位小数 `Z` 格式，发布工具、数据库/API 和客户端验签不因时间文本格式变化产生假失败。
- 发布记录只保存不可变包身份和存储键；每次查询签发新的短期 HTTPS 下载租约，租约只存 token 哈希并追加审计，不修改发布身份。
- 地址过期只允许在全部不可变包身份一致时续签一次；发布撤回后新租约和已有租约均失败关闭。
- 公共查询按 IP 和客户端实例散列限流；不保存原始 IP/实例号，过期计数有界清理。
- 迁移降级明确失败关闭，不通过 downgrade 删除发布权威数据。

### 2.2 客户端检查、下载和安装门禁

- 设置页显示当前版本、检查更新按钮和固定状态文字；未绑定客户端也可进入设置检查。
- Fast UAT Python 包明确不可启动正式更新；自动更新对象只允许正式冻结 EXE 包。
- 发现更新后通过同一 TaskRunner 接单锁先关闭新工作入口；任务 pull、Flow 登记和更新门禁不存在孤儿租约竞态。
- 当前已登记 Flow 继续原样结算；更新线程不持有 UI 锁、任务租约或业务事务。
- 安装前统一检查任务、Flow、租约、UI 锁、Sidecar、Ledger、ActionJournal、C2 Outbox、sent_ack 和未知动作结果。
- 后端确认 `faulted` 且全部业务账本清空时允许安装，但重启后仍保持 `faulted`；后端状态未确认或有未结算事实时明确等待、禁止安装。
- 下载严格校验长度、SHA-256 和 Ed25519；ZIP 拒绝绝对路径、`..`、符号链接、设备文件、Windows 保留名、ADS、尾随点/空格和大小写重复路径。
- 包内 manifest 严格校验版本、平台、提交及全部文件集合/哈希，禁止清单外文件。

### 2.3 独立 Updater、健康检查与回滚

- 正式构建包含独立 `CheJinUpdater.exe`，运行中 Worker 不覆盖自身。
- Updater 二次校验计划、签名包身份、ZIP 和安装安全边界；计划不保存 Worker Token、下载 URL 或发布私钥。
- 旧 Worker 正常退出后，Updater 原子切换 `current / previous`，启动新 Worker并等待 120 秒本地健康标记。
- 新 Worker 在心跳和业务恢复启动前验证实际版本、程序清单/哈希、本地配置、SQLite 和冻结业务字段快照；
  随后正式 UI、TaskRunner、C2 和线程监控进入生产循环，跨不少于 1 秒稳定窗连续存活后才写健康标记。
- Worker 与 Updater 共用唯一纯健康合同；仅创建后台线程或启动函数返回不能宣布健康。
- Updater 结果长期缺失且进程已退出时，目标目录和认证健康证据完整则幂等结算成功，否则只启动一次独立回滚；不再永久等待。
- 受保护 SQLite 表按版本化冻结业务字段比较；兼容新增默认列不误报，冻结字段缺失或变化仍失败关闭。
- 新版本失败时不重复业务动作，保留失败程序和日志，原子恢复并启动旧版本；只保留一份上一版本。
- Windows 正式工作流保留目录切换/失败回滚探针，并新增一个真正启动打包后
  `CheJinWorkerClient.exe` 的成功场景，要求 marker 证明正式 TaskRunner、C2、线程监控存活；
  本机未冒充 Windows 门禁已执行。

## 3. 生产数据流

```text
用户点击检查更新
-> 后端公开查询唯一 published 发布
-> 客户端先关闭新工作入口
-> running Worker 请求 paused，已有 Flow 继续结算
-> 后台下载并验证签名包
-> TaskRunner 唯一安装边界全部清零
-> 外置 CheJinUpdater.exe 二次验证
-> 旧 Worker 正常退出
-> 原子切换程序目录
-> 新 Worker 本地健康检查
-> 成功后恢复原状态；失败则回滚旧程序
```

Updater 只替换程序目录。配置、绑定、SQLite、Ledger、Journal、Outbox、sent_ack、故障证据、用户暂停和 faulted 状态都位于独立数据目录，不得由更新器删除或覆盖。

## 5. 已冻结并实现的更新控制边界

### 5.1 不可变包身份与可续签取货码

`worker_client_releases` 只保存不可变包事实和受控存储键。每次查询为同一发布生成新的短期 HTTPS
地址和追加式审计记录；地址及 token 不进入签名身份。地址失效后客户端只续签一次，并逐字段核对
不可变身份；撤回后新地址和已签发地址都不能下载。实现和测试不得改写旧发布记录。

### 5.2 `faulted` 可更新但不可自动解除

后端确认 `faulted`、无 Task/Flow/租约/UI 锁/Sidecar，且 Journal、Ledger、Outbox、sent_ack 和
未知动作全部清空时允许安装。新版本及回滚后的旧版本都继续显示 `faulted`，必须由运营人员明确
点击“开始接单”解除。任何账本未结算或后端状态无法确认时都禁止安装并显示明确等待原因。

### 5.3 签名时间跨层格式唯一

发布时间在发布工具中先规范化为 UTC 固定六位小数 `Z` 格式，再进入 Ed25519 签名。后端登记、
SQLite/PostgreSQL 读取、HTTP JSON 返回和客户端验签都复用同一语义。贯通测试使用 PowerShell
常见的七位小数输入，实际经过正式签名工具、数据库、HTTP 接口、客户端解析与验签，并下载真实包字节。

### 5.4 正式运行循环稳定后才声明新版本健康

新客户端先完成本地配置、SQLite、程序清单和冻结业务字段快照检查，再启动正式 UI、TaskRunner、
C2 和线程监控。启动调用返回仍不够；唯一纯健康合同要求生产循环跨不少于 1 秒稳定窗连续存活，
期间任何线程退出或启动故障都会阻止 marker。健康门只读取计划中的 120 秒期限，不再存在客户端
10 秒暗门；独立 Updater 在同一窗口内等待并决定是否回滚。
更新门存在期间人工“开始接单”在 TaskRunner 唯一入口本地拒绝，零后端状态修改，避免安装等待被并发改回 `running`。

### 5.5 Updater 结果丢失有限恢复

新客户端持久化并逐次核对 Updater 的 PID、创建时间和可执行文件路径，三项一致才继续等待；单一 PID
存在或已被复用不能证明原进程仍存活。结果对账有 180 秒总截止时间且不会因进程存活而滚动重置。
原进程消失或经三项身份确认卡死并安全终止后，结果超过宽限期仍缺失时，只有本次
request/token、目标 current 目录和稳定健康 marker 全部匹配才能幂等补记成功；其他情况由独立
Updater 执行一次 previous 回滚。令牌或目录证据不足时有限失败、清除永久更新门禁并保持暂停/故障，
禁止无限轮询或自动恢复 running。结果 JSON 损坏、格式错误或 request 错配同样统一有限结算并清除
本次门禁；无法安全终止原 Updater 时绝不启动第二个恢复进程。

### 5.6 兼容 Schema 不误伤业务快照

数据快照只比较版本化冻结业务字段。冻结字段缺失或值变化继续阻断；受保护表新增带默认值的兼容列
不会被误判为数据损坏。未来新业务字段必须通过新快照 schema 显式纳入，不能静默绕过。
