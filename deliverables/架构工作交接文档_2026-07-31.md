## 4. 已确认的核心架构

### 4.1 三层分工

OmniAuto：

- 看微信、OCR、识别气泡、同行头像、操作微信。
- 执行语音转写 RPA、图片复制和 Vision、消息发送。
- 不决定车金授权、消息新旧、状态机、最终回复和数据库身份。

Worker：

- 执行有效短码、`private`、`read-targets`、`authorization_revision` 准入。
- 统一建立文字/语音/图片槽位、角色、顺序和消息身份。
- 持有单会话 UI 锁，串行编排 OmniAuto、后端、Brain 和发送。
- 维护 ActionJournal、Ledger、Outbox 和停止门禁。

后端：

- 管理 Lead、Conversation、状态机、read-target、授权和任务中心。
- 幂等保存消息事实，数据库唯一约束做最终去重。
- 构建 RAG/Brain 上下文、生成 reply_action、接收 sent_ack。
- 不重算客户端图片/文字/语音的左右侧和消息身份。

### 4.2 单会话串行

正式流程：

```text
打开一个授权会话
-> 读文字/语音/图片
-> 完成语音转写和图片Vision
-> 一次messages/ingest
-> 后端状态机和任务中心创建/返回当前batch的reply_action
-> 当前C2 Flow领取自己的chat_reply
-> 等待Brain终态
-> 发送前重新确认会话和授权
-> 执行发送
-> sent_ack后释放会话和UI锁
-> 才处理下一个会话
```

普通任务线程不得抢走当前 C2 Flow 的 `chat_reply`。恢复线程只处理崩溃恢复。

### 4.3 UI锁

- 一个 Worker 同时只操作一个微信会话。
- Vision 和 Brain 等待期间不释放当前会话和 UI 锁。
- 正常长动作不使用固定总业务超时打断。
- 单步骤网络调用保留超时；无进展 watchdog 只识别卡死。
- `sent_ack` 或消息 Outbox 未获后端确认时，停止所有新会话扫描和 UI 动作。

## 5. C1 已确认口径

- C1 只能确认已经向好友发送添加申请，不能确认对方已经通过。
- 点击微信最终“确定”按钮成功即为 `invite_sent`。
- 点击后没有可靠成功状态，诊断截图/OCR不是成功前置条件。
- 明确诊断失败可以记录失败；诊断异常不得把已点击成功降级。
- 等待好友通过阶段不做短码定向搜索，只通过 C2 首屏被动扫描发现。
- 首屏发现短码后先上报，后端确认可读后才能打开会话。
- 好友通过但没有任何消息时，由后端状态机决定是否创建首次开场 Brain 任务。

## 6. C2 已确认口径

### 6.1 唯一准入

```text
有效短码
AND conversation_type=private
AND 当前read-target授权存在
AND authorization_revision未变化
```

- 没有短码的单聊和群聊都不处理。
- 带短码的群聊也必须终止，禁止读取、语音、图片、入库、Brain和回复。
- `unknown` 不允许当 `private` 猜测放行。
- `read-targets=[]` 时可做首屏被动 `sessions` 发现并上报，不得打开、读消息或发送。

### 6.2 当前屏原则

- C2 只处理最终当前屏，不主动上滚。
- 语音转写在统一槽位建立前完成。
- 使用最后一次语音动作后的有效截图；没有有效截图时只补一张 final_read。
- 语音展开或新消息把图片/消息顶出最终屏后，本轮不处理。
- 页面发生变化后旧坐标立即失效，动作前必须重新观察。

### 6.3 角色

正式 `sender_role`：

```text
customer / self / system / unknown
```

- 普通消息必须使用同行头像证据。
- 左侧同行头像为 `customer`，右侧同行头像为 `self`。
- 两侧同时成立或均不成立为 `unknown`。
- 语音转写文字继承父语音角色。
- 图片 Vision 的 `side/visual_side` 只作辅助证据，不得覆盖 C2 角色。

### 6.4 消息身份和顺序

- Worker 生成跨轮 `source_message_key/dedupe_key`。
- OmniAuto 只提供帧内观察和物理 anchor。
- 后端只用 Worker key 和数据库唯一约束做最终去重。
- `screen_order` 只负责最终画面排序，不参与身份。
- scan_id、read_run_id、坐标、时间桶不得成为消息身份。
- Worker Ledger/Outbox减少重复昂贵动作，不能替代后端 dedupe。

## 7. 语音口径

- 使用客户端重新编排 OmniAuto RPA 完成微信语音转文字。
- 当前 Flow 自下而上处理未转写语音。
- 每条动作后重新截图，最后有效截图可直接作为 final_read，避免重复截图。
- 已展开语音通过父语音 anchor 绑定，不作为独立 text 入库。
- 最终只生成一条 `message_type=voice`，正文为转写文字。
- 多条语音正常处理时不使用固定总时限打断；使用进展型 watchdog。
- 已有成功结果不能因后续失败丢失，但会话内不得留下无人接管的 pending。
- 失败语音事实可以入库；上下文不完整时阻断 Brain。

## 9. C3、任务中心和召回

- 后端消息入库后根据状态机决定是否创建 `chat_reply`。
- 任务中心仍是 Brain/Worker 动作调度和恢复中心，不被 C2 绕过。
- 正常当前会话回复任务由仍持锁的 C2 Flow领取并执行。
- Brain是回复决策模型；Vision是图片文字化模型，两者职责不同。
- `no_action` 是业务上无需回复；`failed` 是技术失败，必须保留不同结果。
- 不存在后台人工修消息角色；失败事实通过状态机门禁、后续新消息和自动恢复闭环。
- 业务仍存在转人工/销售接管状态，但不表示有人到后台修图片或语音消息。
- 销售发出消息后进入 `sales_replied_waiting_user`，停止当前AI回复但保留后续召回。
- 客户再次回复时交回AI，继续原状态机链路。
- 召回复用 Brain，使用 `trigger_type=recall + recall_cycle_id`，不由 Worker发送固定文案。
