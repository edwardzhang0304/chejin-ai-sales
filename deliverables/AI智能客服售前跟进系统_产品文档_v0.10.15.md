## 2. 按完整业务流程使用

### 2.1 交付盒子

管理员先安装指定微信 3.9.10.16 x86 和经核验的配套 DLL，配置该盒子的路径、两个不同端口及回调地址，生成“工作微信”和“Worker”图标。在销售实际使用的 Windows 用户环境输入提供方 Key 并验机，一个 Key 当前按 5 台设备计数。已实测同一测试电脑重启免再次输入，不推断换硬件或换用户也免激活。

验机要实际点击图标、核对参数/DLL/端口归属、登录、回调与重启，然后退出测试微信账号。销售收到盒子无需自己放 DLL、敲命令或反复填激活码。正式配置不能照抄 HookLab 测试目录和端口。标准Worker升级包不内置微信或DLL；本次私有新机完整包另含固定微信程序目录和匹配DLL，不含激活码、账号或Token。

### 2.2 后台先安排客户

运营新增线索，系统按手机号去重并分配启用销售，形成加好友待办。销售离线不丢任务；没有可用销售则保持未分配，销售未绑 Worker 则任务阻塞，不能随便派给其他销售。

### 2.3 销售开微信，再开 Worker

1. 点击“工作微信”，扫码登录，窗口保持展开、非最小化。
2. 手动点击 Worker，首次填 ID/Token；以后读取原绑定和业务记录。程序不自动替销售打开 Worker。
3. Worker 做原有窗口位置/大小准备，保存布局；核验微信身份、组件、端口、后台及时间，启动接收器、设置回调、补历史并核对上次动作。
4. 进入待开始，或保留原暂停/故障。销售明确点“开始接单”，通过检查才执行新任务。

“窗口打开在桌面”不要求鼠标一直点着微信；切到 Worker 正常。窗口准备仍在启动做一次；执行加好友时的结果/按钮/残留检查是必要动态截图，不是每次重新初始化窗口。

### 2.4 按手机号加好友

先清空搜索框残留→输入本任务手机号并核对→点击“网络查找手机/QQ号”：

| 找到的界面 | 处理 |
|---|---|
| 无法找到该用户 | 记录本次查找失败结果，清理搜索框，继续其他合格任务；不因此认定整机故障 |
| 头像资料和“添加到通讯录” | 填后端给的申请文案及备注短码，核验后只提交一次，记录邀请已发送 |
| 直接出现好友对话 | 记录已是好友，不补短码、不发欢迎、不为此建立 AI 托管 |
| 未知界面、受限、超时 | 按原失败入口停止/取证，不盲点、不猜已成功 |

三类结果都清理本次弹窗和搜索框，只在有手机号残留时清一次；不能误清聊天输入框。邀请提交成功但收尾失败，仍保留“已经提交”，不重复申请。发出邀请不等于客户已通过。

### 2.5 客户通过与身份确认

Hook 查联系人后，后端核对“本系统任务写入短码＋邀请证据＋唯一 wxid＋对应销售账号”，才把客户绑定到线索。手机号和昵称本身不能保证匹配，手工碰巧有短码的好友也不能直接托管。稳定确认短码被移除后停止托管，接口暂时失败不当删除。

只有合法任务来源的客户走首次开场及后续自动回复。通过好友的系统提示不算客户提问。历史用于补上下文，不批量回复所有过去消息。

### 2.6 收客户消息

不同客户的消息可同时到达并先保存。文字直接进入消息事实；语音等完整音频取得后转写，转写仍在原消息位置；新图片使该客户转人工，其他客户继续。重复回调只合并证据，不重复回复。

消息 ID 是身份证，不保证能按 ID 排序。历史排序字段经校验才可用；启动、重连、发消息前补缺核对。缺页、冲突或跨分库顺序不能证明时，保留消息并停止相关自动发送，不靠猜测补齐。

### 2.7 AI 思考、发送与新消息

客户连发几句话仍组为一批，保留原编排。不同客户可并发思考，默认全局容量 20；同一个客户只处理当前有效的一轮。客户继续说话会使尚未发出的旧答案失效，重新按最新内容判断，不是“一位客户只能问一次”。

后端读取已发布知识和上架车辆的公开事实，经 Brain 和 Guard 批准后生成发送动作。保留每段默认 108 字符、最多 3 段的现有规则；前一段确认成功才发下一段。不能把超长内容截断冒充完整答复。

轮到当前有效发送任务时，才抽取一次 0.5—3 秒等待；每段、开场和召回都适用，原先排队时间不抵扣。等待后仍要检查最新消息和取得共用动作锁，所以不能承诺两条实发间隔永远不超过 3 秒。加好友和发消息互斥；客户消息接收、AI 思考不被这个锁堵住。随机等待不是账号安全的保证。

发送超时或结果未知先查记录，不能自动重发；确认唯一的微信发出记录后才结算。这里的“已发送”不是客户已读或服务器送达证明。

### 2.8 转人工、停止跟进与召回

| 长时间无互动且有召回资格 | 默认 72 小时后预检；每日最多1次、连续无人回复最多3次（真实新客户回复后下一轮重新计），21:00—09:00静默；确认最新消息后走同一回复链 |
| 销售人工回复 | 先确认来源，旧AI未发内容失效；新设计由销售持续负责，只有有效召回确认发出才交回AI；AI自己的回显不算人工 |

本版修复：销售已可靠回复后，先结束对应人工交接；此前未确认的语音保留原记录，不自动再转写，也不永久挡住后续文字回复。旧语音的结果即使在销售回复之后才补交，也不会再次要求销售处理同一件事；客户的新问题已进入处理后，补交这类旧语音也不会取消新问题的回复；人工回复之后的新语音仍保留事实；是否启动转写须服从2.8的负责人及原运行资格，不能为催办新增转写。微信进程的未知调用隔离、暂停接单和关闭 AI 不会因交接结束自动解除。

原转人工通知继续按原事件去重；本次明确新增“客户等销售回复满1小时，每轮飞书提醒一次”，提醒发给负责销售，不因提醒到期恢复AI。通知失败/未知、夜间及离线按技术方案8.3已确认细则处理，不能自行扩接收人或重发。

**已确认的目标流程，源码候选：**

| 发生什么 | 系统怎么做 |
|---|---|
| 销售发过人工消息，客户一直没有回复 | 仍由销售负责；等客户，默认72小时后符合条件才尝试召回 |
| 客户回复了，销售一直没有再回 | AI不插话；从本轮第一条待回复消息计1小时，飞书提醒销售一次 |
| 客户连续又发了几条 | 同一轮，不重新计时、不重复提醒 |
| 销售回复了 | 本轮结束，取消未发提醒；重新等客户回复 |
| 召回只生成了、第1段没发出或结果不明 | 不能因此交回AI；继续按原负责人和真实状态处理 |
| 当前有效AI召回确已发出并完成可靠核对 | 第1段可靠确认发出就交回AI；客户插话取消旧尾段，回答新问题；之后的新故障仍按原规则处理 |
| AI接手后销售又发消息 | 再次交给销售，重复上面的人工流程 |

这里的“一轮”从客户第一条尚未被销售回答的消息开始，到销售下一次回复结束。确认过的旧语音补交、历史重放和重启不重开一轮。人工负责人不等于一直保留未关闭故障；旧故障能按证据结束，客户仍可由销售负责。AI关闭、暂停、拒收及好友关系等原限制继续有效。

灰度旧会话不补算、不追发历史提醒；原记录和发送凭证保留。更新后首次可靠的新消息开始按新规则处理，已有交接、拒收、暂停等限制继续生效。

**六项细则已全部确认，源码候选：**首次转人工保留即时通知，满1小时仍未答再催一次；夜间21:00—09:00的催办顺延到下一个早上9点，届时已回则不发；召回第1段确认发出即交回AI；连续无人回复最多召回3次，客户真正回复后下一轮重新计算，每日最多1次仍保留；离线先等同步，核对仍未答再补催；催办明确发送失败最多重试两次，分别等待1分钟、5分钟，结果未知不盲重发。每次重试都检查销售是否已回以及是否处于夜间，重启不重新计次数。

完整执行边界见[技术方案8.3](AI智能客服售前跟进系统_Hook技术方案_v0.10.11_2026-10-16.md#83-六项执行细则2026-10-22-用户全部确认源码候选)。本次有限重试针对新催办，原即时交接通知保持原规则。明确拒收另行通知销售仍未实施；新出现的不明确流程由工程师先问用户。

## 3. 运营后台与账号

保留线索、车辆、知识、销售、Worker、任务中心六个管理模块和原布局。运营后台不再展示操作日志菜单或页面。复用通用卡片、表格、抽屉、弹窗与分页，编辑在原详情抽屉内完成，不增设另一套 Hook 后台。

数据看板为新增规划模块，指标与页面确认进度见第8节，不计入上述已具备模块。新增看板不改变登录后默认空白工作区的规则。

后台账号由服务端预建。登录只输入账号和密码，无注册、短信、自助找回或新 RBAC；正常运营账号使用原管理权限。登录成功进入默认空白工作区。可撤销 HttpOnly Cookie 会话与 Worker Token 独立，刷新保持会话，失效/退出返回登录页，不能靠浏览器后退看旧数据。账号密码错统一提示，不泄露密码、Token 和堆栈；接口也校验登录和请求来源。

七模块只读自动刷新共用一套逻辑，保留筛选、分页、选择和展开状态；编辑、确认弹窗和提交期间暂停刷新，失败保留上次结果。只读刷新不领取任务、不生成 AI、不触发微信。

### 3.1 线索

客户名称和大陆 11 位手机号必填；微信号、邮箱、备注及自定义信息选填，各联系方式单值。手机号规范化后强去重，重复不新建有效线索，备注追加，记录操作人、时间、次数和历史日期。

线索状态为未分配 unassigned、已分配 assigned、无效 invalid，不物理删除、不另设归档。详情展示基础信息、销售、备注、重复与分配记录、任务链、绑定和最近消息入库时间；不新增没有业务场景的主编辑入口。

标记无效停止该客户新加好友/AI/召回，取消未发工作，保留历史；已经可能执行的动作只核对结算。恢复有效不复活旧任务或旧回复，不能取消原暂停/禁用/转人工；重新核验当前身份和最新事实。运营按钮不是强制撤回已发生微信动作。

### 3.2 销售

字段：姓名、手机号必填；微信号、Worker 可选，状态启用/停用，保留轮询顺序。启用参与轮询，停用不重分历史客户。新增后可在详情内绑定/换/清空 Worker；离线但启用可绑，停用或已绑别人的不可绑。

销售手机号必须对应飞书企业成员；后端用统一发送应用解析其 open_id，运营不手填、不显示该值，不能跨应用复用。详情显示 Worker 在线/运行、今日分配和阻塞任务。

### 3.3 Worker

后台生成 ID/Token，Token 只在详情授权展示，列表不显示；首次客户端绑定实例，后续保存。名称、启停、绑定状态、在线、运行状态、销售、任务、最近心跳保留；详情补工作微信账号与 Hook 检查结果。

Hook 运行显示接单中、暂停接单、已停止接单（客户端故障）、离线；空闲/忙碌只是当前执行情况，不能把暂停投影为接单中。后台没收到的本机短暂网络状态不能擅自推断。

本版不显示、不要求填写 Vision Key，不把缺 Vision 当 Worker 创建或启动障碍；原本地 OCR 加好友能力仍需正常。Worker 无飞书和模型管理权限。

重置绑定轮换 Token，旧客户端不再领新工作；running 时强提示。重置不自动取消/失败/改派原在途任务，不删除恢复证据。销售归属去销售详情修改，不在 Worker 详情另开入口。

### 3.4 任务中心

只有 add_friend（添加通讯录邀请）和 chat_reply（微信文字发送）；开场、普通回复、召回由批次 trigger_type 区分。Hook 收件、绑定、语音、历史与 recall_precheck 不另造任务类型或放入任务中心排队。

| 生命周期 | 可做的运营操作 |
|---|---|
| blocked | 处理阻塞、取消、补备注；未绑 Worker 跳转销售编辑 |
| pending | 取消、补备注 |
| running | 看执行方、取消请求、补备注；实际动作仍受结算门禁约束 |
| completed | 看结果/执行方、补备注，默认不重建 |
| failed / cancelled | 看原因和原记录，需要重试则创建新任务，不能复活终态 |

invite_sent、already_friend、chat_reply_sent、skipped_by_rule 是结果而非任务状态；already_friend 为完成，邀请发出不表示已通过。PHONE_NOT_FOUND 可关联标记线索无效。技术故障、业务失败、按规则跳过、发送未知分开显示。

详情保留当前步骤、Worker、状态、结果/错误码、备注和状态流转。task_events 记录任务变化，operation_logs 记录操作者动作。C2 绑定/消息/转写/人工状态通过线索或 Worker 原详情展示，不设计新的“语音任务”。

### 3.5 操作日志与聊天信息

操作日志在服务端自动保存，供工程师按授权排障查询，不向销售或运营展示独立页面。保留查询鉴权、历史记录及恢复/结算凭证；移除界面不删除日志或停止记录。本项为待发布源码变更。

记录登录退出（不记密码）、线索新增/重复/备注/无效恢复/完整手机号查看、销售启停与绑定变更、Worker 创建启停重置、任务取消重建/解阻、车辆和知识写操作；保留操作者、对象、时间、结果及必要失败原因。

服务端会保存系统托管范围内的客户和己方消息事实、正文、方向、原消息 ID、时间、转写、状态和来源证据。**这不等于采集销售所有私聊，也不等于已经有完整聊天记录查看页面。** 全量运营聊天浏览、跨销售授权和保留周期如需建设另定范围，不在本文把已有详情摘要说成完整聊天 UI。

## 4. Worker 状态、故障与维护

保留开始/暂停、设置、检查更新、运行过程和本机日志。运行过程按本客户本轮分组，启动检查单列，完成后不跳回旧等待，历史人工接管不插入本轮。等待好友通过不占住其他客户全部调度。

暂停或故障禁止启动新转写、模型和动作；已登记操作按原职责收尾，仍可保存授权内消息、补交结果、只读核对。重启保留原停止意图。对销售的一般技术异常简洁报错，由管理员查 incident_id 和日志；不直接退出、不静默重做；检查更新等待可以明确显示当前阻挡原因。

本轮支撑改造包括：连接恢复只清对应等待；共用后台时钟及有界有效期；存储错误先停止业务再收尾；故障证据异步采集；C0—C4 阶段耗时接入 Hook；后台只读刷新；安全更新与双快捷方式；单实例及本地数据保护。详细规则已写入技术方案，不再要求工程师查多份增量说明。

### 4.1 检查更新与安装

待发布源码改进：下载时在“正在下载”后显示实际百分比，例如“正在下载 35%”；下载失败后重新检查从0%开始。百分比100%仅表示完整下载和哈希校验完成，随后仍需解压、验证和安全安装。现有旧客户端不会因服务器发布新包就获得该显示，安装含此改进的版本后生效。

正式EXE先评估实际旧客户端能否按钮升级，能则优先按钮；仅有明确不兼容/失败依据且替代安装已验证时才强升。没有目标包时先做能力评估，成品封存后再做完整升级验收；工具缺项不是必须强升的理由。具体执行顺序见技术方案18.0.3节，Fast UAT流程不变。

暂停、故障、业务离线本身不挡“检查更新”；当前任务、租约、锁、未确认调用、待回传/结算或安全状态不可读会阻挡并显示原因。实际入口重新核验，不能仅凭按钮之前亮着就允许更新。登记更新与新工作共用准入锁；取消/失败只解除本次更新闸门，不恢复人工暂停。

0.10.5本轮现成包未重打，已完成隔离故障停单状态的真实按钮升级；用户原机后续失败，因此该起点到目标的现场路线当前不放行。原包、绑定和记录保留；包已下载并完成哈希校验，失败在临时解压目录提升，尚未开始替换原程序。具体文件占用/权限原因未定，不重复试错。原装0.10.2/0.10.3更新器缺陷不因服务端发新包自动修好，旧起点保持未开放。

仅更新 Worker 且退出/恢复检查通过时可保留微信运行；改 DLL、启动参数或需要隔离旧进程才重启工作微信。数据目录、绑定、暂停/故障、消息、语音及未知动作均保留；不能清空它们来让升级通过。

### 待发布源码：销售一键故障诊断

销售只需双击桌面“车金故障诊断”，导出并发送一个 ZIP，不需要找数据库或执行命令。按用户确认只保留此入口，不恢复“本机执行日志”或设置页导出按钮。诊断显示进度且不阻塞接单界面；完成后自动打开文件位置。关闭诊断窗口不会打断业务，独立诊断在收集结束后退出。

## 5. 车辆管理

### 5.2 车辆列表

页面入口：运营后台左侧导航增加“车辆管理”。

### 5.3 车辆详情、新增和编辑

- 原“车系”自由输入框改为可选单选下拉，名称仍为“车系”，顺序固定为：国产新能源、合资新能源、国产车、德系车、日系车、美系车、韩系车、法系车、其他。不得自由输入或多选，品牌和车型保持原用途。
- 在“能源类型”后增加可选“排量”单行文本输入框，示例“如 1.5L、2.0L”，不做下拉。可清空、最多100字符，不限定档位或强制单位格式；原文展示，不自动追加单位。纯电或未知可不填，不增加上架门槛。
- 在“排量”后增加可选“电池包容量”输入框，单位固定显示 `kWh`（千瓦时，不是kw/h），只输入大于0的整数或小数，如75、82.5；不做下拉。未知或燃油车可以留空，可清空，不补0、不增加保存/上架门槛或能源组合拦截。
- 在“电池包容量”后增加“驱动方式”单选下拉，固定顺序为前驱、后驱、四驱；可不填或清空，详情中文展示。不自由输入、不多选、不默认前驱，不增加保存/上架门槛或组合拦截。
编辑规则：

- 车辆编号、创建时间和更新时间不可修改。
- 点击取消回到详情查看态。
- 有未保存修改时关闭抽屉，提示是否放弃修改。
- 已上架车辆不得清空公开售价，也不得删除最后一张有效图片；需要先下架。
- 车系旧值不属于九项分类时保留原文，编辑处显示“原车系：<原值>（待选择分类）”；未操作车系时修改其他字段不得丢失旧值。主动选择新分类或明确清空才替换，不自动归入“其他”、不强制下架。车系与能源类型分别选择，不自动互填或增加组合拦截。

### 5.5 车辆图片

- 图片只能在车辆创建成功后维护。
- 支持 JPEG、PNG、WebP，单张不超过 10MB。
- 支持一次选择多张图片、查看大图、删除和拖动排序。
- 排序后的第一张图片自动作为主图，不增加单独“设为主图”操作。
- 多图上传按单张处理；部分图片失败时，已成功图片保留，并逐张显示失败文件和原因。
- 已上架车辆不得删除最后一张有效图片。
- Excel 不导入车辆图片，图片统一在车辆详情编辑态维护。
- 车辆图片使用持久化存储，不能使用浏览器或开发机临时路径作为生产地址。

### 5.6 上架和下架

业务状态只保留：

```text
已下架 <-> 已上架
```

上架前服务端必须重新校验：

- 车辆展示名称不为空。
- 公开售价不为空且大于零。
- 至少存在一张有效车辆图片。

缺少资料时不能打开确认上架流程，页面直接列出缺少或错误的内容。资料齐全时二次确认，
确认成功后车辆立即进入客服车辆查询和回复范围。

下架规则：

- 下架需要二次确认，不要求填写原因。
- 下架后车辆仍可在后台查看、搜索和编辑。
- 下架后不再进入新的客服查询、推荐和回复范围。
- 已发送给客户的历史消息不删除。
- 尚未发送且引用该车辆的旧回复，在发送前复核时必须停止发送旧内容。
- 重新上架时重新执行上架资料校验。

### 5.7 Excel 导入流程

正式流程：

```text
下载最新模板
-> 上传 .xlsx
-> 服务端解析和校验
-> 页面预览新增、更新和错误数据
-> 全部通过后运营确认
-> 服务端整批写入
-> 返回导入结果并刷新车辆列表
```

上传规则：

- 只接受系统最新模板生成的 `.xlsx` 文件。
- 文件不超过 8MB，单次最多 2000 行。
- 模板包含`车辆信息`和`字段说明`工作表。
- 能源类型上线时使用新版模板，在“车型”后增加“能源类型”列，只填四种中文名称或留空；旧模板提示重新下载。新增空白为未填写，更新空白保留原值；清空已有值须在车辆详情编辑，非法选项按行报错并阻止整批确认。
- 同一新版模板保留“车系”列，允许值改为上述九项中文或空白；旧自由文本不自动分类，非法非空值逐行报错并整批阻断。更新空白仍保留旧值，模板版本与能源类型共用，不新增平行模板。
- 同一新版模板在“能源类型”后增加“排量”文本列，填写规则与页面一致；新增空白不补值，更新空白保留原值，超长逐行提示并整批阻断。清空已有排量通过详情编辑，不新增模板版本。
- 同一新版模板在“排量”后增加“电池包容量（kWh）”列，只填数值；校验与页面一致，新增空白不补值、更新空白保留，非法值逐行报错并整批阻断。共用模板1.2，清空走详情编辑。
- 同一新版模板在“电池包容量（kWh）”后增加“驱动方式”列，填写前驱、后驱、四驱或留空；新增空白不补值、更新空白保留，非法值逐行报错并整批阻断。共用模板1.2，清空走详情编辑。
- 上传和预览阶段不写入正式车辆数据。
- 不接受运营自行修改表头的普通表格。

预览规则：

- 按车辆展示，不要求运营理解底层 JSON 或字段路径。
- 展示车辆总数、新增数、更新数和错误数。
- 车辆编号留空时显示为新增，并由系统生成编号；已存在的本地车辆编号显示为更新。
- 填写了车辆编号但系统中不存在时显示错误，禁止按新增车辆处理。
- 更新已有车辆时，Excel 空白字段不清空系统已有值。
- 任意一条数据存在错误，整批不能确认导入。
- 不提供“跳过错误继续导入”。修正文件后必须重新上传和校验。

确认规则：

- 确认导入采用整批事务，全部成功才提交，任意写入失败则整批回滚。
- 新增车辆默认已下架。
- 更新已有车辆时保持原有上下架状态。
- 导入成功后显示新增数和更新数，并可返回已刷新的车辆列表。
- 系统写入失败时显示简单原因和错误编号，不展示程序堆栈。
- 第一期不建设独立导入历史页面。

### 5.8 Excel 错误提示

错误文案统一使用“位置 + 问题 + 解决办法”，并使用业务字段名称，不展示技术字段路径。

| 阶段 | 错误场景 | 页面提示 |

| 上传 | 文件损坏 | 文件无法读取，请重新下载模板并填写 |

| 预览 | 填写不存在的车辆编号 | 第 X 行车辆编号不存在；如需新增请清空车辆编号，由系统生成 |

### 5.9 权限、接口和审计

- 第一期不区分车辆管理权限；所有登录成功的账号都可新增、编辑、导入、上传图片和上下架。
- 未登录用户不展示车辆管理页面，直接调用接口也必须被服务端拒绝。
- 浏览器只调用车金后端；前端不得直接读写 Product Master、数据库或存储。
- 新增、编辑、上架、下架、确认导入、图片上传/排序/删除均记录操作人、时间、车辆、
  操作结果和失败原因。
- 内部字段只能在有车辆管理权限的后台页面和接口中返回，不得出现在客户侧响应。

### 5.10 第一期不做

- 在车辆管理页面内编辑知识规则。
- AI 自动生成车辆资料。
- 大风车或其他外部车源 API 自动同步。
- Excel 导入车辆图片。
- 批量上架、批量下架、批量删除。
- 车辆删除。
- 独立导入历史页面。
- 客户看车商城或车辆展示站。

## 6. 知识管理

### 6.1 模块说明

知识管理是运营维护 Brain 正式业务知识的唯一后台入口。运营新增或编辑后先保存草稿，线上已发布内容继续生效。运营人员另行点击发布，系统完成校验和差异确认后才切换线上版本。草稿和未确认的候选修订不影响线上回复；发布成功后只影响新创建的 Brain 消息批次。

知识管理只维护业务规则和知识内容，不修改车辆主数据，不替代车辆管理，也不允许通过知识绕过价格、库存、支付、合同、转人工和发送授权等硬规则。

### 6.2 页面入口和权限

- 现有运营后台左侧导航增加“知识管理”，放在“车辆管理”之后。
- 登录成功后仍进入默认空白工作区，不自动打开知识管理或其他首个模块。
- 后端保留一个知识管理权限点；第一期不增加权限配置页、审核员或批准人角色，现有有效运营账号默认授予该权限，可查看、编辑、发布、归档和回滚。
- 浏览器只调用车金后端，PostgreSQL 是知识内容和发布版本的唯一权威源。
- 不建设 OmniAuto 独立管理后台。

### 6.3 知识列表

列表顶部展示：

- 三张紧凑概览卡片：当前线上版本、今日发布、已发布知识。
- 当前发布版本卡片展示版本号和发布时间；点击整张卡片进入发布记录，不额外显示“查看记录”文字按钮。
- 今日发布卡片展示当天成功发布次数，包含新增、修改和归档发布；发布失败不计入。
- 已发布知识卡片展示当前已发布知识数量，并在次级位置展示累计已归档数量。
- 页面右上角只保留主操作`新增知识`。
- 按标题或正文关键词搜索，并按状态筛选。输入关键词或切换状态后自动刷新列表，不设置“查询/重置”按钮；清空关键词并恢复全部状态后展示全部知识。

知识列表字段：

- 知识标题。
- 状态。
- 最后编辑人。
- 最后更新时间。

列表不增加操作列。点击整行打开右侧详情抽屉；默认不自动打开第一条知识。

### 6.4 知识字段

| 字段 | 是否必填 | 说明 |
|---|---:|---|
| 标题 | 是 | 让运营能快速识别该条知识 |
| 规则正文 | 是 | Brain 可检索和引用的正式知识内容 |

第一期只有少量正式规则，且预计不会形成大规模知识库，因此不设置分类、适用场景、禁止内容、来源或负责人输入项。发布操作人、版本和时间由系统自动记录；Guard 和服务端硬规则继续负责禁止表达及安全约束。

发布前去掉文本首尾空格。服务端统一校验必填、长度、重复内容、空正文、敏感信息和硬规则冲突；标题 1—120 字符、正文 1—5000 字符，与后端 knowledge_management schema 保持一致，前端不得另造兜底字段。

### 6.5 状态

页面状态只使用：

| 状态 | 页面文案 | 对 Brain 的影响 |
|---|---|---|
| `draft` | 草稿 | 仅保存未发布的新增或修改，Brain 不可使用 |
| `published` | 已发布 | 当前线上知识版本包含该内容，Brain 可使用 |
| `archived` | 已归档 | 历史保留，当前线上版本不再包含，Brain 不可使用 |

`draft`是运营可保存、查看和继续编辑的产品状态，但绝不得进入 Brain。已发布条目存在新草稿时，线上仍使用上一个已发布修订。首期不增加“待审核、已批准、已驳回”状态。

### 6.6 查看、新增和编辑

- 新增知识使用居中弹窗，底部提供`取消`和`保存草稿`；保存成功后再从知识详情发起发布。
- 点击列表行打开右侧详情抽屉，查看当前线上内容和历史发布信息。
- 点击`编辑`后直接在详情抽屉内编辑，不再打开新页面或第二个表单。
- 编辑态底部提供`取消 / 保存草稿`。取消或关闭不自动保存本次修改；有未保存修改时关闭抽屉，必须提示是否放弃修改。
- 已保存草稿在查看态显示独立`发布`操作，不与保存草稿合并成一次请求。

### 6.7 发布

知识发布从已保存草稿的知识详情抽屉发起，不在列表页增加批量“发布变更”按钮。点击`发布`后，只处理当前已保存草稿：

```text
自动校验
-> 展示本次新增、修改、归档差异
-> 运营确认发布
-> 服务端构建新的不可变知识版本
-> 构建成功后原子切换当前版本
```

服务端使用已保存的草稿执行校验和差异预览，禁止用浏览器尚未保存的表单内容直接发布。发布确认弹窗必须展示：当前线上版本、目标新版本、当前知识的变更类型、修改前后差异和校验结果。运营只发布当前知识，后端仍生成一份完整、不可变的新知识快照并原子切换。

- 校验未通过时列出“知识标题 + 问题 + 修改建议”，不显示确认发布按钮。
- 构建或切换失败时，提示发布失败和错误编号，当前线上版本保持不变。
- 发布过程中按钮显示加载并防止重复提交。
- 发布成功后刷新列表和版本信息，并明确提示“新创建的 AI 对话批次将使用此版本”。

### 6.8 归档

- 归档入口放在知识详情抽屉，不做物理删除。
- 点击归档后自动校验并展示移除差异；运营确认后直接生成新发布版本并原子切换。
- 归档发布成功后，该知识从当前线上版本移除并显示为已归档。
- 已归档知识仍可查看历史内容和发布记录。

### 6.9 发布记录和回滚

发布记录展示：版本号、操作人、发布时间、变更摘要、构建结果和当前生效标识。点击记录行打开右侧详情抽屉，查看该版本的新增、修改和归档差异。

回滚规则：

- 只能选择构建成功的历史版本作为回滚目标。
- 回滚前展示“当前版本 -> 目标内容”的完整差异并二次确认。
- 回滚成功会创建一个新的发布版本并切换生效，不覆盖、不删除历史记录。
- 回滚失败时当前线上版本保持不变。

### 6.10 Brain 使用规则

- 每个 `message_batch` 创建时固定一个 `knowledge_release_id`。
- 同一批次的正常生成、快速路径、重试、修复和 Guard 必须使用同一知识版本。
- 新知识版本发布后，只影响之后新创建的批次；已经开始处理的批次不跨版本。
- 编辑中的页面内容、未确认候选、构建失败版本和历史非当前版本不得被 Brain 使用。
- 知识发布不要求 Windows Worker 重启，不改变 Worker、C2、任务中心或打包合同。

### 6.11 异常场景

| 场景 | 处理规则 |
|---|---|
| 发起发布失败 | 保留页面输入，提示简单原因，可重新发布 |
| 知识校验失败 | 不进入发布确认，定位到具体知识和问题 |
| 内容与车辆价格、库存等权威主数据冲突 | 阻止发布，引导到车辆管理修改权威数据 |
| 构建知识版本失败 | 发布失败，线上版本不变 |
| 原子切换失败 | 发布失败，线上版本不变，不出现半生效状态 |
| 多人同时编辑或发布 | 服务端拒绝过期提交，提示刷新后重新核对差异 |
| 回滚失败 | 当前版本继续生效，记录失败原因 |

| D07 | 有效沟通率 | 同一筛选条件下 D06 / D05 | 同 D05、D06 | 日期、销售人员、沟通方式 | 百分比，50.00% |
| D08 | 人工平均首次响应时长 | 每轮待人工响应中，从首条待响应客户消息到首条实际人工回复的时长，再按已回复轮次求平均；不从转人工通知时间起算 | 按该轮首条待响应客户消息时间归入日期 | 日期、销售人员 | 时长，底层按秒计算，展示为分秒等易读单位 |
| D09 | 在售库存数 | 当前已上架车辆数，按车辆身份去重 | 当前快照 | 第一期开整体；不受历史日期、销售筛选影响 | 非负整数，25 台 |
| D10 | 已售库存数 | 发生“已上架 -> 已下架”且截至统计时点未被重新上架冲回的车辆数；初始就是下架的不算已售 | 有效下架事件时间 | 日期；第一期不按销售拆分 | 非负整数，5 台 |
| D11 | 成交金额总数 | D10 对应有效下架事件中的公开售价快照之和，不是实收款或财务收入 | 同 D10 | 日期；第一期不按销售拆分 | 金额，580000.00 元 |
| D12 | 接单中的 AI 销售数 | 当前绑定 Worker 且服务端正式投影为“接单中”的去重销售人数；接单中的空闲和忙碌均计入 | 当前快照 | 销售人员；不受历史日期影响 | 非负整数，3 人 |

D03 与 D04 使用不同的时间口径：D03 看期间新确认通过，D04 看期间发出的邀请最终通过情况。不能直接拿 D03 除以期间邀请数代替 D04。好友邀请本身不算 D05 的聊天沟通消息。

### 8.3 筛选与可选值

| 筛选项 | 可选值 | 生效范围与规则 |
|---|---|---|
| 日期 | 今日、昨日、近7天、近30天、自定义日期 | 默认今日；近7天/30天含今天。起始日00:00含、结束日次日00:00不含；今天只统计至当前。各指标按8.2对应事件时间取数 |
| 销售人员 | 全部销售、指定销售；客户归属统计另有未分配 | “全部”保留停用销售的历史数据和未分配客户，不能因销售停用丢掉历史；车辆不受此筛选影响 |
| 沟通方式 | 全部、AI、人工 | 只影响 D05 / D06 / D07；按实际发送来源区分，不用客户当前 AI 开关猜测 |
| AI 销售状态 | 接单中、暂停接单、已停止接单（客户端故障）、离线、未绑定 Worker | 实时分组，服务端按既有 Worker 正式状态统一投影；不新增 Worker 主状态，不用当前是否忙碌代替接单状态 |

AI 销售状态统计按销售人员去重，不把一名销售的任务数当作人数；未绑定只表示没有绑定 Worker 的销售。状态不可取得或数据过期时展示不可用/更新时间，不能把缺数据认定为离线或接单中。在线但暂停、故障停止、未绑定均不计入 D12。

实时 AI 销售状态与当前在售库存明确标为“当前/实时”，不随历史日期筛选伪装成历史快照。全局筛选的页面摆放待草图确认，但上述作用范围固定。

### 8.4 计算所需业务数据

本表说明数据含义及允许取值，不要求全部出现在列表。正式技术字段、事件关联和可回溯范围由架构师统一确认；不得从显示名称或当前值倒推缺失历史。

| 数据对象 | 业务字段 | 含义 / 值与约束 |
|---|---|---|
| 客户 | 客户唯一身份、客户名称、创建时间、线索状态 | 复用 Lead；未分配 / 已分配 / 无效沿用原状态。重复录入不是新客户 |
| 销售归属 | 销售身份、归属生效时间、历史分配记录 | 支持事件发生时归属和指定截止时点归属；未知历史不能以当前销售冒充 |
| 好友邀请及通过 | 邀请记录、客户、对应销售、实际发出时间、首次可靠通过时间、确认依据 | 只算实际邀请和可靠通过；发送未知、already_friend 不作为本次新增通过 |
| 消息事实 | 消息唯一身份、客户、会话、销售归属、实际发生时间、发送方、消息类型、发送确认 | 发送方区分客户 / AI / 人工 / 系统 / 未确认；类型包含文字、语音、图片等真实消息。未知发送不得算已发送 |
| 人工响应轮次 | 客户、销售、首条待响应客户消息及时间、首条人工回复及时间、是否已回复 | 从消息和正式人工交接事实归集，不要求创建新的业务主状态。无人工回复时结束时间为空，不填0 |
| 车辆 | 车辆唯一身份、当前上架状态 | 当前已上架 / 已下架，复用车辆主数据，不增加“已售”主状态 |
| 车辆上下架事件 | 事件身份、车辆、变更前后状态、事件时间、下架时公开售价快照、被哪次重新上架冲回 | 价格为元；原事件和冲回关系保留，重复请求不能重复生成统计事实 |
| AI 销售状态 | 销售身份、当前绑定 Worker、服务端有效状态、状态更新时间 | 复用正式在线/运行/绑定等字段，由统一入口投影；不另建页面兜底状态字段 |

只统计系统授权范围内已可靠采集的消息；不宣称覆盖销售全部微信私聊。语音转写失败但原语音身份和客户归属已确认，仍是一条客户消息事实；是否能 AI 回复继续遵循现行转人工规则，不因报表统计放开。

### 8.5 统一计算规则

#### 客户去重与销售归属

- 同一客户在同一统计范围只计一次；跨多天看总数时重新按客户去重，不能直接相加每日人数。
- 新增客户按创建事件的销售归属统计，客户总量按截止时点归属统计。微信通过、沟通和人工响应按对应业务事件归属统计；D04 按选入邀请客户的销售归属保持分子、分母一致。
- 未分配单独归组；销售停用、Worker 换绑不回写历史业绩。人工响应跨换绑时仍归本轮对应销售，不能只读当前 Worker 的绑定人。
- 同一客户被不同销售实际沟通时，各销售可各计一人；整体仍去重，因此人员行相加不一定等于整体。整体人数必须独立计算。
- 后来标记无效不扣减已经真实发生的新增、沟通、通过等历史事实。本期不自动排除有“测试”字样的客户或备注。

#### 沟通与有效沟通

- “AI”和“人工”按已确认发出的消息来源计数，同一客户可同时进入两组；“全部”取并集，不是两组相加。AI 生成完成、任务已创建、发送结果未知均不算实际沟通。
- 普通回复、开场和召回只要实际发送成功，均可构成己方沟通；好友邀请、系统提示不构成聊天沟通。来源未确认不擅自划为人工或 AI，相关数据完整性需单独提示。
- 每收到一条已去重的客户消息，检查该消息时点向前连续24小时（含边界及当前消息），客户真实消息数大于等于2即达到有效条件；不是自然日，也不是只有固定首轮24小时有效。
- 例如客户10月20日23:55和10月21日00:05各发一条，00:05达到条件。查询21日时必须读取此前24小时的消息上下文，不能只读取21日消息。
- 达到有效条件的时点需在所选期间内，同时该客户属于同样日期、销售、沟通方式筛选下的 D05，才计入 D06。同一客户重复达到条件仍只计一次，因此有效沟通率不超过100%。
- 客户文字、语音、图片均按真实消息条数计数；同一语音的原事件和后续转写只算一条。重复回调、系统“已通过好友”等提示不计；客户真实发送两条相同文字不是重复回调，不能按正文相同去掉一条。
- AI/人工筛选用于选择该组沟通客户，客户回信本身不被硬拆成“给 AI 的”或“给人工的”两份。

#### 人工响应时长

- 一轮从首条尚未被人工响应的客户消息开始，到第一条实际人工回复结束。客户连续追加消息不重置起点；AI 插入回复不充当人工回复、不重置计时。
- 人工回复后客户再发新消息，可形成下一轮。仅 AI 处理且没有人工响应/人工处理要求的轮次，不进入人工平均时长。
- 已有正式人工处理要求但尚未回复的，作为待响应样本保留，不按0秒计入平均；业务状态仍沿用原 Conversation / HandoffEvent 规则。
- 用真实经过时长，夜间和离线时段不扣除；不从飞书通知时间、点击查看时间或任务开始时间计时。
- 按首条待响应客户消息时间归属日期；跨日回复仍属于原轮次。统计时尚未人工回复的，待其实际回复后补齐，历史均值允许相应更新。
- 平均时长 = 已回复轮次总耗时 / 已回复轮次数。整体按轮次数加权，不把每个销售的平均数再直接平均；无已回复样本显示“—”。

#### 车辆已售与金额

- 只把“已上架 -> 已下架”计为已售。新建即下架、编辑下架车辆、对已下架车辆重复下架都不增加已售。
- 使用本次下架时的公开售价快照；之后编辑价格不改变这次已售金额。并非客户实际支付金额，不作收款或财务收入凭证。
- 重新上架冲回该车上一次有效已售数量和金额，并从原下架日期的统计中扣除；历史事件仍保留，不直接删除。
- 再次下架以新下架时间、新公开售价形成一次新的有效已售；不同时累计上一次已被冲回的金额。
- 因重新上架会修正过去统计，本期报表是“截至当前仍有效的已售”，不是不可变的历史成交流水，也不是按冲回日记负数的财务流水。
- 车辆指标第一期仅整体统计；不猜车辆归哪个销售，不按客户归属分摊车辆金额。

| 车辆操作示例 | 有效已售库存数 | 有效成交金额 | 日期归属 |
|---|---|---|---|
| 新建后保持下架 | 0 | 0.00 | 无已售事件 |
| 上架后10月20日以公开售价100000元下架 | 1 | 100000.00 | 10月20日 |
| 下架期间仅把价格改成110000元 | 1 | 100000.00 | 仍为10月20日 |
| 10月21日重新上架 | 0 | 0.00 | 冲回10月20日原统计；当前在售增加1 |
| 10月22日再次以110000元下架 | 1 | 110000.00 | 新计入10月22日，不再计10月20日旧金额 |

#### 空值、时效与历史数据

- 已确认没有记录才显示0；字段缺失、来源不可用、采集不完整分别说明，不用0伪装真实结果。分母为0的比例显示“—”。
- 缺少历史价格快照时不拿当前售价补旧金额；缺少历史归属、通过证据或发送来源时不按当前状态猜测。上线前由架构师核定可准确统计的起始时间及缺失范围，并在报表说明覆盖区间。
- 时间以可靠的业务实际发生时间为准，不以重复回传或入库时间替代；无法确认发生时间的记录不能悄悄落入今天。
- 查询统一记录统计截至时点。迟到消息、稍后确认通过、稍后人工回复和重新上架可按上述规则修正历史统计，不把报表缓存当权威源。
- 数据看板只读，不因刷新或筛选创建任务、发微信、执行车辆上下架或改变 Worker 接单状态。

### 8.6 数据验收标准

| 场景 | 预期结果 |
|---|---|
| 新建一条线索，再用同手机号重复录入并追加备注 | 新增、总量只增1；标记无效后不扣回历史新增 |
| 本期发出10名客户邀请，确认3名通过；另有2名是上期邀请、本期通过 | 本期通过数为5；本期邀请通过率为30.00%，不能用5/10 |
| AI 联系客户A、B，人工联系B、C，客户均未回复 | AI沟通2、人工沟通2、全部3；有效0；不是全部4 |
| 某客户有己方沟通，客户跨午夜、间隔10分钟发两条消息 | 第二条时达到有效；相隔超过24小时且无其他消息则不达到 |
| 一条语音回调两次并随后补转写，一条图片回调两次 | 仍为两条真实客户消息，不重复入库/计数；不能把语音转写当第三条 |
| 客户10:00、10:02发消息，AI10:03回复，人工10:10回复 | 本轮人工首次响应600秒；不是从10:02、10:03或转人工通知起算 |
| 人工已回复轮次分别为60、180秒，另有一轮待人工但未回复 | 平均120秒，待回复不算0；无任何已回复轮次显示“—” |
| 车辆按8.5示例上下架、改价、重新上架 | 按对应日期冲回旧数和旧金额；再次下架只算新售价，重复请求不重复计数 |
| 一销售的Worker接单中但空闲，另一销售暂停但在线 | 接单中的AI销售只计前者；不按有无当前任务计数 |
| 切换到历史日期或某个销售 | 当前AI状态、当前在售库存不伪装成历史数据；车辆不受销售筛选影响 |
| 销售停用/换绑、跨销售沟通、选择未分配 | 历史事实保留，销售归属按8.5取值；整体人数按客户重新去重 |
| 数据来源失败或缺少历史价格/消息来源证据 | 显示不可用/覆盖不足，不以0、当前售价或猜测人工来源填补 |

本表是后续实现验收要求，本轮没有执行数据接口、统计正确性或线上验收。
