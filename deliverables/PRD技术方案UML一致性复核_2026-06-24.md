## 二、核心一致性结论

| 检查项 | PRD 口径 | 技术方案 / UML 口径 | 测试口径 | 结论 |
|---|---|---|---|---|
| 当前 checkpoint | 当前推进 C2 会话绑定 / 微信监听；C3/C4 作为后续正式链路 | C2 是 Worker 运行时事实采集；C3/C4 已定义正式防误发、防误召回链路 | 前端未完成前只做静态 check，不正式测试 | 一致 |
| C2 主链路 | 第一屏主动扫描、第一屏命中优先读取、状态机定向读取、去重入库 | 主时序图和技术方案均按该链路描述；C2 不进入任务中心 | 必测第一屏、定向读取、去重和无补偿扫描入口 | 一致 |
| C2 任务边界 | C2 不定义 `session_scan`、`message_ingest`、`wechat_binding` 为任务中心 `task_type` | UML 明确 C2 不创建 Task，只有 C3 需要发送时才创建 `chat_reply` | 测试不按任务中心任务验收 C2 | 一致 |
| 补偿扫描 | 废弃多屏滚动补偿扫描 | v0.6 明确不执行旧滚动兜底方案 | 删除第二屏 / 第三屏 / 滚动到底 / sessions compensation 测试项 | 一致 |
| C3 发送前刷新 | 发送前必须 `pre_send_refresh`，发现客户新消息则旧回复作废 | 主业务时序图包含发送前定向读取；技术方案要求旧 `reply_action` 变 `superseded` | 必测防误发 | 一致 |
| C4 召回前预检 | 召回到期不能直接创建 / 发送 `follow_up` | 先生成 `recall_precheck` read-target，确认无新客户消息后才允许召回 | 必测防误召回 | 一致 |
| `watching` 状态 | 不作为第一期主状态 | 会话状态机未将 `watching` 作为主状态；技术方案用等待类状态加规则字段表达 | 必测不得返回 `watching` 主状态 | 一致 |
