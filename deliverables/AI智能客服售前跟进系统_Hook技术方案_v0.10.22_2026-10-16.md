旧授权退出与客户端动作并发时，统一按原身份归档收尾：未领取的已取消任务允许以无租约令牌完成原流程；已经登记的消息补交和原语音结果保留原编号、原摘要及回执，仅归档，不进入新一轮 AI。断网或回执丢失后，独立的旧证据清单只重试已有投递和已有语音结果，不创建转写或发送动作。过期邀请结果显示“本轮好友绑定已结束”，不冒充绑定成功，也不升级为设备故障。跨微信进程重启补交时，另外核验当前账号、授权周期和进程，保留旧消息原进程字段；活动业务仍受原进程门禁约束。归档仍校验原账号、授权版本、父消息与正式邀请凭证；无关绑定冲突不能被幂等重试掩盖。

验证口径：隔离 HTTP、SQLite、合成联系人及浏览器实际按钮操作；Windows 删除后重新邀请、真实 Hook、真实模型和销售正常回复仍待后续成品验收。本轮不打包、不部署，不改变已封存0.10.9包及机器合同号。

## 2. 四方分工与架构

| 组成 | 唯一职责 | 不拥有的权力 |
|---|---|---|
| 后端（FastAPI＋PostgreSQL） | 销售/Worker/线索归属、任务租约、消息事实、会话与批次状态、AI 调度、发送许可、人工接管、召回、飞书与审计 | 不直接操作 Windows，不让浏览器直连 Hook |
| Worker（Windows 客户端） | 单实例、启动窗口准备编排、Hook 接入、可靠收件箱/Outbox、C1 执行调度、发送账本、回执补交、故障证据、耗时和更新 | 不自行生成业务回复、不猜客户归属、不自行解除人工暂停 |
| OmniAuto | 客户端侧提供 OCR/窗口/C1 适配；服务端侧提供 Brain、检索、Evidence Pack、Guard；纯合同规则供两端复用 | 服务端 AI 无微信操作权限；客户端 RPA 不拥有业务状态机 |
| Hook / 微信进程 | 本人/联系人资料、回调、历史查询、Voice2Text、SendTextMsg | 不理解线索、短码来源、任务租约和接管状态；HTTP 成功不是业务成功 |
| 运营后台 | 调用后端管理线索、销售、Worker、任务、车辆、知识和日志；显示后端状态 | 不自行裁决任务终态、不保存 Hook/飞书执行密钥 |

仍采用现有后端单体与 Windows Worker，不新增消息微服务、第二套任务系统、第二套恢复线程或本地 AI 大脑。`Conversation` 保存业务状态；`WechatSessionBinding` 保存身份/监听关系；连接健康与本机能力只是执行条件，不再复制一份业务状态。

主数据流：客户微信→Hook→Worker 原始事件落盘→可靠上报→后端消息事实/批次→服务端 OmniAuto Brain/Guard→批准的 ReplyAction/Task→Worker 串行 Hook 发送→发出记录关联→sent_ack 事务结算。

## 3. 环境与交付配置

开发和服务端联调使用 Mac 隔离环境；Windows 测试机验证实际窗口、DLL 和微信动作。联调凭据、数据库、端口及数据目录与生产隔离，不借用生产客户实发。开发不得自行变更生产服务器配置；生产发布必须按另行授权执行。

部署配置在 Worker 受保护 `client_settings` 中使用 `hook_deployment_v1`，字段为 `revision`、`wechat_exe`、`dll_sha256`、`hook_api_port`、`receiver_port`。微信路径必须是本机绝对路径，端口有效且两端口不同；缺项或冲突报错，不能猜端口或自动回退到生产配置。

- Hook API：`http://127.0.0.1:<hook_api_port>`。
- 接收器：`http://127.0.0.1:<receiver_port>/receiveChatBotMsg`。
- DLL：配置中 `WeChat.exe` 同目录的 `version.dll`，核对实际哈希。
- 工作微信参数：`StartPort=<hook_api_port>`、`ConnectType=http`、`RecvType=0`；工作目录是 EXE 父目录。
- 配置、生成快捷方式、进程核验、回调登记共用同一来源。实验端口 30001 和 HookLab 路径不作为正式默认值。
- 本机 HTTP 不等于完全可信：核验监听进程/路径/组件归属，限制访问来源和请求大小；不得对公网暴露 Hook 或接受任意 SQL。

## 4. 从开机到接单

实现边界（搜索与加好友布局）：启动检查在原动作锁和身份核验内建立主窗口区域表，保存搜索框实际像素位置以及页头、网络查找、主窗口结果卡、聊天标题的采集范围；这些固定采集范围沿用受支持版本的布局定义，只在启动时计算。任务复用该表，实时截图只用于验证查询内容、按钮和当前结果，不把启动截图当作当前内容。搜索框输入、查询核对、圈 X 清理和一次键盘补删共用位置。布局失效时清空共享缓存并阻止接单，提示重开 Worker；不在心跳中重新定位或调整微信，重开后的原在途核对门禁仍先于启动定位。

申请表单在首次出现时建立本窗口的字段位置和采集区域；填写申请语和备注连续复用首次字段位置，中间不截图；填写后的页面只在原备注区域严格核对短码，不再次比较表单布局、标签坐标或输入框像素形状。通用动作层原有的身份、前台、窗口和凭证保护保持不变。网络查找选项、联系人结果和确定按钮仍须在当前限定区域内出现并通过原文字/像素校验。原提交凭证先于确认点击落盘，布局缓存不构成重复申请或清除未知结果的许可。

Worker 窗口及网页采用不透明底色，圆角仍由原窗口遮罩处理。窗口显示/隐藏、移动/缩放、页面加载和渲染进程终止仅记录无内容的异步限量元数据，存入 `artifacts/runtime/window-render*.jsonl` 并由桌面诊断入口统一导出；不抓取聊天内容，不因记录失败阻塞界面。本地离屏测试不能替代 Windows 图形合成或远程画面的验收。

1. 后台先录入客户、去重并分配销售，创建待加好友任务；销售电脑离线时任务仍排队。
2. 销售点击配置生成的工作微信图标，加载 Hook，扫码登录并保持窗口展开、可见、非最小化。
3. 销售手动点击 Worker 图标。首次输入原 Worker ID/Token 绑定实例；后续加载原绑定、SQLite、暂停/故障及在途记录。
4. 按原启动入口先准备微信窗口，再摆放 Worker，避免遮挡。由 OmniAuto 一次规范化尺寸/位置并取得布局依据；成功后复用，失败不无限重做。
5. 核验后台凭据、销售/实例关系、微信本人 wxid、版本/DLL、端口归属及合同；接收器监听成功后登记回调，再补历史与核对旧动作。
6. 进入待开始或保留原暂停/故障状态。初始化和恢复不发新好友申请、不自动补发文字、不自动开始接单。
7. 销售点击“开始接单”，统一核验窗口、身份、时间、租约、旧动作/回执与停止状态。通过后才开放新 C1、模型、转写和发送。

“微信窗口打开”不等于持续前台焦点。点 Worker 导致焦点切换是正常行为，不能据此判 Hook 断开。C1 点击输入时由原控件适配取得焦点；Hook 接收器不抢焦点。最小化、隐藏、锁屏和无人登录桌面不能被视为已支持的等价运行环境。

启动准备只做一次不等于后续不截图：搜索结果、表单、提交和清理仍需要各自动态证据。窗口移动、DPI/显示器或进程变化导致旧布局失效时，走原失败/恢复入口，不盲用坐标。0.10.18 已发布包仍按 1060×740 物理像素；本轮 r4 源码候选改为两窗统一逻辑尺寸与共同缩放，搜索 ROI 和 NativeUI 初始化也核对同一目标，不把旧截图坐标直接写死。

## 5. OCR 加好友与首次绑定

### 5.1 C1 单任务闭环

领取资格及租约→共用微信动作锁→复用启动布局→定位主窗口左上搜索框→清残留并核对为空→输入本任务手机号并核对→点击“网络查找手机/QQ号”→识别结果→记录业务事实→清理本任务弹窗/搜索框→回执与 Flow 收尾。

| 结果 | 处理 |
|---|---|
| 无法找到该用户 | 按搜索无结果结算，不申请，不断言手机号永久无微信；正常业务结果不使整个 Worker 故障 |
| 未添加，显示“添加到通讯录” | 进入申请表单，填写服务端 `verify_message` 与 `remark_name`，短码使用 `remark_code`；记意图后只提交一次 |
| 已是好友，直接进入对话 | 必须核验本次手机号查找与返回目标对应；结算 already_friend，不补码、不欢迎、不新增 AI 托管 |
| 超时、限制提示、未知界面或识别不清 | 走原失败/取证出口，不强塞进前三类，不盲点或重复申请 |

正式申请文案和备注由后端生成；自动备注只写客户短码。不得复制实验文案或生成第二套短码。手机号输入沿已测逐位节奏；申请消息和备注各沿原一次剪贴板粘贴及有限纠正规则。长问候语滚动时不得以 OCR 未完整看到问候语为由反复重填；保留已测短码核验和单次提交证据。

三类正常结果以及中断收尾都记录搜索框清理状态：有真实手机号残留才清空一次并核对，灰色“搜索”占位或已空只核对。只清搜索框，不碰聊天输入框和备注。目标不能确认或清理失败时停止新工作，但不能覆盖“邀请已经提交”等事实，更不能据清理失败再申请。锁不持有到客户同意或 AI 完成；释放物理锁也不绕过回执结算门禁。

申请窗口切换复用原 `add_friend_paced_pause('verify')`（默认0.35—0.9秒，仍走原配置），之后只观察当前前台窗口，使用原5秒预算，不重点击。候选必须属于同一已核验微信进程、在本次点击后新出现、可见且不是阴影/提示窗口；不再用固定宽高判断表单类型。连续两次本地窗口观测相符后，仍须通过原申请标题、字段标签、实际控件像素、短码、每次动作的当前帧及提交账本检查。窗口尺寸不同可以进入识别；截图以后布局改变不能授权旧坐标点击。记录窗口类、几何和归属等元数据，不记录标题/聊天内容。

从尝试打开申请窗口开始，到已证明申请窗口关闭之前，任何切换或识别失败均延后清理；不得继续通过旧资料卡清搜索，也不得自动确认/取消未知窗口。原失败回执、未知提交、结算和停止门禁保持。故障恢复在已有结算/心跳/身份门禁之后，复用启动/C1的可见弹窗分类做即时只读核验；遗留弹窗时提示先核对并取消申请窗口，不能显示“可以恢复接单”。关闭后仍需操作者点击开始；按钮处理前后重查，不新增截图、OCR或微信接口请求，不影响正常运行/暂停的收件与结算。

### 5.2 两类身份绑定

销售本人 wxid：凭据和设备实例已验证、Worker 已关联启用销售时，首次核验本人 wxid 后由后端建立账号代次；保持手动开始门槛。后续换号停止新业务，通过原重置/重绑定处理，旧账号事件和账本不能改贴新账号；同一本人 wxid 不由两个有效 Worker 同时控制。

客户 wxid：只对有系统 C1 写码及邀请提交证据的任务查联系人，核对短码、任务/线索/销售/Worker、唯一候选和好友身份后，在后端事务中建立活动绑定。权威范围为销售微信账号＋联系人 wxid。手机号、昵称、头像、最近好友或一个格式正确的手工短码均不能单独建立托管关系。

已有好友首期不补短码、不导入托管。已有合法系统任务关系不因后续任务返回 already_friend 被撤销。未绑定事件只暂存，不交给 Brain。激活前历史用于建立上下文，不能全量当新问题触发回复；通过好友的系统提示不当客户文字，首次开场遵循原唯一控制批次。

明确的同一客户短码备注变化先阻断新外发并复核；现有列表缺项不构成删除证据，当前只允许运营明确确认重新邀请时结束旧托管。旧绑定与历史保留用于原动作结算；新任务正式提交并核验原客户身份后另建新绑定，不能复用旧授权。

## 6. 接收、持久化、排序与历史补缺

回调线程只做来源/大小/结构检查、原始事件及接收序号落盘，事务成功后回应；解析、语音、上报和 AI 异步处理。回调不等待动作锁、模型或客户 A 的处理完成，因此多个客户消息可接收并排队；这不等于无限内存并发。

RawInbox 的事件身份与正式消息身份分开。事件摘要/阶段保留每次观察，正式消息按账号＋原生消息 ID 幂等合并并验证客户归属。相同正文不同 ID 是不同消息；同一语音 ID 的后续音频是补充，不能丢弃。原生 ID 用十进制字符串，不能经 JavaScript 浮点转换。

Worker 通过可靠 Outbox 上报后端；后端先存原生回执，再按唯一入口 dispatch 到 MessageEvent/批次。重复上报返回原确认，不重复创建通知、回复和召回。未知字段、错误身份、群聊及非托管对象不默认归到当前聊天。

### 6.1 排序规则已经落到代码

消息 ID 只用于身份，不是时间序号。`localId` 只作对应 MSG 分库内分页游标；保留 `CreateTime`、`Sequence`、`MsgSequence`、`MsgServerSeq` 原值和库代次。

当前 `hook_history_rules.validate_coverage` 对单个有效 MSG 分库按 `Sequence` 排列，同时要求 `Sequence`、`MsgSequence` 严格递增且 CreateTime 不倒退。跨多个有效分库、缺序号、冲突、邀请边界秒不能确认等情况，覆盖凭证不放行发送；不能把先到先得当作可靠微信先后。

完整覆盖需要两次内容和库目录一致的扫描、页数/行数/上界核对及本地待上报计数为零。库轮转、目录变化、读中变化、超出有界范围或缺页都不能签发“完整”。数据库只用白名单只读模板查询；不能接受后端任意 SQL。游标在页面可靠保存后推进，重叠补查依赖消息 ID 去重。

回调快到但历史尚未落库时可以先保存事实；发送前必须完成需要的历史覆盖。语音先占原消息位置，转写完成补回同一 ID，不按转写完成时间挪到最后。引用只把新写正文作为新输入，保留引用关系；撤回保留原证据并作废依赖它的未发候选。系统通过提示排除出客户问题；文件、未知类型保持明确的非自动回复处理，不伪装文字。

### 6.2 同步屏障与业务编排

待发布修复（2026-10-21）：完整双遍历史中的入向 Type=10000 精确好友验证系统模板，通过客户级 notice 入口复用 C3 HandoffEvent、取消未发工作及原飞书通知，不进入 Worker 技术停单。保存账号代次及原生消息身份派生的提示键，重启/库句柄变化不重复交接。系统提示不伪装聊天消息；复用现有图片/超时交接时，统一合并触发消息、风险与证据，并独立保存好友验证原生边界，不依赖交接主原因/source；所有新增条件均参与结清，不重复通知。统一人工交接结束入口接收本次可信完整历史的提示顺序边界，只有已核实为人工且严格晚于该边界的回复可以结清。提示缺失、旧人工、AI 回显不放行；后续客户消息先按8.2的负责人和待回复轮次处理，只有AI负责时才进入自动回复组批。原发送 settlement/ACK 保持独立，unknown 终态不改为送达，不清 flow/凭证强行恢复。已故障设备需正式保留数据更新后，核对原发送、正常结束旧流程，再由销售恢复接单；旧在线更新若受未结清流程阻挡，由运维验收关闭 Worker 后的保留数据安装路径。

启动、重连和配置变更后重建回调并补历史；日常有界追赶，发送和召回前再检查目标会话最新覆盖。本机序号、已上传事实、库范围和服务端版本一致才形成可用凭证。新客户消息、人工消息、语音补充、撤回或历史晚到推进上下文版本，尚未触发的旧候选失效。

Hook 没有替代 MessageBatch：同客户连续几句话仍按原合并窗口/最大等待组批；不同客户不混批。每会话只有一轮有效工作，新话可以继续落盘并使旧轮失效；不是只允许客户问一次。跨客户生成有界并发，同客户不并发发送相互冲突的答案。

屏障只证明这次可观察的本机微信记录已同步，不证明腾讯服务器绝无尚未同步的新消息。调用前看到新事实必须停发旧稿；调用已发生则保留真实尝试，不假装撤回或重发。

## 7. 语音、图片及消息来源

Voice2Text 前验证本人账号/进程、完整音频与摘要、托管资格、窗口可见非最小化，以及已确认关闭微信原生自动转文字的配置。安装记录 `hook_native_auto_text_confirmation_v1` 与部署 revision 关联；没有操作确认不得猜测该设置已关闭。

语音按同一微信进程串行主动调用，保存调用起止、音频摘要、响应摘要和父消息身份。音频补充中的空字段不能抹掉已有有效内容。回调继续接收；该客户后续回答等前置语音转写完成或进入原失败处理，其他客户可处理。

- 成功转写：只把有原响应证据的文字补入原消息，推进上下文版本。
- 明确失败：保留失败事实，按该客户媒体失败/人工交接规则处理，不猜正文。
- 超时或进程内调用是否结束不明：标 uncertain，隔离该微信进程的新主动调用；不能仅因 HTTP 超时释放通道并重试。
- 原进程退出或明确结束的证据经过校验后，重建连接与覆盖；旧记录仍保留。没有证据不能靠删表解除阻挡。

合法托管客户的新图片只登记真实图片事实并触发原 HandoffEvent，取消未发 AI/召回，按原通知规则通知销售。不调用 Vision、不把不支持伪装成识别失败、不生成解释图片的自动回复。重复回调/历史图片不重复通知；旧历史图片、己方图片、未绑定对象及群聊不一概触发交接。

本版人工交接修复：完整历史、账号/客户与原生顺序、发送来源核验通过后，先复用原人工回复结算入口，不把旧语音转写成功当作结清交接的前提。已应用的可信人工回复之前的语音，共用同一顺序边界退出 AI 前置等待和转写任务清单；原语音状态、正文和回执不改，之后的新语音在AI处理资格成立时仍等待；人工负责期间按8.2保存事实，不为催办新增转写。首次迟到及旧回执重放也复用此人工覆盖判定，不重新建立已处理的交接；保存最后一次已应用人工事实的历史凭证引用，后续不完整读取不能抹去原有证明。新回执仍按原规则留存未知结果和音频摘要，既有回执不可覆盖。已被人工覆盖的旧语音首次补交仅更新原始结果，保留补交前用于回复校验的正文/状态投影；后续历史仍核验同一账号、原生顺序、消息集合及正文，只在可信人工覆盖仍成立时使用该投影，避免仅此旧结果变化作废新客户批次、模型生成或发送许可。未覆盖语音仍使历史失效并按原入口取消旧稿。普通 collector、批次终态、在途与已发送结果不被强制复活。业务交接关闭不解除微信进程未知调用隔离；接单暂停、AI 关闭、拒收和托管资格仍按原门禁执行。

己方消息须与真正触发过的发送日志核对：账号、客户、原动作/分段/尝试、正文、时间及新增历史范围全部匹配，且唯一未占用候选才关联 AI 发出记录。人工同文、多候选、日志缺失保持来源未知。确认没有程序候选及未决动作后才认定人工；AI 回显只结算原动作，不再次触发 Brain。

## 8. AI、知识、车辆与内容安全

模型在后端运行，复用 OmniAuto Brain/检索/Evidence Pack/Guard。链路为最新事实和业务资格→会话上下文→正式知识与 Product Master 检索→候选生成→Guard/必要有界修复→固化 ReplyAction。Worker 只执行批准正文。

- 当前全局模型容量默认 20，跨账号、跨进程使用后端持久槽位；同会话只保留当前轮。慢但活着的调用不得因超时直接释放槽位再开第二个调用；释放校验原调用 token，孤儿回收需实际进程死亡/PID 复用证明。
- 模型、重试、主生成/润色/语义审核额度集中使用原配置。截断输出、上下文耗尽、结构错误不能作为完整答复发出；有限恢复耗尽后按现有 L2/人工流程结束，不无限重试或写固定假答案。
- 产品事实以 Product Master 客户安全投影为权威；公开价格、库存、车型、里程等不得由历史话术或 RAG 改写。内部联系方式、采购价、底价、内部备注不得进入 Evidence Pack。
- 知识是“草稿→校验/差异预览→运营明确发布→新版本快照”，未发布草稿不影响线上。已创建批次保留自己的知识快照，新版本对新批次生效。回滚知识发布是新受审计操作，不修改旧消息事实。
- 车辆新增/编辑/Excel 预览确认导入/上下架、图片上传排序删除均在原车辆模块完成。车辆图片管理仍存在，不等于本版允许微信图片理解或自动发图。
- 首次开场、普通回复、召回共用内容与发送管线；好友通过系统提示不喂成“客户主动说谢谢”。

主要业务对象：Conversation（状态/AI开关/计数/联系时间）、MessageEvent（事实）、MessageBatch（本轮输入/版本/生成尝试）、ReplyAction（批准内容/期限/分段）、Task（租约/执行）、SentAck（结算）、HandoffEvent（原因/通知/关闭）。消息事实与批次更新保持事务一致。

批次收集/生成后进入回复创建、人工、无动作、拒收、被新消息取代或失败；ReplyAction 排队后须 claim 才能 sending，随后 sent/明确失败/unknown。任务 status 使用 pending/running/completed/failed/cancelled 等统一枚举，`chat_reply_sent` 是 result_code，不是另造任务状态。

### 8.1 分段回复

继续使用原分段规则：当前默认每段 108 字符、最多 3 段，由服务端配置和现有分段实现控制，不能截掉多余内容冒充完整回复。每段属于同一 generation/batch，并有 segment_index、前驱 action 和独立回执。前一段没有 sent_ack 成功确认，不发送下一段。新话/失效资格取消未发尾段，已发内容保留；重启不从第一段重发。

### 8.2 人工、拒收和召回（2026-10-22 用户已确认，源码候选）

必须区分三个事实：本客户由谁负责回复、当前在等谁、还有哪些未解除的风险/技术阻挡。HandoffEvent 是交接原因与通知记录，不能代替持续的回复负责人；关闭旧交接事件不等于交回 AI，`ai_enabled` 也不能代替人工/AI所有权。后端统一持久化和判定，Worker只回传可靠消息与执行证据，Brain不自行决定恢复人工会话。

| 触发/条件 | 目标状态及动作 |
|---|---|
| 可靠识别销售人工发言，包括AI回复过程中销售插话 | 该客户持续由销售负责；使旧未发AI和召回失效。已触发动作只核对收尾，不重发 |
| 销售已回复，之后客户未回复 | 等客户回复；从最新可靠销售回复计默认72小时，符合原资格才进入召回预检 |
| 客户在人工负责期间回复，销售未继续回复 | 等销售回复；不交给AI作答，不执行72小时召回。以本轮第一条尚未被人工回答的客户消息计1小时 |
| 同轮客户继续发言 | 继续存消息，不刷新1小时起点、不重复建立提醒轮次 |
| 满1小时仍未被销售回复 | 飞书提醒对应销售，每轮一次；提醒之后仍等销售，不能自动交回AI |
| 销售再次回复 | 结束本轮待回复及未发提醒；继续人工负责，重新进入等客户/72小时召回资格检查 |
| 召回生成、排队、no_action，或第1段尚未可靠确认发出 | 不据此交回AI；保留或恢复原负责人及真实等待状态，失败/未知发送仍按原凭证结算；第1段成功后的尾段故障依8.3 Q3处理 |
| 当前有效召回已经实际发出并获可靠结算 | 以第1段可靠成功结算为切换点，客户后续消息走正常AI回复；不得覆盖更晚的人工接管或硬门禁 |
| AI恢复后销售再次发言 | 再次由销售持续负责，重开人工责任周期，取消尚未发送的旧AI内容 |

每轮指“人工负责期间第一条未被销售回答的客户消息，到销售下一次可靠回复”。同轮连续文字、语音、图片及重复历史不重复起轮；语音补正文不把转写完成时间当客户发言时间。人工负责时不得为了识别催办轮次新增Voice2Text或Brain调用；继续沿授权入口保存原消息和已有结果。已被人工覆盖的旧语音仍按第7节保存，不重开交接、不作废后续有效回复。

负责人、等待状态、轮次、起点、通知发送记录必须持久保存，重启不能丢失或重新计时。提醒和原始转人工通知是不同业务事件，不能用新建HandoffEvent实现每次催办，也不能让每条客户消息再次通知。发送通知前用同一权威状态确认轮次仍有效；销售已回复则取消未发提醒。失败、结果未知和成功分别留证；不能把调用过飞书当作通知成功。夜间/离线/失败统一按8.3已确认规则处理，不另设策略。

高意向、图片和风险继续按原规则交接；投诉、合同/金融/价格承诺按Guard决定直接人工或唯一获批说明后人工。明确拒收须引用本轮真实消息作为hard_opt_out证据：rejected、关闭AI、清召回和取消未发动作，不发客套话；当前不额外发飞书。暂时不考虑/价格高不等于永久拒收。暂停、AI关闭、身份复核、好友限制、无效线索、未知调用等门禁均独立保留，可靠销售消息或召回结算不得绕过未解除门禁。

召回继续复用原recall_precheck→完整最新历史→trigger_type=recall批次→Brain/Guard→分段发送→原回执链。默认72小时、每日最多1次、21:00—09:00（北京时间）静默不变；按连续无人回复最多3次执行；可靠新客户回复重置连续沉默额度，但不重置每日次数，不删除累计历史及原结算证据。客户新消息或销售发言使旧召回资格失效，no_action恢复来源状态且不计成功次数。不得将recall转成customer_message，也不得在批次进入ai_active时就改变回复负责人。

人工/AI所有权切换必须核对当前责任周期、上下文版本及可靠原生顺序。迟到的旧召回ACK只结算原动作，不能覆盖较新的销售接管、客户待人工回复、拒收或新交接；重复ACK不重复切换或计数。同秒事件不能只比较秒级时间戳。客户在召回物理发送/ACK之间插话须结合实际原生先后及第1段可靠确认的切换点判定，不能按网络到达顺序猜测。

飞书仍由后端统一应用发送，按conversation.sales_id解析对应销售的open_id；Worker不持有飞书凭据。原handoff_event_id通知去重不变；本轮新增未回复提醒必须有独立稳定轮次键和持久发送状态，统一复用通知适配器及审计，不另建Worker通知流程。

## 9. 微信动作锁、发送与结果结算

C1 加好友与 Hook 发文字共用本机微信动作锁。Voice2Text 等可能在微信进程内持续执行的主动调用同样纳入单进程互斥；只读历史按允许的有界调度执行。回调落盘、可靠上报和不同客户的 AI 不占该锁。未知主动调用未结束时，不能靠释放 Python 锁宣称微信空闲。

轮到当前有效发送任务执行时，独立抽取并持久保存 500—3000ms 发前等待，第一条、开场、召回及每段都适用。此前排队或等待旧锁的时间不能抵扣；不是以上一条发送结束为计时点，也不是所有排队任务同时倒计时。等待不持微信动作锁，不占长数据库事务；到期仍须取得锁与最新许可，不能承诺总间隔不超过 3 秒。

到期后重新检查：账号/实例/代次→本会话同步覆盖→有效线索及短码托管→最新 batch/action/分段→无媒体或来源疑点→Guard/配额/时段/租约。后端原子 claim，Worker 在调用前再核对本机新事件；不得本地改一句再发送。

发送顺序：持久动作准备记录→获得后端 claim/begin 授权并记录真实尝试边界→单次 SendTextMsg→保存原响应→发出回调/历史关联→回执入 Outbox→服务端事务结算。真正未触发和已经可能触发分开保存，发送接口禁止通用 HTTP 自动重试。

| 证据 | 允许结论 |
|---|---|
| 工具受理/HTTP 200 | 已取得响应，不能直接记 sent |
| 唯一关联到本机微信发出记录 | 按 hook_outgoing_record 合同结算；不是客户送达/已读证明 |
| 可靠证明未进入动作 | 按原未触发失败入口结算，新动作仍需重新授权 |
| 超时、多候选、无充分记录 | unknown/uncertain，查原动作，不自动补发 |
| 后端确认丢失 | 重传同一回执，不再次调 SendTextMsg |

物理锁释放不等于下一任务获准：旧 Outbox、sent_ack、任务/Flow 和未知执行风险仍按原全 Worker 安全门禁处理。客户失效/解绑后可用原凭证只核对旧发送；reconciliation_only 不授权新消息、新批次或新发送。

### 客户状态变化与原发送收尾（2026-10-27）

- **尚未取得发送许可**：领取被拒时，通过原 `native-recovery` 的 `send_unpermitted` 类型复核原 Worker、账号/进程、Flow、任务/批次和租约；后台重新执行现有资格规则。仅确认无发送许可且原任务已终态或确实失去资格时，结束旧任务/剩余旧回复。不凭客户端错误码调用通用 fail，不改变人工责任、召回周期或销售暂停。
- **已有许可但未触发**：本地单纯到期与账号/进程变化分开；历史读后出现新回调（begin 前或 begin 后）也不得发送旧回复。实时与重启复用同一未触发凭证入口，保留 permit/intent/hash；trigger 或 outcome 已存在就禁止走此入口。原 not-triggered 回执及 Flow finish 可幂等补交。
- **已经触发**：合法 coverage 的正文、媒体、排序等未就绪状态不等于设备损坏。原发送专用覆盖允许只读观察原确认期限；期限前保留共享未知发送门禁，期限到后仍由原 observe/settle 按证据结算，缺充分记录只能 unknown，不能据等待状态确认发送、更不能补发。错误账号、摘要冲突、非法行不属于此等待。
- **只暂停一个客户**：先核对同一 Worker、账号、epoch、peer（该接口携带时）和修订范围，再返回客户暂停/库存修订过期。历史、邀请发现、关系复核和回调上报沿相同判定；刷新库存后继续其他客户。拒收/尚未派发的回调保留本机 outbox 与原始事实，不伪造存储回执；恢复授权后从新库存重新同步，不在暂停期间启动 AI。
- 请求/回执丢失保留原恢复请求，Worker 重启补交后再结束原 Flow。正式诊断仍只使用桌面“车金故障诊断”，收集上述原凭证和收尾回执。
- 分段未许可恢复由后台 `inflight_unpermitted_tasks` 提供原 Flow、批次、生成代次内的任务关联，第二/末段不再按首段任务 ID 查请求。客户暂停后不在可执行业务库存，也仍可核对原请求；只读库存不授予发送许可，其他目录的请求不自动重放。领取后、物理 begin 前再次通过统一跟进资格入口检查客户是否失效。
- 暂停客户恢复授权后，旧 revision 的投递不能假记 `stored`。新 revision 必须实际得到原生消息保存回执和 `facts_stored` 登记回执，且同 Worker/实例/账号/epoch/进程/绑定/peer/原始包及完整消息内容一致，才将旧投递收尾为 `covered_by_new_authorization`。原 payload、旧回执、替代 envelope 和两份新回执一并保留；与新回执的本地落库处于同一事务。旧版本已保存的新投递重启后须重新取得幂等登记回执才能补齐关联。
- 更新门禁和原始收件箱到期清理共用覆盖凭证校验；只有保存、没有登记回执或覆盖不完整仍阻止更新、保留原始包。正常未完成投递跳过清理，不当作损坏导致全机故障；凭证身份/摘要不一致仍报错且清理事务回滚。到期归档保存完整投递记录，诊断 SQLite 快照继续收集关联凭证并按原规则隐藏消息正文。此收尾不证明发送成功、不触发 AI 或补发。
- 消息登记及派发回执复用合同层 `unique_message_facts`：同一账号/peer 包内相同原生编号、方向、类型和正文只产生一份业务事实；同编号冲突仍拒绝。原始回调、各 entry_position 和传输回执的 message_count 保持不变，覆盖证明仍核对完整原 envelope，不能将业务去重当成删除证据。
- 诊断优先级复用覆盖证明校验后才把 `covered_by_new_authorization` 降为历史；未知状态、缺失/损坏/超出检查预算的证明仍优先。校验受既有快照时限和单元格大小限制，缺项写入清单；预算内联动收集原始包摘要、投影、投递和覆盖证明，不通过扩大预算掩盖遗漏。

## 10. 暂停、故障、恢复及时间校准

人工暂停、故障、业务离线和连接等待是不同事实。停止接单禁止启动新 C1/模型/转写/发送；已 running 的操作按原规则安全结束或失败，已触发动作必须结算。账号接收授权仍有效时可继续保存消息、补交既有事实和只读恢复；不趁恢复生成下一段。

后台确认 faulted 且原任务终态时，原 task_terminal finish 可取消未发尾段；sending 仍阻挡，不能把仅本地故障或普通暂停等同该条件。C1 执行前保存任务/Flow/fence/账号关联及工厂调用开始标记；只有可靠未进入 UI 的证据才补交未执行失败，文件缺失不等于未执行。

| 场景 | 统一处理 |
|---|---|
| C1 窗口/本机 OCR 故障 | 先持久停止新工作，再采证/补交；不能只停 C1 继续发送 |
| 后台网络断开/临时 502/慢心跳 | 保留事实与原状态，显示连接或时间等待；恢复后补交并重同步，不误判换号或自动解除人工暂停 |
| SQLite 读写/磁盘故障 | 普通连接不重复初始化写入；统一存储失败入口停单，独立诊断降级；主循环先通知业务线程停止，再等待写入退出 |
| 语音或发送结果未知 | 保留原尝试，隔离相应进程主动调用，核对原记录；不重复触发 |
| 账号/组件/端口归属改变 | 停新工作，区分旧 epoch 与新实例，重建环境后再授权 |
| 历史缺口或排序不可信 | 可以保存新事实，但不签发该会话发送覆盖 |
| 图片人工接管 | 只停止该客户自动回复/召回，其他合格客户继续；不当全机故障 |

后台时间由 HookConnectionManager 按 credentials＋registration.scope 持有唯一 HookBackendClock，连接和正式任务共用；同身份重建接收器不另开一只时钟，换账号/进程则新作用域。

当前合格采样 RTT 上限 1 秒，锚点有效期 120 秒。已有有效锚点且慢回包区间一致时继续使用旧锚点，但慢样本不延长寿命；无锚点、过期、跳变/不一致仍等待或报错。失败后迟到旧样本或新的慢样本不能解除失败，只有更晚的合格快样本可恢复校准。校准恢复不恢复人工暂停/真实故障，也不复用旧任务权限。

连接自身恢复先结清 connection 所属等待，再汇总 business/存储/协议等门槛，防止等待标记反过来永远阻止自身清除。UI 查询安全状态不等待网络心跳持有的连接锁：返回“正在核对微信连接”，不冻住界面或拿未核验进程放行。

### 10.1 Hook 停单恢复与明确未送达查询（2026-10-27 用户确认，待开发/复审）

本节是新增开发要求，不表示源码已实现、已推送或销售已安装。保留当前版本号；正式发布号另按原发布流程确定。五类客户级误停修复基线为 `850dd79`，本项不得回退其分类与收尾。Windows 实机测试继续暂停；本项不授权打包部署、操作销售微信或联系运维。

目标：确有风险先停；能够证明仅本次请求未送达的只读查询允许有限重试；故障后销售通过原有界面和桌面入口完成安全恢复，不执行命令、不删除记录。暂停、等待、故障、进程隔离、业务结果未知分别记录，不能以一个忽略码名单代替。

本地实现候选（2026-10-27，待5号复审、未打包）：实际 loopback HTTP 只在显式建立连接阶段失败、尚未调用 request 时记录明确未送达；请求写入、响应读取及无法分类仍按未知处理。重试预算使用同一 SQLite 调用证据链持久化，正常1/5秒等待不占微信动作锁；重启或运行意图变化取消本轮，不能重置预算。用户已确认复用底部按钮：仅明确未送达且本轮耗尽/取消时显示“重新检查连接”，后台检查先保持原暂停/故障，按钮不开始接单。旧进程结束证明单独留存，不改写原调用/发送记录。桌面ZIP和升级保护包含传输依据、预算及新旧进程关联；已结证据沿原关键证据保留期清理，未结不清理。 重试事件关联实际首条传输证据编号；缺少未送达依据时不能自动重试。导出预算内先收原未结调用关联证据，再收本轮未完重试，旧已结束拒连和普通成功查询不能挤掉这些现场；超预算沿原收集清单说明缺项。

#### RCV-1：结果不明后的安全恢复

| 原因 | 恢复原则 |
|---|---|
| 后台短暂断网 | 原连接等待与补交规则；不改变人工暂停，不重放微信动作 |
| 窗口/弹窗未就绪 | 按原窗口核验与清理规则处理；旧任务未收尾不接新任务 |
| 本机存储/容量/权限故障 | 导出可得证据并交管理员处理；重启不能代替修复，诊断部分失败须明确缺件 |
| Hook 调用已发出或是否送达不明 | 保留原调用隔离及业务凭证，按下列操作和程序核验流程恢复 |

销售操作沿原两个程序：桌面“车金故障诊断”导出证据 → 退出 Worker → 正常关闭工作微信 → 用配套“工作微信”快捷方式重新打开并登录原账号 → 销售手动打开 Worker → 程序完成旧记录核验 → 销售明确点击“开始接单”。只展示可执行步骤及故障编号，内部错误、原始响应和身份详细信息留在诊断，不恢复操作日志页面、不增加设置页导出入口。

- 不自动关闭/重启微信、不强杀、不教销售删 SQLite/transactions/调用隔离记录。如果退出或导出不能正常完成，明确提示失败/缺件并保留已得证据，交管理员处理，不引导重复试错。
- 配套快捷方式复用 Worker 部署配置生成 EXE 路径、工作目录及 `StartPort=<配置端口>`、`ConnectType=http`、`RecvType=0`；不硬编码 30001，不改为普通 EXE 入口。这是调用未知场景的恢复步骤，不扩大为所有故障或每次升级都重启微信。
- 仅重启 Worker、原微信进程仍在，不能解除该代次的未知调用隔离。识别原进程可靠结束与新进程代次，不能只比较 PID 或仅因超时推断进程结束；组件/端口/参数/账号/Worker/epoch 的原核验继续有效。
- 原进程结束只能证明原进程内调用不会继续执行，不能证明消息未发出、邀请未提交或语音业务已结算。新进程只按原恢复职责核对历史、原调用/发送/语音账本及回执，重建合法回调并补缺；不复活旧动作，不复用旧许可，不伪造成功或未触发。
- 原调用隔离与原业务结果分别收尾。保留原代次、调用标识、状态及新旧关联；允许新代次进行经身份核验的恢复，不把旧未决记录当成普通过期日志删除。若原机制/提供方依据不足以证明安全，保持停止并先问用户，不自行放宽。
- 现有 TaskRunner 故障恢复入口统一汇总后端停止确认、旧 Flow/任务结算、未知结果、线程、窗口、时间与存储检查。条件满足后显示可恢复，操作者明确开始；心跳成功、重新登录或组件恢复都不能自动解除真实故障/人工暂停。结果仍不明时继续原核对/人工处置规则，不新增“等待多久算未发送”。

#### RCV-2：本地传输送达确定性与有界重试

后台网络等待与本地 DLL 调用风险是两件事。由实际传输入口根据底层阶段及证据统一分类，向 gateway、调用账本、history session、connection、dispatcher、恢复与诊断消费者传递，不由各消费者再按异常文案猜测。

| 分类 | 判定依据与处理 |
|---|---|
| 明确未送达 | 必须可靠证明本次请求未进入 Hook 执行，不只看 `ConnectionError`/`Timeout` 类名或错误码。只有符合只读资格且没有其他阻挡的请求进入下述预算 |
| 已送达但结果不明/是否送达不明 | 保留 uncertain/calling 的原隔离和停单，不自动重试；走 RCV-1 |
| 响应/身份/凭证校验失败 | 原故障处理；不作为连接重试，不因收到 HTTP 响应就视为业务完成 |
| 无法分类/旧记录缺证明 | 保守按不明处理，不能用字段缺失默认未送达 |

- 本轮自动重试仅限经审的只读查询：登录状态、数据库目录、正式历史查询、联系人查询。`QueryDB` 只允许现有正式只读查询入口及原 SQL 限制，不按路由名允许任意 SQL。每次重试重新核对身份/进程与相关历史边界，失败的历史覆盖证明不继续使用。
- 自动重试预算：初次调用后最多额外 2 次，依次等待 1 秒、5 秒；参数由统一定义提供，不在多个循环复制。等待可中断，不持有共享微信动作锁睡眠；重试执行仍取得原动作锁并重新核验。
- 同一失败查询/等待事件的预算不能被外层 tick、内层 HTTP 重试、客户端重启或重新创建对象无限刷新；禁止嵌套库自动重试扩大次数。耗尽后保持连接等待，不继续高频调用。再次发起须经现有操作者检查/开始入口明确启动新一轮并重新核验；若现有入口不能表达该动作，先向用户确认，不自行新增按钮或定时重试策略。
- 发送文字、提交好友申请、语音转文字、配置回调均不在通用自动重试范围。即使能确认发送未触发，也只沿原未触发凭证与权威状态完成原任务收尾；后续动作须重新检查客户当前资格并取得新许可，不能直接重放旧请求。
- 明确未送达应以证据结束本次调用的“可能仍执行”判断，但不能假记业务成功、清除其他调用的不明状态，或解除共享未知发送门禁。底层没有可靠证明就不降级。
- 等待/重试期间发生暂停、故障、更新、退出、账号/进程变化、客户资格变化或新的未知调用，立即停止本轮重试；已在执行的调用按原结果保存，不假装撤销已触发动作。恢复接单沿原入口，不能以一次只读成功取消人工暂停或真实故障。

#### 统一职责与证据

Worker 现有传输/gateway统一产出分类及有界重试结果，调用账本保存原作用域、调用标识、送达依据、尝试次序与结果；history/connection/dispatcher只消费同一规则。TaskRunner负责原故障状态、停止与显式恢复。后端仍是账号/客户资格、任务/Flow/许可与结算权威；OmniAuto C1保留原窗口/内容/清理与提交凭证。不得为本项新增平行状态机、笼统忽略名单或自动补发通道。

复用原诊断链：故障生产入口 → 停止/收尾 → 原账本与回执落盘 → 桌面诊断正式导出 → ZIP。同一 Worker/账号代次/进程/调用及适用的 conversation/cycle/batch/action/task/native ID可关联；明确未送达的证据不能只存一句异常文本。保留原记录哈希、恢复关联、重试预算与取消原因；不导出密钥/完整聊天，缺件与写盘失败有明确说明。不得手工预填本应由程序产生的证据。

#### 贯通验收与交付

| 验收场景 | 必须证明的最终结果 |
|---|---|
| 只重启 Worker，旧微信仍在 | 未知调用隔离仍有效，原账本不丢失，不发新动作 |
| 旧进程结束→新进程→同账号→原恢复入口 | 身份、原任务及回执逐项核对，通过后仍等待操作者开始；正常恢复不能永久卡住 |
| PID复用/换号/组件或端口不符/死亡证明不足 | 拒绝放行，不把“进程不一样”当身份正确 |
| 原发送成功但响应丢失；查询仍无足够结果 | 前者原历史结算且只发一次；后者继续未知保护，均不补发 |
| 恢复再次断网/重复回执/中途退出重启 | 沿原任务幂等续查，不重复提交，不覆盖原失败；第二客户不串号，共享门禁正确生效 |
| 实际传输入口可证明请求未送达 | 合格只读初次+最多2次，间隔1/5秒；正式查询结果进入后续消费者，无虚假的长期未知调用 |
| 实际请求已到达但延迟/丢响应；部分写入/无法判定 | 不降级未送达，不自动重试；记录真实不明并隔离 |
| 重试耗尽/调度再次tick/对象重建/Worker重启 | 不隐式重置预算形成无限重试；仅明确新一轮和重新核验后继续 |
| 既有未知发送+新的明确未送达查询 | 原未知发送保护及原记录不被覆盖/清除 |
| 暂停/更新/退出/换号/进程变化发生在等待或重试间 | 可中断，后续物理调用为0；锁正常竞争等待与锁失效仍区分 |
| 非只读动作、任意SQL、坏响应、账本写盘失败 | 不进入只读重试放行；必要停单、原错误和缺件证据保留 |
| 从上述真实生产故障入口到最终ZIP | 无手工补证；可追溯分类、停止、原动作、恢复与最终结果；源原件哈希不变，脱敏及部分失败明确 |

本地采用受控传输故障与真实本地HTTP/SQLite、正式Worker调度/恢复/导出入口贯通；底层输送阶段必须由实际可测入口产生，不以直接抛某错误码代替。正常、危险反向和旧缺陷对照均保留。生产者输出进入消费者，不能只报分类器或重试器单测数。保住人工/召回首段切AI/销售再接管、分段、消息去重、旧语音补交、证据优先级等受影响边界，未变有效基线可复用。

工程师交精确SHA、工作区差异、现行文档、分类依据及无法证明清单、原始测试输出/哈希、旧失败/跳过和未验限制；架构师5号依AGENTS及testing.rules第9节独立复审。同一版本分别列源码、本地替身/故障注入、真实AI/飞书、Windows/真实Hook与生产，不把本地通过等同销售验收。Windows继续暂停，不为取证恢复实机、不要求销售源码环境、不自动打包部署；需提供方/设备/不清楚业务时先问用户。

## 11. 后端数据、接口与安全边界

后端持久化账号绑定、MessageEvent、MessageBatch、ReplyAction、Task/SentAck、HandoffEvent、召回状态、HookNativeReceipt/HistoryReceipt/VoiceReceipt 及跨进程生成槽位。Worker SQLite 保存原始收件箱、上报队列、历史游标/覆盖、语音/主动调用账本、发送日志、保护配置与耗时队列。已知身份/业务状态以后端为权威，本机证据为执行恢复依据，两者不能互相覆盖猜测。

下列相对路由均在现有 `/api` 下，沿原 Worker 凭据、客户端实例与 Flow/fencing 校验，不新建开放控制通道：

| 接口 | 作用 |
|---|---|
| `POST /workers/{worker_id}/wechat/messages/native-observations` | 校验 Hook envelope、保存原生观察回执 |
| `POST /workers/{worker_id}/wechat/native-bindings` | 任务写码/邀请证据与联系人唯一候选绑定 |
| `POST /workers/{worker_id}/wechat/native-events/{event_uuid}/dispatch` | 将已收原生事实幂等接入领域消息 |
| `POST /workers/{worker_id}/wechat/native-history/coverage` | 两次有界历史覆盖，或明确的旧发送只读核对 |
| `POST /workers/{worker_id}/wechat/native-voice/result` | 同父消息/音频/尝试的转写或失败事实 |
| `POST /workers/{worker_id}/wechat/native-work` | 原业务/在途库存；观察模式不启动新模型 |
| `POST /workers/{worker_id}/wechat/native-replies/{action_id}/claim`、`begin` | 原动作许可及执行开始边界 |
| 同路径 `settle`、`observe`、`not-triggered` | 关联发送结算、只读原发送观察、可信未触发失败 |

envelope 包含 transport/schema、Worker/instance、self_wxid/account_epoch/process_generation、binding_id/revision/peer_wxid、event/source_event UUID、receive_seq、raw_evidence_digest、observed_at、messages。消息含字符串原生 ID、位置、方向、类型、正文、source/revision、原时间、媒体阶段、排序字段、库及库代次、from/to/会话类型/原方向。当前正式普通消息类型白名单 text/voice/image；引用/撤回等先经专门适配，未知字段拒绝而非静默默认。

共享纯规则集中在 `hook_contract_rules`、`hook_event_rules`、`hook_history_rules` 等适配器，Worker/后端不得各写一份宽松解释。API schema、结构号、产品修订和来源哈希一致校验；不能通过改变 transport 绕过旧证据要求。`HookVoiceResult` 对成功正文/响应摘要、失败错误码、音频范围、同一尝试及 UTC 起止实行显式校验。

业务日志、原聊天、图像、手机号、Token、Key 和完整联系人列表按最小必要处理；公开仓库、安装包和普通错误提示不包含真实截图/配置/密钥。旧 OCR 未完成记录按原结构保留并由旧兼容入口解释，不批量改写成 Hook 消息或删除兼容代码。

## 12. 支撑模块必须一起闭环

投影容量修复候选（2026-10-25）：用户确认同一 `hook_observation_projection` 表统一为 **128 MiB**，每包最多200项。后台接收与业务/历史补取/恢复均从 `create_projection_store()` 构造；原回调 inbox 的128 MiB与待投递 outbox 的32 MiB是不同存储职责，不随本次修改。满额拒绝当前整包、保留原始接收与未处理位置；只沿原保留规则回收已确认可清理记录，之后重新读取原包，不删除未知记录或补发消息。

| 账号失效/线索无效 | 新业务被统一资格入口拒绝；旧事实和原发送仍可受限结算，不把历史挂到新用户 |

运营后台操作日志仅作为服务端排障与审计记录保留，不再提供销售/运营可见的菜单或页面。保留 `operation_logs` 写入、鉴权查询接口以及恢复/结算逻辑对相关凭证的读取；不得随前端页面删除数据或后端能力。此项为待发布源码变更。

### 2026-10-26 发送诊断与业务凭证分离（候选，未部署）

统一 `hook_send_diagnostics` 只消费已有发送/历史查询结果，不能授权发送、重试、清凭证或决定结算。正常发送后的核对与保留凭证恢复通过同一 `_sync` 入口取证；旧目录恢复携带已验证原凭证目录，仅供诊断读取。当前账号/客户范围、数字排序、分页、双读、回调屏障和未知发送原结算均保持。

已有 schema 查询确认 Status 列存在时，在原 page SELECT 增加有界文本投影 `diagnostic_status`。该字段在统一 `validate_response` 内从业务行剥离，原字段及范围校验仍严格；原始 capture 继续保留返回，历史存储重放使用相同剥离入口。无该列沿原查询；NULL、缺值、异常值明确标记，不猜测 Status 的业务含义。

每个动作最多保留64个变化事件、每个数据库快照32条同文候选、一次双读合计64条候选与32个数据库快照，文件上限256 KiB。连续重复观测合并次数和首末时间，超限保留首事件与最新变化并计数省略；同文不同本地编号不合并为同一次发送，未观察到不宣称删除或未送达。文件位于 artifacts/tasks，transactions 原凭证不变；桌面 ZIP 先保护当前/未完成动作的全部原始凭证、接口返回及索引关联历史，再收补充诊断；已完成任务诊断留在普通任务收集阶段，体积、时间及文件数预算不扩张；附发送取证说明。凭据及正文不复制进诊断，使用摘要关联；缺失与失败通过清单/统一有界失败日志呈现。

客户端无法提供未暴露的提供方内部错误或微信服务器回执；此取证改进不保证单包能证明所有网络/提供方根因。旧版本没有保存的初始现场也不能追溯补造。
