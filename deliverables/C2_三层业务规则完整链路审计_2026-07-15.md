# C2 OmniAuto / Worker / 后端三层业务规则完整链路审计

审计日期：2026-07-15（北京时间）

审计范围：C2 会话扫描、绑定、定向读取、消息识别、语音转写、消息规范化、去重、停止收口和后端入库。

审计方式：源码静态审计 + V16.85 Windows 实机日志与截图回放。

本轮边界：仅审计和提出统一方案，未修改任何业务代码。

## 1. 结论

当前系统没有实现完整意义上的“三层统一”。V16.84 统一的是最终 `message ingest V2` 的部分字段和后端冲突校验，没有统一此前的屏幕识别和流程控制。

当前真实结构是：

```text
OmniAuto：识别一次角色、类型、语音、转写关系和消息身份
    ↓
Worker：再次判断角色、类型、是否需要转写、转写关系、内容和消息身份
    ↓
后端：再次抽取/清洗语音内容、判断语音失败、选择去重和入库规则
```

本次审计了 22 个业务规则域：

- 6 个属于合理分层或当前口径基本一致；
- 其余 16 个需要通过合同明确所有权或收口重复实现；
- 其中至少 10 个已经存在实机冲突、二次覆盖或控制链路缺口。

V16.85 的 sales 语音漏转已经证明这不是理论风险：同一张截图中，OmniAuto parser 已把 `4" (c` 判为 `self + voice`，但只读语音提示拒绝 parser 来源；Worker 自己的另一套占位符正则也没有命中，因此没有调用 `voice_transcribe`。

三层统一不能是“三层复制同一套 if/regex”，而应是：

```text
一个业务事实只有一个裁判
其他层只消费结构化结果或做合同校验
```

建议先确认本文第 8、9 节，再允许开发。

## 2. 当前完整业务链路

```text
Worker 定时触发首屏扫描
-> OmniAuto sessions 截图、OCR、生成可见会话行
-> Worker 从会话标题提取 remark_code，组装 scan-result
-> 后端校验短码、lead、sales、worker 和绑定唯一性
-> 后端按会话状态生成 read-targets
-> Worker 拉取 read-targets，做本轮去重、冷却和本地校验
-> Worker 调 OmniAuto 定位目标会话
-> OmniAuto 用 visible/current/search_by_remark_code 定位并确认目标
-> Worker 再查 read-targets
-> Worker 调 OmniAuto messages 读取当前屏幕消息
-> OmniAuto OCR 分组，判断角色、类型、语音状态和消息身份
-> Worker 再判断是否存在未转写语音
-> 如命中，Worker 调 OmniAuto voice-transcribe
-> OmniAuto 自下而上处理当前屏幕语音并绑定转写文本
-> Worker 复核目标，再调 OmniAuto messages
-> Worker 将 messages 与 voice_transcription 再匹配，生成 V2 消息
-> 后端校验绑定、角色、类型、状态、语音正文和去重键
-> 后端写入 message_events，更新 conversation 状态
```

停止监听后的正确口径：

- 目标相关的定位、读取、语音转写和入库必须停止；
- 常驻 `first_screen_session_scan` 可以继续，它不是对已停止目标的读取；
- 当前只有 `voice_transcribe` 支持运行中取消，`locate_chat/get_messages` 不支持。

## 4. OmniAuto 当前规则

### 4.1 会话扫描

- 会话标题候选必须位于左侧会话区和有效纵向范围。
- 相邻候选小于最小行距时只保留一行。
- 标题会去掉粘连的昨天/时间后缀。
- 相同标题按 `duplicate_name_index` 区分。
- `rpa_session_key` 由会话类型、名称和 duplicate discriminator 生成。
- `row_fingerprint` 含标题、标题框、y bucket 和重复序号。

证据：`wechat_win32_ocr_sidecar.py:11620-11698`。

风险：物理 y 位置只适合当前首屏快速定位和排查，不适合永久业务身份。

### 4.2 消息分组

- 只读取聊天区、标题栏下方、输入区上方的 OCR。
- 先按横向位置判断 self/customer/unknown。
- 同行头像明确时，用头像角色覆盖横向判断。
- 同侧且垂直间距小的 OCR 行会合并为一个气泡。
- “时长行 + 下方无头像文字”会作为语音转写组合继承父角色。
- 顶部裁切、输入框草稿、文件卡片、菜单等有独立过滤。

证据：`wechat_win32_ocr_sidecar.py:11835-12052`。

### 4.3 角色存在三套内部规则

1. `classify_message_side_details`：横向 lane。
2. `message_row_avatar_role_details`：同行左/右头像视觉结构。
3. `voice_anchor_sender_role`：优先 item 角色，否则按 anchor 中心 x 推断。

证据：`wechat_win32_ocr_sidecar.py:4930-4960, 12072-12130, 3161-3175`。

用户确认的唯一主规则应为：

```text
消息气泡与左头像同行 -> customer
消息气泡与右头像同行 -> self
语音转写文字没有同行头像 -> 继承父语音气泡角色
```

lane 只能是头像缺失时的低置信 fallback，不能覆盖明确头像证据。

### 4.4 语音存在四路候选

1. parser 已解析出的未转写 voice。
2. OCR 时长文本，如 `4"`、`4" (c`。
3. 左侧灰色语音气泡结构。
4. 右侧绿色语音气泡结构。

`find_voice_context_menu_anchor_target` 会合并四路，并取最下方候选。

证据：`wechat_win32_ocr_sidecar.py:3526-3628, 3647-3940, 3971-4027`。

但 `visible_untranscribed_voice_hint` 又只接受两个 visual source，拒绝 parser/OCR source。

证据：`wechat_win32_ocr_sidecar.py:4030-4055`。

因此“实际转写动作认可四路候选，决定是否启动转写只认可两路候选”，OmniAuto 内部已不统一。

### 4.5 已/未转写判断

- `voice_duration_text_like` 支持多种 OCR 变体，包括 `4" (c`。
- parser 用“时长 + 非时长文本”区分未转写占位和转写组合。
- visual detector 用下方文字布局排除已转写气泡。
- 右键菜单出现“收起文字”判为已转写。
- flow 尾部再次用 `has_untranscribed_voice` 和 remaining candidate 判 partial/completed。

证据：`wechat_win32_ocr_sidecar.py:2847-2931, 3396-3450, 4770-4830, 2740-2819`。

### 4.6 voice flow

- 当前屏候选自下而上处理。
- 成功、已转写、错误菜单、未知菜单、失败 anchor 分别进入集合，避免本轮重选。
- 点击后截图/OCR；未确认时做被动截图复核。
- 有进展时 watchdog 续命，无进展达到配置才停；另有 hard safety timeout。
- 有成功项但仍有残留返回 partial；全部完成返回 completed。

证据：`wechat_win32_ocr_sidecar.py:1941-2819`。

### 4.7 transcript 绑定

- transcript 必须位于父语音下方允许间距。
- customer/self 分别检查靠左/靠右。
- 角色、时长和 anchor identity 参与绑定。
- 绑定后记录被标为 voice 并继承 anchor 角色。

证据：`wechat_win32_ocr_sidecar.py:3208-3395`。

该判断必须由 OmniAuto 独占，因为只有它同时掌握点击前后截图、气泡位置和菜单状态。

### 4.8 身份和去重

- envelope 生成 `observation_id/message_id/bubble_id/canonical_visual_id/canonical_input_id/source_message_key`。
- `canonical_visual_id` 包含内容、角色、message id、bubble id 和 rect。
- voice anchor stable key 仍包含 x/y bucket、角色和时长。
- 多截图合并另按 `sender + content + occurrence` 去重。

证据：`wechat_message_envelope.py:333-428`、`message_identity.py:132-233`、`wechat_win32_ocr_sidecar.py:2954-3050, 5143-5205`。

风险：名称虽叫 stable/canonical，但内容展开、页面位移和坐标变化都可能改变它，不能直接等同跨进程永久 ID。

## 5. Worker 当前规则

### 5.1 扫描、短码和目标

- 只从会话标题提取 `CJ...`，不从消息预览提取。
- 后端正式绑定。
- Worker 按 `conversation_id + remark_code` 做本轮去重。
- Worker 检查 locator、OCR 置信度、失败/成功冷却。
- visible 优先，未命中用短码搜索；多个阶段重复拉 read-targets。

证据：`wechat_c2.py:15, 70-143`、`task_runner.py:1143-1414, 1444-1935`。

目前只有轮询授权，没有 `authorization_revision`，不能原子证明动作仍属于同一次监听授权。

### 5.2 Worker 自己有第二套语音启动器

Worker 先检查 visual hint 白名单，再遍历 messages，用另一套正则判断正文。

证据：`task_runner.py:37-70`。

该正则与 OmniAuto 的 duration/placeholder 规则不同，V16.85 的 `[语音] 4" (c` 正好落入差异。

### 5.3 Worker 再次推断角色和类型

- `sales/sales_candidate -> self`，`contact -> customer`。
- `audio -> voice`。
- duration 字段可再次推为 voice，image path 可推为 image，其他默认 text。
- OCR 时长前缀 + 正文还能再次把消息升级为 voice。

证据：`wechat_c2.py:147-212`。

风险：Worker 不掌握完整屏幕结构，却能改变 OmniAuto 的角色和类型。

### 5.4 Worker 有第二个 transcript 绑定器

匹配顺序：

1. source aliases 相交；
2. 消息必须是 voice；
3. 内容 hash；
4. 同角色优先；
5. 同时长优先；
6. 取第一个候选；
7. 未匹配 transcription entry 还能追加成独立 voice。

证据：`wechat_c2.py:462-550, 632-787`。

此前 customer/self 串角色、同一语音 text/voice 双入库和旧转写绑定新语音，都存在这类二次匹配空间。

### 5.5 Worker 再次生成身份和去重

- 从七类 alias 中按顺序选择，再 hash 成新 `source_message_key`。
- dedupe 按 voice 正文、anchor、OCR 结构、原始 id、图片 hash、内容+位置和 raw payload 多分支生成。
- 同 source key 时 voice 可覆盖非 voice。

证据：`wechat_c2.py:246-431, 641-650`。

风险：OmniAuto 已生成 source identity，Worker 又重新挑选和 hash；最终身份受字段存在性、转写内容和坐标变化影响。

### 5.6 Worker 状态

- completed/partial/cancelled 显式映射，其余非空状态一律 failed，空状态反而 completed。
- task runner 又把 completed、partial、no_visible_voice 都当成可继续读取并上报。

证据：`wechat_c2.py:286-296`、`task_runner.py:1740-1782`。

### 5.7 Worker 停止

- voice sidecar 每约 0.5 秒检查本地 stop 和后端授权，可 terminate/kill。
- locate/get_messages 使用不可取消的 `subprocess.run`。
- 停止发生在授权检查之后、sidecar 返回之前时，定位或读取仍会尾随完成。

证据：`rpa_bridge.py:149-208, 377-442`、`task_runner.py:1574-1600, 1705-1732`。

## 6. 后端当前规则

### 6.1 绑定和 read-targets

- remark_code 无候选、多候选、跨 session 重复、lead 不存在/重复、sales/worker 冲突均有状态。
- 同 remark_code 的旧有效绑定会软退役。
- read-targets 只返回 bound、允许监听、身份完整、未删除且 conversation 未关闭的绑定。
- read_reason 由 conversation 状态决定并排序。

证据：`backend/app/services/wechat_service.py:190-590`。

这一段后端是业务状态单一裁判，方向正确。

### 6.2 V2 入库

- remark_code 必须存在并与绑定一致。
- 每条必须有 source_message_key。
- 同一请求内 source_message_key 不得重复。
- role/type/flow 必须在枚举内，item_state 必须 completed。
- unknown sender 忽略。
- `conversation_id + dedupe_key` 由数据库唯一约束兜底。

证据：`wechat_service.py:737-885`、`models/wechat.py:63-96`。

### 6.3 后端仍重判 voice 正文

后端会：

- 从 raw_payload 或 content 递归找正文；
- 拒绝纯时长占位；
- 拒绝大段 sidecar payload；
- 再删除时长 token；
- 从多个字段寻找 voice failure code；
- V1 另算 voice 内容去重键。

证据：`wechat_service.py:609-723, 789-826`。

这些是历史防御代码，但意味着后端未完全信任 V2 canonical content。正式合同应是“非法即拒绝”，不是“后端再猜一个正文”。

### 6.4 V1/V2 双合同

- schema 默认 version 1，允许 1 到 2。
- V1 会归一角色/类型并重算 voice dedupe。
- V2 使用 Worker 枚举和 dedupe。

证据：`backend/app/schemas/wechat.py:28-51`、`wechat_service.py:593-712, 748-826`。

兼容分支本身不一定是 bug，但正式 C2 路由混跑两套语义会增加审计和回归复杂度。

## 7. V16.85 失败证据

日志包：`c2_v1685_sales_20260715_102340_103615.zip`。

两轮 messages 截图都能看到右侧 4 秒 sales 语音。OCR 事实：

```json
{
  "text": "4\" (c",
  "bounds": [812, 620, 862, 645],
  "confidence": 0.724
}
```

当前代码回放结果：

```text
parse_messages_from_ocr
=> sender_role=self
=> type=voice
=> content=[语音] 4" (c

visible_untranscribed_voice_hint
=> detected=false
```

完整根因链：

1. OmniAuto duration 规则认可 `4" (c`。
2. parser 已生成 `self + voice`。
3. 合并候选时 parser voice anchor 有效。
4. hint 只接受 visual source，拒绝 parser source，返回 false。
5. visual self detector又会排除已被 parser 覆盖的区域，避免普通文字误判。
6. Worker fallback 正则不同，没有识别 `[语音] 4" (c`。
7. 最终不进入 `voice_transcribe_current_chat`。

这是源码与真实日志共同证明的根因，不是推测。

现有测试覆盖了“无 OCR 时视觉发现语音”“普通绿色文字不误判”“processed anchor 不重选”和“多来源自下而上”，但没有覆盖：

```text
同一个语音已被 parser 判为 voice，
messages hint 仍必须让 Worker 启动 voice flow。
```

也没有用真实 `4" (c` 同时跑 OmniAuto hint 和 Worker trigger 的跨层合同测试。

## 8. 三层统一后的唯一所有权

| 业务事实 | 唯一裁判 | 其他层可做 | 其他层禁止 |
|---|---|---|---|
| 屏幕会话行 | OmniAuto | 传输、保存证据 | 重算物理行 |
| 标题 remark_code | Worker 共享合同模块 | 后端校验 lead 唯一性 | 从消息预览猜短码 |
| 绑定/监听状态 | 后端 | Worker按授权执行 | 本地自行恢复停用绑定 |
| 动作授权 | 后端 revision + Worker取消 | OmniAuto响应 cancel | 用旧缓存继续 |
| OCR 行归属 | OmniAuto | 保留证据、枚举校验 | Worker按内容改角色 |
| 消息类型 | OmniAuto | 枚举转换 | Worker再次升级/降级 |
| 未转写语音 | OmniAuto | Worker只读 typed state | Worker跑语音正则 |
| 语音顺序/processed | OmniAuto | Worker等待结果 | Worker重排 anchor |
| transcript 父语音 | OmniAuto | Worker按 parent key 合并 | Worker按内容重新配对 |
| voice 正文 | OmniAuto | 透传、格式校验 | Worker/后端从 payload 猜正文 |
| canonical message | Worker | 后端验证保存 | 后端重分类 |
| 跨轮 dedupe_key | Worker 共享合同模块 | DB 唯一约束 | 后端再算业务 dedupe |
| conversation 状态 | 后端 | Worker接收结果 | RPA决定业务状态 |
| state/error 枚举 | 共享 schema | 三层产出合同枚举 | 各层自建近义状态 |

## 9. 建议冻结的三个合同

### 9.1 `C2ObservationV3`：OmniAuto -> Worker

```text
observation_id
screen_run_id
conversation_target_evidence
row_kind: text_bubble | voice_bubble | voice_transcript | image | system
sender_role: customer | self | system | unknown
sender_role_source: same_row_left_avatar | same_row_right_avatar | inherited_voice_parent | geometry_fallback
message_type
voice_state: not_voice | untranscribed | transcribed | failed
voice_anchor_key
parent_voice_anchor_key
content_raw_ocr
content_clean
bubble_rect
avatar_rect
quality_flags
evidence
```

硬规则：

- `voice_bubble + untranscribed` 就是启动依据，Worker 不再跑正则。
- `voice_transcript` 必须有 `parent_voice_anchor_key`，否则不能上报 voice。
- 转写前后必须保持同一 `voice_anchor_key`，不能因新增文字或轻微位移换身份。
- 坐标只作当次定位证据，不能单独作为跨进程永久身份。

### 9.2 `C2CanonicalMessageV3`：Worker -> 后端

```text
contract_version=3
read_run_id
conversation_id
authorization_revision
source_message_key
dedupe_key
sender_role
message_type
content
item_state
flow_state
observation_refs
evidence
```

硬规则：

- Worker 不包含 OCR 正则、头像/坐标角色规则或 transcript 几何规则。
- 同一 source key 只能有一个最终解释。
- voice 只能来自已绑定 parent anchor 的 transcribed observation。
- partial 可上报已 completed 的 item；失败 anchor 必须有独立结果，不能上报占位符。

### 9.3 `C2ControlV1`：后端 -> Worker -> OmniAuto

```text
conversation_id
remark_code
authorization_revision
read_reason
issued_at
expires_at
cancelled_at
```

硬规则：

- locate/messages/voice/ingest 都携带同一 revision。
- 后端停止后 revision 失效。
- 三个 sidecar 动作都支持同一 cancel callback。
- cancelled 是控制流终态，不得继续下一阶段。

## 10. 必须收口的多套规则

1. 删除 Worker 的语音正文正则业务判断，只读 `voice_state`。
2. 删除 Worker 根据 duration/content/image path 重判 OmniAuto 类型。
3. 删除 Worker 按内容 hash/角色/时长二次绑定 transcript。
4. V3 后端不再递归猜 voice 正文，非法直接拒绝。
5. 状态和错误码改为共享 schema。
6. OmniAuto 四路候选可保留，但必须先汇总成同一个 observation；hint、click、remaining 共同消费。
7. OmniAuto 角色优先级固定为：同行头像 > 父语音继承 > 几何 fallback。
8. source_message_key、dedupe_key 各只有一个定义，不能每层一个 canonical。
9. 正式 C2 Worker 路由只接受当前合同；V1 如保留，单独走 legacy adapter。

## 11. 开发前合同测试

必须先把真实截图和日志做成 golden fixtures：

1. 左侧未转写 customer voice。
2. 左侧已转写 customer voice。
3. 右侧未转写 self voice。
4. 右侧已转写 self voice。
5. 真实 OCR `4" (c`：parser、hint、Worker trigger 结论一致。
6. 普通绿色 self text 不得触发 voice。
7. 图片内部 OCR 不得生成普通 text/voice。
8. 转写后页面整体位移，voice anchor 不变。
9. 两条同角色、同时长语音不得串 transcript。
10. 一条成功、一条失败：成功可上报，失败不报占位符。
11. 停止发生在 locate/messages/voice 各阶段，不得进入下一阶段。
12. Worker/后端重启后重复读取，dedupe_key 稳定。
13. 同 source 同时出现 text/voice 或 customer/self，合同必须失败。
14. 语音被新增 transcript 顶出当前屏幕后，不主动滚动追踪。

测试分层：

- OmniAuto fixture replay：只验证 ObservationV3。
- Worker contract tests：只输入 ObservationV3，验证 CanonicalMessageV3，不能加载 OCR 正则。
- Backend contract tests：只输入 CanonicalMessageV3，验证授权、合同和唯一约束。
- 最后做端到端 golden test，证明三层对 source/role/type/state 一致。

## 12. 开发顺序

1. **P0-1：冻结第 8、9 节所有权和合同。**
2. **P0-2：统一 OmniAuto Observation。** parser/OCR/visual 先汇总，hint/click/remaining 读取同一结果。
3. **P0-3：瘦身 Worker。** 移除 OCR/语音识别和二次 transcript matching。
4. **P0-4：后端成为严格合同消费者。** V3 不重判正文、角色和类型。
5. **P0-5：统一取消链路。** locate/get_messages/voice 都可取消并校验 revision。
6. **P1：同步技术手册、接口 schema、版本文档和测试口径。**

## 13. 开发准入结论

不建议只修改 V16.85 的 source whitelist。那只能让本次 `4" (c` 进入 voice flow，不能解决角色、类型、transcript 绑定、身份、状态和停止仍有多套规则的问题。

允许开发前应确认：

1. 第 8 节唯一所有权矩阵。
2. 第 9 节三个合同及版本策略。
3. 第 11 节 golden fixtures 作为准入测试。

本审计没有修改 OmniAuto、Worker 或后端业务代码。
