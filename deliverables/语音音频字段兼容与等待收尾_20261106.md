# 语音音频字段兼容与等待收尾

状态：开发候选；未上线，Windows 原生链路待验。真实客户材料只保存在私有取证目录。

## 已确认问题

同一种语音的音频可能随原消息放在 `voice_hex`，也可能在后续补充回调的 `voice_data` 中。原程序只读取后者；仅收到前者时，即使音频已经到达，也不会开始转写。等待没有终止机制，后续文字会被未完成的语音阻塞。

## 修复边界

1. Worker 使用统一 `hook_voice_payload` 解析入口，支持两个字段。保留十六进制、大小、SILK 前缀、声明长度检查；两个非空字段必须解码后完全一致。坏字段不能被另一个好字段掩盖。
2. `hook_voice` 仍负责同一账号、时期、进程、客户、原生消息 ID 和 XML 长度核对。重复回调合并为同一音频；原有转写凭证、未知调用隔离和禁止自动重试不变。
3. 内嵌音频的原消息仍作为父消息上传。音频只留在 Worker，后台仅接收父消息元数据，随后由原转写结果入口完成该消息。新投影标记 v4，原 v2/v3 凭证保留、继续可读，不覆盖旧记录。
4. 没有音频时 Worker 调用新增 `native-voice/audio-wait`，复用转写入口的绑定与父消息鉴权。后台以首次报告的服务器时间记录等待；60 秒后仍未取得音频，复用已有客户转人工入口。时间持久化在原消息证据，不由客户端报时，也不因重启或频繁轮询重置。
5. 等待超时使用 `HOOK_VOICE_AUDIO_MISSING`，不伪造“调用转写失败”或语音结果凭证，不绕过原语音处理后直接发送文字。重复报告与已处理的历史语音不重复开启人工通知。其他客户继续调度。

## 交付条件

- Worker 与后台需配套更新：新增等待接口不能仅更新 Worker 后接旧后台。
- 本地验证使用合成音频与隔离的 HTTP/SQLite；不等于真实微信、DLL、模型或销售电脑验收。
- 实机至少验证：仅 `voice_hex` → 一次转文字 → 原父消息完成 → 文字上下文按序进入生成/审核 → 一次发送及核对；同音频补充回调不重复转写或发送。
- 验证无音频等待、重启、到期转人工、另一客户继续处理；不重新执行旧未知转写或未知发送。
- 本会话先向用户报告，未经用户确认不交架构师，不正式打包或上线。

## 同批查车说明修复与验收范围

用户已授权本批语音修复与查车说明一起交架构师 5 号复审，明确审核超时暂不修改。

查车协议仍使用现有字段及严格校验，只替换共享 `QUERY_INSTRUCTION` 的含糊说明：用中文解释品牌、车系分类、车身类型、能源、驱动、所在地、排量、里程和电池容量；明确 `model` 是轿车/SUV/MPV等车身类型，具体车名使用 `name_queries`。说明等于、多选、数值上限下限的区别；不支持的否定条件保留为文字列表，不能擅自缩小客户需求。外层仍只能包含 `catalog_query`，不增加字段或放宽校验。

真实 DeepSeek 使用历史捕获的完整需求理解请求；旧版请求哈希与历史记录一致，新版只替换共享查询说明。相似话术修改客户原话及上一轮客服的车型确认，其他输入保持冻结。总计 16 次真实调用：8 次首轮对照、4 次格式说明复验、4 次最终版本复验；每次最多 60 秒，无模型自动重试、无客户发送。这些调用只验证需求理解与查询，不代表审核和完整发送链路成功，也未验证超时修复。

旧版再次误报轿车筛选不支持。中间版本虽然车身类型理解正确，仍有外层多字段及未支持条件类型错误，保留失败记录。最终 4 次（原话、轿车改述、MPV、排除SUV）均通过严格校验与查询；排除SUV按现有能力保留待核实，不算已完成筛选。有限样本不保证后续每次模型输出正确，原有校验、有限恢复和人工接管仍然保留。

具体车名对照中，模型正确走 `name_queries`，但“宝马320Li”未能在冻结候选名称“18款宝马320Li”及其别名中精确匹配。本次不改变车名匹配实现，此项不能算端到端成功；复审应明确区分字段选择正确与车名匹配能力限制。

语音本地 HTTP/SQLite 链路已通过，Windows 原生待验。语音回归的 4 项失败已在未修改基线上分别复现：Mac不能执行Windows进程退出检查、旧在途流程错误码断言、人工接管后语音状态旧断言、共享契约源哈希旧基线。未通过修改断言消除这些失败。
