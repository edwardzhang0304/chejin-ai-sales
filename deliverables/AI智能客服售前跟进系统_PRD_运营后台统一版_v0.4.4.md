# 第二部分：正文需求

## 1. 当前系统要解决什么问题

车金要做的是一个售前跟进系统。现在不要一上来做复杂 AI，而是先把基础链路做稳：

1. 运营把客户录进系统。
2. 系统按轮询规则分给销售。
3. 销售绑定对应的 Windows Worker。
4. Worker 在商家电脑上操作微信，给客户发送添加通讯录邀请。
5. Worker 把微信里的客户会话和消息同步回服务端。
6. 服务端知道每条消息属于哪个客户、哪个销售、哪个 Worker。

当前 checkpoint 的底线是：C0 能把客户分配清楚，C1 能把添加通讯录邀请发出去，C2 能把微信会话和消息变成服务端可信事实。不做 C3 AI 自动回复发送，不做 C4 召回/人工跟进。

当前实现状态说明：V16.18 已验证 C2 非第一屏 `search_by_remark_code` 定向读取链路，覆盖搜索浮层截图进入报告、搜索、候选点击、标题/短码二次确认和 `messages` 读取。C3/C4 仍按技术方案存在设计口径，但不作为本轮 C2 验收通过条件。

## 2. 技术方案分段口径

| 分段 | 白话说明 | 当前 PRD 口径 |
|---|---|---|
| C0 线索入库与分配 | 运营把客户录入系统，系统去重、分销售、生成加好友任务 | 当前做 |
| C1 add_friend | Worker 操作微信搜索客户、写客户短码、发送添加通讯录邀请 | 当前做 |
| C2 会话绑定/微信监听 | Worker 扫描微信第一屏，第一屏命中优先读取；服务端按状态机返回定向读取目标，完成绑定、读取和去重入库 | 当前 checkpoint 做 |
| C3 AI 回复发送 | 消息入库后，服务端 AI 大脑生成回复，经 Guard 审核后生成 reply_action，再创建 chat_reply 任务由 Worker 发送 | 当前不做 |
| C4 召回/人工跟进 | 召回到期后先进入召回前确认，读取微信事实确认无新客户消息后，才允许创建 follow_up；人工跟进按状态机处理 | 当前不做 |

说明：

- C2 是 Worker 运行时事实采集能力，不进入统一任务中心。
- C2 不定义为 `task_type`，不创建 `session_scan`、`message_ingest` 这类任务。
- 统一任务中心只承接需要 Worker 执行动作的任务，例如 C1 `add_friend`、后续 C3 `chat_reply`、后续 C4 `follow_up`。
- C2 接口响应固定不下发 AI 发送动作，产品口径等价于 `next_action=none`。
- C2 定向读取目标必须包含 `conversation_id + remark_code`。定向读取确认客户靠服务端会话 ID 和客户短码双重校验，`display_name` 只是微信展示名，只能辅助定位，不能作为客户身份主依据。
- OmniAuto 在本系统里不是单一 RPA 概念：服务端复用其 AI 大脑、RAG、Guard 和回复编排能力；Worker 端复用其 RPA Sidecar 操作本机微信。
- AI 大脑在服务端。Worker 只负责读取微信事实、上报消息、领取已批准的任务并执行，不自己调用大模型，不自己判断是否回复，也不自己决定回复内容。
- C3 的完整产品链路是：`消息入库 -> 服务端 AI 大脑生成回复 -> Guard 审核 -> 生成 reply_action -> 创建 chat_reply 任务 -> Worker 发送微信消息`。
- C3 不是“模型自己决定一切”。模型只输出结构化建议，最终动作由服务端按会话状态、业务规则、风控、RAG 证据、Guard 结果和配置阈值统一决定。
- C3 发送前必须做 `pre_send_refresh`。如果发送前发现客户新消息，旧 `reply_action` 变为 `superseded`，不得继续发送旧回复。
- C4 召回到期不得直接创建或发送 `follow_up`，必须先进入 `recall_precheck`，读取微信事实后再决定是否召回。
- `watching` 不作为会话主状态；等待类会话统一用 `waiting_user_reply / recalled_waiting_user / sales_replied_waiting_user` 加规则字段表达。

## 5. 总体业务流程

```text
C0:
运营新增客户
-> 系统用手机号去重
-> 系统按销售轮询规则分配
-> 服务端创建 add_friend 任务

C1:
-> Windows Worker 领取任务
-> Worker 调用 OmniAuto 操作微信
-> 搜索手机号/微信号
-> 写入客户短码
-> 发送添加通讯录邀请
-> 服务端记录任务结果

C2:
-> 第一屏主动扫描
-> 第一屏命中会话优先读取
-> 服务端按状态机返回定向读取目标
-> 识别客户短码并绑定 lead / conversation / sales / worker
-> 读取允许读取的会话消息
-> 按 dedupe_key 去重入库

C3/C4:
-> C2 稳定验收后，后续才进入 AI 回复发送、召回和人工跟进
-> C3 链路为：消息入库 -> 服务端 AI 大脑生成回复 -> Guard 审核 -> reply_action -> chat_reply 任务 -> Worker 发送
-> C3 发送前必须复核目标会话，发现客户新消息则旧回复作废
-> C4 到期先做召回前确认，确认无新客户消息后才允许 follow_up
```

## 7. 线索管理

### 7.1 模块说明

线索就是客户售前跟进记录。运营先把客户录进系统，系统检查手机号是否重复，再分配给销售。

### 7.2 新增客户字段

| 字段 | 是否必填 | 说明 |
|---|---|---|
| 客户名称 | 是 | 客户显示名 |
| 手机号 | 是 | 中国大陆 11 位手机号；作为去重主依据 |
| 微信号 | 否 | 客户微信号或运营已知的微信信息 |
| 邮箱 | 否 | 客户邮箱 |
| 备注 | 否 | 客户需求、车型、预算等 |
| 自定义信息 | 否 | 保留自定义字段能力 |

规则：

- 手机号必须填写。
- 手机号重复时，不允许新建第二条有效线索。
- 重复手机号如填写备注，备注追加到原线索备注记录，不覆盖原备注。
- 第一阶段来源固定为人工录入，不做来源管理。
- 批量导入当前不做。

### 7.3 线索状态

| 状态 | 页面文案 | 含义 |
|---|---|---|
| `unassigned` | 未分配 | 没有可用销售或分配失败 |
| `assigned` | 已分配 | 已分配给销售 |
| `invalid` | 无效 | 运营标记为无效线索 |

规则：

- 不做物理删除。
- 不再设计归档状态。
- 无效线索可以恢复。
- 恢复后如有销售，回到已分配；如无销售，回到未分配。

### 7.4 重复录入

重复判断：

- 以手机号为强去重依据。
- 重复时提示已有线索、重复次数、重复日期。
- 重复录入要记录操作人、时间、本次备注。

提示示例：

```text
该手机号已存在，不能重复新建。
已重复录入 3 次，日期：2026-06-01、2026-06-08、2026-06-22。
本次备注已追加到原线索。
```

### 7.5 线索详情

线索详情展示：

- 客户基础信息。
- 联系方式。
- 当前销售。
- 当前状态。
- 备注记录。
- 重复录入记录。
- 分配记录。
- 任务链路。
- 会话绑定状态。
- 最近消息入库时间。

线索详情不提供“编辑线索”作为主操作；当前没有明确使用场景，避免增加无效入口。

### 8.1 模块说明

销售管理用来维护谁可以接收线索，以及这个销售对应哪台 Worker。

### 8.2 销售字段

| 字段 | 说明 |
|---|---|
| 销售姓名 | 必填 |
| 手机号 | 选填 |
| 微信号 | 选填 |
| 状态 | 启用 / 停用 |
| Worker | 选填，可后续绑定 |

规则：

- 新增销售时 Worker 可暂不绑定。
- 绑定或更换 Worker 在销售详情抽屉内编辑，不另开复杂页面。

- 已停用 Worker 不可绑定。
- 已绑定其他销售的 Worker 不可重复绑定。

### 8.3 销售详情

销售详情展示：

- 基础信息。
- 状态。
- 当前 Worker。
- Worker 在线 / 离线。
- 今日分配。
- 阻塞任务。

点击“编辑销售”后，在详情抽屉内直接编辑字段。

## 9. Worker 管理

### 9.1 模块说明

Worker 是商家电脑上的执行终端。后台先创建 Worker，系统生成 Worker ID 和 Worker Token，客户端用这两个信息完成绑定。

### 9.2 Worker 字段

| 字段 | 说明 |
|---|---|
| Worker ID | 服务端生成的唯一标识 |
| Worker Token | 客户端绑定凭证，只在详情展示 |
| Worker 名称 | 方便运营识别 |
| 启用状态 | 启用 / 停用 |
| 绑定状态 | 未绑定 / 已绑定客户端 |
| 在线状态 | 在线 / 离线 |
| 运行状态 | 空闲 / 忙碌 / 暂停接单 |
| 当前销售 | 当前绑定的销售 |
| 当前任务 | 正在执行的任务 |
| 最近心跳 | 最近一次客户端心跳时间 |

### 9.3 创建和绑定

规则：

- 新增 Worker 后，服务端生成 Worker ID 和 Worker Token。
- 新增成功后自动打开 Worker 详情，方便复制 ID 和 Token。
- Worker Token 不在列表展示，只在详情展示。
- 客户端首次启动时输入 Worker ID + Worker Token 完成绑定。
- 同一个 Worker 只能绑定一个客户端实例。
- 客户端绑定成功后，本机保存绑定信息；下次打开自动校验后进入工作台。

### 9.4 重置绑定

重置绑定用于换电脑或清掉旧客户端绑定。

规则：

- 后台 Worker 详情提供“重置绑定”。
- 重置后旧客户端不能继续心跳和领取任务。
- 重置时生成新的 Worker Token。
- 如果当前存在 running 任务，页面强提示，但允许继续重置。
- 重置绑定不自动取消、失败或改派 running 任务，任务需要在任务中心处理。

## 10. 任务中心

### 10.1 模块说明

任务中心是运营看任务状态和异常的地方。服务端负责任务调度，任务中心负责让运营看见任务发生了什么，并处理需要人工介入的情况。

### 10.2 任务类型

当前主要任务：

| task_type | 页面文案 | 当前是否做 |
|---|---|---|
| `add_friend` | 添加通讯录邀请 | C1 做 |
| `chat_reply` | AI 回复发送 | C3 做，当前不做 |
| `follow_up` | 召回发送 | C4 做，当前不做 |

任务中心结构要保留扩展性，但当前只验收 C1 `add_friend` 任务。

C2 注意：

- C2 的 `session_scan`、`message_ingest`、`wechat_binding` 不允许定义为 `task_type`。
- C2 不进入统一任务中心。
- C2 数据写入 `wechat_session_bindings`、`message_events` 和会话监听状态。
- 后台可以在线索详情、Worker 详情或必要状态区展示 C2 结果，但不把 C2 当任务处理。

### 10.3 任务状态

| status | 页面文案 | 含义 |
|---|---|---|
| `blocked` | 阻塞 | 任务已创建，但条件不满足，不能领取 |
| `pending` | 待处理 | 可以被 Worker 领取 |
| `running` | 处理中 | Worker 已领取，正在处理 |
| `completed` | 已完成 | 任务完成，具体结果看 result_code |
| `failed` | 失败 | 执行失败，具体原因看 error_code |
| `cancelled` | 已取消 | 人工取消 |

规则：

- `status` 只表示任务生命周期。
- `invite_sent` 不是 status，只能是 result_code。
- `already_friend` 是完成结果，不是失败。
- 终态任务不得再次领取。
- failed / cancelled 后如需重试，创建新任务，原任务保留。

### 10.4 add_friend 结果

| result_code | 页面文案 | 说明 |
|---|---|---|
| `invite_sent` | 已发送添加通讯录邀请 | 不代表客户已同意好友申请 |
| `already_friend` | 已是好友 | 不需要再发送好友申请 |

### 10.5 失败原因

| error_code | 页面文案 |
|---|---|
| `PHONE_NOT_FOUND` | 手机号未找到客户 |
| `WECHAT_ID_NOT_FOUND` | 微信号未找到客户 |
| `PHONE_INVALID` | 手机号无效 |
| `ADD_CONTACT_ENTRY_NOT_FOUND` | 添加通讯录入口未找到 |
| `REMARK_WRITE_FAILED` | 客户短码写入失败 |
| `INVITE_SEND_FAILED` | 邀请发送失败 |
| `WECHAT_WINDOW_NOT_FOUND` | 微信窗口未找到 |
| `RPA_COMPONENT_NOT_READY` | 自动化组件不可用 |
| `ACCOUNT_RESTRICTED` | 账号受限 |
| `OPERATION_TOO_FREQUENT` | 操作过于频繁 |
| `NETWORK_ERROR` | 网络异常 |
| `WORKER_INTERRUPTED` | 执行中断 |
| `OTHER` | 其他 |

### 10.6 操作规则

| 状态 | 可用操作 |
|---|---|
| blocked | 处理阻塞、取消任务、补充备注 |
| pending | 取消任务、补充备注 |
| running | 查看执行方、取消任务、补充备注 |
| completed | 查看结果、查看执行方、补充备注 |
| failed | 重新创建任务、查看执行方、补充备注 |
| cancelled | 查看取消信息、重新创建任务、补充备注 |

扩展动作：

- `add_friend + PHONE_NOT_FOUND` 可标记线索无效。
- `SALES_WORKER_NOT_BOUND` 跳转销售详情，进入编辑态并聚焦 Worker 字段。
- completed 默认不允许重新创建任务。

### 10.7 任务事件和操作日志边界

| 类型 | 说明 | 展示位置 |
|---|---|---|
| task_events | 任务自己怎么流转 | 任务详情状态流转 |
| operation_logs | 谁在后台做了什么 | 操作日志模块 |

同一个动作可能同时写两类记录。例如运营取消任务：任务事件记录任务变成 cancelled，操作日志记录谁取消了任务。

## 11. Windows Worker 客户端

### 11.1 模块说明

Worker 客户端安装在商家 Windows 电脑上。商家只看到一个“车金 Worker 客户端”。在 Worker 端，OmniAuto 以 RPA Sidecar 形式被复用，用来操作本机微信；它不作为独立产品展示，也不需要商家单独操作。

### 11.2 客户端要做什么

- 绑定 Worker 身份。
- 上报心跳。
- 开始接单 / 暂停接单。
- 按自动接单时段控制是否领取任务。
- 领取 add_friend 任务。
- 调用 OmniAuto 操作本机微信。
- 展示当前任务链路。
- 上报执行步骤、结果、失败原因。
- 保存本机执行日志。
- 失败时上传关键截图证据。
- C2 阶段调用 OmniAuto sessions/messages 能力扫描会话和读取消息。

### 11.3 启动和接单

规则：

- 首次绑定成功后默认暂停接单，不自动领取任务。
- 点击“开始接单”后才领取 pending 任务。
- 点击“暂停接单”后不再领取新任务。
- 如果暂停时已有 running 任务，当前任务继续执行到完成或失败，之后停止领取。
- 关闭客户端或断线时，running 任务不自动失败；超过 10 分钟未恢复时任务中心提示执行方离线。

### 11.4 自动接单时段

规则：

- 默认关闭。
- 开启后，每天支持一个接单时间段。
- 支持跨天，例如 21:00 到次日 08:00。
- 非接单时段客户端仍在线，但 run_status 为 paused，不领取新任务。
- 到结束时间时不打断当前 running 任务，任务完成或失败后暂停接单。

### 11.5 add_friend 执行链路

任务链路只展示已经发生和正在发生的步骤，不展示未来步骤。

建议步骤：

1. 已领取任务。
2. 正在检查自动化组件。
3. 正在打开微信桌面客户端。
4. 正在搜索手机号。
5. 手机号未找到时，尝试搜索微信号。
6. 正在进入添加通讯录流程。
7. 正在写入客户短码。
8. 正在发送好友申请。
9. 正在读取执行结果。
10. 执行成功或执行失败。

### 11.6 客户短码备注规则

客户短码是系统识别客户的关键标识。

规则：

- 服务端为客户生成唯一客户短码。
- Worker 领取 add_friend 任务时，任务必须包含客户短码。
- RPA 自动写入微信备注的内容只有客户短码。
- 系统不自动写入销售说明、客户需求、车型、预算或申请说明。
- 销售后续可以在微信备注里追加人工说明。
- 销售追加说明时必须保留客户短码。
- 只要备注里仍包含客户短码，系统后续就能继续识别和绑定客户。
- 如果短码被删除、改写或无法识别，系统进入异常处理或人工核对。

示例：

```text
系统自动写入：CJ8F3A2C
销售可改为：CJ8F3A2C 预算15万 看SUV 已到店
不允许改为：预算15万 看SUV 已到店
```

### 11.7 失败后的接单策略

| 失败类型 | 示例 | 是否继续接单 |
|---|---|---|
| 单条客户数据型失败 | 手机号找不到、微信号找不到、手机号无效 | 继续下一条 |
| 执行步骤失败 | 添加入口找不到、短码写入失败、邀请发送失败 | 单次继续；连续 3 次停止 |
| 运行环境型失败 | 微信窗口找不到、OmniAuto 不可用、网络异常 | 停止领取 |
| 账号风控型失败 | 账号受限、操作频繁 | 停止领取 |
| 未知型失败 | OTHER | 默认停止 |

### 11.8 日志和截图

规则：

- 本机执行日志放在设置页，不放在工作台首页。
- 本机日志保留最近 30 天，最多 1000 条。
- 成功任务默认不上传截图。
- 失败任务上传关键失败截图。
- 本机失败截图保留 7 天或最多 300 张。
- 服务端失败证据保留 30 天。

## 12. C2：会话绑定与微信监听

### 12.1 模块说明

C2 的目标是把微信里的会话和消息变成服务端可信事实。它不是 AI 回复阶段，也不是任务中心里的任务。

简单说：

```text
先知道这条微信会话是谁
再知道这条消息有没有入库
最后才有资格进入后续 AI 回复
```

### 12.2 C2 做什么

- Worker 调用 OmniAuto sessions 扫描微信当前第一屏。
- 第一屏命中的会话优先读取消息。
- Worker 空闲时拉取服务端按状态机生成的定向读取目标，读取目标必须包含客户短码 `remark_code`。
- 从会话展示名或备注中识别客户短码。
- 服务端用短码绑定 lead / conversation / sales / worker。
- Worker 对服务端允许读取的会话读取消息。
- 服务端按 dedupe_key 去重入库。
- 后台展示绑定状态、监听状态、消息入库状态和错误原因。

### 12.3 C2 读取策略

C2 的正式读取策略由三部分组成：

```text
第一屏主动扫描
-> 第一屏命中优先读取
-> 状态机定向读取
-> 去重入库
```

第一屏主动扫描：

- Worker 只读取微信当前可见会话列表。
- 命中短码、未读提示、预览变化或近期活跃的已绑定会话时，进入第一屏命中队列。
- 第一屏命中会话优先读取消息，避免客户刚发来的消息被延后处理。
- 第一屏扫描只上报微信事实，不直接判断是否回复，不创建任务。

状态机定向读取：

- 服务端根据 conversation 状态、最近消息时间、最近发送时间和召回规则返回读取目标。
- 每个读取目标必须返回 `conversation_id + remark_code`，用于 Worker 定位和服务端身份校验。
- 定向读取确认客户靠 `conversation_id + remark_code` 双重校验。
- `display_name` 只能作为微信展示名辅助定位或页面展示，不能作为客户身份主依据。
- Worker 按服务端给出的目标定向读取，不自行扩大读取范围。
- 定向读取前要去掉本轮第一屏已经处理过的会话，避免重复读取。
- Worker 读取到会话后，必须把读取结果中的短码与目标 `remark_code` 做一致性校验。
- 找不到目标会话、微信不可控或 OCR 低置信时，记录 `error_code`，不做不确定操作。

read-targets 必填字段：

| 字段 | 是否必填 | 产品含义 |
|---|---|---|
| `conversation_id` | 是 | 服务端会话 ID，和 `remark_code` 一起用于客户身份确认 |
| `lead_id` | 是 | 客户线索 ID |
| `sales_id` | 是 | 归属销售 ID |
| `worker_id` | 是 | 应执行读取的 Worker |
| `remark_code` | 是 | 客户短码，和 `conversation_id` 一起用于客户身份确认 |
| `read_reason` | 是 | 读取原因，例如等待客户回复、召回前确认、转人工后监听 |
| `rpa_session_key` | 否 | 已知微信会话定位信息 |
| `display_name` | 否 | 微信展示名，只能辅助定位和展示 |

读取目标校验规则：

- `conversation_id` 或 `remark_code` 缺失时，不下发为正常读取目标。
- 已绑定会话如果缺失短码，进入异常或待复核，不作为正常读取目标继续读取。
- Worker 读取到的会话短码与目标 `remark_code` 不一致时，不入库为正常客户消息，记录错误并进入待复核。
- 服务端和 Worker 不得仅凭 `display_name`、昵称、头像、手机号尾号等弱特征确认客户身份。

可进入定向读取的典型状态：

| conversation.status | 读取目的 |
|---|---|
| `friend_added` | 新好友刚识别，读取是否已有首条客户消息 |
| `ai_active` | AI 接待中，读取客户新消息 |
| `waiting_user_reply` | 我方已回复，确认客户是否有新消息 |
| `waiting_sales_reply` | 已转人工，确认销售是否已经回复 |
| `sales_replied_waiting_user` | 销售已回复，确认客户是否有新消息 |
| `recalled_waiting_user` | 已召回，确认客户是否有新消息 |
| `recall_precheck` | 召回前确认客户是否没有新消息 |

状态原则：

- `watching` 不作为 conversation 主状态。
- 等待客户回复的场景用 `waiting_user_reply / recalled_waiting_user / sales_replied_waiting_user` 表达。
- 读取频率、优先级、是否可召回由规则字段和服务端调度决定，不新增一个泛化的“观察中”主状态。

### 12.4 C2 不做什么

- 不生成 AI 回复。
- 不自动发送微信消息。
- 不创建正式 reply_action 发送流程。
- 不创建 `chat_reply` 任务。
- 不创建 `session_scan`、`message_ingest`、`wechat_binding` 任务。
- 不进入统一任务中心。
- 不做 RAG、模型选择、Guard、安全审核。
- 不做飞书通知。
- 不做自动召回。
- 未绑定会话不得触发 AI 回复。

### 12.5 会话绑定规则

绑定成功必须满足：

- 会话中识别到唯一客户短码。
- 短码能匹配唯一有效线索。
- 线索能关联到当前销售。
- 当前 Worker 与销售绑定关系一致，或服务端允许该 Worker 监听该销售会话。
- 不存在冲突的有效会话绑定。

绑定成功后：

- 创建或确认 conversation。
- 建立 lead_id / conversation_id / sales_id / worker_id 关系。
- 记录 rpa_session_key、display_name、row_fingerprint 和最近扫描时间。
- Worker 后续可以读取该会话消息。
- 后续定向读取仍必须带 `conversation_id + remark_code` 做身份校验；历史绑定关系不能替代本次短码校验。

### 12.6 绑定失败和未绑定

| 场景 | 状态 | 处理 |
|---|---|---|
| 没识别到客户短码 | `unbound` | 不进入消息读取主流程 |
| 短码被销售移除、会话关闭或客户拒绝 | `disabled` | 停止监听，不自动回复 |
| 短码格式非法或不存在 | `binding_failed` | 提示核对 |
| 短码匹配不到线索 | `binding_failed` | 提示数据缺失或短码异常 |
| 短码匹配多条线索 | `needs_review` | 人工核对，不自动选择 |
| 线索已绑定其他活跃会话 | `needs_review` | 人工核对 |
| Worker 与销售不匹配 | `binding_failed` | 防止跨销售误绑定 |

规则：

- 未绑定会话不自动回复。
- 未绑定会话不自动创建回复任务。
- 短码丢失后，不用昵称、头像、手机号尾号等弱特征自动绑定。
- 已绑定会话如读取时缺失短码，不能继续作为正常读取目标，需进入异常或待复核。
- `disabled` 优先级高于其他绑定状态；会话关闭、拒绝或短码移除后，不允许后续扫描自动重新开启监听。

### 12.7 消息入库和去重

规则：

- Worker 只读取服务端允许读取的已绑定会话。
- 服务端允许读取的会话必须具备有效 `remark_code`；缺失短码的会话先走异常或待复核。
- Worker 上报消息事实，不判断业务归属。
- 服务端负责入库和去重。
- 同一条消息必须生成稳定 dedupe_key。
- 同一 conversation_id + dedupe_key 只能成功入库一次。
- Worker 重启、断网重试、重复扫描不得造成重复消息。
- 重复消息不触发后续任务，不覆盖原消息。

### 12.8 C2 状态

会话绑定状态：

| 状态 | 页面文案 | 含义 |
|---|---|---|
| `unbound` | 未绑定 | 扫描到会话，但没有可用短码 |
| `binding_candidate` | 待校验 | 扫描到短码候选，等待服务端校验 |
| `bound` | 已绑定 | 已绑定到唯一线索和会话 |
| `needs_review` | 待人工核对 | 多短码、多线索、绑定冲突或短码丢失风险 |
| `binding_failed` | 绑定失败 | 有短码但无法完成绑定 |
| `disabled` | 已停止监听 | 会话关闭、拒绝或短码被销售移除 |

监听状态：

| 状态 | 页面文案 | 含义 |
|---|---|---|
| `not_started` | 未开始监听 | 尚未进入监听 |
| `listening` | 监听中 | 已绑定，可读取消息 |
| `paused` | 已暂停 | Worker 暂停或不在接单时段 |
| `degraded` | 降级监听 | OCR 低置信、读取失败但未完全不可用 |
| `error` | 监听失败 | 连续扫描/读取失败或微信不可控 |
| `disabled` | 已停止监听 | 会话关闭、拒绝或短码移除 |

消息入库接口处理结果：

说明：以下值只作为 C2 消息入库接口本次处理结果，字段名为 `results[].ingest_result`。`message_events` 只保存已入库消息事实，不再保存 `ingest_status` 字段。

| ingest_result | 页面文案 | 含义 |
|---|---|---|
| `ingested` | 已入库 | 首次成功写入 |
| `duplicated` | 重复消息 | dedupe_key 已存在，跳过 |
| `ignored` | 已忽略 | 系统消息、低价值消息或状态不允许处理 |
| `failed` | 入库失败 | 接口或数据处理失败 |

状态原则：

- `bound` 是 C2 后续读取消息的唯一正常入口。
- `needs_review / binding_failed / unbound` 均不得触发 AI 回复。
- `disabled` 优先级最高；会话关闭、拒绝或短码移除后，后续扫描不得重新开启监听，除非人工重新生成或恢复短码并重新绑定。
- C2 不创建 `reply_action`；即使消息成功入库，响应也只能返回 `next_action=none`。
- 服务端是状态唯一事实源；Worker 只上报扫描和消息事实，不直接改变最终业务状态。
- C2 绑定、监听、读取失败统一使用 `error_code`，不得再使用 `reason_code`。

### 12.9 C2 错误码

| error_code | 页面文案 |
|---|---|
| `SESSION_SCAN_FAILED` | 会话列表扫描失败 |
| `SESSION_REMARK_CODE_NOT_FOUND` | 会话未识别到短码 |
| `SESSION_REMARK_CODE_INVALID` | 短码格式非法或不存在 |
| `SESSION_REMARK_CODE_DUPLICATED` | 一个短码匹配多条活动线索 |
| `SESSION_BINDING_CONFLICT` | 短码匹配到其他销售或 Worker |
| `SESSION_BINDING_DISABLED` | 会话已关闭、拒绝或短码已移除 |
| `MESSAGE_READ_FAILED` | 已绑定会话读取消息失败 |
| `MESSAGE_CONVERSATION_NOT_BOUND` | 上报消息的会话未绑定 |
| `MESSAGE_DEDUPE_KEY_MISSING` | 消息缺少去重键 |
| `MESSAGE_INGEST_DUPLICATED` | 去重键已存在 |
| `WECHAT_WINDOW_NOT_READY` | 微信窗口不可控 |
| `RPA_SIDECAR_TIMEOUT` | OmniAuto Sidecar 超时 |

### 12.10 C2 到 C3 的边界说明

C2 结束后，系统只是有了“可信会话和可信消息”，还没有进入自动回复。

后续 C3 的产品边界是：

```text
消息入库
-> 服务端 AI 大脑判断是否需要回复、转人工、等待或召回
-> 服务端 AI 大脑结合 RAG 生成候选回复
-> Guard 做安全、合规、业务规则审核
-> 审核通过后生成 reply_action
-> 服务端创建 chat_reply 任务
-> Worker 领取 chat_reply 任务
-> Worker 调用 OmniAuto RPA Sidecar 操作微信发送
```

关键规则：

- Worker 不自己调用大模型。
- Worker 不自己决定是否回复。
- Worker 不自己生成或改写回复内容。
- Worker 只执行服务端已经批准并下发的 `chat_reply` 任务。
- 如果服务端判断需要转人工、等待或不回复，不创建 `chat_reply` 任务。
- 当前 checkpoint 只做到 C2，不验收 C3 的 AI 生成、Guard 审核、`reply_action` 和 `chat_reply` 发送。

### 12.11 C3 产品口径：什么时候回复

C3 只有在所有条件都满足时，才允许自动回复：

- 会话已绑定，且客户短码仍有效。
- `ai_enabled=true`，会话没有被人工接管、关闭、拒绝或停止监听。
- 最新客户消息已成功入库，且不是重复消息。
- 服务端已完成消息合并，形成当前有效 `message_batch`。
- 当前不在静默时段内，且未超过单会话、销售、Worker 或全局回复上限。
- 客户问题属于可自动回复范围，例如基础咨询、车型偏好、预算范围、购车需求收集、常规看车引导。
- RAG、车源索引或知识库能提供足够证据支撑回复。
- AI 大脑输出结构化结果，且 `decision=send_reply`。
- Guard 审核通过；如果 Guard 要求改写，则改写后仍必须再次通过。
- 服务端生成 `reply_action`，并创建唯一 `chat_reply` 任务。

规则：

- AI 生成的只是候选回复，不等于一定发送。
- 服务端调度器负责最终决策，不把发送顺序、旧回复作废、幂等判断交给模型。
- 客户连续发多条消息时，旧 `reply_action` 必须作废，基于最新消息重新生成。
- Worker 只能发送服务端 `claim-send` 成功且发送前复核通过后返回的最终文本。

发送前复核规则：

```text
Worker claim chat_reply
-> 对目标会话执行 pre_send_refresh
-> 服务端处理新读到的微信事实
-> 判断 reply_action 是否仍然有效
```

| 复核结果 | 处理 |
|---|---|
| 没有客户新消息 | 允许 Worker 发送原 `reply_action` |
| 发现客户新消息 | 原 `reply_action.status=superseded`，不发送旧回复；新消息进入新的消息批次 |
| 目标会话不确认或读取失败 | 不发送，记录 `error_code`，等待重试或人工处理 |

产品表现：

- 被新消息取代的回复在后台展示为“已被新消息取代”。
- 这类 `reply_action` 不算发送失败，也不要求 Worker 重试原文本。
- 任务中心如已生成对应 `chat_reply`，展示为已取消或已作废，并说明“发送前发现客户新消息”。

### 12.12 C3 产品口径：什么时候转人工

出现以下任一情况，C3 必须转人工或停止 AI 自动回复，不创建 `chat_reply` 任务：

| 场景 | 处理 |
|---|---|
| 会话未绑定、短码失效、会话关闭、客户拒绝、已人工接管 | 不生成回复 |
| 客户明确要人工、要销售电话、要到店地址、要立即成交 | 转人工 |
| 客户问底价、最低价、经理价、能不能再便宜 | 转人工 |
| 客户问事故、泡水、火烧、重大维修、质保纠纷 | 转人工 |
| 客户问贷款、征信、分期包过、定金、合同、退款 | 转人工 |
| 客户投诉、威胁、提到报警、律师、平台举报 | 转人工 |
| RAG 无证据、证据冲突、车源信息缺失或过期 | 转人工或本轮不回复 |
| 模型超时、异常、输出格式不合法、置信度不足 | 短重试；超过次数转人工 |
| Guard 结果为 `handoff` 或 `block` | 转人工 |
| Guard 要求改写但改写失败 | 转人工 |
| 服务端决策为 `pause` | 暂停 AI，等待人工处理 |
| Worker 发送结果未知、文本 hash 不一致、发送失败不可确认 | 人工核查，不自动补发 |
| 销售已经在微信里人工回复 | AI 停止，进入销售跟进状态 |

转人工后的规则：

- 会话进入 `waiting_sales_reply`。
- `ai_enabled=false`。
- 不再为该会话创建新的 `chat_reply` 任务。
- 客户继续发消息时，不由 AI 自动回复；是否提醒销售按后续通知规则处理。
- 飞书通知是否发送属于后续通知能力，不影响“AI 先停手”的主规则。

### 12.13 C3 产品口径：什么时候等待或不回复

以下情况不应强行回复，也不一定转人工：

- 重复消息、系统消息、撤回提示、低价值状态消息。
- 客户连续输入中，服务端仍在等待消息合并窗口结束。
- 静默时段内收到客户消息。
- 当前会话已达到频率限制或当日回复上限。
- 客户表达“稍后再说、先看看、考虑一下”，但没有明确高意向或风险问题。
- 服务端判断本轮无需回复，例如销售刚回复过、上一条 AI 回复仍在等待客户确认。

处理规则：

- 记录 `no_action` 或 `retry_later` 原因。
- 不创建 `chat_reply` 任务。
- 不让 Worker 执行发送。
- 如果服务端决策为 `pause`，按“暂停 AI、等待人工处理”处理，不归入普通等待。

### 12.14 C4 产品口径：召回前确认

C4 进入开发时，召回到期不等于可以直接发送。服务端必须先让会话进入 `recall_precheck`，再读取微信事实。

召回前确认流程：

```text
waiting_user_reply / recalled_waiting_user / sales_replied_waiting_user 到达召回时间
-> Conversation.status=recall_precheck
-> 服务端返回召回前确认读取目标
-> Worker 定向读取该会话
-> 服务端根据读取结果重新判断
```

| 读取结果 | 处理 |
|---|---|
| 读到客户新消息 | 不召回；客户消息进入 C3 判断，决定 AI 回复、转人工或等待 |
| 未读到客户新消息 | 允许创建 `follow_up` 任务，由 Worker 发送固定召回文案 |
| 读到销售人工回复 | 不召回；状态进入 `sales_replied_waiting_user` |
| 读取失败、目标不确认或微信不可控 | 不召回；记录 `RECALL_PRECHECK_FAILED` 或具体 `error_code` |

规则：

- `recall_precheck` 只是召回前确认状态，不代表已经发送召回。
- 只有确认客户没有新消息后，才允许创建和发送 `follow_up`。
- 召回前确认失败时，默认不发送，避免把过期话术发给已经回复过的客户。

## 17. 验收标准

### 17.0 字段口径验收

- 后端接口响应不得出现废弃字段：`runtime_status / current_task_id / client_bind_status / status_flow / executor_status / lead_status / reason_code / ingest_status`。
- 前端类型、状态映射和页面数据模型不得出现上述废弃字段。
- Worker 心跳、任务领取、步骤上报、结果回传、C2/C3 上报字段不得出现上述废弃字段。
- Task 详情和任务事件流只使用 `events`，不得返回或读取 `status_flow`。
- C2 绑定、监听、读取失败只使用 `error_code`，不得使用 `reason_code`。
- C2 消息入库接口处理结果使用 `results[].ingest_result`，不得在 `message_events` 中保存或展示 `ingest_status`。
- C3 会话业务状态只能从 `Conversation.status / ai_enabled / reply_count / handoff_reason_code / handoff_at` 读取和写入。
- `WechatSessionBinding` 只展示绑定和监听字段，不展示或承载 AI 业务状态。
- 废弃字段只允许出现在历史兼容说明或废弃字段表中。

### 17.1 线索和销售

- 可以人工新增客户。
- 手机号重复时不新建线索。
- 重复录入会提示次数和日期。
- 重复备注追加到原线索。
- 新线索能按轮询规则分配给启用销售。
- 停用销售不再分配新线索。
- 销售可绑定、更换、清空 Worker。

### 17.2 Worker 管理

- 新增 Worker 后生成 Worker ID 和 Worker Token。
- 新增后自动打开 Worker 详情。
- Worker Token 不在列表展示，只在详情展示。
- 客户端可用 Worker ID + Worker Token 绑定。
- 同一个 Worker 不能绑定多个客户端。
- 重置绑定后旧客户端失效，新 Token 生效。

### 17.3 任务中心

- 可以查看任务列表和详情。
- 可以按状态、类型、销售、Worker 筛选。
- blocked / pending / running / completed / failed / cancelled 状态准确。
- completed 展示 result_code。
- failed 展示 error_code。
- running 展示 current_step。
- failed / cancelled 重新创建新任务时原任务保留。

### 17.4 Windows Worker add_friend

- 客户端首次绑定成功后再次打开不要求重新绑定。
- 开始接单后能领取 add_friend 任务。
- 暂停接单后不领取新任务。
- 非接单时段在线但不领取任务。
- Worker 能调用 OmniAuto 搜索手机号或微信号。
- Worker 能写入客户短码。
- Worker 能发送添加通讯录邀请。
- 邀请发送后任务为 completed + invite_sent。
- 已是好友时任务为 completed + already_friend。
- 失败时任务为 failed + error_code。
- 客户是否同意好友申请不作为当前验收项。

### 17.5 C2 会话绑定/微信监听

- Worker 可以扫描微信会话。
- Worker 只按第一屏主动扫描、第一屏命中优先读取、状态机定向读取执行 C2。
- 第一屏命中会话能优先读取并上报消息事实。
- 服务端能按状态机返回定向读取目标。
- 定向读取目标必须包含 `conversation_id + remark_code`。
- Worker 读取时必须校验目标 `remark_code` 与会话短码一致。
- Worker 定向读取前能去掉本轮已经处理过的第一屏命中会话。
- 能识别包含客户短码的会话。
- 服务端能用唯一短码绑定 lead / conversation / sales / worker。
- 绑定成功后后台可见。
- 未识别短码的会话不自动绑定。
- 短码删除或改写时能展示错误原因。
- 已绑定会话缺失短码时进入异常或待人工核对，不作为正常读取目标。
- 短码匹配多条线索时进入待人工核对。
- `display_name` 不得作为客户身份主依据。
- Worker 只读取服务端允许读取的已绑定会话。
- 同一消息重复上报不重复入库。
- Worker 重启后重复扫描不导致历史消息重复入库。
- 未绑定会话不得触发 AI 回复或自动发送。
- C2 不验收 AI 回复生成、AI 回复发送、飞书通知和自动召回。

### 17.6 C3 后续验收口径

C3 后续进入开发时，验收不只看“能不能发消息”，还要看“该回复才回复，该转人工就转人工，该等待就等待”。

自动回复验收：

- 客户消息入库后，服务端能形成当前有效 `message_batch`。
- 满足自动回复条件时，服务端生成候选回复并通过 Guard。
- Guard 通过后，服务端创建唯一 `reply_action` 和唯一 `chat_reply` 任务。
- Worker 发送前必须 `claim-send`，claim 失败不得操作微信。
- Worker 发送前必须执行 `pre_send_refresh`。
- 发送前发现客户新消息时，旧 `reply_action.status=superseded`，Worker 不得发送旧回复。
- Worker 只发送服务端批准文本，不能改写内容。
- 发送成功后，状态更新为 `reply_action.sent`、`task.completed`、`conversation.waiting_user_reply`。

转人工验收：

- 高意向、高风险、底价、金融、合同、投诉、人工诉求等场景不自动发送。
- RAG 证据不足、模型失败、Guard 阻断时不编造回复。
- 转人工后 `ai_enabled=false`，不再创建新的 `chat_reply` 任务。
- 销售人工回复后，AI 停止该会话自动回复。

等待和幂等验收：

- 客户连续发消息时，旧 `reply_action` 被置为 `superseded`，不发送过期内容。
- 静默时段、频率限制、重复消息、低价值消息不创建 `chat_reply` 任务。
- Worker 发送失败或结果未知时，不自动补发同一内容。
- 同一 `reply_action_id` 不会被发送两次。

### 17.7 C4 后续验收口径

C4 后续进入开发时，验收重点不是“到期就发”，而是“确认客户没回复才发”。

- 到达召回时间后，会话先进入 `recall_precheck`。
- `recall_precheck` 期间不创建可发送的 `follow_up` 任务。
- Worker 按服务端目标定向读取该会话。
- 读到客户新消息时，不发送召回，消息进入 C3 判断。
- 读到销售人工回复时，不发送召回，状态进入 `sales_replied_waiting_user`。
- 未读到客户新消息时，才允许创建 `follow_up` 任务。
- 读取失败、目标不确认或微信不可控时，不发送召回，并记录 `error_code`。
- 后台能展示召回前确认中、确认通过、确认失败和失败原因。

## 18. 风险和待确认问题

| 问题 | 当前口径 |
|---|---|
| AI 回复是否进入当前 checkpoint | 不进入，C2 只做绑定和消息事实 |
| 未绑定会话能否回复 | 不能 |
| 短码丢失后是否解除历史绑定 | 第一版不立即解除，但提示风险；最终策略待架构师确认 |
| dedupe_key 怎么生成 | 由架构师技术评审确认 |
| 监听异常放任务中心还是 Worker 状态 | 不作为任务中心任务；必要时在线索详情 / Worker 详情展示监听状态和错误原因 |
| 图片和文件消息是否识别内容 | C2 只入库事实和摘要，不做图片识别 |
| Worker 暂停是否打断当前任务 | 不打断，当前任务完成或失败后暂停接单 |
| 成功任务是否上传截图 | 默认不上传 |
| C3 自动回复默认阈值 | 待项目方确认；包括置信度、静默时段、频率限制、每日回复上限 |
| C3 人工接管关键词清单 | 待项目方确认；第一版建议先覆盖底价、事故、泡水、火烧、贷款、定金、合同、地址、投诉、人工 |
| C3 页面是否单独做会话详情页 | 当前建议先复用线索详情 / 任务中心 / Worker 详情展示，不单独做复杂 AI 工作台 |
