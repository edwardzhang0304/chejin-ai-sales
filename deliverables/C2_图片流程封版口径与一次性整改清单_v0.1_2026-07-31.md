# C2 图片流程封版口径与一次性整改清单

版本：v0.1

日期：2026-07-31

状态：架构口径冻结。客户端、OmniAuto、Worker 和后端必须按本文一次性整改；不得再按单个测试案例自行增加分支、状态、接口或消息身份算法。

适用范围：C2 当前屏图片发现、角色确认、稳定身份、剪贴板取图、真实 Vision、消息入库、Brain 上下文、失败门禁、重启恢复和 Windows UAT。

## 1. 审计结论与根因

当前代码的正常主链已经具备：

```text
final_read统一槽位
-> NEW/OLD/OUTBOX判定
-> 只处理NEW_IMAGE
-> 动作前重新确认原图片
-> 右键复制并校验剪贴板代次和图片指纹
-> 内存Vision
-> 回填原槽位
-> messages/ingest
-> 图片后最终当前屏收敛
```

但还不能直接进入正式 Windows UAT。剩余问题分为三类：

1. **架构口径此前没有写完整**
   - 没有区分“初次观察就无法确认发送方”和“已经建立稳定身份后，动作前复核失败”。
   - 没有规定历史图片如何继续进入下一轮 Brain 上下文。
   - 没有明确图片车型匹配只能使用服务端权威车源。
2. **实现存在真实 UAT 风险**
   - 普通 1080p Windows 原始位图可能在压缩前就被 3 MB 限制拒绝。
   - Vision 子进程只给一轮请求时长，但子流程合法包含两轮模型请求。
   - 检测器最多返回 8 张图片且没有“结果被截断”信号。
3. **工程产品约束未完全收口**
   - 剪贴板中的客户原图没有在取入内存后清除。
   - Provider 地址、请求风格和模型结果缺少严格校验。
   - 三层分别手写图片结果结构，限制值已经不一致。

因此本轮不是继续修某个案例，而是按本文完成一次跨层收口。

## 2. 三层唯一分工

### 2.1 OmniAuto

负责：

- 从同一张当前微信画面观察文字、语音和 `image_bubble`。
- 为图片给出 `bubble_rect`、物理视觉指纹和同行头像角色证据。
- 动作前重新截图，用同一套 C2 同行头像规则复核原图片。
- 右键图片、OCR 确认“复制”、点击复制。
- 从当前剪贴板代次读取位图，在内存中缩放和编码。
- 调用真实 Vision，输出经过正式 schema 校验的文字化结果。
- 释放图片内存并清除本次复制产生的系统剪贴板内容。

不负责：

- 生成 `conversation_id/source_message_key/dedupe_key`。
- 用图片位于左侧或右侧另判 `customer/self`。
- 用客户端本地产品库决定车金正式 `product_id`。
- 决定是否启动 Brain、状态机或 handoff。

### 2.2 Worker

负责：

- 使用有效短码、`private`、`read-targets` 和 `authorization_revision` 准入会话。
- 用最终画面统一建立文字、语音和图片槽位及 `screen_order`。
- 生成唯一跨轮 `source_message_key/dedupe_key`。
- 先查 Ledger/Outbox，只把 `NEW_IMAGE` 交给 OmniAuto。
- 持有同一会话和 UI 锁，等待 Vision 完成后重新读取最终当前屏。
- 把图片终态回填原槽位，形成同一份 V3 `messages/ingest` 请求。
- 只保存白名单文字结果和动作证据，不保存图片原始字节。

不负责：

- 自己实现第二套图片检测、发送方判断、Vision 结果模型或产品匹配规则。
- 因单个图片失败丢弃同批其他可靠事实。
- 把 `ignored/pending/discovered` 当作已入库图片。

### 2.3 后端

负责：

- 校验 V3 请求、幂等入库和数据库最终去重。
- 保存图片 `completed/failed` 事实及白名单文字结果。
- 使用服务端权威车源/RAG把视觉描述映射到正式产品。
- 为 Brain 提供当前轮和历史轮的完整紧凑图片上下文。
- 对未解决的 `customer/self` 图片失败应用与语音一致的上下文门禁。
- 根据状态机决定 Brain、reply_action、任务中心和 handoff。

不负责：

- 重算图片左右侧、角色、槽位顺序或消息身份。
- 接收原图、Base64、本地路径或 Provider 原始响应。

## 3. 唯一处理顺序

```text
1. 恢复历史sent_ack、消息Outbox和voice/image媒体事务
2. 真实Vision能力预检
3. 取得C2会话准入并打开一个private短码会话
4. initial_read发现当前屏消息类型
5. 处理当前屏全部可处理的新语音
6. 使用最后一条语音动作后的有效截图，或只补一张final_read
7. 在final_read同时建立文字、语音、图片统一槽位
8. 自上而下建立screen_order
9. Worker生成稳定消息身份并查询Ledger/Outbox
10. 身份冲突先形成帧级门禁；不得先复制图片
11. OLD/OUTBOX图片不做图片动作
12. 逐条处理NEW_IMAGE
13. OmniAuto重截当前窗口并重新确认短码、private、原图片和同行头像角色
14. 图片已出屏：本轮移除，不上滚、不失败
15. 图片仍在屏但已确认身份复核失败：零点击，形成failed事实
16. 身份复核成功：右键、菜单OCR、点击复制
17. 校验剪贴板代次变化，并确认剪贴板图片指纹属于目标气泡
18. 把位图读入内存，先按源尺寸安全上限解码，再缩放压缩到Provider上限
19. 清除本次复制产生的Windows剪贴板内容
20. 调用真实Vision；结果必须通过共享schema
21. completed或failed立即写ActionJournal/Ledger；释放图片内存
22. 每次图片动作导致画面变化后，重新观察最终当前屏
23. 处理新出现且仍可见的新语音/图片；被顶出屏的消息不追
24. 所有当前屏新槽位收口后，按最终screen_order组装同一V3请求
25. 写Outbox后调用现有messages/ingest
26. 后端确认事实；存在上下文门禁则不启动Brain
27. 无门禁且有客户触发消息：同一会话、同一UI锁等待batch和Brain
28. 执行reply_action并完成sent_ack后，才释放会话和UI锁
```

Vision 请求期间来了新消息，不取消正在处理的原图片，也不使用旧坐标点击新内容。原图片完成后执行第 22 步，以新画面继续收敛。

## 4. 图片候选与终态矩阵

| 观察场景 | 是否建立稳定图片消息 | 是否点击/Vision | 结果 |
|---|---:|---:|---|
| 检测器正常，确实没有图片 | 否 | 否 | 正常继续 |
| 检测器异常、锚点失败或结果被截断 | 否 | 否 | 帧级 `C2_IMAGE_OBSERVATION_FAILED`，禁止 Brain |
| 初次观察为图片气泡，但同行头像角色不可信 | 否 | 否 | 帧级 `MESSAGE_IDENTITY_UNCONFIRMED`；不得写 `ignored` Ledger，后续新画面可重新观察 |
| 已有可靠角色和稳定身份，Ledger 为 OLD | 是 | 否 | 复用 `completed/failed` |
| 已有 Outbox | 是 | 否 | 只重传同一 JSON |
| NEW_IMAGE 动作前已经出屏 | 否 | 否 | 本轮移除，不上滚、不产生 failed |
| NEW_IMAGE 仍在屏，动作前角色变更、unknown 或无法唯一匹配 | 是 | 否 | `failed + C2_IMAGE_SLOT_RECONFIRM_FAILED` |
| 已点击复制，剪贴板未就绪 | 是 | 不调用模型 | 使用可取消的无进展等待；超时后 `failed` |
| 剪贴板位图有效但与目标视觉指纹不符 | 是 | 不调用模型 | 同进程、同 UI 锁、重新确认同一稳定身份后最多允许重新复制一次；再次不符则 `failed`。重启恢复不得重做 |
| Vision 成功且结果 schema 合法 | 是 | 是 | `completed` |
| Vision 网络、超时、Provider 或结果 schema 失败 | 是 | 是 | `failed`，不自动重复 Vision |

`ignored` 只允许表示 OmniAuto 在建立业务图片身份前已经明确证明“该视觉对象不是聊天图片消息”。一旦 Worker 已建立图片 `source_message_key`，终态只允许 `completed/failed`；不得用 `ignored` 静默丢消息。

## 5. 内存、尺寸和剪贴板合同

源图安全上限和 Provider 请求上限必须分开：

| 阶段 | 约束 |
|---|---|
| Windows `CF_DIB/CF_DIBV5/CF_BITMAP` 解码 | 先按像素数和原始内存上限校验；20,000,000 像素对应的 RGB/RGBA 原始位图可以大于 3 MB，不得用 Provider 的 3 MB 上限提前拒绝 |
| 已编码源图片 | 可保留独立源文件上限，例如 12 MB；仍须校验格式、像素和解压炸弹 |
| Vision 请求图片 | 最大边 2048；最终编码不得超过 3 MB |
| 编码策略 | 先缩放；照片类 RGB 使用有界质量 JPEG/WebP 逐级压缩，透明图或压缩后仍满足上限时可用 PNG；不得只做无损 PNG 一次编码 |
| 无法压到上限 | 形成明确 failed 图片事实，不写临时文件 |

剪贴板规则：

1. 只能读取点击“复制”后产生的新剪贴板代次。
2. 必须校验剪贴板图片视觉指纹与目标气泡一致。
3. 图片复制到进程内存并完成指纹校验后，清除当前代次；不得把客户图片留在 Windows 剪贴板历史或云同步。
4. 生产测试机必须关闭 Windows 剪贴板历史和跨设备同步。
5. 清理失败记录安全告警，但不能把已经确认的图片换成其他内容。
6. 剪贴板等待必须是可取消的无进展 watchdog，不能把固定 2.5 秒当作所有机器和大图的业务时限。
7. 微信缩略图与复制原图可能发生缩放、压缩或中心裁切。必须在唯一
   `fingerprints_match` 比较器中支持经过 UAT 证明的变换；不得在业务编排中绕过
   指纹验证或为某张样图增加特殊分支。

## 6. Vision 调用合同

### 6.1 配置安全

- `base_url` 必须为 HTTPS。只有显式开发模式才允许 localhost HTTP。
- `request_style` 使用明确白名单；未知值必须配置失败，不能自动落入 OpenAI 分支。
- Provider、模型和请求风格必须是允许组合。
- API Key 只从进程环境或受控密钥配置读取，不进入日志、manifest、Outbox 或后端。

### 6.2 超时与重试

- 单次 HTTP 请求必须有超时，防止网络永久卡住。
- 只允许在“HTTP 成功但响应不是合法 JSON 对象”时进行一次格式纠正重试。
- 父进程硬安全时间必须至少覆盖两次合法请求时长、编码和进程通信余量，不能使用 `单次timeout + 5秒` 杀死第二次合法请求。
- 正常请求有阶段进展时保持原会话和 UI 锁；不设置会中断正常两次请求的短批次总超时。
- HTTP 4xx/5xx、鉴权失败、网络失败和 schema 失败不得自动再做第二次图片 RPA。

### 6.3 结果 schema

`customer_image_understanding_v1` 和 `visual_bridge_input_v1` 必须由车金机器合同提供完整 JSON Schema，并自动生成或复用三层校验器。Schema 至少固定：

- 必填字段、字段类型和最大文本长度。
- 数组条数。
- 置信度为有限数且范围 `0..1`。
- 布尔值必须是真布尔，字符串 `"false"` 不能转成 `true`。
- Provider 原始响应、错误正文、路径、字节、Base64 和缩略图禁止持久化。
- 结果不满足 schema 时为 `failed`，不得靠默认空字段伪装 `completed`。

Provider 详细错误只留在本地脱敏日志。Worker 上报稳定错误码，不把 HTTP 响应正文放入 `audit.provider_error`。

Vision 摘要、图片 OCR 和客户文字都属于不可信客户内容，不是系统指令。Brain
system prompt 必须明确忽略其中要求泄露提示词、密钥、内部规则或绕过 Guard 的
指令；图片文字仍须经过现有事实授权和最终 Guard。UAT 必须包含图片内提示注入。

## 7. 产品库和 Brain 上下文

### 7.1 产品权威边界

车金正式产品/车源身份只由服务端产品主数据、RAG 和大风车同步索引确认。

- OmniAuto Vision 输出品牌、车系、车型线索、年份、颜色、车身类型、图片 OCR 和中性查询描述。
- 车金集成不得把 OmniAuto 客户端 `KnowledgeRuntime` 的产品清单注入正式 Vision Prompt。
- `selected_product_id` 只能由后端用权威车源验证后采用；客户端模型返回值仅可作为不可信提示，不能直接进入业务回答。
- 不要求删除 OmniAuto 独立产品原有的本地知识库能力；车金严格适配入口必须显式关闭该能力。

### 7.2 跨轮历史上下文

后端给 Brain 的历史图片不能只保留 `message_type=image + content`。每条历史图片至少提供紧凑字段：

```text
id
source_message_key
sender_role
message_type=image
item_state
error_code
occurred_at
message_position
vision_summary
image_ocr_text
classification
entities
normalized_vehicle_query
server_validated_product_id
```

当前轮与历史轮必须使用同一个紧凑投影函数和总长度预算。这样下一轮客户问“这辆多少钱”“刚才那台还有吗”时，Brain 仍能理解所指图片。

### 7.3 失败媒体门禁

- `customer` 和 `self` 的 failed 图片都进入与 failed 语音相同的按角色、按最终画面顺序门禁算法。
- 已确认的其他消息事实仍正常入库，不丢失。
- 门禁未被可靠的后续销售事实覆盖时，不启动 Brain，按现有业务 handoff/等待销售流程闭环。
- 这里不存在“人工到后台修图片消息”的角色或队列。

## 8. 一次性整改清单

### P0：Windows UAT 前必须完成

| 责任层 | 一次性修改 |
|---|---|
| OmniAuto | 分离原始位图与 Provider 大小限制；支持常见 1080p DIB/HBITMAP；自适应缩放压缩；剪贴板使用可取消的无进展等待并在复制后清空；统一指纹比较器覆盖微信缩略图变换；图片数量不静默截断；严格校验 Vision 结果 |
| Worker | 初始角色不可信改为帧级身份门禁，不再持久化 `ignored`；父子进程超时覆盖完整合法重试；Provider 配置使用 HTTPS/风格白名单；恢复协调器先于 Vision 预检 |
| 后端 | failed 图片门禁覆盖 `customer/self`；历史图片上下文保留紧凑结构和失败状态；服务端验证正式产品 ID |
| 三层共享 | 为两个图片结果对象增加完整 JSON Schema、共享样例和生成式合同测试；升级合同 revision/SHA，禁止手抄三套限制 |

### P1：正式发布前完成

| 责任层 | 修改 |
|---|---|
| OmniAuto/Worker | Provider 详细错误只进本地脱敏日志；增加剪贴板清理失败指标、图片编码耗时和压缩前后尺寸指标 |
| Worker/后端 | 两轮图片指代测试、失败媒体位置门禁测试、超过候选容量测试和崩溃恢复测试 |
| 打包 | manifest 记录合同 SHA、OmniAuto commit 和测试结果，但绝不记录 API Key、原图或 Provider 响应 |
| Brain/Guard | 把图片 OCR、Vision 摘要和客户文本标记为不可信内容，增加图片提示注入回归 |

### P2：后续治理

- 将车金严格 Vision 入口做成唯一 allowlist；OmniAuto 上游兼容代码可以保留，但不得从车金 Worker 调用。
- 根据 Windows 真实样本调整图片编码质量和模型成本指标，不能改变消息身份或失败语义。

## 9. 禁止工程师自行改变的事项

1. 不新增图片上传接口、图片任务、图片 pending/deferred 或第二套消息表。
2. 不恢复本地图片路径、截图裁切图片、旧 Vision compatibility 入口。
3. 不用 `visual_side` 取代 C2 同行头像角色。
4. 不把初始角色不可信图片持久化为 `ignored`。
5. 不因 Vision 慢释放当前会话/UI 锁并处理其他会话。
6. 不因某张图片失败丢弃同批文字、语音或其他成功图片。
7. 不让客户端本地产品库成为车金正式产品 ID 的事实源。
8. 不用 mock 模型结果宣称真实 Vision 流程通过。
9. 不为修某个 UAT 案例复制一条专用分支；状态和错误码先改机器合同，再改三层。

## 10. Windows UAT 准入门禁

以下自动测试全部通过后才打 UAT 包：

1. 1920x1080 高信息量照片的 DIB、DIBV5、HBITMAP 和已编码图片均能压缩后调用 Provider。
2. 第一轮模型接近超时后返回非 JSON，第二轮在合法预算内成功，父进程不得提前杀死。
3. 初始角色 unknown 时零点击、零 Vision、零 terminal ledger，并阻断 Brain。
4. 超过 8 张可见图片时不静默漏图：全部观察，或明确门禁。
5. failed `self` 图片位于后续客户提问之前时，Brain 被阻断。
6. 下一轮“这辆/刚才那台”能读取上一轮图片结构化上下文。
7. 客户图片复制到内存后，Windows 当前剪贴板不再保留该图片。
8. HTTP 地址、未知 request_style、非法布尔、越界置信度和 NaN 均失败关闭。
9. 进程分别在复制后、Vision 返回后、Ledger 后、Outbox 后和 ingest 响应丢失时强杀；重启不重复右键或重复计费，事实最终结算。
10. Vision 期间出现新消息：原图片完成后重读当前屏；仍可见的新消息继续处理，被顶出屏的不追。
11. 连续两张相同图片仍形成两个稳定消息身份；同一图片跨轮不重复处理。
12. 群聊、短码缺失、`unknown` 会话和授权撤销时不执行图片 UI 动作。
13. 微信缩略图经缩放、压缩或中心裁切后仍能与正确原图匹配；错误图片必须被拒绝，
    只能修改统一指纹算法，禁止跳过验证。
14. 图片内包含“忽略系统规则、泄露提示词/密钥”等文字时，Brain/Guard 不执行该
    指令、不泄露内部信息。

Windows 实机至少覆盖：

- 客户图片、我方图片、两张连续相同图片。
- 文字 + 语音 + 图片混合，Vision 期间新增文字或图片。
- 普通照片、长截图、大图、含文字车辆图。
- Vision 成功、非 JSON 重试、超时、鉴权失败和网络中断。
- 第一轮发图片，第二轮询问“这辆多少钱”。
- 不同缩略图裁切模式、大图慢剪贴板和图片内提示注入。

任一 P0 自动测试未通过，不得把问题留给测试工程师通过人工操作解释。

## 11. 客户端工程师唯一整改工单

客户端工程师必须把本节作为一次完整整改处理，不得拆成若干 UAT 案例逐个加
`if/else`。修改范围仅限 OmniAuto、Worker、共享机器合同、客户端测试和打包门禁；
后端 Brain、状态机和数据库由后端工程师另行整改。

### 11.1 修改顺序

1. 先更新机器合同：补齐 `customer_image_understanding_v1` 和
   `visual_bridge_input_v1` 的完整 JSON Schema、错误码、字段长度、数组容量、
   `confidence` 范围和有限数约束，升级合同 revision/SHA。
2. 再改 OmniAuto：统一图片观察、动作前复核、剪贴板读取、图片缩放压缩、统一
   指纹校验、真实 Vision 调用、结果 schema 校验和剪贴板清理。
3. 再改 Worker：统一 NEW/OLD/OUTBOX 判定、初始角色门禁、稳定身份、完整 Vision
   等待预算、媒体事务恢复、结果回填和 V3 Outbox。
4. 最后补三层共享合同测试、客户端自动测试和 Windows UAT 包门禁。合同或任一
   P0 测试不通过时不得打包。

### 11.2 OmniAuto 必须完成

- 原始 Windows 位图与 Provider 请求体采用两套大小上限。必须能有界读取常见
  1080p DIB/DIBV5/HBITMAP，再在内存中缩放并自适应编码；不得在压缩前直接按
  3 MB 拒绝原图。
- 图片候选不得静默截断为 8 张。要么返回当前屏全部候选，要么明确返回
  `observation_truncated=true`，由 Worker 阻断本轮 Brain。
- 图片动作前重新截图，使用 C2 已有的同行头像角色证据和统一
  `fingerprints_match` 复核同一张图片；不得另写左右侧角色规则。
- 只读取点击“复制”后产生的新剪贴板代次。读取并验证后清除本次剪贴板内容；
  不保存本地图片、不上传原图到车金后端、不恢复任意旧剪贴板内容。
- 剪贴板等待使用可取消的无进展 watchdog。正确图片首次校验失败时，只允许在
  同进程、同 UI 锁、重新确认同一稳定身份后再复制一次；重启恢复不得再次右键。
- 真实 Vision 最多按合同执行一次非 JSON 修复请求。结果必须通过共享 schema；
  非法布尔、NaN、越界置信度、超长字段和未知结构都必须失败关闭。
- 车金严格入口禁止注入 OmniAuto 本地 `KnowledgeRuntime` 产品清单。只输出中性
  的品牌、车系、车型线索、OCR、实体和查询描述，不决定正式 `product_id`。
- Provider 详细响应只进入本地脱敏、限长日志，不得进入消息、Outbox 或安装包。

### 11.3 Worker 必须完成

- 恢复协调器必须先于 Vision 能力预检和任何新 C2 扫描，优先结算
  `sent_ack`、消息 Outbox 和未完成媒体事务。
- 初次观察图片但同行头像角色不可信时，返回帧级
  `MESSAGE_IDENTITY_UNCONFIRMED`：零点击、零 Vision、零 terminal ledger，并
  阻断本轮 Brain；后续自然新画面仍可重试。
- 已有可信角色和稳定 `source_message_key` 后，动作前复核找不到原图片或角色不再
  可信，写 `failed/C2_IMAGE_SLOT_RECONFIRM_FAILED`。此时不得降成 `ignored`。
- `ignored` 只能用于建立业务图片身份前，已经证明该对象不是聊天图片的情况。
  一旦有稳定 `source_message_key`，图片终态只允许 `completed/failed`。
- Vision 父进程预算必须覆盖合同允许的全部 HTTP 尝试、图片处理、IPC 和收尾；
  单次 HTTP 仍保留超时，但不能用一轮请求时长杀死合法第二轮。
- Provider 正式配置只允许 HTTPS、明确的 request style、模型和域名白名单；
  localhost HTTP 只能通过显式开发开关启用。日志、manifest 和异常中不得出现 Key。
- Vision 全程保持当前会话和 UI 锁。完成后重新读取最终当前屏，仍可见的新消息
  继续进入同一会话 Flow，被顶出屏幕的消息不主动上滚追踪。
- 图片 `completed/failed` 必须回填原统一槽位，与文字、语音共用一份 V3
  `messages/ingest` 和 Outbox；不得新增图片上传接口、图片任务或图片专用消息表。

### 11.4 不得回归的既有流程

此次只能收口图片流程，不得改坏 C1 加好友、短码 + `private` 唯一准入、文字读取、
语音转写、统一 sender_role、最终画面排序、当前屏不主动上滚、单会话 UI 锁、
Outbox 优先恢复、授权 revision、停止监听和 `sent_ack` 未结算时停止新扫描等既有
约束。OmniAuto 上游新代码只吸收本次审计需要的能力，车金已经修改并验证过的这些
约束不得被覆盖或回退。

### 11.5 客户端交付物

客户端工程师完成后一次性交付：

1. OmniAuto 与 Worker 修改清单及对应提交。
2. 机器合同 revision、SHA 和三层共享样例。
3. 第 10 节全部客户端相关自动测试结果。
4. 高信息量 1920x1080 图片压缩前后尺寸、编码耗时和 Provider 请求大小证据。
5. 真实 Vision 成功、合法二次请求、超时、鉴权失败和网络中断证据；不得只交 mock。
6. 工作区 clean、OmniAuto commit、Worker commit、合同 SHA 和测试结果写入
   manifest 的候选包。任何 API Key、原图和 Provider 响应不得进入 manifest。

## 12. 已接受但必须治理的运营风险

第一阶段如果继续把同一个 Vision API Key 分发到所有 Windows 客户端，必须明确：

1. 安装到客户端的共享密钥理论上可被提取，不能视为真正保密。
2. 使用独立 Vision 子账号/密钥、最小权限、模型白名单、域名白名单、日/月费用
   上限、异常调用告警和可快速轮换机制；不得与 Brain 或其他生产系统共用密钥。
3. 正式商用前确认第三方模型的图片保存期限、训练使用、数据地域和隐私条款，并
   在产品隐私告知中说明客户图片会发送给第三方模型处理。
4. 后续优先迁移为服务端短期令牌或受控代理；该迁移不能改变当前单会话 UI 锁和
   同一 Flow 等待 Vision 终态的业务语义。
