# C1-C3 事务恢复与事实结算统一架构

版本：v0.1

日期：2026-07-31

状态：架构口径已冻结，客户端和后端实现待按本文统一整改；整改完成前不得继续按单个测试案例追加恢复分支，不得打新的 Windows UAT 包。

机器合同说明：当前 `contracts/c2_contract_v3.json` 的 `3.10.0` 是整改前实现快照，
不是本架构的目标合同。为避免只有枚举变化、运行代码尚未支持的半升级，本轮只冻结
架构文档；后端实施的第一个提交必须一次性升级合同 revision、schema、共享样例和
合同测试，客户端随后基于同一提交接入。`3.10.0` 不得用于新包发布。

## 1. 本次为什么重新收口

当前问题的根因是流程模型缺了一层，不是某一个图片错误码写错：

1. 原流程把“还能不能操作微信”“已经产生的事实要不要保存”“能不能推进 Brain”混成了一个授权结果。
2. 图片后来补了专用恢复分支，语音没有进入同一全局恢复门禁。
3. `unbound / binding_failed` 本来是可恢复状态，却被图片恢复接口当成永久 `target_terminated`。
4. `target_terminated` 允许 Worker 在后端没有保存事实时直接把本地记录改成 `not_required`，存在事实丢失。
5. Vision 能力检查排在事务恢复之前，图片模型缺配置时可能连已有 Outbox、发送回执和无需模型的事实结算也一起卡住。

因此，本次不再修“图片恢复特例”，而是建立一套覆盖 C1、C2、C3 的事务规则。

## 2. 三个概念必须分开

| 概念 | 只回答什么问题 | 唯一决定方 |
|---|---|---|
| UI 准入 | Worker 现在还能不能打开或继续操作这个微信会话？ | 后端授权，Worker执行 |
| 事实结算 | 已经观察到或已经处理完成的事实，是否已经被后端可靠接收？ | 后端持久化确认 |
| 业务推进 | 这些事实是否允许改变会话状态、启动 Brain、创建回复或召回？ | 后端状态机 |

硬规则：

```text
UI 准入失效，只能停止新的微信动作；
不能据此删除已经产生的事实。

事实可以补录，不代表可以推进当前状态机；
只有当前有效授权下的完整事实才能启动 Brain。
```

## 3. 全系统统一不变量

1. 同一个 Worker 同一时间只允许一个微信 UI 事务。
2. 不可逆动作前必须先落盘 `not_attempted`，紧邻物理点击前推进为 `trigger_attempted`，取得可靠结果后推进为 `confirmed`。
3. 只要出现 `trigger_attempted / confirmed`，对应动作结果就必须由后端明确结算后，Worker 才能删除本地日志、Ledger 或 Outbox。
4. `not_attempted` 且全部条目都能证明未触发动作时，可以在本地直接删除，不请求后端。
5. 语音和图片统一称为 `media_fact`，共用恢复队列、恢复授权和结算规则；禁止继续保留图片专用全局门禁。
6. 已完成或已失败的媒体事实都必须结算；失败不是 pending，也不自动重复右键、复制、转写或调用 Vision。
7. 后端未确认的 `sent_ack`、消息 Outbox 或媒体事实，会阻断新的微信 UI 动作和任务领取。
8. 暂停监听只禁止新的微信 UI 动作；纯网络重传、回执确认和无需微信的事实结算继续运行。
9. Vision、Brain 或其他能力预检只能阻断会使用该能力的新动作，不能阻断历史 Outbox、`sent_ack` 或事实结算。
10. 正常业务 Flow 不设置固定总时限；单步骤无进展由 watchdog 结束为明确 failed/unknown，已经完成的结果不能被后续失败覆盖。
11. 后端唯一约束是最终去重防线；Worker 本地 Ledger 负责避免重复昂贵动作，两者都不能取消。
12. 任意恢复结果都必须有稳定状态和 `trace_id`，不得让 Worker 解析错误文字自行猜测。

## 4. Worker 启动与每轮动作前的唯一恢复顺序

每次启动、重连、暂停恢复，以及领取 C1/C3 任务或开始 C2 扫描前，都执行同一个全局门禁：

```text
1. 重传 sent_ack Outbox
2. 重传完整 messages/ingest Outbox
3. 恢复 voice/image ActionJournal 和等待结算的 media Ledger
4. 恢复任务中心中的 add_friend/chat_reply 任务状态
5. 上述全部得到后端确认后，才检查本轮所需能力
6. 能力就绪后，才允许新的微信 UI 动作
```

说明：

- 正常串行流程理论上不会同时留下多类未完成事务；若历史版本留下多类记录，按上面顺序逐类处理。
- 恢复只处理原记录，不生成新消息身份，不重新执行昂贵动作。
- `sent_ack` 优先级最高，防止已经发送的右侧气泡被后续扫描误判为销售人工消息。

## 5. 媒体事实统一恢复状态机

### 5.1 Worker 本地记录要求

语音和图片在不可逆动作前都必须保存可重放的文字化观察，至少包含：

```text
transaction_id
conversation_id
original_worker_id
original_binding_id
original_authorization_revision
original_read_reason
remark_code
rpa_session_key
source_message_key
dedupe_key（可以在最终组装时补齐）
message_type
sender_role及角色证据
稳定物理anchor
observed_at
screen_order
action_phase
business_state
error_code
terminal_payload
```

图片原始位图不得写入 ActionJournal、Ledger、Outbox 或后端。语音和图片都必须有足以形成 completed/failed 消息事实的 `replayable_observation`；不能只保存坐标。

### 5.2 三种恢复决定

后端恢复决定只允许：

| `recovery_decision` | 含义 | Worker行为 |
|---|---|---|
| `resume_current_target` | 原会话仍是同一 Worker 的有效短码 private 会话，允许继续操作微信。 | 只打开原会话，重新确认标题/private 后完成正常 C2 Flow。 |
| `settle_without_ui` | 不再允许操作原会话，但后端可以结算原事务。 | 不打开微信；通过既有 `messages/ingest` 完成事实或技术终态结算。 |
| `retry_later` | 网络异常、后端暂不可判断，或现有证据不足以选择 fact_only/technical_terminal。 | 原记录不变，阻断新 UI，按退避重试。 |

未知或缺失决定一律按 `retry_later`。

### 5.3 `settle_without_ui` 的两种结算模式

| `settlement_mode` | 使用条件 | 后端结果 |
|---|---|---|
| `fact_only` | 后端能证明原 Worker、原绑定、原 conversation 和短码身份一致，只是当前已暂停、关闭、解绑或授权变化。 | 消息事实按幂等键入库；`state_transition_applied=false`；不创建 batch，不启动 Brain，不创建回复或召回。 |
| `technical_terminal` | 原绑定不存在、Worker 所有权变化、短码/会话身份冲突，无法安全把内容归入当前业务会话。 | 后端持久化事务终结审计及精确 `source_message_key` 结果；不伪造 `message_event`，不启动 Brain。 |

只有后端返回每个 `source_message_key` 的 `ingested / duplicated / technical_terminal` 确认后，Worker 才能将本地记录置为 confirmed 并删除动作日志。

### 5.4 为什么不再使用原 `target_terminated`

原 `target_terminated` 同时表达了三件不同的事：

- 不能再打开微信；
- 不需要保存事实；
- 可以删除本地记录。

这三个结论并不总是同时成立。新架构废弃媒体恢复和消息 Outbox 中“收到 `target_terminated` 就本地丢弃”的语义。历史名称可在兼容层读取，但必须映射到 `settle_without_ui`，且后端完成结算前不能清理。

## 6. 绑定和短码状态的唯一解释

| 后端状态/证据 | UI准入 | 恢复决定 |
|---|---|---|
| `bound + listening + private + 有效短码` | 可按 read-target 操作 | `resume_current_target` |
| `paused / degraded / binding_failed / unbound`，但后端仍能证明原 Worker + 原绑定 + 原 conversation + 原短码身份 | 不开始新 UI | `settle_without_ui + fact_only`；只结算旧事实，不改变当前绑定状态 |
| `needs_review`，但冲突不影响原事务身份 | 不开始新 UI | `settle_without_ui + fact_only` |
| 会话关闭、客户拒绝、短码已被可靠确认移除、绑定被禁用 | 不开始新 UI | 已有事实走 `settle_without_ui` |
| Worker 所有权变化、短码冲突、conversation 身份不可信 | 不开始新 UI | `settle_without_ui + technical_terminal` |
| 网络失败、服务端 5xx、原事务身份暂时无法证明 | 不开始新 UI | `retry_later` |

短码缺失确认规则：

1. 一次首屏 OCR 没识别到短码，只能算“本次未观察到”，不能把已有 bound 会话改成永久 unbound/disabled。
2. 新会话没有短码时不准入，也不创建可读绑定。
3. 已绑定会话的短码移除必须有后端可审计的确认来源，例如明确关闭操作，或专门授权的标题复核证据。
4. 低置信、截断、列表行变化和单次 OCR 缺失只能进入 `degraded/retry_later`。
5. 确认短码移除后停止新 UI 和自动化；移除前已经产生的事实仍必须结算。

自动标题复核只允许用于“此前已经 bound、同一会话行仍在第一屏可见”的目标：

```text
首次高质量首屏观察不到原短码
-> 后端只签发 binding_recheck（不是普通 read-target）
-> Worker 只按原可见行打开一次
-> 页面稳定后取得两张独立标题 ROI 证据
-> 两张都能确认 private 且原短码不存在
-> 上报 remark_code_removed_confirmed
-> 后端 disabled，并让旧事实走 settle_without_ui
```

`binding_recheck` 禁止读取消息、转语音、复制图片、调用 Vision、Brain 或发送。原行
不在第一屏、标题置信不足、两张证据冲突时保持 `degraded/retry_later`，不得搜索一个
已经不存在的短码。后台明确关闭仍是另一种可靠确认来源。

## 7. C1、C2、C3 分别如何闭环

### 7.1 C1 添加好友

- 任务中心拥有 `add_friend` 任务和租约。
- 最终“确定”按钮点击函数返回成功即为 `confirmed + invite_sent`，不等待微信成功文案。
- 点击后明确风控可以形成业务失败；诊断截图/OCR异常不能推翻已确认点击。
- `trigger_attempted` 后进程退出时，只恢复原任务结果，不自动再次点击。
- C1 只证明邀请已发送；好友通过必须由 C2 首屏发现有效短码 private 会话后确认。

### 7.2 C2 文字、语音、图片

- 文字只有观察和入库，不执行昂贵媒体动作。
- 语音与图片共用 `media_fact` 恢复协议。
- 语音由 Worker 编排 OmniAuto RPA 转写；图片由 Worker 编排 OmniAuto 复制和 Vision。
- 最终当前屏统一建立槽位、角色、顺序和消息身份。
- 当前屏新增消息一次组成 V3 批次；后端确认前进入 Outbox 并阻断新 UI。
- 已结算历史事实不重复上报；Brain 从后端 `message_events` 读取历史上下文。

### 7.3 C3 Brain、任务中心和发送

- `messages/ingest` 只上报事实；后端据当前状态创建 `message_batch`。
- Brain/Guard 在后端生成 `reply_action`，任务中心创建同一 batch 的 `chat_reply`。
- 正常链路由仍持有原会话和 UI 锁的 C2 Flow 优先 claim 该任务；普通任务线程不得并发争抢。
- Worker 回复前重新观察当前屏；有客户新消息则先增量入库并 supersede 旧回复。
- 发送点击前写 `trigger_attempted`；确认右侧新气泡后写 `confirmed` 和可靠 `sent_ack` Outbox。
- `sent_ack` 未获后端确认时整个 Worker 不开始新微信动作。
- 发送结果未知上报 `unknown` 并结束原回复动作，不自动补发。

### 7.4 召回

- 召回由后端状态机产生 `recall_precheck`，不是 Worker 固定文案任务。
- Worker 打开原会话先读新消息；有客户新消息就取消本轮召回并走普通 C2。
- 无新消息时后端创建 recall batch，Brain/Guard 生成回复，最终仍是 `chat_reply + sent_ack`。
- 与普通回复共用同一串行、刷新、发送和恢复合同。

## 8. 接口收口

不新增图片或语音专用后端接口。

### 8.1 恢复授权

沿用：

```http
GET /api/workers/{worker_id}/wechat/conversations/{conversation_id}/read-authorization
```

恢复请求必须携带或引用本地事务摘要：

```text
recovery_transaction_id
action_kind
source_message_key_digest
original_authorization_revision
```

响应：

```json
{
  "allowed": false,
  "recovery_decision": "settle_without_ui",
  "settlement_mode": "fact_only",
  "settlement_token": "***",
  "conversation_id": "...",
  "trace_id": "..."
}
```

`settlement_token` 只能绑定当前 Worker、原 conversation、恢复事务和 source key 摘要，短时有效，不得写日志。
建议使用服务端签名的 5 分钟 token；同一事务在有效期内可幂等重试，不能设计成
第一次网络响应丢失后就失效的一次性 token。请求头固定为
`X-C2-Settlement-Token`。

`source_message_key_digest` 只有一种算法：

```text
sha256(UTF-8(sorted(unique(source_message_key)).join("\n"))).hexdigest()
```

Worker 和后端必须读取共享合同样例验证，禁止各自选择 JSON 序列化或原数组顺序。
恢复时缺少 `dedupe_key` 的媒体事实，由 Worker 调用现有唯一消息身份组装器从
replayable observation 补齐；不得在恢复协调器中再造哈希规则。

### 8.2 事实结算

沿用：

```http
POST /api/workers/{worker_id}/wechat/messages/ingest
```

新增授权范围，不新增平行 endpoint：

```text
authorization_scope=active_read | fact_settlement
```

- `active_read`：当前正常 C2 入库，可以按状态机规则创建 batch。
- `fact_settlement`：必须携带 `settlement_token`；只保存事实或技术终态，固定 `state_transition_applied=false`，固定 `message_batch=null`。

正常消息和恢复消息继续共用 V3 消息结构、`source_message_key`、`dedupe_key` 和数据库唯一约束。

### 8.3 后端持久化

新增一张通用恢复结算表，不使用 handoff 记录冒充技术事务：

```text
wechat_recovery_settlements
  id
  worker_id
  conversation_id（可空）
  recovery_transaction_id
  action_kind
  source_message_key_digest
  settlement_mode
  source_results_json
  error_code
  trace_id
  settled_at
```

唯一约束：

```text
unique(worker_id, recovery_transaction_id)
```

`fact_only` 在同一个数据库事务中写 `message_events` 和 settlement；
`technical_terminal` 只写 settlement。两者都不得创建 `message_batch`、
`reply_action`、召回或 handoff；技术恢复失败不是“等待人工处理消息”。

## 9. 当前代码相对目标架构的统一差异

这些是同一流程缺口，不应再拆成零散 bug：

1. 全局恢复门禁只查询图片 Ledger/ActionJournal，语音没有进入。
2. 语音 ActionJournal 没有完整 `replayable_observation`，跨重启无法脱离 UI 结算。
3. `unbound / binding_failed` 被返回为 `target_terminated`，与其非永久状态冲突；
   正确行为是能证明原事务身份时 `fact_only`，不能证明时 `retry_later`。
4. `target_terminated` 会把图片 Ledger 改成 `not_required` 并删除日志，但后端没有保存事实。
5. 消息 Outbox 遇到目标失效也允许直接终结，存在相同事实丢失语义。
6. Vision 预检排在恢复门禁之前，可能阻断无需 Vision 的历史事务恢复。
7. 单次首屏未识别短码会把已有绑定写成 `unbound`，缺少“未观察到”和“确认移除”的区分。
8. 图片恢复状态、函数和日志名都写死 image，继续扩展会形成第二套语音恢复代码。
9. 当前 `record_ingest_technical_terminal` 使用 handoff 记录技术终态；这会把协议
   恢复错误混成销售接管，且绑定不存在时仍无法持久化，必须改为通用 recovery
   settlement。

整改必须以“统一 media transaction coordinator + 统一 backend settlement policy”完成，禁止在现有图片函数旁复制一套 voice 分支。

## 10. UAT 前的架构门禁

只有以下全部通过，才允许打 Windows UAT 包：

1. 正常文字、语音、图片混合会话完整入库并完成 Brain 回复。
2. 语音点击后、图片复制后、Vision 返回后、ingest 前分别强杀进程，重启不重复昂贵动作且事实最终结算。
3. 恢复期间短码暂时 OCR 缺失、`binding_failed/unbound/degraded` 不丢事实；
   原身份可信时无需打开微信即可 fact_only 结算，身份暂不可证时保持 retry_later。
4. 短码确认移除或会话关闭后，旧事实通过 `fact_settlement` 入库但不推进状态机、不启动 Brain。
5. Worker 所有权变化或身份冲突时形成 `technical_terminal`，不把事实写到错误会话。
6. Vision 缺配置时，历史 sent_ack、Outbox 和无需 UI 的事实结算仍可完成；新的 C2 图片流程保持禁止。
7. 暂停监听时不做微信 UI 动作，但已有 Outbox 和事实结算继续。
8. 语音和图片使用同一恢复协调器、同一状态表和同一表驱动测试，不存在图片专用业务分支。
9. 所有 completed/failed 集合单调增加；任何恢复路径都不能把已完成事实改成 `not_required`。
10. `sent_ack` 未确认、消息 Outbox 未确认或媒体事实未结算时，C1/C2/C3 均不能开始新的微信动作。

## 11. 实施顺序

1. 架构师先同步主技术手册、接口合同和 PUML，本文件是本轮唯一恢复口径。
2. 后端先实现恢复决定、结算 token、`fact_settlement` 和状态机隔离。
3. 客户端再把 image 专用恢复重构为 voice/image 共用协调器，并补齐语音可重放观察。
4. 三层共用合同样例和表驱动测试后，再做 Windows 故障注入回归。
5. 测试通过后才能升级版本和打包。
