## 二、本次主要修改

### 1. OmniAuto、Worker、后端统一为同一套 C2 V3 规则

以前三层会分别猜测消息角色、消息类型和语音归属，容易出现同一条消息在不同层被解释成不同结果。

V16.86 改为：

```text
OmniAuto：只识别页面结构和事实
Worker：唯一负责生成最终消息
后端：只校验并保存，不重新猜测
```

三层共同使用 `c2_contract_v3.json`，角色、类型、状态和来源字段只有一套定义。

### 2. 语音识别使用气泡、头像和转写组合结构

- 左侧灰色语音气泡与同行左头像绑定为 `customer`。
- 右侧绿色语音气泡与同行右头像绑定为 `self`。
- 语音转出的灰色文字必须绑定到对应语音 anchor，继承原语音角色。
- 普通文字不会因为正文、距离或页面位置相似而被改成语音。
- OCR 即使把右侧 `4"` 识别成 `4" (c`，仍应由气泡和头像结构发现这条 self 语音。
- 只处理当前屏幕仍可见的语音；转写后被顶出屏幕的语音本轮不追、不滚动。

### 3. Worker 成为唯一消息规范化入口

- 普通文字只从结构化 text observation 生成。
- voice 只从已确认并绑定到 anchor 的真实转写结果生成。
- 同一来源不能同时生成 text 和 voice。
- 转写展开文字不能再次作为普通文字入库。
- 不再使用正文正则、宽松距离或后端清洗重新修改角色和类型。

### 4. 停止监听支持执行中取消

- 定位、初读、语音转写、会话复核和最终读取过程中都会复查 `read-targets`。
- 目标停止后，正在运行的 sidecar 会被终止，不再继续操作微信或上报消息。
- 后端增加独立授权版本；旧任务即使晚到，也会被拒绝入库。
- 普通首屏扫描不会改变授权版本，不会误杀正常读取。

## 三、本轮重点测试

### 场景 A：customer 与 self 两侧语音

当前屏幕同时准备：

- 至少 2 条左侧 customer 未转写语音。
- 至少 1 条右侧 self/sales 未转写语音。
- 至少 2 条普通文字，左右两侧各一条更好。

预期：

- 当前屏幕内语音逐条完成真实转写。
- customer 语音上报为 `customer + voice`。
- self/sales 语音上报为 `self + voice`。
- voice 正文是转写文字，不是 `4"`、`(c`、菜单文字或其他 UI 文本。
- 普通文字保持 `text`，不会被改成 voice。

### 场景 B：同一语音不得重复操作或重复入库

观察语音处理全过程，并让监听继续运行至少两轮。

预期：

- 已成功转写的语音不会再次被右键。
- 不点击头像，不出现“拍一拍”。
- 不使用 Esc 关闭菜单，不导致微信窗口消失。
- 同一语音只产生一条 voice 事件。
- 同一语音不能同时产生 text 和 voice。
- 第二轮读取不得重复入库第一轮消息。

### 场景 C：页面变化与当前屏幕边界

准备多条语音，使第一条转写展开后页面产生轻微位移。

预期：

- 不主动滚动页面寻找屏外语音。
- 重新截图后按新的页面结构定位下一条仍可见语音。
- 被顶出当前屏幕的语音允许留到后续自然可见时处理，不算本轮漏转。
- 已转出的文字必须继续绑定原语音，不能绑定到相邻语音。

### 场景 D：停止监听收口

在以下两个时机分别测试一次停止监听：

1. Worker 已获取目标但尚未开始语音转写。
2. Worker 正在执行语音转写。

预期：

- 停止后该目标不再进入新的 `target_chat_locating`、`visible_hit_message_read` 或 `voice_transcribe_current_chat`。
- 已在执行的 sidecar 被取消，不继续点击微信。
- 停止后新增 `message_events=0`。
- 最终 UI 锁释放，`locked=false`。

注意：Worker 仍处于“开始接单”状态时，常驻 `first_screen_session_scan` 可以继续运行。它只扫描第一屏会话列表，不等于继续读取已停止的 C2 目标，不能单独据此判失败。

## 四、通过标准

本轮至少满足以下条件才能判 C2 通过：

| 验收项 | 通过标准 |
|---|---|
| customer 语音 | 至少 1 条真实转写并以 `customer + voice` 入库 |
| self/sales 语音 | 至少 1 条真实转写并以 `self + voice` 入库 |
| 转写正文 | 为可消费的真实文本，不含时长占位符、菜单或 OCR UI 噪声 |
| 类型隔离 | 同一来源只能有一种最终类型，展开文字不重复作为 text 入库 |
| 角色一致 | `sender_role`、消息信封角色、头像侧和 voice anchor 角色一致 |
| 完成状态 | 成功语音为 completed；不得把未确认语音伪装成 completed |
| 去重 | 同轮、跨轮均不重复入库同一消息 |
| 页面操作 | 不滚动、不点头像、不重复右键成功语音、不使用 Esc 导致窗口消失 |
| 停止收口 | 目标停止后无新定位、读取、转写和入库，锁最终释放 |

如果 customer 或 self 任一侧本轮没有准备新语音，应记录为“未覆盖”，不能把未覆盖写成该侧失败，也不能据此判完整 C2 通过。

## 五、缺陷反馈必须附带的证据

如果不通过，请同时提供：

1. 开始监听、出现问题、停止监听的北京时间，精确到秒。
2. 肉眼看到的最后 3 至 5 个操作，例如右键了哪条语音、点击了什么菜单、是否点到头像。
3. 最终微信窗口截图。
4. 对应时间范围的 Windows 日志压缩包。
5. 新增 `message_events` 明细：`message_id/source_message_key/sender_role/message_type/content/item_state/flow_state`。
6. 相关 `quality_flags`、错误码及 Worker 心跳步骤。

测试结论应区分：

```text
功能失败：准备了对应数据，但结果错误。
未覆盖：本轮没有对应 customer/self 新语音，无法验证。
停止后正常首屏扫描：允许，不等于目标读取尾随。
停止后目标定位/读取/转写：不允许，属于收口失败。
```
