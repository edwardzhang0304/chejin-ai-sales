# C2 V16.100 文字与语音顺序专项首轮结果

## 1. 修正结论

**结论：不通过。发现 1 个 P0 阻断问题，表现为两个关联结果：已转写语音漏入库，最终统一排序未完成。**

初始画面中的两条 8 秒语音在 23 秒语音展开转写正文后被顶出当前屏幕。按照“不主动滚动读取屏幕外语音”的业务规则，这两条 8 秒语音不属于最终画面的处理范围，不判定为漏转。

本轮真正的问题是：23 秒语音仍在最终画面内且已成功展开转写正文，但后端没有对应 voice 事件；客户端随后只上报 3 条文字，位置为 `screen_order=1、3、4`，并且全部标记为 `initial_read`，没有形成完整 `final_read` 顺序。

## 4. 缺陷记录

### BUG-C2-V16100-ORDER-001

**标题：** 可见语音已成功转写但未绑定回 voice 事件，客户端以 initial_read 部分上报文字并留下顺序空洞。

**严重等级：** P0

**前置条件：**

- V16.100 Worker。
- private 会话 `CJONE001`。
- 当前屏幕包含文字和多条未转写语音。
- 语音展开允许造成自然页面位移，但禁止主动滚动。

**复现步骤：**

1. 打开 `CJONE001`，保持窗口不操作。
2. 开启 C2 read-target。
3. Worker 进入 `voice_transcribe_current_chat`。
4. 23 秒语音成功展开长文本，两条上方 8 秒语音自然移出屏幕。
5. 等待最终读取和 V3 ingest。
6. 查询 `message_events` 的角色、类型、正文和 `message_position`。

**实际结果：**

1. 最终画面仍可见 23 秒语音及完整转写正文。
2. 后端没有任何 voice 事件。
3. 仅入库 3 条文字，`screen_order=1、3、4`。
4. 三条文字均为 `frame_source=initial_read`。
5. 后端 ingest 返回 200，不是接口拒绝。

**预期结果：**

1. 23 秒语音稳定绑定为 `customer + voice + 完整转写正文`。
2. 最终 V3 数组按最终画面输出 4 条消息。
3. `screen_order` 连续为 `1、2、3、4`。
4. 语音转写后的权威消息位置使用 `frame_source=final_read`。
5. 不处理已经移出屏幕的两条 8 秒语音，也不主动滚动寻找。

**影响范围：** 已成功转写的客户语音数据丢失；后端只保留部分文字，最终业务消息顺序不完整，无法支持后续 AI 判断和上线验收。

## 5. 开发修复要求

1. 转写后最终读取必须识别已展开语音，并用稳定 anchor 将转写正文绑定回原 voice 槽位。
2. 已发生语音转写时，不得退回 `initial_read` 部分上报。
3. 统一排序完成前不得提交缺少可见 voice 槽位的部分 V3 数组。
4. 最终数组应为 `self text -> customer voice -> self text -> customer text`。
5. 保持“不主动滚动、不处理最终画面外语音”的现有规则。
