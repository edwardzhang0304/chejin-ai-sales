# AI智能客服售前跟进系统 PRD

版本：v0.9.6

日期：2026-08-14

产品范围：C0—C4、运营后台登录、第一期车辆管理/Product Master、人工接管与飞书通知。

当前唯一产品口径：运营录入并分配客户，Windows Worker 在服务端授权下操作微信，服务端统一完成消息事实、AI 回复、召回、人工接管和通知。会话转人工后，服务端通过车金统一飞书应用机器人立即且至多一次通知该会话所属销售；不为销售分别配置机器人。

---


## 1. 当前系统要解决什么问题

车金要做的是一个售前跟进系统。产品按 C0-C4 分段：

1. 运营把客户录进系统。
2. 系统按轮询规则分给销售。
3. 销售绑定对应的 Windows Worker。
4. Worker 在商家电脑上操作微信，给客户发送添加通讯录邀请。
5. Worker 把微信里的文字、语音和图片事实同步回服务端。
6. 服务端确认消息归属，调用 AI 大脑和 Guard 决定回复、等待或转人工。
7. Worker 只发送服务端已经批准的回复。

当前底线是：C0 能把客户分配清楚，C1 能把添加通讯录邀请发出去，C2 能把文字、语音和图片变成服务端可信事实，C3 能在发送前完成最新消息复核并防止重复或过期回复。C4 召回必须先确认客户没有新消息，不能到期直接发送。

## 2. 技术方案分段口径

| 分段 | 白话说明 | 当前 PRD 口径 |
|---|---|---|
| C0 线索入库与分配 | 运营把客户录入系统，系统去重、分销售、生成加好友任务 | 当前做 |
| C1 add_friend | Worker 操作微信搜索客户、写客户短码、发送添加通讯录邀请 | 当前做 |
| C2 会话绑定/微信监听 | Worker 按授权读取 private 单聊，将文字、语音和图片按统一顺序、稳定身份和去重规则入库 | 当前范围 |
| C3 AI 回复发送 | 消息入库后，服务端 AI 大脑生成回复，经 Guard 审核后生成 reply_action，再创建 chat_reply 任务由 Worker 发送 | 当前范围 |
| C4 召回/人工跟进 | 召回到期后先读取微信事实；确认无新客户消息后创建 `trigger_type=recall` 的批次和 `chat_reply` | 当前范围 |
| 车辆管理/Product Master | 运营维护真实车辆、图片和上下架状态，服务端只向客服提供已上架车辆的客户可用字段 | 第一期当前做 |

说明：

- C2 是 Worker 运行时事实采集能力，不进入统一任务中心。
- C2 不定义为 `task_type`，不创建 `session_scan`、`message_ingest` 这类任务。
- 统一任务中心只承接需要执行和追踪的业务任务，当前核心是 C1 `add_friend` 和 C3/C4 共用的 `chat_reply`；召回不再新增 `follow_up` 任务类型。
- C2 `messages/ingest` 不直接下发发送动作；它可以返回当前 `message_batch`，由同一会话流程继续等待服务端 Brain/Guard 终态。
- C2 定向读取目标必须包含 `conversation_id + remark_code`。定向读取确认客户靠服务端会话 ID 和客户短码双重校验，`display_name` 只是微信展示名，只能辅助定位，不能作为客户身份主依据。
- C2 统一采集文字、语音和图片事实：语音使用微信自带“转文字”并以 `message_type=voice` 入库；图片只在 Worker 内存中调用 Vision，原图不落盘、不上传服务端。
- 语音消息识别不等于 AI 语音回复，不做语音内容智能总结，不接外部 ASR，不改变 C3/C4 范围。
- OmniAuto 在本系统里不是单一 RPA 概念：服务端复用其 AI 大脑、RAG、Guard 和回复编排能力；Worker 端复用其 RPA Sidecar 操作本机微信。
- AI 大脑在服务端。Worker 只负责读取微信事实、上报消息、领取已批准的任务并执行，不自己调用大模型，不自己判断是否回复，也不自己决定回复内容。
- C3 的完整产品链路是：`消息入库 -> 服务端 AI 大脑生成回复 -> Guard 审核 -> 生成 reply_action -> 创建 chat_reply 任务 -> Worker 在当前会话内复核并发送微信消息`。
- C3 不是“模型自己决定一切”。模型只输出结构化建议，最终动作由服务端按会话状态、业务规则、风控、RAG 证据、Guard 结果和配置阈值统一决定。
- C3 发送前必须做 `pre_send_refresh`。如果发送前发现客户新消息，旧 `reply_action` 变为 `superseded`，不得继续发送旧回复。
- C4 召回到期不得直接创建或发送任务，必须先进入 `recall_precheck`；确认无新消息后创建 `trigger_type=recall` 的批次，最终仍使用 `chat_reply` 发送。
- `watching` 不作为会话主状态；等待类会话统一用 `waiting_user_reply / recalled_waiting_user / sales_replied_waiting_user` 加规则字段表达。

## 5. 总体业务流程

```text
C0:
运营新增客户
-> 系统用手机号去重
-> 系统按销售轮询规则分配
-> 服务端创建 add_friend 任务

C1:
-> Windows Worker 领取任务
-> Worker 调用 OmniAuto 操作微信
-> 搜索手机号/微信号
-> 写入客户短码
-> 发送添加通讯录邀请
-> 服务端记录任务结果

C2:
-> 第一屏主动扫描
-> 第一屏命中会话优先读取
-> 服务端按状态机返回定向读取目标
-> 识别客户短码并绑定 lead / conversation / sales / worker
-> 同步确认会话为 private 且 authorization_revision 有效
-> 读取当前屏文字、语音和图片
-> 语音必要时调用微信自带转文字；图片在本机内存调用 Vision
-> 按统一 screen_order 和稳定消息身份去重入库

C3:
-> 服务端形成 message_batch
-> OmniAuto Brain + RAG 生成候选回复
-> Guard 审核
-> 生成 reply_action 和 chat_reply 任务
-> Worker 保持当前会话，在发送前执行 pre_send_refresh
-> 没有新消息才发送；发现新消息则旧 reply_action=superseded
-> 上报 sent_ack 后结束本次单会话事务

C4:
-> 到期先进入 recall_precheck
-> Worker 定向读取微信事实
-> 确认无客户新消息后创建 trigger_type=recall 的 message_batch
-> Brain/Guard 通过后仍创建 chat_reply 任务发送

车辆管理:
运营新增车辆或上传 Excel
-> 系统先校验并预览，不直接写入
-> 运营确认后整批导入
-> 新车辆默认下架
-> 运营补齐公开售价和至少一张图片
-> 上架后才进入客服车辆查询和回复范围
```

## 6. 当前范围和不做范围

### 6.1 当前做

- 运营后台：指定账号登录、登录会话保持、会话失效和退出登录。
- C0：人工新增客户、手机号强去重、重复录入备注追加。
- C0：销售轮询分配、销售启用/停用、销售绑定/更换/清空 Worker。
- C0：Worker 新增、启用、停用、重置绑定。
- C1：任务中心 add_friend 任务列表和任务详情。
- C1：Windows Worker 绑定、心跳、开始接单、暂停接单。
- C1：Worker 领取 add_friend 任务，调用 OmniAuto 执行微信加好友。
- C1：客户短码写入微信备注，add_friend 结果和失败原因回传。
- C2：第一屏主动扫描、第一屏命中优先读取、状态机定向读取、短码识别、private 单聊准入和 V3 授权。
- C2：文字、语音和图片使用统一消息顺序、稳定消息身份、去重入库和异常事实结算。
- C2：语音调用微信自带转文字；图片仅在 Worker 进程内存调用 Vision，原图不落盘、不上传服务端。
- C2：必要的后台绑定、监听、消息类型、处理结果和错误原因展示。
- C3：服务端 OmniAuto Brain、RAG、Evidence Pack、Guard、reply_action 和 chat_reply 链路。
- C3：Worker 在当前单会话内执行发送前复核、发送、sent_ack 和防重复发送。
- 车辆管理：车辆列表、搜索、详情、新增、编辑、图片上传/排序/删除、上架和下架。
- 车辆管理：Excel 模板下载、上传、预览校验和整批确认导入。
- 车辆管理：客户可用字段与内部字段隔离，关键操作写入操作日志。
- 通用：操作日志和必要审计。

### 6.2 当前不做

- 不让 Worker 自己调用大模型、生成或改写回复内容。

- 不上传或保存微信图片原图，不新增图片专用上传接口或图片任务。
- 不把群聊或会话类型不明确的会话降级为 private 处理。
- 不做旧的多屏滚动补偿扫描。
- 不新增召回专用 `follow_up` 任务或召回专用模型。
- 不为每个销售分别配置飞书机器人，不在运营后台输入机器人 ID 或 `open_id`。
- 飞书通知不做交互按钮、超时二次提醒、人工补发和复杂通知规则。
- 不做抖音小风车 API。
- 不做销售移动端。
- 不做 Mac Worker。
- 不做独立知识规则页面或复杂 AI 工作台。
- 不做 AI 自动生成车辆资料。
- 不做大风车或其他外部车源 API 自动同步。
- 不通过 Excel 导入车辆图片。

- 不做复杂权限管理、角色分级、只读账号和模块权限配置页。
- 不做自助注册、短信验证码、第三方登录和自助找回密码。

### 6.3 运营后台登录

一句话规则：未登录用户不得查看或操作后台数据；指定账号登录成功后，拥有运营后台全部功能权限。

账号规则：

- 第一期只使用“账号 + 密码”登录。
- 账号由管理员或实施人员在服务端预先创建，登录页不提供注册入口。
- 账号必须唯一且处于启用状态；停用账号不能登录。
- 所有能登录的账号权限相同，均可访问并操作全部后台模块。
- 账号创建、停用和密码重置暂不做后台页面，由服务端或实施工具处理。

登录页字段：

| 项目 | 规则 |
|---|---|
| 账号 | 必填，输入后去掉首尾空格 |
| 密码 | 必填，默认隐藏，支持显示/隐藏 |
| 登录按钮 | 未填完时不提交；提交后显示加载并防止重复点击 |

登录结果：

- 登录成功：进入后台默认空白工作区，不自动打开第一个模块。
- 账号或密码错误：统一提示“账号或密码错误”，不告知账号是否存在。
- 账号停用：提示“账号已停用，请联系管理员”。
- 网络或服务异常：提示“暂时无法登录，请稍后重试”。

会话和退出：

- 会话有效期内刷新页面不要求重新登录。
- 会话失效或账号被停用时，返回登录页并提示“登录已失效，请重新登录”。
- 登录后在左侧导航底部展示当前账号入口，点击可退出登录。
- 退出后清除登录会话并返回登录页；浏览器后退不得重新查看后台数据。
- 所有后台数据接口都必须由服务端校验登录状态，不能只在前端隐藏页面。
- 密码不得明文存储，不得出现在 URL、操作日志和错误文案中。

## 7. 线索管理

### 7.1 模块说明

线索就是客户售前跟进记录。运营先把客户录进系统，系统检查手机号是否重复，再分配给销售。

### 7.2 新增客户字段

| 字段 | 是否必填 | 说明 |
|---|---|---|
| 客户名称 | 是 | 客户显示名 |
| 手机号 | 是 | 中国大陆 11 位手机号；作为去重主依据 |
| 微信号 | 否 | 客户微信号或运营已知的微信信息 |
| 邮箱 | 否 | 客户邮箱 |
| 备注 | 否 | 客户需求、车型、预算等 |
| 自定义信息 | 否 | 保留自定义字段能力 |

规则：

- 手机号必须填写。
- 手机号、微信号、邮箱各只保存一个值，新增客户弹窗不提供“添加多条联系方式”。
- 手机号重复时，不允许新建第二条有效线索。
- 重复手机号如填写备注，备注追加到原线索备注记录，不覆盖原备注。
- 第一阶段来源固定为人工录入，不做来源管理。

### 7.3 线索状态

| 状态 | 页面文案 | 含义 |
|---|---|---|
| `unassigned` | 未分配 | 没有可用销售或分配失败 |
| `assigned` | 已分配 | 已分配给销售 |
| `invalid` | 无效 | 运营标记为无效线索 |

规则：

- 不做物理删除。
- 不再设计归档状态。
- 无效线索可以恢复。
- 恢复后如有销售，回到已分配；如无销售，回到未分配。

### 7.4 重复录入

重复判断：

- 以手机号为强去重依据。
- 重复时提示已有线索、重复次数、重复日期。
- 重复录入要记录操作人、时间、本次备注。

提示示例：

```text
该手机号已存在，不能重复新建。
已重复录入 3 次，日期：2026-06-01、2026-06-08、2026-06-22。
本次备注已追加到原线索。
```

### 7.5 线索详情

线索详情展示：

- 客户基础信息。
- 联系方式。
- 当前销售。
- 当前状态。
- 备注记录。
- 重复录入记录。
- 分配记录。
- 任务链路。
- 会话绑定状态。
- 最近消息入库时间。

线索详情不提供“编辑线索”作为主操作；当前没有明确使用场景，避免增加无效入口。

## 8. 销售管理

### 8.1 模块说明

销售管理用来维护谁可以接收线索，以及这个销售对应哪台 Worker。

### 8.2 销售字段

| 字段 | 说明 |
|---|---|
| 销售姓名 | 必填 |
| 手机号 | 必填；用于匹配销售在车金飞书应用下的接收人身份 |
| 微信号 | 选填 |
| 状态 | 启用 / 停用 |
| Worker | 选填，可后续绑定 |
| 轮询排序 | 用于销售轮询分配 |

规则：

- 启用销售参与线索轮询。
- 停用销售不再分配新线索，历史线索不变。
- 销售手机号必须与其飞书企业成员账号绑定的手机号一致。
- 新增或修改销售手机号后，由服务端通过车金统一飞书应用匹配该销售的应用内 `open_id`。
- `open_id` 不由运营人员查找或录入，也不在销售列表和详情中展示。
- 同一个人在不同飞书应用下的 `open_id` 不同，只允许使用车金当前发送应用获取的 `open_id`。
- 新增销售时 Worker 可暂不绑定。
- 绑定或更换 Worker 在销售详情抽屉内编辑，不另开复杂页面。
- 离线但启用的 Worker 可以绑定；离线只影响领取任务，不影响归属。
- 已停用 Worker 不可绑定。
- 已绑定其他销售的 Worker 不可重复绑定。

### 8.3 销售详情

销售详情展示：

- 基础信息。
- 状态。
- 当前 Worker。
- Worker 在线 / 离线。
- 今日分配。
- 阻塞任务。

点击“编辑销售”后，在详情抽屉内直接编辑字段。

## 9. Worker 管理

### 9.1 模块说明

Worker 是商家电脑上的执行终端。后台先创建 Worker，系统生成 Worker ID 和 Worker Token，客户端用这两个信息完成绑定。

### 9.2 Worker 字段

| 字段 | 说明 |
|---|---|
| Worker ID | 服务端生成的唯一标识 |
| Worker Token | 客户端绑定凭证，只在详情展示 |
| Worker 名称 | 方便运营识别 |
| 启用状态 | 启用 / 停用 |
| 绑定状态 | 未绑定 / 已绑定客户端 |
| 在线状态 | 在线 / 离线 |
| 运行状态 | 空闲 / 忙碌 / 暂停接单 |
| 当前销售 | 当前绑定的销售 |
| 当前任务 | 正在执行的任务 |
| 最近心跳 | 最近一次客户端心跳时间 |

### 9.3 创建和绑定

规则：

- 新增 Worker 后，服务端生成 Worker ID 和 Worker Token。
- 新增成功后自动打开 Worker 详情，方便复制 ID 和 Token。
- Worker Token 不在列表展示，只在详情展示。
- 客户端首次启动时输入 Worker ID + Worker Token 完成绑定。
- 同一个 Worker 只能绑定一个客户端实例。
- 客户端绑定成功后，本机保存绑定信息；下次打开自动校验后进入工作台。

### 9.4 重置绑定

重置绑定用于换电脑或清掉旧客户端绑定。

规则：

- 后台 Worker 详情提供“重置绑定”。
- 重置后旧客户端不能继续心跳和领取任务。
- 重置时生成新的 Worker Token。
- 如果当前存在 running 任务，页面强提示，但允许继续重置。
- 重置绑定不自动取消、失败或改派 running 任务，任务需要在任务中心处理。

## 10. 任务中心

### 10.1 模块说明

任务中心是运营看任务状态和异常的地方。服务端负责任务调度，任务中心负责让运营看见任务发生了什么，并处理需要人工介入的情况。

### 10.2 任务类型

当前主要任务：

| task_type | 页面文案 | 当前是否做 |
|---|---|---|
| `add_friend` | 添加通讯录邀请 | C1 做 |
| `chat_reply` | 微信消息发送 | C3 已使用；普通回复、好友开场和召回共用，来源由 `trigger_type` 区分 |

说明：召回不再使用独立 `follow_up` 任务。召回前先执行 `recall_precheck`，通过后形成 `trigger_type=recall` 的消息批次，最终仍创建 `chat_reply`。

C2 注意：

- C2 的 `session_scan`、`message_ingest`、`wechat_binding` 不允许定义为 `task_type`。
- C2 的语音转写、图片理解和事实结算也不定义为独立任务类型。
- C2 不进入统一任务中心。
- C2 数据写入 `wechat_session_bindings`、`message_events` 和会话监听状态。
- 后台可以在线索详情、Worker 详情或必要状态区展示 C2 结果，但不把 C2 当任务处理。

### 10.3 任务状态

| status | 页面文案 | 含义 |
|---|---|---|
| `blocked` | 阻塞 | 任务已创建，但条件不满足，不能领取 |
| `pending` | 待处理 | 可以被 Worker 领取 |
| `running` | 处理中 | Worker 已领取，正在处理 |
| `completed` | 已完成 | 任务完成，具体结果看 result_code |
| `failed` | 失败 | 执行失败，具体原因看 error_code |
| `cancelled` | 已取消 | 人工取消 |

规则：

- `status` 只表示任务生命周期。
- `invite_sent` 不是 status，只能是 result_code。
- `already_friend` 是完成结果，不是失败。
- 终态任务不得再次领取。
- failed / cancelled 后如需重试，创建新任务，原任务保留。

### 10.4 业务结果

add_friend：

| result_code | 页面文案 | 说明 |
|---|---|---|
| `invite_sent` | 已发送添加通讯录邀请 | 不代表客户已同意好友申请 |
| `already_friend` | 已是好友 | 不需要再发送好友申请 |

chat_reply：

| result_code | 页面文案 | 说明 |
|---|---|---|
| `chat_reply_sent` | 微信消息已发送 | 具体是客户回复、好友开场还是召回，由关联批次的 `trigger_type` 展示 |
| `skipped_by_rule` | 已按规则跳过 | 会话状态或规则已不允许发送，不等于执行失败 |

`trigger_type` 页面文案：

| trigger_type | 页面文案 |
|---|---|
| `customer_message` | 客户消息回复 |
| `friend_welcome` | 好友开场 |
| `recall` | 客户召回 |

### 10.5 失败原因

| error_code | 页面文案 |
|---|---|
| `PHONE_NOT_FOUND` | 手机号未找到客户 |
| `WECHAT_ID_NOT_FOUND` | 微信号未找到客户 |
| `PHONE_INVALID` | 手机号无效 |
| `ADD_CONTACT_ENTRY_NOT_FOUND` | 添加通讯录入口未找到 |
| `REMARK_WRITE_FAILED` | 客户短码写入失败 |
| `INVITE_SEND_FAILED` | 邀请发送失败 |
| `WECHAT_WINDOW_NOT_FOUND` | 微信窗口未找到 |
| `RPA_COMPONENT_NOT_READY` | 自动化组件不可用 |
| `ACCOUNT_RESTRICTED` | 账号受限 |
| `OPERATION_TOO_FREQUENT` | 操作过于频繁 |
| `NETWORK_ERROR` | 网络异常 |
| `WORKER_INTERRUPTED` | 执行中断 |
| `REPLY_ACTION_EXPIRED` | 回复已过期，未发送 |
| `REPLY_ACTION_SUPERSEDED` | 发送前发现客户新消息，旧回复已作废 |
| `REPLY_ACTION_CLAIM_CONFLICT` | 回复发送权已被其他执行方领取 |
| `SEND_TEXT_HASH_MISMATCH` | 实际发送内容与服务端批准内容不一致 |
| `SEND_RESULT_UNKNOWN` | 发送结果无法确认，禁止自动补发 |
| `OTHER` | 其他 |

### 10.6 操作规则

| 状态 | 可用操作 |
|---|---|
| blocked | 处理阻塞、取消任务、补充备注 |
| pending | 取消任务、补充备注 |
| running | 查看执行方、取消任务、补充备注 |
| completed | 查看结果、查看执行方、补充备注 |
| failed | 重新创建任务、查看执行方、补充备注 |
| cancelled | 查看取消信息、重新创建任务、补充备注 |

扩展动作：

- `add_friend + PHONE_NOT_FOUND` 可标记线索无效。
- `SALES_WORKER_NOT_BOUND` 跳转销售详情，进入编辑态并聚焦 Worker 字段。
- completed 默认不允许重新创建任务。

### 10.7 任务事件和操作日志边界

| 类型 | 说明 | 展示位置 |
|---|---|---|
| task_events | 任务自己怎么流转 | 任务详情状态流转 |
| operation_logs | 谁在后台做了什么 | 操作日志模块 |

同一个动作可能同时写两类记录。例如运营取消任务：任务事件记录任务变成 cancelled，操作日志记录谁取消了任务。

## 11. Windows Worker 客户端

### 11.1 模块说明

Worker 客户端安装在商家 Windows 电脑上。商家只看到一个“车金 Worker 客户端”。在 Worker 端，OmniAuto 以 RPA Sidecar 形式被复用，用来操作本机微信；它不作为独立产品展示，也不需要商家单独操作。

### 11.2 客户端要做什么

- 绑定 Worker 身份。
- 上报心跳。
- 开始接单 / 暂停接单。
- 按自动接单时段控制是否领取任务。
- 领取 add_friend 任务。
- 调用 OmniAuto 操作本机微信。
- 展示当前运行过程。
- 上报执行步骤、结果、失败原因。
- 保存本机执行日志。
- 失败时上传关键截图证据。
- C2 阶段调用 OmniAuto sessions/messages 能力扫描会话和读取消息。
- C2 阶段按授权处理文字、语音和图片；图片原图只在当前进程内存短暂存在。
- C3 阶段保持当前会话和 UI 锁，等待服务端 Brain/Guard 结果，领取并发送当前批次的 `chat_reply`。
- 发送前执行 `pre_send_refresh`，输入前和点击前复核消息序列。
- 发送后将 `sent_ack` 可靠写入本地 Outbox，再上报服务端；结果未知时禁止自动补发。

### 11.3 启动和接单

规则：

- 首次绑定成功后默认暂停接单，不自动领取任务。
- 点击“开始接单”后才领取 pending 任务。
- 点击“暂停接单”后不再领取新任务。
- 如果暂停时已有 running 任务，当前任务继续执行到完成或失败，之后停止领取。
- 关闭客户端或断线时，running 任务不自动失败；超过 10 分钟未恢复时任务中心提示执行方离线。

### 11.4 自动接单时段

规则：

- 默认关闭。
- 开启后，每天支持一个接单时间段。
- 支持跨天，例如 21:00 到次日 08:00。
- 非接单时段客户端仍在线，但 run_status 为 paused，不领取新任务。
- 到结束时间时不打断当前 running 任务，任务完成或失败后暂停接单。

### 11.5 统一工作台和当前运行过程

产品页面收口为四类：

1. 首次绑定页。
2. 统一工作台。
3. 设置页和接单时段设置页。
4. 本机执行日志明细页。

绑定页规则：

- 主标题为“绑定 Worker”。
- 只展示 Worker ID、Worker Token 和绑定按钮。
- 不展示“输入后台生成的 Worker ID 和 Token”等辅助说明。
- 首次绑定成功后进入工作台；本机保留有效绑定时，下次启动不重复绑定。

工作台固定结构：

1. 顶部显示服务端连接状态和最近心跳时间。
2. 无业务任务时显示绑定销售、接单状态、自动化组件状态和微信状态。
3. 有业务任务时显示任务类型、客户和归属销售等必要信息。
4. 中间统一显示“当前运行过程”。
5. 底部显示当前接单状态和“开始接单 / 暂停接单”操作。

当前运行过程以“一次客户处理事务不断链”为主规则。首屏扫描、定向读取、媒体处理、服务端判断和
AI 回复不再切换成三套互相割裂的过程画面；同一客户事务内，客户端持续追加已经真实发生的节点：

```text
发现目标客户（第一屏命中 / 状态机定向读取）
-> 定位并确认客户会话
-> 读取客户最新消息
-> 识别语音消息（实际发生才展示）
-> 理解图片消息（实际发生才展示）
-> 消息已回传服务端
-> 服务端正在判断处理方式
-> 生成并审核 AI 回复（实际进入 AI 回复才展示）
-> 发送前复核
-> 发送微信消息
-> 确认并回传结果
```

链路按实际结果结束，不补画未发生节点：没有新消息显示“本次检查完成”；服务端判定无需回复、
转人工、AI 回复成功或处理失败时，分别停在对应终态。`add_friend` 仍是独立业务流程，不并入客户
读取与回复事务。

只有首屏扫描尚未命中具体客户时，按以下无客户过程独立展示：

```text
扫描微信会话第一屏 -> 未发现待处理客户 -> 等待下一轮检查
```

首屏一旦发现目标客户，即从“发现目标客户”开始进入该客户的连续事务，不再另起定向读取或 AI 回复画面。

多个运行节点超过可视高度时必须支持鼠标滚轮、触控板、键盘和拖动滚动；滚动条使用窄圆角中性灰滑块，
常态低干扰、悬停和拖动时适度增强，不使用粗重的浏览器默认样式。滚动条只改变展示位置，不改变运行状态。

无具体客户事务时的显示优先级：

```text
业务任务
> 状态机定向读取
> 第一屏主动扫描
> 等待下一轮检查
```

通用展示规则：

- 只展示 Worker 已经进入的阶段，不展示未到达的未来步骤。
- Worker 调用 OmniAuto 前，可将自己已知的当前阶段直接同步给本地 UI，不需要等待服务端返回。
- OmniAuto 单次调用内部的 OCR、点击、输入等细步骤不伪装成实时进度。
- RPA 调用期间只展示一个真实的阶段级节点，例如“正在执行微信加好友”或“正在发送微信消息”。
- OmniAuto 返回后，客户端可用实际结果补充已发生的详细执行链路。
- 执行中显示运行时长；完成或失败后停止计时。
- 完成或失败结果保留到下一个运行过程开始，不要求人工点击继续。
- 客户端处于暂停接单时，已开始的当前操作继续展示并执行到结束。

无业务任务时：

| 实际状态 | 当前运行过程文案 |
|---|---|
| 本轮无操作 | 等待下一轮检查 |
| 第一屏主动扫描中 | 正在扫描微信会话第一屏 |
| 第一屏扫描完成 | 扫描完成，发现 X 个会话，命中 X 个目标 |
| 状态机定向读取中 | 正在定位并读取目标会话 |
| 定向读取完成 | 读取完成，发现 X 条新消息；无新消息时如实显示 |
| 非接单时段 | 当前不在接单时段 |

AI 回复相关的微信消息发送阶段：

```text
读取客户最新消息
-> 等待服务端生成回复
-> 执行发送前复核
-> 正在发送微信消息
-> 确认并回传结果
```

离线显示规则：

- 服务端不可达是连接异常，不单独换成一套工作台页面。
- 本机仍在执行已开始操作时，保留当前运行过程，不因离线清空。
- 本地执行完成但尚未上报时，显示“执行已完成，等待恢复后回传”。
- 无当前操作时，显示“服务端连接中断，正在尝试恢复”。

原 13 个预览场景继续作为 UI 验收场景，但不代表 13 张独立产品页面。其中两个“暂停接单 + 无任务”使用同一视觉状态。

### 11.6 add_friend 执行链路

执行中只展示 Worker 已知的阶段级进度。OmniAuto 返回后，客户端可根据实际结果展示已发生的详细链路，不展示未到达步骤。

执行中建议阶段：

1. 任务已领取。
2. 正在检查运行环境。
3. 正在执行微信加好友。
4. 正在确认并回传结果。

执行完成后可展示的实际结果步骤：

1. 已领取任务。
2. 正在检查自动化组件。
3. 正在打开微信桌面客户端。
4. 正在搜索手机号。
5. 手机号未找到时，尝试搜索微信号。
6. 正在进入添加通讯录流程。
7. 正在写入客户短码。
8. 正在发送好友申请。
9. 已点击最终“确定”，如仍停留在“添加朋友”页则安全关闭该页；任务完成。或在点击前明确失败。

规则：最终“确定”按钮的物理点击是业务完成点。点击成功且未可靠识别到明确风控/失败提示时，任务记录为 `completed + invite_sent`；如可靠识别到明确失败则按对应 `error_code` 结束。点击后等待约 1—2 秒，只有顶部标题明确仍为“添加朋友”时才点击右上角 X 收尾；正文内容和文字数量不参与判断。微信没有可依赖的“客户已同意”状态；收尾诊断或关闭失败不能把成功点击改成失败，也不增加 `waiting_ui_response` 状态。

### 11.7 客户短码备注规则

客户短码既是系统识别客户的关键标识，也是系统是否继续托管该微信会话的开关。

规则：

- 服务端为客户生成唯一客户短码。
- Worker 领取 add_friend 任务时，任务必须包含客户短码。
- RPA 自动写入微信备注的内容只有客户短码。
- 微信备注名中不自动写入销售说明、客户需求、车型或预算，只写客户短码。
- 好友验证消息与微信备注是两个字段；验证消息使用服务端配置文案，不拼进客户备注。
- 销售后续可以在微信备注里追加人工说明。
- 销售追加说明时必须保留客户短码。
- 只要备注里仍包含客户短码，系统后续就能继续识别和绑定客户。
- 如果短码被删除、改写或无法识别，系统进入异常处理或人工核对。
- 单次 OCR 未识别到短码不能直接关闭托管；必须按复核规则确认短码确实被移除。
- 确认短码被移除后，`Conversation.status=closed`，系统停止自动回复、召回和主动监听，但不把客户标记为拒绝。
- 销售需要恢复系统跟进时，优先恢复该客户原短码，不能直接为同一客户生成第二个有效短码。

示例：

```text
系统自动写入：CJ8F3A2C
销售可改为：CJ8F3A2C 预算15万 看SUV 已到店
不允许改为：预算15万 看SUV 已到店
```

线下好友接入：

- 销售线下自行添加微信好友时，可在控制面生成客户短码和推荐备注名，并创建或关联线索。
- 销售把该短码写入微信备注后，Worker 扫描识别并按正常 private/V3 规则建立会话绑定。
- 该工具只生成/恢复短码，不代替微信加好友，不绕过手机号去重和销售归属规则。
- 该页面能力按后续排期实现；当前不影响 C1 自动加好友主链验收。

### 11.8 失败后的接单策略

| 失败类型 | 示例 | 是否继续接单 |
|---|---|---|
| 单条客户数据型失败 | 手机号找不到、微信号找不到、手机号无效 | 继续下一条 |
| 执行步骤失败 | 添加入口找不到、短码写入失败、邀请发送失败 | 单次继续；连续 3 次停止 |
| 运行环境型失败 | 微信窗口找不到、OmniAuto 不可用、网络异常 | 停止领取 |
| 账号风控型失败 | 账号受限、操作频繁 | 停止领取 |
| 未知型失败 | OTHER | 默认停止 |

### 11.9 日志和截图

规则：

- 本机执行日志放在设置页，不放在工作台首页。
- 本机日志保留最近 30 天，最多 1000 条。
- 成功任务默认不上传截图。
- 失败任务上传关键失败截图。
- 本机失败截图保留 7 天或最多 300 张。
- 服务端失败证据保留 30 天。

## 12. C2：会话绑定与微信监听

### 12.1 模块说明

C2 的目标是把微信里的会话和消息变成服务端可信事实。它不是 AI 回复阶段，也不是任务中心里的任务。

简单说：

```text
先知道这条微信会话是谁
再知道这条消息有没有入库
最后才有资格进入后续 AI 回复
```

### 12.2 C2 做什么

- Worker 调用 OmniAuto sessions 扫描微信当前第一屏。
- 第一屏命中的会话优先读取消息。
- Worker 空闲时拉取服务端按状态机生成的定向读取目标，读取目标必须包含客户短码 `remark_code`。
- 从微信会话标题/备注中识别客户短码，并同步确认会话类型为 `private`。
- 服务端用短码绑定 lead / conversation / sales / worker。
- Worker 只对当前 `authorization_revision` 允许的会话读取消息。
- Worker 将文字、语音和图片放入同一当前屏消息序列，生成稳定 `source_message_key` 和 `dedupe_key`。
- 服务端完成最终去重、事实入库和状态机判断。
- 后台展示绑定状态、监听状态、消息类型、入库结果和错误原因。

### 12.3 C2 读取策略

C2 的正式读取策略由三部分组成：

```text
第一屏主动扫描
-> 第一屏命中优先读取
-> 状态机定向读取
-> private + 当前授权复核
-> 文字/语音/图片统一读取
-> 稳定身份去重入库
```

第一屏主动扫描：

- Worker 只读取微信当前可见会话列表。
- 命中短码、未读提示、预览变化或近期活跃会话时，先上报扫描事实；短码命中本身不是读取授权。
- 同一红点与同一规范化预览只形成一个后端未读代次；该代次已完整读取后，会话行上下移动、红点边框或新扫描编号不得在冷却内重复唤醒。
- 读取代次 N 期间又到达 N+1 时，本轮只能结算 N；N+1 必须保留为待处理。无法仅凭预览证明的重复同文消息不提前唤醒，但到正常冷却时间后仍必须读取。
- 只有命中当前read-target授权且顶部标题确认private的会话才进入第一屏读取队列。
- 第一屏扫描只上报微信事实，不直接判断是否回复，不创建任务。
- read-targets为空时允许继续扫描，但必须清空本地读取队列。

状态机定向读取：

- 服务端根据 conversation 状态、最近消息时间、最近发送时间和召回规则返回读取目标。
- 每个读取目标必须返回 `conversation_id + remark_code + authorization_revision`。
- 定向读取确认客户靠业务身份、顶部private证据和当前授权共同校验。
- `display_name` 只能作为微信展示名辅助定位或页面展示，不能作为客户身份主依据。
- Worker 按服务端给出的目标定向读取，不自行扩大读取范围。
- 定向读取前要去掉本轮第一屏已经处理过的会话，避免重复读取。
- Worker 读取到会话后，必须把读取结果中的短码与目标 `remark_code` 做一致性校验。
- 找不到目标会话、微信不可控或 OCR 低置信时，记录 `error_code`，不做不确定操作。
- 会话列表可能在截图与点击之间自动重排。点击后如果标题明确不含目标短码，必须保持零消息读取、零媒体操作、零入库和零发送；丢弃旧坐标，重新截取安全基线后，在同一授权内最多按目标短码精确搜索一次。
- 恢复定位不再使用新首屏坐标快速路径，必须直接使用服务端下发的目标短码定向搜索，且只允许唯一候选。搜索后仍点错、授权已失效或界面无法恢复时，本轮结束但继续处理其他客户。
- 如果标题已包含目标短码，但明确为群聊或会话类型仍无法确认，这是目标身份不安全，不是列表重排误点；本轮直接结束，不再搜索、不读取、不转写、不识图、不入库。

read-targets 必填字段：

| 字段 | 是否必填 | 产品含义 |
|---|---|---|
| `conversation_id` | 是 | 服务端会话 ID，和 `remark_code` 一起用于客户身份确认 |
| `lead_id` | 是 | 客户线索 ID |
| `sales_id` | 是 | 归属销售 ID |
| `worker_id` | 是 | 应执行读取的 Worker |
| `remark_code` | 是 | 客户短码，和 `conversation_id` 一起用于客户身份确认 |
| `authorization_revision` | 是 | 当前读取授权版本；停止或重授权后旧版本失效 |
| `unread_generation` | 是 | 本次读取票据冻结的后端未读代次；Worker 必须原样带到入库结算 |
| `read_reason` | 是 | 读取原因，例如等待客户回复、召回前确认、转人工后监听 |
| `rpa_session_key` | 否 | 已知微信会话定位信息 |
| `display_name` | 否 | 微信展示名，只能辅助定位和展示 |

读取目标校验规则：

- `conversation_id`、`remark_code` 或 `authorization_revision` 缺失时，不下发为正常读取目标。
- 已绑定会话如果缺失短码，进入异常或待复核，不作为正常读取目标继续读取。
- Worker 读取到的会话短码与目标 `remark_code` 不一致时，不入库为正常客户消息，记录错误并进入待复核。
- 服务端和 Worker 不得仅凭 `display_name`、昵称、头像、手机号尾号等弱特征确认客户身份。

可进入定向读取的典型状态：

| conversation.status | 读取目的 |
|---|---|
| `friend_added` | 新好友刚识别，读取是否已有首条客户消息 |
| `ai_active` | AI 接待中，读取客户新消息 |
| `waiting_user_reply` | 我方已回复，确认客户是否有新消息 |
| `waiting_sales_reply` | 已转人工，确认销售是否已经回复 |
| `sales_replied_waiting_user` | 销售已回复，确认客户是否有新消息 |
| `recalled_waiting_user` | 已召回，确认客户是否有新消息 |
| `recall_precheck` | 召回前确认客户是否没有新消息 |

状态原则：

- `watching` 不作为 conversation 主状态。
- 等待客户回复的场景用 `waiting_user_reply / recalled_waiting_user / sales_replied_waiting_user` 表达。
- 读取频率、优先级、是否可召回由规则字段和服务端调度决定，不新增一个泛化的“观察中”主状态。

单会话串行原则：

- Worker 打开一个已授权会话后，在同一 UI 锁内完成文字、语音、图片读取和事实入库。
- 如果服务端为本批消息启动 C3，Worker 保持当前会话，等待该 `message_batch` 的 Brain/Guard 终态。
- 需要发送时先执行 `pre_send_refresh`，确认没有新客户消息后才领取发送许可并发送。
- 当前会话达到发送成功、明确失败、结果未知、转人工或无需动作等终态后，才释放 UI 锁并处理下一个会话。

### 12.4 C2 边界

- C2 自身只负责微信事实采集，不在 Worker 本地生成 AI 回复。
- C2 `messages/ingest` 不直接返回可发送文本；服务端可以根据本批事实启动 C3。
- `reply_action` 和 `chat_reply` 只能由服务端 C3 创建，Worker 不能自行创建。
- 不创建 `session_scan`、`message_ingest`、`wechat_binding` 任务。
- 不为语音转写、图片理解或事实结算创建独立任务。
- 不进入统一任务中心。
- RAG、模型选择、Guard 和业务决策都在服务端 C3，不在 Worker C2。
- 未绑定会话不得触发 AI 回复。

### 12.5 会话绑定规则

绑定成功必须满足：

- 会话中识别到唯一客户短码。
- 顶部标题同步确认会话为 private；群聊或类型不明确不得准入。
- 短码能匹配唯一有效线索。
- 线索能关联到当前销售。
- 当前 Worker 与销售绑定关系一致，或服务端允许该 Worker 监听该销售会话。
- 不存在冲突的有效会话绑定。

绑定成功后：

- 创建或确认 conversation。
- 建立 lead_id / conversation_id / sales_id / worker_id 关系。
- 记录 rpa_session_key、display_name、row_fingerprint 和最近扫描时间。
- Worker 后续可以读取该会话消息。
- 后续读取仍必须带 `conversation_id + remark_code + authorization_revision` 做身份和授权校验；历史绑定关系不能替代本次校验。

### 12.6 绑定失败和未绑定

| 场景 | 状态 | 处理 |
|---|---|---|
| 没识别到客户短码 | `unbound` | 不进入消息读取主流程 |
| 单次扫描未识别到已有短码 | `degraded` | 保留原绑定，停止本轮正常读取，等待再次确认 |
| 后台明确关闭、客户拒绝，或按复核流程确认短码已被移除 | `disabled` | 停止新的监听和自动动作 |
| 短码格式非法或不存在 | `binding_failed` | 提示核对 |
| 短码匹配不到线索 | `binding_failed` | 提示数据缺失或短码异常 |
| 短码匹配多条线索 | `needs_review` | 人工核对，不自动选择 |
| 线索已绑定其他活跃会话 | `needs_review` | 人工核对 |
| Worker 与销售不匹配 | `binding_failed` | 防止跨销售误绑定 |

规则：

- 未绑定会话不自动回复。
- 未绑定会话不自动创建回复任务。
- 短码丢失后，不用昵称、头像、手机号尾号等弱特征自动绑定。
- 已绑定会话单次缺失短码时进入 `degraded`，不能直接覆盖原有 `bound` 事实或判定销售已删除短码。
- 只有后台明确关闭，或服务端签发只允许检查标题的复核并由两次独立稳定结果确认原短码不存在，才可进入 `disabled`。
- `disabled` 优先级高于其他绑定状态；会话关闭、拒绝或短码移除后，不允许后续扫描自动重新开启监听。

### 12.7 消息入库和去重

规则：

- Worker 只读取服务端允许读取的已绑定会话。
- 服务端允许读取的会话必须具备有效 `remark_code`；缺失短码的会话先走异常或待复核。
- Worker 上报消息事实，不判断业务归属。
- 服务端负责入库和去重。
- 同一条消息必须生成稳定 `source_message_key` 和 `dedupe_key`；页面坐标、扫描轮次和绝对时间不能作为消息主身份。
- 同一 conversation_id + dedupe_key 只能成功入库一次。
- Worker 重启、断网重试、重复扫描不得造成重复消息。
- 重复消息不触发后续任务，不覆盖原消息。
- 文字、语音和图片按最终当前屏从上到下形成统一 `screen_order`，不得把语音转写文字或图片理解结果统一追加到批次末尾。
- `sender_role` 正式值为 `customer / self / system / unknown`；`unknown` 不触发 AI。

事实结算规则：

- 授权撤销只停止新的微信 UI 动作，不能删除动作撤销前已经产生的消息事实。
- 已产生的语音/图片事实可以通过既有消息入库接口以事实结算方式补录。
- 事实结算只保存事实，不推进 Conversation 状态机、不启动 Brain，也不能借机重新操作微信。
- 暂时的 `unbound / binding_failed / needs_review / degraded / paused` 不是永久丢弃事实的理由；身份可信时结算事实，暂时无法证明身份时保留并稍后重试。

### 12.8 C2 语音消息识别

### 12.8.1 模块说明

真实客户可能发微信语音。C2 如果只处理文字，会把“客户已经回复”误判为“客户沉默”，后续可能影响 AI 回复、召回和人工接管判断。

语音能力边界：

- 不做 AI 语音回复。
- 不做语音内容智能总结。
- 不接外部 ASR。
- 不把语音转写做成任务中心任务。

### 12.8.2 主流程

```text
客户或销售发送微信语音
-> Worker 定位已确认会话
-> Worker 同步确认有效短码、private和当前读取授权
-> Worker 首次messages发现未转写语音后，调用 OmniAuto 点击微信自带“转文字”
-> 微信生成转写文本
-> Worker 调用最终messages新截图，复核目标并把文字绑定原语音
-> 服务端按 message_type=voice 入库
-> 后续状态机按发送方和转写结果判断
```

入库规则：

| 字段 | 产品口径 |
|---|---|
| `message_type` | 固定为 `voice` |
| `content` | 微信自带转文字后的文本 |
| `sender_role` | 客户语音为 `customer`；销售侧统一为 `self`；无法确认则 `unknown`且不触发AI |
| `raw_payload.voice_transcription_meta` | 保存父语音anchor、转写状态、截图证据、质量标记等 |

### 12.8.3 状态规则

| 场景 | 处理 |
|---|---|
| 客户语音转写成功 | 按客户新消息处理，`message_type=voice` 入库；后续可进入 C3 判断 |
| 销售手机端发语音且桌面同步成功 | 按销售人工回复处理，本轮不触发 AI，状态进入 `sales_replied_waiting_user`；不自动关闭 `ai_enabled` 硬开关 |
| 客户语音转写失败，且目标客户已确认 | 不触发 AI，不召回，不把语音时长当正文；会话进入 `waiting_sales_reply`，提示人工查看 |
| 客户语音转写失败，但目标客户未确认 | 只记录失败证据，不改变会话主状态 |
| 只识别到“5秒语音”等时长 | 不作为正文，不触发 AI，不召回 |
| 发送方无法确认 | 不触发 AI，记录待复核或失败证据 |

规则：

- 语音转写成功后，系统不得继续把该客户误判为沉默。
- 语音转写失败时，不得自动回复，也不得错误召回。
- 销售侧语音属于人工介入信号，不得触发 AI 自动回复。
- 同一条语音转写文本不得重复入库，也不得重复触发后续判断。
- 语音转写正文不得再作为独立text入库；只能绑定父语音形成一条voice事实。
- `item_state/flow_state` 只描述本轮处理结果，不新增语音任务或数据库业务状态机。

### 12.8.4 后台展示

消息记录需要展示：

- 消息类型：语音。
- 标识文案：语音转文字。
- 转写文本。
- 发送方：客户 / 销售 / 未确认。
- 入库时间。

语音转写失败时，后台文案统一为：

```text
语音转写失败，需人工查看
```

会话详情需要展示：

- 转写失败原因。
- 错误码。
- 截图证据入口。
- 最近一次转写时间。

### 12.8.5 错误码

| error_code | 页面文案 |
|---|---|
| `VOICE_TRANSCRIBE_FAILED` | 语音转写失败，需人工查看 |
| `VOICE_TRANSCRIBE_CLICK_FAILED` | 语音转文字入口点击失败 |
| `VOICE_TRANSCRIBE_LOCK_TIMEOUT` | 语音转写等待超时 |
| `VOICE_TRANSCRIBE_EMPTY` | 未获得可用转写文本 |
| `VOICE_MESSAGE_UNCONFIRMED` | 语音消息发送方或客户身份未确认 |
| `TARGET_NOT_CONFIRMED_FOR_VOICE_TRANSCRIBE` | 目标客户未确认，未执行语音转写 |

### 12.9 C2 图片消息理解

图片与文字、语音属于同一个 C2 会话读取流程，不单独建立图片任务、上传页面或人工传图流程。

主流程：

```text
最终当前屏识别图片气泡
-> 与文字、语音一起确认发送方、稳定消息身份和画面顺序
-> 仅对当前屏新图片执行一次本机内存图片读取和 Vision
-> Vision 结果通过结构校验
-> 按 message_type=image 回填原图片所在顺序并入库
```

产品规则：

- 图片只有明确 `customer` 或 `self` 角色且身份稳定时，才允许执行图片操作；角色为 `unknown` 时不点击、不调用 Vision、不触发 Brain。
- 新图片识别成功时，以 `message_type=image + item_state=completed` 入库，只保存允许展示的文字理解结果。
- 图片技术失败时，以 `message_type=image + item_state=failed` 入库错误码和必要审计，不伪装成文字消息，也不自动重复识别。
- 图片在动作前已被新消息顶出当前屏时，本轮不处理、不上滚追踪；后续自然回到当前屏时再按新老判定处理。
- 已处理、失败或等待上报的图片不得再次执行复制和 Vision；后端未确认时只重传既有 JSON。
- 微信原图只在 Worker 当前进程内存中短暂存在，处理后立即释放；不得落本地文件、上传服务端、写入日志或截图证据。
- 图片 Vision 只负责把图片转换为结构化事实，不直接生成客户可见回复；正式产品、车源和价格只能由服务端权威数据确认。
- 客户或销售图片处理失败时，同批已确认文字和语音仍可入库，但本批不得绕过失败门禁触发 Brain。
- 图片识别能力未就绪时，暂停新的 C2 扫描和打开会话；已落盘的 sent_ack、消息 Outbox 和无需微信 UI 的事实结算仍继续处理。

后台展示：

- 消息类型：图片。
- 处理结果：识别成功 / 识别失败。
- 识别成功时展示文字摘要、图片 OCR 和服务端确认的业务信息。
- 识别失败时展示错误原因和处理时间，不提供原图查看入口。

主要错误文案：

| error_code | 页面文案 |
|---|---|
| `C2_VISION_NOT_READY` | 图片识别能力未就绪，已暂停新的会话读取 |
| `C2_IMAGE_SLOT_RECONFIRM_FAILED` | 图片位置已变化，无法安全确认原消息 |
| `C2_IMAGE_MENU_OPERATION_FAILED` | 图片读取操作失败 |
| `C2_IMAGE_OBSERVATION_FAILED` | 图片消息识别失败 |
| `MESSAGE_IDENTITY_UNCONFIRMED` | 图片发送方或消息身份无法确认 |

### 12.10 C2 状态

业务会话主状态 `Conversation.status`：

| 状态 | 页面文案 | 产品含义 |
|---|---|---|
| `new` | 新线索 | 已进入系统，等待分配 |
| `assigned` | 已分配 | 已分配销售，等待生成或恢复加好友任务 |
| `add_friend_blocked` | 加好友阻塞 | 销售未绑定可用 Worker，任务不可领取 |
| `add_friend_pending` | 待加好友 | add_friend 任务等待 Worker 执行 |
| `add_friend_sent` | 已发送好友邀请 | 只代表邀请已发出，不代表客户已同意 |
| `friend_added` | 已识别好友 | Worker 已确认有效短码、private 和可用会话，等待首次消息判断 |
| `ai_active` | AI 接待中 | 客户新消息可进入服务端 Brain/Guard 判断 |
| `waiting_user_reply` | 待客户回复 | AI、好友开场或普通我方回复已发出 |
| `recall_precheck` | 召回前确认中 | 正在读取微信事实，尚未允许发送召回 |
| `recalled_waiting_user` | 已召回，待客户回复 | 召回消息已发送 |
| `waiting_sales_reply` | 待销售回复 | 已转人工，普通实时 AI 回复被状态门禁阻断 |
| `sales_replied_waiting_user` | 销售已回复，待客户回复 | 已识别销售人工回复；客户再回复时可重新进入 AI 判断 |
| `rejected` | 客户已拒绝 | 不再回复、不召回 |
| `closed` | 已关闭自动跟进 | 销售关闭托管或确认移除短码，不再执行自动动作 |

状态原则：

- `Conversation.status` 只承载客户业务生命周期，不用于 Worker 领取任务。
- `waiting_sales_reply / sales_replied_waiting_user` 通过状态门禁控制普通实时 AI；销售回复不会自动把 `ai_enabled` 改为 `false`。
- `recall_precheck` 不是“已召回”，只有召回 `chat_reply` 发送成功后才进入 `recalled_waiting_user`。
- `closed` 与 `rejected` 含义不同：前者是系统退出自动跟进，后者是客户明确拒绝。

会话绑定状态：

| 状态 | 页面文案 | 含义 |
|---|---|---|
| `unbound` | 未绑定 | 扫描到会话，但没有可用短码 |
| `binding_candidate` | 待校验 | 扫描到短码候选，等待服务端校验 |
| `bound` | 已绑定 | 已绑定到唯一线索和会话 |
| `needs_review` | 待人工核对 | 多短码、多线索、绑定冲突或短码丢失风险 |
| `binding_failed` | 绑定失败 | 有短码但无法完成绑定 |
| `disabled` | 已停止监听 | 后台明确关闭、拒绝，或按复核流程确认短码已移除 |

监听状态：

| 状态 | 页面文案 | 含义 |
|---|---|---|
| `not_started` | 未开始监听 | 尚未进入监听 |
| `listening` | 监听中 | 已绑定，可读取消息 |
| `paused` | 已暂停 | Worker 暂停或不在接单时段 |
| `degraded` | 降级监听 | OCR 低置信、读取失败但未完全不可用 |
| `error` | 监听失败 | 连续扫描/读取失败或微信不可控 |
| `disabled` | 已停止监听 | 会话关闭、拒绝或短码移除 |

消息入库接口处理结果：

说明：以下值只作为 C2 消息入库接口本次处理结果，字段名为 `results[].ingest_result`。`message_events` 只保存已入库消息事实，不再保存 `ingest_status` 字段。

| ingest_result | 页面文案 | 含义 |
|---|---|---|
| `ingested` | 已入库 | 首次成功写入 |
| `duplicated` | 重复消息 | dedupe_key 已存在，跳过 |
| `ignored` | 已忽略 | 系统消息、低价值消息或状态不允许处理 |
| `failed` | 入库失败 | 接口或数据处理失败 |

状态原则：

- `bound` 是 C2 后续读取消息的唯一正常入口。
- `needs_review / binding_failed / unbound` 均不得触发 AI 回复。
- `disabled` 优先级最高；会话关闭、拒绝或短码移除后，后续扫描不得重新开启监听，除非人工重新生成或恢复短码并重新绑定。
- 单次短码缺失只能进入 `degraded`，不能直接进入 `disabled`。
- C2 不创建 `reply_action`；`messages/ingest` 不直接下发发送动作，但可返回当前 `message_batch` 供同一会话流程等待 C3 结果。
- 服务端是状态唯一事实源；Worker 只上报扫描和消息事实，不直接改变最终业务状态。
- C2 绑定、监听、读取失败统一使用 `error_code`，不得再使用 `reason_code`。

### 12.12 C2 到 C3 的边界说明

C2 完成事实入库后，服务端才有资格启动 C3。C2 和 C3 的职责仍然分开，但运行时可以在同一个已打开会话和同一把 UI 锁内串行完成。

后续 C3 的产品边界是：

```text
消息入库
-> 服务端 AI 大脑判断是否需要回复、转人工、等待或召回
-> 服务端 AI 大脑结合 RAG 生成候选回复
-> Guard 做安全、合规、业务规则审核
-> 审核通过后生成 reply_action
-> 服务端创建 chat_reply 任务
-> Worker 领取 chat_reply 任务
-> Worker 调用 OmniAuto RPA Sidecar 操作微信发送
```

关键规则：

- Worker 不自己调用大模型。
- Worker 不自己决定是否回复。
- Worker 不自己生成或改写回复内容。
- Worker 只执行服务端已经批准并下发的 `chat_reply` 任务。
- 如果服务端判断需要转人工、等待或不回复，不创建 `chat_reply` 任务。
- C3 固定使用服务端生成和 Guard 审核、Worker 发送前复读并执行的单一链路，不建立平行回复流程。

新好友首次激活规则：

| 首次读取结果 | 处理 |
|---|---|
| 已有客户消息 | 不发固定开场，直接进入普通客户消息 C3 判断 |
| 已有无法关联既有 AI 回执的 `self` 消息 | 视为销售人工回复，取消开场，进入 `sales_replied_waiting_user` |
| 双方都没有消息 | 创建一次性 `trigger_type=friend_welcome` 批次，由 Brain/Guard 生成开场内容 |

同一会话只允许成功创建并发送一次好友开场；已发送、已取消或被客户/销售消息取代后不得重复开场。

### 12.13 C3 产品口径：什么时候回复

C3 只有在所有条件都满足时，才允许自动回复：

- 会话已绑定，且客户短码仍有效。
- 会话已经同步确认是 `private`，并持有当前有效读取授权。
- `ai_enabled=true`，会话没有被人工接管、关闭、拒绝或停止监听。
- 最新客户文字、成功转写语音或成功理解图片已按 V3 合同入库，且不是重复消息。
- 同批不存在未解决的客户/销售语音或图片失败、发送方不明、消息身份冲突等安全门禁。
- 服务端已完成消息合并，形成当前有效 `message_batch`。
- 当前不在静默时段内，且未超过单会话、销售、Worker 或全局回复上限。
- 客户问题属于可自动回复范围，例如基础咨询、车型偏好、预算范围、购车需求收集、常规看车引导。
- RAG、车源索引或知识库能提供足够证据支撑回复。
- AI 大脑输出结构化结果，且 `decision=send_reply`。
- Guard 审核通过；如果 Guard 要求改写，则改写后仍必须再次通过。
- 服务端生成 `reply_action`，并创建唯一 `chat_reply` 任务。

规则：

- AI 生成的只是候选回复，不等于一定发送。
- AI 不设置固定回复轮次上限；是否继续接待由会话状态、客户意图、风控、证据和人工接管共同决定。
- 服务端调度器负责最终决策，不把发送顺序、旧回复作废、幂等判断交给模型。
- 客户连续发多条消息时，旧 `reply_action` 必须作废，基于最新消息重新生成。
- Worker 只能发送服务端 `claim-send` 成功且发送前复核通过后返回的最终文本。
- 正常链路由当前 C2 单会话流程保持会话和 UI 锁，直接续接当前批次的 Brain、复核和发送；不释放后再由另一条普通线程重新抢会话。

发送前复核规则：

```text
Worker claim chat_reply
-> 对目标会话执行 pre_send_refresh
-> 服务端处理新读到的微信事实
-> 判断 reply_action 是否仍然有效
```

| 复核结果 | 处理 |
|---|---|
| 没有客户新消息 | 允许 Worker 发送原 `reply_action` |
| 发现客户新消息 | 原 `reply_action.status=superseded`，不发送旧回复；新消息进入新的消息批次 |
| 目标会话不确认或读取失败 | 不发送，记录 `error_code`，等待重试或人工处理 |

产品表现：

- 被新消息取代的回复在后台展示为“已被新消息取代”。
- 这类 `reply_action` 不算发送失败，也不要求 Worker 重试原文本。
- 任务中心如已生成对应 `chat_reply`，展示为已取消或已作废，并说明“发送前发现客户新消息”。

### 12.14 C3 产品口径：什么时候转人工

出现以下任一情况，C3 必须转人工或停止 AI 自动回复，不创建 `chat_reply` 任务：

| 场景 | 处理 |
|---|---|
| 会话未绑定、短码失效、会话关闭、客户拒绝、已人工接管 | 不生成回复 |
| 客户明确要人工、要销售电话、要到店地址、要立即成交 | 转人工 |
| 客户问底价、最低价、经理价、能不能再便宜 | 转人工 |
| 客户问事故、泡水、火烧、重大维修、质保纠纷 | 转人工 |
| 客户问贷款、征信、分期包过、定金、合同、退款 | 转人工 |
| 客户投诉、威胁、提到报警、律师、平台举报 | 转人工 |
| RAG 无证据、证据冲突、车源信息缺失或过期 | 只禁止未经证据支持的具体车型、价格、库存、车况或业务承诺；普通需求澄清和不声明商品事实的安全常识可以回复。确需人工确认时优先生成一次 Guard 批准的客户可见承接并 `reply_then_handoff`；只有回复本身也无法安全生成时才允许静默 handoff，不得把“车辆库为空”一律等同于“不回复” |
| 模型超时、异常、输出格式不合法、置信度不足 | 短重试；超过次数转人工 |
| Guard 结果为 `handoff` 或 `block` | 转人工 |
| Guard 要求改写但改写失败 | 转人工 |
| 服务端决策为 `pause` | 暂停 AI，等待人工处理 |
| Worker 发送结果未知、文本 hash 不一致、发送失败不可确认 | 自动发送正式终止，禁止补发，会话转销售正常接管 |
| 销售已经在微信里人工回复 | AI 停止，进入销售跟进状态 |

转人工后的规则：

- 会话进入 `waiting_sales_reply`，并存在一条未关闭的 `HandoffEvent`。
- “当前仍在转人工中”的权威条件是 `Conversation.status=waiting_sales_reply` 且存在未关闭的 `HandoffEvent`，不能只看会话状态。
- 如果未关闭 `HandoffEvent` 仍存在，但 `Conversation.status` 因异常漂移成普通状态，后端必须将其重新投影为 `waiting_sales_reply`。
- 普通实时 AI 回复由 `waiting_sales_reply` 状态门禁阻断；`ai_enabled` 只在人工明确关闭全部自动化时设为 `false`。
- 销售回复前不为该会话创建新的普通 `chat_reply` 任务。
- 首次进入 `waiting_sales_reply` 时，服务端立即触发一次飞书通知，提醒该会话所属销售到微信查看并处理。
- 客户继续发消息时，不由 AI 自动回复；第一期不因后续消息或销售超时重复发送飞书提醒。
- 销售回复后进入 `sales_replied_waiting_user`；客户再次回复时重新进入 `ai_active`，长期未回复时仍可由 Brain 召回。
- 飞书通知成功或失败都不改变会话转人工事实；通知失败时仍保持 `waiting_sales_reply`，不恢复 AI 自动回复。

### 12.15 C3 产品口径：什么时候等待或不回复

以下情况不应强行回复，也不一定转人工：

- 重复消息、系统消息、撤回提示、低价值状态消息。
- 客户连续输入中，服务端仍在等待消息合并窗口结束。

以下情况不得归入“正常静默”：

- 客户提出低风险购车需求，而当前 Product Master 暂无候选。系统仍应由 Brain 询问预算内的车型偏好、用途、空间、油耗、能源类型等必要条件，不得编造具体车源。
- Brain 已生成无具体商品事实、无价格库存车况承诺的有效澄清回复，但审稿层仅因 `no_relevant_business_evidence` 将其清空。
- 审稿层决定转人工后，Brain 修复结果为空且没有生成客户可见承接。该情况属于生成/审稿链路失败，必须按同一批次有界修复，不能伪装成正常 `no_action`。
- 静默时段内收到客户消息。
- 当前会话已达到频率限制或当日回复上限。
- 客户表达“稍后再说、先看看、考虑一下”，但没有明确高意向或风险问题。
- 服务端判断本轮无需回复，例如销售刚回复过、上一条 AI 回复仍在等待客户确认。

处理规则：

- 记录 `no_action` 或 `retry_later` 原因。
- 不创建 `chat_reply` 任务。
- 不让 Worker 执行发送。
- 如果服务端决策为 `pause`，按“暂停 AI、等待人工处理”处理，不归入普通等待。

### 12.16 C4 产品口径：召回前确认

召回到期不等于可以直接发送，服务端必须先让会话进入 `recall_precheck`，再读取微信事实。

召回前确认流程：

```text
waiting_user_reply / recalled_waiting_user / sales_replied_waiting_user 到达召回时间
-> Conversation.status=recall_precheck
-> 服务端返回召回前确认读取目标
-> Worker 定向读取该会话
-> 服务端根据读取结果重新判断
```

| 读取结果 | 处理 |
|---|---|
| 读到客户新消息 | 不召回；客户消息进入 C3 判断，决定 AI 回复、转人工或等待 |
| 未读到客户新消息 | 允许创建 `trigger_type=recall` 批次，由同一个 OmniAuto Brain 生成召回文案，Guard 通过后再创建 `chat_reply` 任务 |
| 读到销售人工回复 | 不召回；状态进入 `sales_replied_waiting_user` |
| 读取失败、目标不确认或微信不可控 | 不召回；记录 `RECALL_PRECHECK_FAILED` 或具体 `error_code` |

规则：

- `recall_precheck` 只是召回前确认状态，不代表已经发送召回。
- 只有确认客户没有新消息后，才允许创建并发送 `trigger_type=recall` 的 `chat_reply`。
- 召回不设置独立 `follow_up` 任务类型，也不由 Worker 使用固定文案发送。
- 召回前确认失败时，默认不发送，避免把过期话术发给已经回复过的客户。

### 12.17 转人工飞书通知

该功能用来解决“AI 已经停手，但销售不知道需要接管”的问题。它只负责通知，不代替销售在微信中回复客户。

准备条件：

- 车金已建立飞书企业组织，并创建一个车金统一自建应用机器人。
- 销售已加入车金飞书企业，且本人或所属部门在该应用的可用范围内。
- 飞书应用已开启机器人能力，申请通过手机号获取用户标识和发送消息所需权限，并完成发布。
- 飞书企业认证不作为产品层硬条件；如飞书在应用发布或权限审批时明确要求，由飞书管理员按平台要求完成。

接收人匹配：

```text
运营新增或修改销售手机号
-> 服务端使用车金飞书应用凭证查询成员
-> 将返回的应用内 open_id 与销售绑定
```

- 手机号只是匹配条件，最终发送目标是车金飞书应用下的 `open_id`。
- 飞书机器人不能向任意人发消息；接收人必须是应用可见且可用范围内的企业成员。
- 会话所属销售通过 `conversation.sales_id` 确定，不根据 Worker 绑定关系临时猜测接收人。
- 销售换绑或未绑 Worker 都不影响飞书通知路由。

通知流程：

```text
服务端决定转人工
-> Conversation.status 首次进入 waiting_sales_reply
-> 生成唯一转人工事件
-> 按 conversation.sales_id 查找销售接收人身份
-> 车金飞书应用机器人发送一次通知
-> 记录成功或失败结果
```

转人工权威判断：

```text
Conversation.status = waiting_sales_reply
且存在 closed_at 为空的 HandoffEvent
-> 当前仍在转人工中

存在未关闭 HandoffEvent，但 Conversation.status 漂移
-> 后端重新投影为 waiting_sales_reply
```

通知内容至少包含：

- 标题：客户已转人工，请及时处理。
- 客户名称和脱敏手机号。
- 转人工原因的可读文案。
- 转人工时间。
- 处理提示：请到微信查看该客户并回复。

异常和幂等规则：

- 同一 `handoff_event` 只发送一次，会话重复保持或被重新投影为 `waiting_sales_reply` 都不得重复通知。
- 销售不存在、手机号无法匹配、不在应用可用范围、飞书返回错误或网络失败时，记录通知失败和错误原因。
- 通知失败不回滚转人工状态，不让 AI 恢复回复，也不要求 Worker 参与补发。
- 第一期不做自动重试、人工重发和销售超时二次提醒。

UI 边界：

- 不新增飞书设置页，不在销售页增加“机器人 ID”或 `open_id` 输入项。
- 复用新增/编辑销售中已有的手机号字段；该字段改为必填，需增加必填校验，但不改变页面结构。
- 通知结果首期保存在转人工事件和服务端日志中，不新增页面展示、测试发送按钮或通知补发入口。

参考：飞书官方的 [Open ID 获取说明](https://open.feishu.cn/document/faq/trouble-shooting/how-to-obtain-openid?lang=zh-CN) 和 [通过手机号或邮箱查询用户 ID](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/contact-v3/user/batch_get_id)。

## 14. 车辆管理

### 14.1 模块说明

车辆管理是运营维护真实在售车辆的唯一后台入口。运营可以人工新增、编辑或通过 Excel
导入车辆，上传车辆图片，并决定车辆是否上架。只有已上架车辆的客户可用字段，才能
进入后续客服查询和回复范围。

第一期只做车辆管理，不做独立知识规则页面、复杂 AI 工作台或外部车源自动同步。

### 14.2 车辆列表

页面入口：运营后台左侧导航增加“车辆管理”。

列表顶部提供：

- `新增车辆`。
- `导入车辆`。
- `全部 / 已上架 / 已下架`状态筛选。
- 按车辆展示名称、车辆编号、品牌或车系搜索。

列表字段：

- 车辆主图。
- 车辆展示名称。
- 车辆编号。
- 品牌 / 车系。
- 首次上牌。
- 表显里程。
- 公开售价。
- 上下架状态。
- 更新时间。

交互规则：

- 列表不增加“操作”列，点击整行打开右侧车辆详情抽屉。
- 列表只展示上下架状态，不直接放状态开关，避免误操作。
- 没有车辆时显示空状态，并提供新增车辆和导入车辆入口。
- 新增、编辑、导入或上下架成功后，列表自动刷新。

### 14.3 车辆详情、新增和编辑

车辆详情使用右侧抽屉，展示图片、客户可用资料、仅内部可见资料、状态和更新时间。

点击`编辑车辆`后，当前详情抽屉直接切换为编辑状态，不再打开新页面或第二个表单。

新增车辆使用居中弹窗：

- 只有车辆展示名称为保存必填项。
- 车辆编号由系统生成，不由运营填写。
- 新增车辆默认已下架。
- 保存成功后关闭新增弹窗，并自动打开新车辆详情抽屉。
- 因为图片上传依赖已生成的车辆 ID，新增弹窗不上传图片；保存后在详情编辑态维护图片。

编辑规则：

- 车辆编号、创建时间和更新时间不可修改。
- 点击取消回到详情查看态。
- 有未保存修改时关闭抽屉，提示是否放弃修改。
- 已上架车辆不得清空公开售价，也不得删除最后一张有效图片；需要先下架。

Evidence Pack、RAG 结果或最终回复。

### 14.5 车辆图片

- 图片只能在车辆创建成功后维护。
- 支持 JPEG、PNG、WebP，单张不超过 10MB。
- 支持一次选择多张图片、查看大图、删除和拖动排序。
- 排序后的第一张图片自动作为主图，不增加单独“设为主图”操作。
- 多图上传按单张处理；部分图片失败时，已成功图片保留，并逐张显示失败文件和原因。
- 已上架车辆不得删除最后一张有效图片。
- Excel 不导入车辆图片，图片统一在车辆详情编辑态维护。
- 车辆图片使用持久化存储，不能使用浏览器或开发机临时路径作为生产地址。

### 14.6 上架和下架

业务状态只保留：

```text
已下架 <-> 已上架
```

上架前服务端必须重新校验：

- 车辆展示名称不为空。
- 公开售价不为空且大于零。
- 至少存在一张有效车辆图片。

缺少资料时不能打开确认上架流程，页面直接列出缺少或错误的内容。资料齐全时二次确认，
确认成功后车辆立即进入客服车辆查询和回复范围。

下架规则：

- 下架需要二次确认，不要求填写原因。
- 下架后车辆仍可在后台查看、搜索和编辑。
- 下架后不再进入新的客服查询、推荐和回复范围。
- 已发送给客户的历史消息不删除。
- 尚未发送且引用该车辆的旧回复，在发送前复核时必须停止发送旧内容。
- 重新上架时重新执行上架资料校验。

### 14.7 Excel 导入流程

正式流程：

```text
下载最新模板
-> 上传 .xlsx
-> 服务端解析和校验
-> 页面预览新增、更新和错误数据
-> 全部通过后运营确认
-> 服务端整批写入
-> 返回导入结果并刷新车辆列表
```

上传规则：

- 只接受系统最新模板生成的 `.xlsx` 文件。
- 文件不超过 8MB，单次最多 2000 行。
- 模板包含`车辆信息`和`字段说明`工作表。
- 上传和预览阶段不写入正式车辆数据。
- 不接受运营自行修改表头的普通表格。

预览规则：

- 按车辆展示，不要求运营理解底层 JSON 或字段路径。
- 展示车辆总数、新增数、更新数和错误数。
- 车辆编号留空时显示为新增，并由系统生成编号；已存在的本地车辆编号显示为更新。
- 填写了车辆编号但系统中不存在时显示错误，禁止按新增车辆处理。
- 更新已有车辆时，Excel 空白字段不清空系统已有值。
- 任意一条数据存在错误，整批不能确认导入。
- 不提供“跳过错误继续导入”。修正文件后必须重新上传和校验。

确认规则：

- 确认导入采用整批事务，全部成功才提交，任意写入失败则整批回滚。
- 新增车辆默认已下架。
- 更新已有车辆时保持原有上下架状态。
- 导入成功后显示新增数和更新数，并可返回已刷新的车辆列表。
- 系统写入失败时显示简单原因和错误编号，不展示程序堆栈。
- 第一期不建设独立导入历史页面。

### 14.8 Excel 错误提示

错误文案统一使用“位置 + 问题 + 解决办法”，并使用业务字段名称，不展示技术字段路径。

| 阶段 | 错误场景 | 页面提示 |
|---|---|---|
| 上传 | 非 `.xlsx` 文件 | 请选择系统模板生成的 `.xlsx` 文件 |
| 上传 | 文件超过 8MB | 文件不能超过 8MB，请压缩或拆分后重新上传 |
| 上传 | 文件损坏 | 文件无法读取，请重新下载模板并填写 |
| 上传 | 模板版本不匹配 | 模板版本已更新，请下载最新模板 |
| 上传 | 工作表或表头被修改 | 模板结构已被修改，请使用系统原始模板 |
| 预览 | 填写不存在的车辆编号 | 第 X 行车辆编号不存在；如需新增请清空车辆编号，由系统生成 |
| 预览 | 缺少展示名称 | 车辆 CAR-001 缺少车辆展示名称 |
| 预览 | 编号格式错误 | 第 X 行车辆编号格式错误，仅支持字母、数字、下划线、点和短横线 |
| 预览 | 同一字段重复 | 车辆 CAR-001 的“公开售价”重复填写 |
| 预览 | 数字格式错误 | 第 X 行“公开售价”格式错误，请填写数字 |
| 预览 | 日期格式错误 | 第 X 行“首次上牌”格式错误，请填写为 YYYY-MM |
| 预览 | 超过行数限制 | 单次最多导入 2000 行，请拆分文件 |
| 预览 | 与非本地车源编号冲突 | 车辆编号 CAR-001 已被其他车源使用，请修改编号 |
| 确认 | 服务端写入失败 | 导入失败，本次未写入任何数据，请稍后重试。错误编号：XXX |

同一车辆有多个错误时一次性全部展示。文件错误停留在上传步骤，数据错误停留在预览
步骤；确认导入失败进入结果步骤并明确本次没有写入数据。

### 14.9 权限、接口和审计

- 第一期不区分车辆管理权限；所有登录成功的账号都可新增、编辑、导入、上传图片和上下架。
- 未登录用户不展示车辆管理页面，直接调用接口也必须被服务端拒绝。
- 浏览器只调用车金后端；前端不得直接读写 Product Master、数据库或存储。
- 新增、编辑、上架、下架、确认导入、图片上传/排序/删除均记录操作人、时间、车辆、
  操作结果和失败原因。
- 内部字段只能在有车辆管理权限的后台页面和接口中返回，不得出现在客户侧响应。

### 14.10 第一期不做

- 独立知识规则页面。
- AI 自动生成车辆资料。
- 大风车或其他外部车源 API 自动同步。
- Excel 导入车辆图片。
- 批量上架、批量下架、批量删除。
- 车辆删除。
- 独立导入历史页面。
- 客户看车商城或车辆展示站。

- AI 接待状态：AI 接待中、待客户回复、已转人工、已暂停、已关闭。
- 最近客户消息。
- 最近一次服务端决策：自动回复、转人工、不回复、暂停、稍后重试。
- 决策原因：规则命中、RAG 证据不足、Guard 阻断、模型失败、人工接管、静默时段、频率限制等。
- 候选回复摘要和最终发送文本。
- Guard 结果：通过、改写后通过、转人工、阻断。
- RAG / 车源 / 知识库证据摘要，不展示敏感内部字段。
- `reply_action` 状态：待发送、发送中、已发送、已过期、已作废、失败、结果未知。
- `reply_action` 被取代时展示为“已被新消息取代”，说明旧回复未发送。
- 对应 `chat_reply` 任务状态和错误码。
- 转人工原因、转人工时间、当前销售。
- 召回前确认状态：展示“召回前确认中”、确认结果和失败原因。

任务中心需要展示：

- `chat_reply` 任务类型。
- 任务状态。
- 当前步骤。
- 执行 Worker。
- 发送结果。
- 失败原因。
- `reply_action_id`。
- 被新消息取代、过期、发送结果未知等原因。

Worker 客户端需要展示：

- 当前 `chat_reply` 任务。
- 服务端已批准的最终回复文本摘要。
- 发送步骤。
- 发送成功、失败或结果未知。
- 不提供编辑回复内容入口。

页面原则：

- 页面只展示服务端最终决策和审计信息，不让运营误以为模型可以绕过服务端直接发送。
- 敏感字段、内部底价、采购价、经理价、车主隐私、内部备注不展示给 AI 证据区。
- `send_reply / handoff / no_action / pause / retry_later` 必须有可读原因。

## 16. 服务端数据要求

### 16.1 核心对象

| 对象 | 用途 |
|---|---|
| lead | 客户线索 |
| sales | 销售，包含与车金飞书应用接收人的匹配关系 |
| worker | Worker 档案 |
| sales_worker | 销售和 Worker 绑定关系 |
| task | 自动化任务 |
| task_event | 任务状态流转 |
| operation_log | 后台操作日志 |
| conversation | 客户会话 |
| wechat_session_binding | 微信会话绑定 |
| message_event | 消息事件 |
| message_batch | 同一会话本轮待处理的消息批次 |
| reply_action | 服务端批准的一次回复动作 |
| sent_ack | Worker 发送结果确认 |
| handoff_event | 转人工事件和通知结果 |

### 16.2 关键约束

- 同一手机号只能有一条有效线索。
- 同一 Worker 同一时间只能绑定一个客户端实例。
- 同一 Worker 不可同时绑定多个销售。
- 同一有效线索同一时间只能有一个未完成 add_friend 任务。
- 同一 conversation_id + dedupe_key 只能入库一条消息。
- 未绑定会话不得进入 AI 回复链路。
- C2 只允许有效短码且顶部标题明确为private的会话读取；group/unknown立即阻断。
- read-targets必须包含conversation_id、remark_code和authorization_revision；旧授权不得入库。
- 同一会话同一时间只能有一个 active message_batch。
- 同一 reply_action 只能创建一个 chat_reply 任务并获得一次发送结果确认。
- 图片原始字节不得进入服务端、数据库、日志或任务证据。
- 车辆编号必须唯一；新增车辆必须留空并由服务端生成，已存在编号用于更新，填写不存在编号必须报错且禁止创建。
- 只有已上架车辆的客户可用字段可以进入客服 Evidence Pack；内部字段必须在服务端投影时移除。
- 车辆 Excel 确认导入必须整批提交或整批回滚，不允许部分写入。
- 车辆图片必须使用持久化文件卷或对象存储，数据库只保存可追溯引用和顺序。
- 车辆主数据、图片引用和导入预览复用技术方案 v0.9.6 的 Product Master 接入；PRD 不另行发明表名、接口字段或同义数据对象。
- 启用销售必须有可用手机号；历史销售缺少手机号时，上线前必须补齐。
- 飞书接收人标识只能保存车金当前自建应用返回的 `open_id`，不得混存飞书 `user_id / union_id`。
- 同一转人工事件只有一个通知结果；重复状态计算和重复事件不得造成重复发送。
- 当前转人工状态必须同时满足 `Conversation.status=waiting_sales_reply` 和存在未关闭 `HandoffEvent`；存在未关闭事件时，后端对错误漂移的普通会话状态执行权威重投影。
- 飞书应用凭证和 `tenant_access_token` 只由服务端管理，不返回前端，不下发 Worker。

### 16.3 工程字段统一口径

本节以技术方案 v0.9.6 为准，是后端接口、Worker 上报、前端类型和测试验收的字段准入标准。

规则：

- 后端、Worker、前端不得自行新增同义字段、兜底字段或临时兼容字段。
- 字段命名冲突时，以技术方案 v0.9.6 的正式字段为准。
- 废弃字段只能出现在历史兼容说明或废弃字段表，不得出现在新接口响应、前端类型、Worker 上报字段或页面数据模型中。
- 如果确需新增字段，必须先由架构师更新技术方案，PRD 同步后再进入开发。

Worker 正式字段：

| 字段 | 含义 |
|---|---|
| `online_status` | Worker 是否在线，由服务端根据心跳计算 |
| `run_status` | 是否接单，固定为 `running / paused` |
| `running_status` | 是否正在执行本地任务，固定为 `idle / running` |
| `rpa_component_status` | OmniAuto RPA Sidecar 是否可用，固定为 `ready / unavailable` |
| `wechat_status` | 微信桌面客户端状态，固定为 `logged_in / not_found / logged_out / unknown` |
| `client_binding_state` | Worker 客户端绑定状态，固定为 `unbound / bound / reset_required` |
| `current_task` | 当前执行中的任务 ID，字段名就叫 `current_task` |
| `current_step` | 当前执行步骤 |

Task 正式字段：

| 字段 | 含义 |
|---|---|
| `status` | 任务生命周期：`blocked / pending / running / completed / failed / cancelled` |
| `result_code` | 任务成功后的业务结果 |
| `error_code` | 任务失败原因 |
| `block_code` | 任务阻塞原因 |
| `events` | 任务事件流；运营后台只读取 `events` |

Conversation 正式字段：

| 字段 | 含义 |
|---|---|
| `status` | 客户/会话业务状态 |
| `ai_enabled` | 该会话是否允许 AI 自主回复 |
| `reply_count` | AI 已成功发送回复次数 |
| `handoff_reason_code` | 转人工原因码 |
| `handoff_at` | 进入等待销售回复的时间 |

WechatSessionBinding 正式字段：

| 字段 | 含义 |
|---|---|
| `bind_status` | 微信会话与线索绑定状态 |
| `listen_status` | 微信会话监听/读取状态 |
| `allow_listening` | 是否允许 Worker 读取该会话消息 |
| `error_code` | 绑定、监听或读取失败原因 |

MessageEvent 正式字段：

| 字段 | 含义 |
|---|---|
| `contract_version` | C2 协议结构代号，内部固定为 `3`，不属于灰度发布版本，不得对外称为“客户端版本”或“合同版本” |
| `contract_revision` | 当前灰度合同版本，固定为 `0.9.6`；必须与客户端、后端、OmniAuto、生成 Schema、manifest 和安装包版本完全一致 |
| `authorization_revision` | 本次读取使用的授权版本，旧授权不得入库 |
| `sender_role` | V3正式值为 `customer / self / system / unknown`；销售侧统一为self，unknown不触发AI |
| `message_type` | `text / image / voice / system / file / unknown`；语音转文字统一为 `voice` |
| `content` | 消息正文；语音保存转写文本，图片保存白名单文字理解结果或为空 |
| `source_message_key` | 稳定消息来源身份，页面移动、重启和授权变化后不变 |
| `dedupe_key` | 消息去重键 |
| `row_kind` | 当前微信消息行类型 |
| `sender_role_source` | 发送方判断证据来源 |
| `item_state` | 单条消息处理结果；图片允许 `completed / failed` |
| `flow_state` | 本轮消息读取流程结果 |
| `raw_payload` | 保存 row_kind、sender_role_source、item_state、flow_state、语音父 anchor，以及图片白名单理解结果等 V3 证据；不得含图片原始字节 |

边界规则：

- C3 会话业务状态只能归到 `Conversation.status / ai_enabled / reply_count / handoff_reason_code / handoff_at`。
- `WechatSessionBinding` 只负责微信绑定和监听，不承载 AI 业务状态。
- C2 绑定、监听、读取失败统一使用 `error_code`，不得使用 `reason_code`。
- C2 消息入库接口处理结果使用 `results[].ingest_result`，不得在 `message_events` 中保存 `ingest_status`。
- C2 语音消息入库使用 `message_type=voice`，不得新增独立语音任务状态。
- C2 图片消息入库使用 `message_type=image`，不得新增独立图片任务、图片上传接口或图片业务状态机。
- 任务事件流统一使用 `events`，不得再使用 `status_flow`。

废弃字段：

| 废弃字段 | 替代字段 |
|---|---|
| `runtime_status` | `running_status` |
| `current_task_id` | `current_task` |
| `client_bind_status` | `client_binding_state` |
| `status_flow` | `events` |
| `executor_status` | `execution.worker` |
| `lead_status` | `business_object.lead.status` |
| `reason_code` | `error_code` 或 `handoff_reason_code` |
| `ingest_status` | `results[].ingest_result` |

## 17. 接口边界

### 17.1 后端要提供

- 指定账号的登录、当前登录信息、会话失效和退出登录能力；具体字段和接口名先由架构师固定。
- 所有运营后台业务接口必须校验登录状态；未登录请求统一拒绝。
- 线索创建、查询、标记无效、恢复。
- 销售创建、编辑、启停、绑定 Worker。
- 根据销售手机号匹配车金飞书应用下的接收人 `open_id`。
- 会话首次进入 `waiting_sales_reply` 时生成幂等的转人工通知事件，并向 `conversation.sales_id` 对应销售发送飞书通知。
- 保存飞书通知的发送结果、错误码、错误摘要和发送时间，且失败不回滚会话状态。
- Worker 创建、编辑、启停、重置绑定、心跳。
- 任务列表、任务详情、领取、步骤上报、结果回传、失败上报、取消、重试。
- C2 会话扫描结果上报。
- C2 待读取会话拉取。
- C2 消息事件上报，支持 `message_type=voice` 和 `raw_payload.voice_transcription_meta`；正文统一放在 `content`。
- C2 图片事实继续通过同一消息事件接口上报，支持 `message_type=image` 和白名单结构化理解结果，不接收原图。
- C3 提供 AI 大脑、RAG、Evidence Pack、Guard、消息批次、reply_action、chat_reply 和 sent_ack 能力。
- 车辆列表、搜索、详情、新增、编辑、上架和下架。
- 车辆图片上传、读取、排序和删除。
- Excel 最新模板下载、文件预览校验和整批确认导入。
- 对客车辆查询只返回已上架车辆的客户可用字段，不返回 VIN、车牌号、采购价格和内部备注。
- 操作日志查询。
- 所有接口响应字段必须符合 16.3 工程字段统一口径，不得新增临时兼容字段。

### 17.2 Worker/RPA 要调用

- 绑定 Worker。
- 心跳。
- 开始接单 / 暂停接单。
- 领取 add_friend 任务。
- 上报 add_friend 步骤。
- 上报 add_friend 结果或失败。
- 调用 OmniAuto 操作微信。
- 调用 OmniAuto sessions 扫描会话。
- 调用 OmniAuto voice-transcribe 执行微信自带语音转文字。
- 调用 OmniAuto messages 读取消息。
- 调用 OmniAuto Vision 在本机内存中理解当前屏新图片。
- 上报 C2 会话扫描和消息事件。
- C3 保持当前会话等待服务端批次结果，只领取并发送服务端已批准的 chat_reply，不直接调用大模型。
- 发送前执行 pre_send_refresh、claim-send 和消息序列复核，发送后可靠上报 sent_ack。
- Worker 上报字段必须符合 16.3 工程字段统一口径，不得同时上报正式字段和废弃字段。

### 17.3 不提供或不新增

- AI 语音回复接口。
- 外部 ASR 接口。
- Worker 本地 AI 决策或回复生成接口。
- 图片原图上传、Base64 入库、图片文件下载或图片专用任务接口。
- 召回专用 `follow_up` 任务接口；召回统一复用 `chat_reply`。
- 销售级机器人 ID 或 Webhook 配置接口。
- 前端直接查询飞书 `open_id` 或保管飞书应用凭证的接口。
- 飞书人工补发、通知按钮和销售超时二次提醒接口。
- C4 不新增专用接口，固定复用 `recall_precheck` 与 `chat_reply`。
- 抖音小风车表单同步接口。
- 废弃字段兼容接口和页面兜底字段。
- 大风车或其他外部车源自动同步接口。
- Excel 车辆图片导入接口。
- 独立知识规则页面专用接口。

## 18. 验收标准

### 18.0 字段口径验收

- 后端接口响应不得出现废弃字段：`runtime_status / current_task_id / client_bind_status / status_flow / executor_status / lead_status / reason_code / ingest_status`。
- 前端类型、状态映射和页面数据模型不得出现上述废弃字段。
- Worker 心跳、任务领取、步骤上报、结果回传、C2/C3 上报字段不得出现上述废弃字段。
- Task 详情和任务事件流只使用 `events`，不得返回或读取 `status_flow`。
- C2 绑定、监听、读取失败只使用 `error_code`，不得使用 `reason_code`。
- C2 消息入库接口处理结果使用 `results[].ingest_result`，不得在 `message_events` 中保存或展示 `ingest_status`。
- C3 会话业务状态只能从 `Conversation.status / ai_enabled / reply_count / handoff_reason_code / handoff_at` 读取和写入。
- `WechatSessionBinding` 只展示绑定和监听字段，不展示或承载 AI 业务状态。
- 废弃字段只允许出现在历史兼容说明或废弃字段表中。

### 18.1 线索和销售

- 可以人工新增客户。
- 手机号重复时不新建线索。
- 重复录入会提示次数和日期。
- 重复备注追加到原线索。
- 新线索能按轮询规则分配给启用销售。
- 停用销售不再分配新线索。
- 销售可绑定、更换、清空 Worker。
- 新增或编辑销售时手机号必填，且后端能用该手机号匹配飞书应用接收人。

### 18.2 Worker 管理

- 新增 Worker 后生成 Worker ID 和 Worker Token。
- 新增后自动打开 Worker 详情。
- Worker Token 不在列表展示，只在详情展示。
- 客户端可用 Worker ID + Worker Token 绑定。
- 同一个 Worker 不能绑定多个客户端。
- 重置绑定后旧客户端失效，新 Token 生效。

### 18.3 任务中心

- 可以查看任务列表和详情。
- 可以按状态、类型、销售、Worker 筛选。
- blocked / pending / running / completed / failed / cancelled 状态准确。
- completed 展示 result_code。
- failed 展示 error_code。
- running 展示 current_step。
- failed / cancelled 重新创建新任务时原任务保留。
- `chat_reply` 能按 `trigger_type` 区分客户消息回复、好友开场和召回。
- 召回不出现独立 `follow_up` 任务类型。

### 18.4 Windows Worker add_friend

- 客户端首次绑定成功后再次打开不要求重新绑定。
- 开始接单后能领取 add_friend 任务。
- 暂停接单后不领取新任务。
- 非接单时段在线但不领取任务。
- Worker 能调用 OmniAuto 搜索手机号或微信号。
- Worker 能写入客户短码。
- Worker 能发送添加通讯录邀请。
- 邀请发送后任务为 completed + invite_sent。
- 已是好友时任务为 completed + already_friend。
- 失败时任务为 failed + error_code。
- 客户是否同意好友申请不作为当前验收项。

### 18.5 C2 会话绑定/微信监听

- Worker 可以扫描微信会话。
- Worker 只按第一屏主动扫描、第一屏命中优先读取、状态机定向读取执行 C2。
- 第一屏命中会话能优先读取并上报消息事实。
- 服务端能按状态机返回定向读取目标。
- 定向读取目标必须包含 `conversation_id + remark_code`。
- Worker 读取时必须校验目标 `remark_code` 与会话短码一致。
- Worker 定向读取前能去掉本轮已经处理过的第一屏命中会话。
- 能识别包含客户短码的会话。
- 只有有效短码、顶部标题明确为 private 且命中当前 read-target 授权的会话才能读取。
- 群聊、会话类型不明、第一屏同码多候选时不搜索、不读取、不转写、不识图、不入库。
- `read-targets=[]` 时可以继续第一屏事实扫描，但不得打开会话或新增消息。
- 停止监听或重新授权后，旧 `authorization_revision` 的入库请求必须被拒绝。
- 服务端能用唯一短码绑定 lead / conversation / sales / worker。
- 绑定成功后后台可见。
- 未识别短码的会话不自动绑定。
- 短码删除或改写时能展示错误原因。
- 已绑定会话缺失短码时进入异常或待人工核对，不作为正常读取目标。
- 短码匹配多条线索时进入待人工核对。
- `display_name` 不得作为客户身份主依据。
- Worker 只读取服务端允许读取的已绑定会话。
- 普通消息、语音和图片使用统一 `sender_role` 和最终当前屏顺序；`unknown` 不触发 AI。
- 同一消息的 `source_message_key` 在页面移动、Worker 重启和授权变化后仍保持稳定。
- 客户语音能调用微信自带转文字并按 `message_type=voice` 入库。
- 客户语音转写成功后，系统不再把客户误判为沉默。
- 销售手机端语音同步到桌面后，按销售人工回复处理，不触发 AI。
- 语音转写失败时，不触发 AI，不召回，不把语音时长当正文。
- 目标客户已确认但语音转写失败时，进入 `waiting_sales_reply` 并提示人工查看。
- 目标客户未确认时，语音转写失败只记录证据，不改变会话主状态。
- 后台消息记录能展示“语音转文字”标识。
- 后台能展示“语音转写失败，需人工查看”、失败原因和截图证据入口。
- 客户和销售的新图片能在 Worker 当前进程内调用真实 Vision，并按 `message_type=image` 入库结构化文字结果。
- 图片原始字节不落本地文件、不上传服务端、不写日志或截图证据。
- 新图片成功或失败都形成明确终态，不出现图片 `pending / deferred`。
- 已完成、已失败或等待 Outbox 上报的图片不会重复执行复制和 Vision。
- 图片在动作前已被顶出当前屏时不主动上滚追踪；仍在当前屏但身份无法确认时零点击并形成失败事实。
- 图片或语音失败不得被伪装成普通文字，也不得绕过门禁触发 Brain。
- 文字、语音和图片按最终画面顺序入库，不把转写或图片结果统一追加到批次末尾。
- 授权撤销后停止新的 UI 动作；撤销前已产生的媒体事实仍能结算，但事实结算不推进状态机、不启动 Brain。
- 同一消息重复上报不重复入库。
- 同一条语音不会重复入库。
- Worker 重启后重复扫描不导致历史消息重复入库。
- 未绑定会话不得触发 AI 回复或自动发送。
- C2 验收与 C3/C4 分开计算；C2 通过不能用来代替 AI 回复、飞书通知或自动召回验收。

### 18.6 C3 验收口径

C3 验收不只看“能不能发消息”，还要看“该回复才回复，该转人工就转人工，该等待就等待”。

自动回复验收：

- 客户消息入库后，服务端能形成当前有效 `message_batch`。
- 满足自动回复条件时，服务端生成候选回复并通过 Guard。
- Guard 通过后，服务端创建唯一 `reply_action` 和唯一 `chat_reply` 任务。
- Worker 发送前必须 `claim-send`，claim 失败不得操作微信。
- Worker 发送前必须执行 `pre_send_refresh`。
- 正常链路由当前 C2 单会话流程持有会话和 UI 锁，完成 Brain、发送前复核、发送终态后才处理下一会话。
- 发送前发现客户新消息时，旧 `reply_action.status=superseded`，Worker 不得发送旧回复。
- Worker 只发送服务端批准文本，不能改写内容。
- 发送后全屏 OCR 漏掉右侧长文字气泡时，只有右侧结构候选的同排头像确认为本人，且局部增强 OCR 全文与本次发送正文完全一致，才能确认发送成功；任一证据不明时禁止自动补发。
- 发送成功后，状态更新为 `reply_action.sent`、`task.completed`、`conversation.waiting_user_reply`。

转人工验收：

- 高意向、高风险、底价、金融、合同、投诉、人工诉求等场景不自动发送。
- RAG 证据不足、模型失败、Guard 阻断时不编造回复。
- 转人工后由 `waiting_sales_reply` 状态阻断普通实时 AI 回复；不得自动关闭 `ai_enabled` 硬开关。
- 销售人工回复后进入 `sales_replied_waiting_user`，当前不回复；客户再次回复时交回 AI，长期未回复时仍可进入 Brain 召回。

等待和幂等验收：

- 客户连续发消息时，旧 `reply_action` 被置为 `superseded`，不发送过期内容。
- 静默时段、频率限制、重复消息、低价值消息不创建 `chat_reply` 任务。
- Worker 发送失败或结果未知时，不自动补发同一内容。
- 同一 `reply_action_id` 不会被发送两次。
- 物理发送结果无法确认时进入 `unknown_send_result`，结束原动作并禁止自动补发。

### 18.7 C4 验收口径

C4 的验收重点不是“到期就发”，而是“确认客户没回复才发”。

- 到达召回时间后，会话先进入 `recall_precheck`。
- `recall_precheck` 期间不创建可发送的 `chat_reply` 任务。
- Worker 按服务端目标定向读取该会话。
- 读到客户新消息时，不发送召回，消息进入 C3 判断。
- 读到销售人工回复时，不发送召回，状态进入 `sales_replied_waiting_user`。
- 未读到客户新消息时，才允许创建 `trigger_type=recall` 的批次；Brain/Guard 通过后创建 `chat_reply` 任务。
- 系统不存在召回专用 `follow_up` 任务类型。
- 读取失败、目标不确认或微信不可控时，不发送召回，并记录 `error_code`。
- 后台能展示召回前确认中、确认通过、确认失败和失败原因。

### 18.9 运营后台登录

- 未登录访问任意后台页面时，进入登录页，不展示后台数据。
- 服务端预先创建且已启用的账号，输入正确账号和密码后能登录。
- 登录成功后能查看并操作线索、车辆、销售、Worker、任务中心和操作日志全部模块。
- 登录成功后进入后台默认空白工作区，不自动打开第一个模块。
- 账号或密码错误时显示统一错误文案，不暴露账号是否存在。
- 账号停用后不能登录，已建立的登录会话也必须失效。
- 会话有效期内刷新页面不需要重新登录。
- 会话失效时返回登录页，并提示“登录已失效，请重新登录”。
- 退出登录后，浏览器后退不得重新查看后台数据。
- 所有后台业务接口都对未登录请求统一拒绝，不能只做前端页面拦截。
- 操作日志能追溯登录成功、登录失败和退出登录，不保存密码。
- 第一期页面不出现注册、找回密码、角色选择或权限配置入口。

### 18.10 转人工飞书通知

- 车金只配置一个统一飞书自建应用机器人，销售记录不需要分别配置机器人 ID 或 Webhook。
- 销售已加入车金飞书企业并在应用可用范围内时，服务端能通过销售手机号获取当前应用下的 `open_id`。
- 会话首次进入 `waiting_sales_reply` 时，正确销售能立即收到一条转人工通知。
- 判断当前是否仍在转人工中时，同时校验 `Conversation.status=waiting_sales_reply` 和未关闭 `HandoffEvent`，不得只校验任一条件。
- 存在未关闭 `HandoffEvent` 而会话状态异常漂移时，后端能重新投影为 `waiting_sales_reply`，且不因重投影重复发送飞书通知。
- 通知包含客户名称、脱敏手机号、可读转人工原因、转人工时间和到微信处理提示。
- 同一 `handoff_event` 只通知一次，状态重算、服务重启或重复事件不导致重复发送。
- 手机号不匹配、销售不在应用可用范围或飞书发送失败时，服务端记录失败原因。
- 通知失败时会话仍保持 `waiting_sales_reply`，AI 不恢复，Worker 不参与飞书补发。
- 第一期不验收销售超时二次提醒、自动重试、人工重发和交互卡片按钮。
- 运营后台不新增飞书配置页、`open_id` 字段或通知详情页；只将现有销售手机号改为必填。

### 18.11 全业务场景覆盖清单

原独立场景矩阵的有效内容统一并入本节，不再维护第五份产品文档。每类场景都必须落到本文
既有状态、页面和验收项；无法落入时先修改 PRD，不能由代码自行增加业务状态。

| 场景阶段 | 必须覆盖的主场景 | 产品终态 |
|---|---|---|
| 线索进入 | 手工录入、Excel/API 适配、重复手机号、字段不完整 | 拒绝、合并或进入待分配，原因可见 |
| 分配销售 | 有可用销售、销售停用、销售无 Worker、重新分配 | 唯一 `sales_id`，与 Worker 绑定关系分离 |
| 加好友 | 正常邀请、已是好友、明确失败、租约失效、人工暂停 | `invite_sent/already_friend/failed`，不伪造好友已激活 |
| 首次激活 | 首屏发现、新好友非首屏、短码搜索、授权失效、群聊/身份不明 | 仅正式短码 private 单聊且授权有效时读取 |
| 客户消息 | 文字、语音、图片、连续相同内容、动作期间新增消息 | 形成唯一身份、最终顺序和可追溯事实 |
| AI 回复 | 有权威证据、无知识、模型超时、发送前新消息、发送结果未知 | 回复、有限重试、转人工或禁止补发 |
| 人工接管 | 客户媒体失败、高意向、明确拒收、合同/支付/赔偿、销售实际接管 | `waiting_sales_reply` 或明确关闭，普通 AI 停止 |
| 等待与召回 | 客户未回复、销售已回复、召回到期、召回前发现新消息 | 等待、取消召回或生成唯一 recall 回复 |
| 停止与恢复 | 暂停接单、客户端重启、Outbox 未确认、历史技术 handoff 恢复 | 事实不丢失、不重复动作、其他短码可继续 |
| 后台运营 | 登录、线索/销售/Worker/任务/日志、车辆维护、上下架、导入 | 权限一致、操作可审计、内部字段不对客 |

横向验收底线固定为：不回错人、不重复发送、不编造事实、不漏掉最新客户消息；不能安全自动处理时，
只影响实际受影响的会话或消息，不得无依据停止全部 Worker。

## 19. 风险和待确认问题

| 问题 | 当前口径 |
|---|---|
| C3 是否建立平行回复链路 | 不建立；只使用技术方案定义的服务端 Brain/Guard、reply_action、chat_reply 和发送前复读链路 |
| 未绑定会话能否回复 | 不能 |
| 短码丢失后是否解除历史绑定 | 单次缺失只降级；后台明确关闭或按复核流程两次稳定确认移除后才停止托管 |
| 消息如何防重复 | Worker 生成稳定 source_message_key/dedupe_key，服务端以 conversation_id + dedupe_key 做最终唯一约束 |
| 监听异常放任务中心还是 Worker 状态 | 不作为任务中心任务；必要时在线索详情 / Worker 详情展示监听状态和错误原因 |
| 图片如何处理 | 当前屏新图片在 Worker 内存调用 Vision，服务端只保存文字白名单结果和审计，不保存原图；文件消息不在本轮内容理解范围 |
| 语音是否做智能总结 | 不做；只使用微信自带转文字结果作为消息事实 |
| 语音是否接外部 ASR | 不接；本轮只调用 OmniAuto 点击微信自带转文字 |
| 语音转写失败是否召回 | 不召回；目标客户已确认时提示人工查看，目标未确认时只记录失败证据 |
| Worker 暂停是否打断当前任务 | 不打断，当前任务完成或失败后暂停接单 |
| 成功任务是否上传截图 | 默认不上传 |
| C3 自动回复默认阈值 | 待项目方确认；包括置信度、静默时段、频率限制、每日回复上限 |
| C3 人工接管关键词清单 | 待项目方确认；第一版建议先覆盖底价、事故、泡水、火烧、贷款、定金、合同、地址、投诉、人工 |
| C3 页面是否单独做会话详情页 | 当前建议先复用线索详情 / 任务中心 / Worker 详情展示，不单独做复杂 AI 工作台 |
| C4 召回默认配置 | 已统一为连续 72 小时无新消息后检查、单客户最多 3 个周期、每日最多 1 次、21:00—次日 09:00 静默；服务端可配置，文案由 Brain/Guard 生成 |
| 飞书企业和应用准备 | 车金建立飞书企业、完成自建应用机器人、权限、可用范围和发布；销售加入该企业并使用同一手机号 |
| 历史销售手机号缺失 | 上线前补齐；未补齐或无法匹配时不能保证转人工通知送达 |
| 飞书接收人字段名 | 由架构师在技术方案中固定唯一字段；字段值只允许保存当前应用的 `open_id`，不得混存 `user_id / union_id` |
| 当前工程依赖 | 车辆信息复用 OmniAuto Product Master/KnowledgeRuntime/RAG/Guard，车金 PostgreSQL 是业务权威数据源；具体来源提交只记入版本更新记录 |
| VIN、车牌号、采购价格是否长期保留 | 第一期按内部字段保留且禁止对客；待业务确认真实使用场景后再决定是否精简，不阻塞本期设计 |
