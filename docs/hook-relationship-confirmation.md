# 好友通知驱动的绑定、离线补查与诊断证据

## 范围

按用户 2026-11-04 的进一步要求，备注只用于刚加好友的首次确认。确认通过后，使用已有 wxid、账号代次、绑定修订和授权校验，不在分段发送期间反复检查备注。不新增流程暂存、分段切换或旧许可重发机制。

2026-11-05 调整：新绑定在原 `native-bindings` 统一入口已核验原邀请凭证、微信身份和唯一短码，创建时记为 `relationship_initial_check=verified`。不再为新绑定另读一次通讯录。已有 `pending` 记录仍保留原保护，不能直接改成通过。

## 通知与离线补查

- 加好友提交完成后只等待，不按 8 秒或 30 秒周期读取通讯录。
- 正式回调先落本机原始收件表。当前账号、当前账号代次、带可靠消息编号的入站私聊触发核对；普通客户新消息也可补上漏掉的通过通知。通过提示的文字本身不作为绑定依据。
- Worker 启动或回调连接重新建立时，对后台授权的待绑定邀请做一次共享补查；微信重新登录后的新接收连接也走此入口。没有待核对任务不调用联系人接口。
- 一轮内所有邀请共用一次返回；候选必须通过原任务、账号、唯一短码及后台冲突校验。已绑定客户普通聊天不触发新通讯录读取。
- 运营明确授权复用旧邀请的档案接续，按该授权任务触发一次核对，仍由后台验证旧托管已退出。
- 扫描每次最多 32 个原始包；最近 4096 个原生消息标识去重。启动补查覆盖积压，不对每页积压再读取一次。超过去重窗口的极旧回放可能再次触发核对，绑定仍幂等。
- 一轮阶段、原回调编号和摘要、通讯录摘要及每项结果持久化。后台断网重试复用本轮磁盘快照，不重新读取 DLL；账号/进程变化后不能复用旧快照。
- 重开时先恢复未结束轮次；本次库存新增、旧轮次未覆盖的邀请单独排入一次启动补查，不用旧快照代替，也不重置旧轮次的补查次数。
- 只有统一网关证明请求尚未送达，才进入现有有限重试。耗尽后沿用人工“重新检查连接”，不因重启重置预算。未知调用仍保留原隔离与恢复凭证。
- 首次未找到短码时，同轮在 2 秒、5 秒后最多补查两次，全部邀请共享返回；补查次数与每次比较持久化，Worker 重开继续原轮次而不重置次数。短码重复、身份矛盾和通知对象不符不套用这项重试。两次仍未匹配就结束本轮并显示“好友绑定待核对”；后续新消息或新连接可以触发新核对，不恢复无限轮询。仍不能声称实时回调保证绝不遗漏。
- 临时动作锁占用属于尚未执行查询，保留同轮等待锁释放；锁在执行后丢失、未知接口结果继续原隔离流程，不能混入上述可重试分类。
- 绑定成功后下一轮库存转入原消息历史核对、AI、串行发送和回执结清流程；不自动重发邀请或旧回复，不解除人工暂停。

## 旧待确认记录的一次复核

共享 `hook_contact_rules` 负责对象、身份和短码解析。

- 首次正常匹配：完成初始确认，不增加第二次读取或截图。
- 首次明确备注变化：后端保留首次证据并给一次性确认标识，不关闭 AI、不转人工、不取消欢迎语。Worker 收到后重新调用一次联系人接口，不复用首次返回。
- 第二次正常匹配：完成初始确认，原排队回复按原发送条件执行。不会解除人工暂停、故障或既有人工接管。
- 连续两次明确变化：沿用原人工核对入口，保存两次目标证据。
- 缺失、重复、结构不明确或读取失败：仍为初始待确认，不推断删除或备注变化。等待后续通知或启动/重连补查；取消周期重查。每轮每客户最多增加一次异常确认读取。
- 确认标识限定绑定修订、账号与进程代次，五分钟过期。旧请求不能再次确认。中间不确定或正常观察打断连续变化。

初始确认完成后库存不再安排此绑定的备注检查；迟到的备注观察不会重新创建暂缓状态。因此备注确认不会出现在已获准的同一条分段回复中，不会将其误送到“客户追加消息”的旧取消恢复分支。已有连续分段、未确认发送及恢复保护完全沿用。

## 证据

诊断包仅保存目标客户必要字段：预期短码、目标 wxid、匹配数、字段名/类型/值、截断标记与摘要。身份匹配对象和短码匹配对象分别最多两个，每对象十六字段、字符串前 256 字符；省略数量明确。无匹配也保存零匹配结论，重复短码保留相关候选必要字段；不导出其他联系人的通讯录内容。

记录包含账号代次、进程代次、绑定修订、读取尝试编号、时间、read/compare/post/complete 阶段及具体失败代码。首次或第二次读取的传输错误、非法响应、HTTP 拒绝、过大响应、身份异常均进入同一目标记录。身份异常仍向上抛出，不伪造关系结论。接口拒绝保留阶段和状态码。

每绑定修订保留 `latest.json` 与确认异常的 `confirmed.json`；普通匹配不覆盖旧异常。原桌面诊断入口优先将这些文件纳入故障 ZIP，沿用脱敏及收集清单。可选证据文件写失败时复用独立、有界的 `evidence-recorder-failures.jsonl`，保存原原因、目标和缺件说明，不再尝试写 SQLite 日志覆盖第一原因。全盘不可写时不能保证生成文件，现有全局存储与身份门禁不变。

## 验收边界

后端与 Worker 配套变更，发布时按现有合同同步流程交付。本轮不打包、不部署、不改生产客户。

本地使用隔离 SQLite、实际 HTTP 入口、生产库存与调度消费者、合成模型/联系人返回及实际故障 ZIP。物理微信发送用明确的测试边界代替，Windows 实机待验。两次独立接口调用不能证明提供方内部无缓存，旧现场未保存的联系人返回不能补造。

## 存储与交付

`hook_friend_discovery` 保存消费游标和未结束轮次；`transactions/hook/friend-reads` 保存原返回供同轮幂等重试，`friend-discovery` 保存轮次结论。没有新增常驻通讯录缓存。桌面诊断 ZIP 收集游标与轮次目标字段，不导出整本通讯录或无关联系人。旧原始凭证不删除。

本次新增模块为运行时普通 Python 导入，Worker 打包沿用普通导入的依赖扫描；未改变 DLL、启动参数和 OCR 加好友步骤。后端必须先更新库存中 `remark_code` 与授权接续标记；旧后台不支持时明确报告协议缺口，不回退到周期读取。

## 已绑定客户的历史通知缺口（2026-11-07）

好友绑定成功后，某个历史回调编号可能既不在当前授权聊天历史中，也没有足够证据证明它属于绑定前。该情况不能作为“已处理”或“已发送”排除，也不能无限重读。

- 统一历史入口对同一账号代次、同一客户、同一缺失编号最多执行三轮边界核对（首次加两次补查）。每轮仍保留原双遍历史与分页校验；三轮不是三次 HTTP 请求，也不是读取通讯录。
- 查询前将次数写入本机数据库，Worker 重启、绑定重新读取或新消息不会重置该编号的次数。只有可靠证明属于绑定前的记录才算该缺口已解决。
- 耗尽后保留缺失编号及原始采集，发布不完整历史回执，通过现有转人工入口明确交销售处理，仅取消该客户尚未发送的自动回复。其他客户继续；已触发的发送仍走原凭证核对，禁止补发。
- 已转人工且没有新回调时，将负向等待结果保存在磁盘，后续轮询及 Worker 重启不再重复读取该客户历史。该结果不授予发送权限；新消息或微信进程变化后可核验当前历史，但不续加旧编号的核对次数。
- 新证据补齐时恢复历史完整性，不自动解除人工接管。经完整原生顺序证明、晚于缺口及交接时已知消息的销售回复，复用现有交接收尾入口。缺口仍不明时保留人工处理，不把旧消息当成新回复或成功发送。
- 桌面故障诊断导出查询次数、负向等待快照、原始历史回执与缺失编号；不增加应用内入口。
- 协议新增可选 `missing_callback_ids`，只表达不完整历史。需先部署支持该字段的后台，再发布客户端；旧客户端仍保留原严格行为。未知发送核对入口不复用此等待快照。
