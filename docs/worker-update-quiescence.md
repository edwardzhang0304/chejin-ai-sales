# 检查更新接管规则

用户点击正式 Worker 的“检查更新”后，即进入更新模式。微信未打开、未登录、Worker 暂停或故障，都不能单独使入口不可点击。重复更新及正在进行的时间修复仍互斥。

## 请求与替换分开

1. `begin_update_check` 在短临界区通过原停止入口先持久化暂停（原故障仍保留），再登记更新请求、关闭新业务入口。请求首次落盘就包含保持停止标记，不等待更新线程才暂停；恢复时也必须先保存停止状态，再解除更新门禁。按钮预览不扫描历史、租约或微信连接，也不等待任务的网络锁。
2. 原进程停止启动后续连接检查、历史读取、OCR 监听轮次及客户业务。已经进入的轮次允许保存结果，安装边界同时检查轮次计数和原有持久化凭证。
3. 更新线程通过原停止状态入口暂停接单，故障保持故障；下载和验签使用原流程。无新版本、失败或取消后仍保持停止接单，须销售手动恢复。
4. 已发起的发送、写入、回执及结果不明记录不能删除或假定成功。下载完成后等候原安全边界，最长 120 秒；仍未安全结束则显示具体原因，保留原程序与记录。既有已签名待读取交接能力仍按原规则核验。
5. 原始回调继续保存到退出阶段，由原写入者关闭流程确认停止；停止新消息投影不等于丢弃原始消息。绑定、历史、未知发送及未回传记录不清理。

## 新进程与兼容

原进程的检查停机标记仅属于本次进程。新进程仍执行启动健康检查；跨进程的新业务禁入标记继续保留，直到原认证结果核对结束。否则新程序可能无法提供健康证明。

新请求把 `keep_stopped_after_update` 同时保存到状态和安装计划，成功/回退后不自动接单。旧请求的结果恢复保持旧格式兼容，不把历史凭证删除或冒充新请求。

改动位于现有 Worker 模块，无新增可执行入口、独立补丁程序或打包依赖。Hook DLL、工作微信快捷方式、协议和后端未改。现有 EXE 不会因源码修复自动改变。

## 验证范围

源码验证覆盖：真实调度循环占用时点击、禁止新轮次、无微信情况下走到安装边界、未知发送阻挡替换、原始回调保留、OCR 停扫、重新启动的健康检查、更新结果保持停止以及时间同步互斥。使用临时 SQLite、localhost 合成 Hook 服务及替代的安装/系统操作，不代表 Windows 成品验收。

后续发布必须用原装旧客户端与封存目标包，实际验证微信正常登录下暂停更新、微信未打开、故障状态，以及更新后绑定/未完成记录保留。当前用户报告过按钮失败的旧版本，不得仅凭新源码通过就宣称其按钮已修好。
