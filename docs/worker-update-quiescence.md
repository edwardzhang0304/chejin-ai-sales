# 检查更新接管规则

用户点击正式 Worker 的“检查更新”后，即进入更新模式。微信未打开、未登录、Worker 暂停或故障，都不能单独使入口不可点击。重复更新及正在进行的时间修复仍互斥。

## 请求与替换分开

1. `begin_update_check` 在短临界区通过原停止入口先持久化暂停（原故障仍保留），再登记更新请求、关闭新业务入口。请求首次落盘就包含保持停止标记，不等待更新线程才暂停；恢复时也必须先保存停止状态，再解除更新门禁。按钮预览不扫描历史、租约或微信连接，也不等待任务的网络锁。
2. 原进程停止启动常规连接检查、全量客户读取、好友发现及新任务。已经进入的轮次允许保存结果；持久化的原回执、待上传和原回复保留受限的后续消费轮次，安装边界同时检查轮次计数和原有凭证。
3. 更新线程同步已保存的停止状态，不再重复创建暂停意图；后端确认同一状态也不产生新的人工操作版本。故障保持故障，下载和验签使用原流程。无新版本、失败或取消后仍保持停止接单，须销售手动恢复。
4. 已发起的发送、写入、回执及结果不明记录不能删除或假定成功。下载完成后等候原安全边界，最长 120 秒；仍未安全结束则显示具体原因，保留原程序与记录。既有已签名待读取交接能力仍按原规则核验。
5. 原始回调继续保存到退出阶段，由原写入者关闭流程确认停止；停止新消息投影不等于丢弃原始消息。绑定、历史、未知发送及未回传记录不清理。

## 原回复收尾

用户已明确：第一段发出后点更新，等这条回复发完再安装，期间不接新任务。

- 仅本次进程捕获的原 Flow 可以继续；本地、API 和后端流程必须一致，暂停必须属于本次更新意图。新的人工操作、退出、紧急停止及真实故障仍阻断继续发送。
- Hook 的原回复许可贯穿调度和最终发送检查：等待结束后，以及取得微信操作锁、后端许可返回后、触发前，均复核同一更新意图。被撤销且尚未触发时沿用原未发送结算；已有触发或结果不明时不得伪造未发送凭证。
- Hook 只读取原客户、处理原回复批次；后端沿用原身份和顺序校验，允许同一批次、同一生成轮次的后续段领取。不同客户、不同批次、前段未确认以及故障/离线仍拒绝领取。
- OCR 继续共用原回执与批次恢复入口。暂停时的批次读取授权额外要求：同一个已登记读取流程、当前有效批次、第一段的发送许可由本流程在暂停前签发且已有成功回执；新的流程不能借用历史回复的许可。
- 原回复所需的临时读取失败沿用原重试次数及意图，不因更新自己的暂停/ACK 重置预算。后续真正的人工操作仍使旧意图失效。
- 结果不明的物理发送只走原核对与回执路径，不重新发送。无法确认或回传失败时保留原记录，不冒充安全安装。

## 并发与网络边界

状态意图锁只保护本地状态登记；与轮次登记锁共同使用时，顺序为状态意图锁在前。故障恢复的完整就绪检查放在状态锁外，提交恢复状态前仍核对原意图版本和更新门禁。

Hook 新 Flow 的心跳和启动请求不占状态意图锁。它们仍受原业务准入锁串行保护，并登记活动轮次：更新可立即保存停止意图，但安装必须等待该轮次结束。心跳晚到时不能继续登记新 Flow；启动请求已经发出时，先前保存的 Flow 记录保留，不能把未知结果算作空闲。界面定位失败引起的暂停也先本地保存，再于状态锁外同步后端。

## 新进程与兼容

原进程的检查停机标记仅属于本次进程。新进程仍执行启动健康检查；跨进程的新业务禁入标记继续保留，直到原认证结果核对结束。否则新程序可能无法提供健康证明。

新请求把 `keep_stopped_after_update` 同时保存到状态和安装计划，成功/回退后不自动接单。旧请求的结果恢复保持旧格式兼容，不把历史凭证删除或冒充新请求。

改动位于现有 Worker 模块和后端原回复领取/批次授权入口，无新增可执行入口、独立补丁程序、打包依赖或数据库字段。Hook DLL、工作微信快捷方式、请求协议未改。后续发布需要包含配套后端实现；现有 EXE 不会因源码修复自动改变。

## 验证范围

源码验证覆盖：真实调度循环占用时点击、禁止新任务轮次、无微信情况下走到安装边界、未知发送阻挡替换、原始回调保留、OCR 停扫、重新启动的健康检查、更新结果保持停止以及时间同步互斥。新增链路使用正式业务生产者和正常消费循环验证 Hook 分段收尾、回执响应丢失、Flow 结束请求失败、原读取重试及 OCR 三段收尾，并检查权限越界。使用临时 SQLite/PostgreSQL、localhost 合成 Hook 服务及替代的安装/系统操作，不代表 Windows 成品验收。

后续发布必须用原装旧客户端与封存目标包，实际验证微信正常登录下暂停更新、微信未打开、故障状态，以及更新后绑定/未完成记录保留。当前用户报告过按钮失败的旧版本，不得仅凭新源码通过就宣称其按钮已修好。
