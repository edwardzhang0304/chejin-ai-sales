# 车辆管理与 AI 查询字段对应

查询先遍历租户的全部有效上架车源，再筛选、排序和限制展示数量。网页分页、历史推荐和本轮展示上限不能代替全库筛选。

| 管理字段 | AI 查询入口 | 边界 |
| --- | --- | --- |
| 公开车名 | `name_queries` | 同名需明确，不猜车辆 ID |
| 公开价格 | `budget` | 总预算、首付、月供分开，沿用统一预算口径 |
| 品牌、车系、车身类型、能源、驱动、所在地、排量 | 对应字段 `eq/in` | 排量是文字，不作数字大小比较；model 是车身类型，不是年款 |
| 外观颜色、内饰颜色 | `exterior_color/interior_color` 的 `eq/in` | 白/白色等基本颜色同义；不擅自合并特殊色名、双色 |
| 首次上牌日期 | `first_registration` 的 `eq/gte/lte` | 严格 YYYY-MM，按年月排序；不是出厂日期或年款 |
| 表显里程、电池容量 | `mileage_km/battery_capacity_kwh` 的 `gte/lte` | 单位分别为公里、kWh |
| 公开描述 | 同一公开事实材料 | 自由文字不冒充结构化筛选；事故、油耗等无法可靠查询的条件保留待核实 |
| VIN、车牌、采购价、内部备注 | 不进入模型公开材料或筛选 | 继续保留私有边界 |

`adapters/vehicle_fields.py` 统一声明可筛选字段、颜色比较和上牌年月规则；管理端和查询端共用年月格式。跨层测试检查管理字段是否有明确去向，新增字段时必须同步决定查询或保密职责。

## 数据不足与需求不明分开

- 客户说清了条件、库存字段缺失或暂不能筛选：`partial`。保留明确需求，介绍已核实范围内的具体车辆时说明剩余条件待核实，不强制客户重复确认。
- 客户预算、指代、条件本身有矛盾或不明确：`clarification_required`，仍须澄清。
- 未完成查询：`unavailable`，不得用空列表声称没有车。
- 只有全部条件核实才有完整匹配总数及价格上下界；部分核实保留 null，不转换成零或完整匹配。
- “先举例两台”不代表“总共只有两台”；审核和回复共享同一回执说明，不强制补造全库数量。

新逻辑只影响本轮查询。旧回执采用只读视图解释，原记录不改写；已有未知发送不补发。

## 验证范围

合成数据覆盖字段别名、日期边界、缺失/畸形字段、全库后限量、私有字段隔离及旧回执解释。贯通测试从车辆管理 API 入库，经真实查询与 Brain/Guard，到模拟 Hook 历史核对、原发送收尾；外部模型和微信接口使用合成替身，不等于真实模型质量或 Windows 实机验收。

2026-11-07 另完成真实模型验证：使用项目配置的 `deepseek-v4-flash`，4 组虚构需求和虚构库存共调用 12 次。覆盖外观颜色、内饰颜色、首次上牌时间及三项组合；外观场景将目标车放在 66 台同价但颜色不符的车之后。模型实际提取的条件、全库筛选结果、最终回复的车名/价格/颜色/上牌时间相符，4 组均完成模拟原发送核对，没有转人工。该结果是有限样本验证，不代表模型永不出错，也不替代 Windows 实机验收。

本轮不新增自由文字拦截或第二层模型审查。验证重点是查询契约、完整筛选和同一车辆资料的正确传递；身份、权限、协议、原发送核对等已有职责继续保留。真实模型测试凭据仅在测试进程内使用，原始实验材料保留在本地私有取证目录，不纳入公开提交。
