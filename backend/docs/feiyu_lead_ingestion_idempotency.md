# Feiyu lead ingestion: idempotency and source handling

## Purpose and audit result

This document records the follow-up to PR #17 (`85ae619`). The supplied review's four findings are confirmed in the source:

1. `create_feiyu_lead` calls the native phone-based creation service for every delivery. Replaying one clue therefore increments `duplicate_count`, writes another duplicate event, and may append the same note again. A reused clue ID with a different phone bypasses the phone check and creates another lead and task.
2. The endpoint passes `custom_fields` through. The add-friend task service treats a top-level `custom_fields.remark_code` as the internal task code.
3. The native service always writes `source_type="manual"` and `source_name_snapshot="人工录入"` for new records.
4. The Feiyu request model rejects `remark`; native create and duplicate handling already persist a first note and append a later genuine repeat note when `LeadCreate.remark` is supplied.

The endpoint's shared secret and compact response are useful and remain in place. Native round-robin assignment and add-friend task creation remain the only business paths.

## Frozen external contract

- Keep `POST /api/integrations/feiyu/leads` and `X-Feiyu-Forward-Secret` authentication.
- Keep the compact successful response and the existing `409 LEAD_PHONE_DUPLICATED` response for a genuinely new clue that matches an existing phone.
- Keep `customer_name`, `phones`, `wechats`, `emails`, and `custom_fields`; add optional `remark`.
- Read the Feiyu clue identity from `custom_fields.feiyu.id` (accept `clue_id` as an alias). The receiver must place the value selected by `FEIYU_CLUE_ID_FIELD` in this field. If no clue identity is available, preserve legacy phone-only behavior and state that this request cannot be made strictly idempotent.
- Scope identities by authenticated forwarder account. `X-Feiyu-Account-ID` is set from receiver configuration, never from raw Feiyu payload fields. The server fallback account is `default` for existing one-account callers. The backend validates the header against the server-side `FEIYU_ACCOUNT_IDS` comma-separated allowlist (default `default`); never let the request create its own account namespace. Each configured receiver identity must use a stable allowlisted account ID; do not infer an account from campaign IDs or customer data.
- `custom_fields.feiyu` remains the external source namespace. A top-level `custom_fields.remark_code` is rejected; system task codes continue to be generated by the native task service.
- Feiyu-created new leads use the `feiyu` source type and `飞鱼线索` display source. A genuine repeat submission never replaces the customer's first source; its current source details remain in the native duplicate-event payload.
- A same-account, same-clue retry returns the stored result without creating another lead, duplicate event, note, assignment, task, or round-robin advance. If the saved contact identity differs, return `409 FEIYU_CLUE_IDENTITY_CONFLICT` without business writes.

## Transaction and recovery behavior

For identified clues, the receiver's account/clue receipt and the native business operation are committed in one database transaction. The receipt stores a keyed fingerprint of normalized contact identities, the associated lead, the HTTP status, and the compact response body. It does not store raw phone values.

The receipt lookup and identity lock happen before calling the native create path. An existing receipt with a matching fingerprint replays its stored response. A changed phone, WeChat ID, or email for the same identity fails closed. A new clue ID that hits the native phone duplicate path commits the one native duplicate event and the receipt together. This lets the receiver safely retry after the database committed but the acknowledgement was lost.

PostgreSQL uses a transaction-scoped identity lock and a unique `(account_id, clue_id)` constraint. The existing native lead-creation lock still protects phone deduplication and is acquired inside the same transaction. A database/commit error rolls back all business and receipt writes; the receiver can retry the request.

Requests with no clue ID keep legacy behavior for compatibility, but cannot distinguish a transport retry from a new customer submission. The receiver's configured clue-ID field must therefore be mapped for strict production behavior. Existing historical rows are not automatically backfilled: account scope and unsanitized historical identity cannot be inferred safely.

## Notes and source history

The receiver maps Feiyu's structured customer `business` entries to a concise `remark`, preserving the native note workflow. Initial submission creates the regular note; a new clue ID for the same customer uses the existing duplicate append flow. Replaying that clue returns the first receipt and does not append again.

The first successful lead keeps its original source label. Later clue IDs are retained as native duplicate events, including the current `custom_fields.feiyu` source details and note. A same-ID retry is only an acknowledgement replay and does not rewrite source or notes.

## Required acceptance cases

1. Send one account/clue 10 times: one receipt and one business effect; duplicate count, notes, tasks and assignment cursor stay fixed after the first attempt.
2. Commit the first request, discard its response, and retry: return the saved business result and keep all counts fixed.
3. Reuse the account/clue with a different phone, WeChat ID or email: return identity conflict and leave the original customer and task unchanged.
4. Reuse a phone with a new clue ID: create exactly one native duplicate event and note append; retrying the new clue must not increment either again.
5. Reuse a clue ID under another server-allowlisted account: treat it as a separate source identity while retaining native phone deduplication; reject an account ID outside the allowlist before writes.
6. Submit `custom_fields.remark_code`: reject before writes; verify the task code is system-generated.
7. Create through Feiyu and through manual entry: manual source remains unchanged; Feiyu source is visible on new Feiyu leads.
8. Verify assignment, worker-unbound task blocking, and add-friend task creation use the existing native services.
9. Verify the receiver maps the configured clue-ID field and customer business fields, then repeat the same POST after a simulated lost acknowledgement.
10. Run SQLite endpoint tests and PostgreSQL concurrency/transaction tests where a local test database is available. Do not connect to production services.

## Limits

- A `default` account fallback preserves the original one-account contract. Multiple Feiyu accounts sharing one receiver must each have a distinct, server-configured account identity; an account identifier copied from the Feiyu body is not authoritative.
- A request without a clue ID remains accepted for backward compatibility and does not gain strict retry idempotency.
- The existing phone-based native lead model remains unchanged: a new clue ID with an existing phone is one genuine repeat-lead event on the original customer, not a second customer row.
- This work changes local source and tests only. It does not migrate or deploy a production database and does not merge or push PR #17.
