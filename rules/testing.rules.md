# 测试 Rules

版本：v0.4.4

日期：2026-09-21

适用对象：测试准入、测试执行、回归、UAT、缺陷、自动化、测试报告，以及代码审计、架构复审、修复复审、合并复审。

## 1. 测试准入硬规则

测试可以提前参与需求评审、接口评审、用例设计、测试数据准备和联调冒烟，但正式测试执行必须等前后端开发完成、前后端自测完成、前后端联调完成后才能开始。

禁止把“联调可测版本”当作“正式测试版本”。

除非用户明确要求追溯历史、清理旧版或比对旧版，测试不得打开、引用或依据旧版/废弃文档判断当前测试范围、准入条件、测试结论或验收状态。

| 状态 | 含义 | 是否允许正式测试 |
|---|---|---|
| 可开发联调 | 前后端可开始对接口和页面 | 不允许 |
| 可测试准入 | 开发自测完成、联调完成、核心阻塞缺陷关闭 | 允许 |
| 可验收 | 正式测试通过、验收标准明确、遗留问题已确认 | 允许验收 |

## 2. 测试结论优先级

同一事项出现多个报告时：

1. 后续回归报告优先于首轮测试报告。
2. 原始结果 JSON 优先于二手总结。
3. 自动化结果只证明其实际覆盖范围；真实用户失败反馈立即阻断对应路径，不能因缺少日志或既有 CI 通过而忽略。根因再依据日志、版本和复现证据确认，不能用模拟成功覆盖实机失败。
4. 代码实现只能证明“存在实现”，不能替代测试通过。
5. 测试通过不等同于客户验收通过。
6. P0 或旧阶段测试结果不能替代当前 C2 结论；正式 Windows C2 历史基线和后续受影响范围回归统一以《版本更新记录》绑定的提交、包 SHA 与原始证据为准，不得混写成当前候选通过。

## 3. P1a 前端验收防漏测规则

P1a 前端验收必须从“元素存在 / 接口返回”升级为“用户可读、可点、可完成、状态真实变化”。

必须遵守：

1. 销售新增、编辑、启用/停用、Worker 绑定/更换/清空必须真实操作。
2. Worker 新增、编辑、详情、Token 展示、重置绑定必须真实操作。
3. 任务中心已完成复测；后续回归必须覆盖状态筛选、任务详情、领取、回传、失败原因、取消、重试和跳转处理。
4. 操作后必须验证业务结果变化，而不是只验证 DOM 中有文字。
5. 错误提示、重复提示、成功提示不得遮挡标题、表单项、按钮。
6. 保存失败、权限不足、空数据、加载失败等场景，必须验证用户下一步入口是否可见可点。
7. 每个 P1a 前端用例至少包含功能断言、展示断言、可用性断言。
8. 用户截图指出的问题，必须反向补自动化或复测用例。
9. 测试报告不得用“已展示提示”这种模糊口径。
10. 测试结论必须区分接口通过、交互通过、展示通过。

## 4. UI 测试规则

1. 当前 UI 按本地设计稿/本地静态稿验收。
2. 视觉复核必须使用固定视口、固定数据、固定页面状态。
3. 桌面主分辨率至少覆盖 `1440x1000`。
4. 移动端如果非 P1a 范围，必须在报告中明确标注“不作为 P1a 通过依据”。

## 5. Worker 客户端发包测试规则

Worker 客户端每次发包测试必须检查：

1. 安装包出厂状态为未绑定。
2. 安装包内不得包含 Worker Token、`worker_id`、`client_instance_id` 或本机绑定缓存。
3. 首次启动必须进入绑定页。
4. 输入 Worker ID / Worker Token 后，本机可以保存绑定并在退出重启后恢复。
5. 重新发包不得带入上一台机器的缓存、runtime、local storage、SQLite 本机数据或任何机器级状态。

若发现安装包自带绑定状态、Token 或机器缓存，直接判定为发包不合格，不得进入正式测试。

客户端自动升级发布前还必须执行 `operations.rules.md` 第 2—4 节：原始已发布 Worker、其内置 Updater、本次正式包和真实“检查更新”入口必须贯通验证；受控旧 Worker 替身、直接构造更新计划和新装成功只作补充证据。未通过不得开放生产自动更新或向用户承诺可升级。

## 5.1 运营后台登录测试规则

运营后台登录进入正式测试前必须覆盖：

1. 正确密码、错误密码、未知账号和停用账号。
2. 刷新保持登录、空闲/绝对过期、主动退出、账号停用和密码重置使旧会话失效。
3. 未登录遍历全部后台业务接口均返回 401，不能只验证页面被隐藏。
4. 任意登录成功账号均可完成全部后台写操作，不再出现 viewer/只读差异。
5. Cookie 具备 HttpOnly、生产 Secure、SameSite 和正确 Path；前端不保存 Bearer Token。
6. 登录限速、Origin/CSRF 拒绝、登录成功/失败/退出审计及密码、Cookie、哈希脱敏。
7. Worker Token 访问后台、后台 Cookie 访问 Worker 身份接口均被拒绝。

当前静态 Admin Bearer Token、localStorage Token 或角色只读测试只能证明旧实现，不得
作为正式登录通过依据。

## 6. 测试报告要求

测试报告必须包含：

1. 测试范围。
2. 不测范围。
3. 环境和入口。
4. 执行结果。
5. 失败项和缺陷编号。
6. 证据路径。
7. 结论：通过 / 有条件通过 / 不通过。
8. 遗留问题是否阻塞验收。

## 7. 当前测试结论口径

当前可以说：

```text
销售管理、Worker管理和任务中心均已有测试依据。C1已有稳定基线；C2 已在
`v16.130.0 / 8ee53e1` 完成文字、语音、图片、安全准入、统一顺序、跨轮去重和
停止监听的正式 Windows 实机验收。双仓统一后的 `v16.132.0 / 37139bfd` 已完成
自动化及受影响范围 Windows 回归。C3 自动回复此前已实机测试且当前无已知问题。
```

当前不能说：

```text
v16.132.0 的受影响范围冒烟等同于新的全量正式 Windows 安装包验收。
```

原因：`v16.130.0` 的结论只绑定该提交和安装包；`v16.132.0` 当前只继承明确执行
并通过的受影响范围，后续正式安装包仍必须
按代码变化补自动化和实机证据，不能直接套用旧包结论。

## 8. 正式发布的测试证据复用

源码测试和成品验收分开。工程师指定受影响测试及不测范围，可信 CI 保存提交、输入指纹、测试清单、原始报告、运行 ID/attempt 和结果。源码或依赖变化后旧凭证失效；文档或独立发布工具变化不要求重测无变化的业务代码。跳过、失败、未执行不得登记为通过。正式发布不默认全量回归；缺少证据应列出缺项并停止，由工程师补齐对应范围。是否覆盖变更仍由工程师和复审负责，凭证校验不能把少量测试包装成全部业务已验证。安装包及原始旧客户端升级验收仍按第5节和运维约束执行。

## 9. 每次审计必查：规则统一性

来源：用户于2026-09-21明确要求。代码审计、架构复审、修复复审和合并复审每次均须执行，不能以“这轮只改几行”“原测试全过”免除。该项是在原审计范围上增加必查重点，不替代业务正确性、异常闭环、代码质量和测试真实性检查。

### 9.1 检查尺度与责任

围绕本次受影响的业务事件追踪全部可达判断入口及上下游，不只看改动行；不要求每次重审无关的整个项目，也不凭空扩造低现实性的场景。检索范围及未覆盖部分必须说明。

审计者负责独立核对规则来源、职责划分、调用关系及测试是否覆盖实际传递链。发现冲突时分别说明：设计口径是否冲突、实现是否偏离、测试/前次审计漏了哪一段；有证据才归因，不能一律归咎开发，也不能把漏审解释成“测试已经通过”。

### 9.2 必查清单

1. **谁定义规则、谁负责判断。** 对本次业务事件，按当前技术方案和机器合同定位权威定义、负责模块、实际实现及调用方。尤其检查 OmniAuto 的界面事实/执行证据、Worker 的任务执行/持久化/回传、后端的业务状态/调度是否各自遵守既定职责；具体边界以当前合同为准，不借审计另起设计。
2. **同一件事是否还有第二套口径。** 检索同义函数、阈值、字段、错误码和状态转换，不局限相同函数名。核对普通路径，以及实际相关的发送前、段间、回调、重试、重启恢复、旧记录兼容、降级与开关路径：新入口采用新规则后，旧入口是否仍可按旧标准放行或拦截。每个保留的独立分支须有明确适用条件与一致性依据。
3. **上下游是否要同一份证据。** 沿实际生产者到消费者检查证据字段的含义、坐标/时间/帧归属、缺失默认值和版本兼容。覆盖实际经过的封装、序列化、接口、本地保存和恢复边界；不能前面丢字段、后面强制要求，也不能上游已判失败、下游却按成功收尾。当前帧证明不得无条件当作后续帧证明。
4. **规则叠加后有没有互相打架。** 对同一输入/事件核对各层结论及最终动作，特别是放行、重试、取消旧回复、继续AI、转人工、停单、补交和恢复接单。检查单层各自合理、连起来却互相否定、循环等待、重复执行或无法收尾的情况。不同职责的保护可以保留；不得仅因有多处检查就认定重复或直接删掉。
5. **共享规则是否真是同一来源。** 检查调用方是否实际调用共用实现，还是只统一名称、又在本地追加另一套语义。车金内置 OmniAuto 与共享仓的受影响模块、生成合同及消费者须按既定同步机制核对内容/指纹。合法镜像、生成代码和基于同一合同的独立复核不算第二套设计；独立阈值、默认值、兜底或未经声明的语义分叉才是需解释的风险。
6. **测试有没有绕开冲突点。** 必须用真实生产者输出进入真实消费者，贯通本次受影响的判断/传递边界，断言最终行为而非仅字段存在。涉及事故图时使用原图和真实 OCR；必要的系统或物理操作替身须披露。不得手工补出生产链丢失的证明、替程序触发本应自动发生的回调、直接改状态来证明贯通。局部单测可以构造字段，但不能代替这类贯通证据。
7. **正反例是否能发现旧冲突。** 根据本次风险验证正常情况应通过、危险情况应拒绝，以及相关旧记录/恢复入口应如何处理。修复验证须有针对性的反向对照：恢复冲突判断、去掉传递或关闭自动衔接时，对应正例应失败；不能只证明局部函数变了。保留原始输出、代码指纹和替身边界，不把互相重复的测试数量当成覆盖证明。

### 9.3 报告与放行标准

每次审计结论必须包含“规则统一性”结果，至少说明：

- 本次检查的业务事件、权威规则来源及涉及模块/入口。
- 是否存在有效的旧规则入口、平行判定、上下游字段/状态冲突；无发现也要注明已核查范围。
- 跨边界正反例的实际结果、原始证据及未覆盖范围。

对本次受影响链路，确认存在规则冲突或缺少关键传递链证据时，不得宣称该链路复审通过；缺证不自动认定为代码缺陷，应明确列为待补证。不得据局部通过声称“整个项目没有多套规则”或承诺以后不会再漏场景。

整改优先统一已有规则入口、补齐合同传递或移除已确认废弃判断；不默认增加一层兜底、一套评分、另一种恢复流程或大规模重构。审计发现问题不等于获准改产品代码，仍遵守用户确认及工程师实施的分工。
