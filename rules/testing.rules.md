# 测试 Rules

版本：v0.1

日期：2026-06-03

适用对象：测试准入、测试执行、回归、UAT、缺陷、自动化、测试报告。

## 1. 测试准入硬规则

测试可以提前参与需求评审、接口评审、用例设计、测试数据准备和联调冒烟，但正式测试执行必须等前后端开发完成、前后端自测完成、前后端联调完成后才能开始。

禁止把“联调可测版本”当作“正式测试版本”。

| 状态 | 含义 | 是否允许正式测试 |
|---|---|---|
| 可开发联调 | 前后端可开始对接口和页面 | 不允许 |
| 可测试准入 | 开发自测完成、联调完成、核心阻塞缺陷关闭 | 允许 |
| 可验收 | 正式测试通过、验收标准明确、遗留问题已确认 | 允许验收 |

## 2. 测试结论优先级

同一事项出现多个报告时：

1. 后续回归报告优先于首轮测试报告。
2. 原始结果 JSON 优先于二手总结。
3. 自动化验收结果优先于人工口头描述。
4. 代码实现只能证明“存在实现”，不能替代测试通过。
5. 测试通过不等同于客户验收通过。

## 3. P0 前端验收防漏测规则

前端 P0 验收必须从“元素存在 / 接口返回”升级为“用户可读、可点、可完成、状态真实变化”。

必须遵守：

1. 禁止把“元素存在”当作“功能通过”。
2. 禁止把“接口返回成功”当作“页面通过”。
3. 按钮、下拉框、Tab、提示文案必须真实点击、选择或切换。
4. 操作后必须验证业务结果变化，而不是只验证 DOM 中有文字。
5. 错误提示、重复提示、成功提示不得遮挡标题、表单项、按钮。
6. 重复手机号、保存失败、权限不足、空数据、加载失败等场景，必须验证用户下一步入口是否可见可点。
7. 每个 P0 前端用例至少包含功能断言、展示断言、可用性断言。
8. 用户截图指出的问题，必须反向补自动化或复测用例。
9. 测试报告不得用“已展示提示”这种模糊口径。
10. 测试结论必须区分接口通过、交互通过、展示通过。

## 4. UI 测试规则

1. 当前 UI 按本地设计稿/本地静态稿验收。
2. 新增客户弹窗此前只测了结构存在，未按本地稿验证视觉一致性；该项必须重测。
3. 视觉复核必须使用固定视口、固定数据、固定页面状态。
4. 桌面主分辨率至少覆盖 `1440x1000`。
5. 移动端如果非 P0 范围，必须在报告中明确标注“不作为 P0 通过依据”。

## 5. 测试报告要求

测试报告必须包含：

1. 测试范围。
2. 不测范围。
3. 环境和入口。
4. 执行结果。
5. 失败项和缺陷编号。
6. 证据路径。
7. 结论：通过 / 有条件通过 / 不通过。
8. 遗留问题是否阻塞验收。

## 6. 当前测试结论口径

当前可以说：

```text
P0 API、UAT、Vite 冒烟、性能已有通过证据。
```

当前不能说：

```text
桌面 UI 全盘完全通过。
```

原因：新增客户弹窗与本地设计稿不一致，需修复复测。
