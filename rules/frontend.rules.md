# 前端 Rules

版本：v0.4.3

日期：2026-07-03

适用对象：Vite/React 前端、页面实现、弹窗、交互、浏览器验收、设计还原。

## 1. 开发前澄清

涉及代码实现、页面开发、工程化迁移或重构前，必须确认：

| 检查项 | 必须确认的问题 |
|---|---|
| 产物性质 | 当前看到的是设计稿、静态原型、旧实现、临时代码，还是正式工程 |
| 工程基准 | 最终交付入口是 Vite/React、静态 HTML 还是其他工程 |
| 复用策略 | 静态稿/原型是迁移来源，还是仅视觉参考 |
| 设计基准 | 当前以哪个本地设计稿/截图/静态稿为准 |
| 功能基准 | 只是还原视觉，还是必须接真实 API 可用 |
| 验收口径 | 截图一致、功能可用、测试通过是否都要满足 |

未确认前不得新建平行实现。

除非用户明确要求追溯历史、清理旧版或比对旧版，前端不得打开、引用或依据旧版/废弃文档判断当前页面范围、设计基准、开发任务或验收标准。

处理缺陷时，必须先完成问题定责和证据梳理，说明现象、复现条件、涉及层级、日志/截图/接口证据和待验证假设；未确认根因前不得直接改代码、不得用临时兜底字段或绕过式逻辑掩盖问题。

确认根因后的修复必须直面根因，不允许用缓存、跳过校验、降低门禁、强行兜底或其他绕过方案替代根因修复。兜底链路只能作为正常业务降级路径保留，例如 Worker C2 读取前首屏扫描未唯一命中目标时，可以降级为 `search_by_remark_code` 定向搜索；但如果根因是 OmniAuto 首屏 OCR/解析漏掉可见会话，则必须修复 OCR/解析能力，不能只靠最近缓存或直接搜索绕过。

每次缺陷修复必须同步补齐能证明根因是否解决的报告字段、截图或结构化日志，避免回归失败后无法判断是 OCR、解析、Worker 调度、后端状态还是人工测试现场问题。

## 2. 当前 P1a 前端口径

1. 当前本地 UI 基准是 `website/ops-admin.html/css/js`。
2. 当前正式前端工程是 `frontend/`。
3. 销售管理已升级为 P1a：Worker 绑定状态、阻塞任务、详情抽屉原地编辑、新增销售可选 Worker。
4. Worker 管理已进入正式前端：Worker 列表、详情、Token、启停、心跳、绑定销售、重置绑定。
5. 任务中心已进入正式前端并已完成复测；后续只按缺陷或验收反馈修改。
6. 车金 Worker 客户端本期只做 Windows 单应用，不做 Mac 版。
7. Worker 客户端 UI 基准为 `website/worker-workbench.html/css/js` 和 `deliverables/P1a_车金Worker客户端_Windows单应用_UI草图说明_2026-06-11.md`。
8. OmniAuto 只能作为 Worker 客户端内置 RPA 执行组件表达，不得做成第二个应用、第二个品牌或商家需要单独操作的入口。
9. OmniAuto 仓库同步必须先以 `meta-xucong/omniauto` 更新用户 fork `edwardzhang0304/omniauto`，再让本地从 `edwardzhang0304/omniauto` 拉取；不得绕过用户 fork 直接把 `meta-xucong/omniauto` 作为本地集成来源，也不得强推覆盖用户 fork。
10. Worker 客户端自动接单时段只控制是否领取新任务，不控制在线/离线；页面文案必须使用 `自动接单时段`，非接单时段下 Worker 状态仍写 `暂停接单`，不得写成 `在线时段 / 离线时段`。
11. Worker 客户端设置首页只放 `自动接单时段` 入口；具体开关、接单开始时间、接单结束时间和说明文案放在 `设置 / 接单时段设置` 二级页，结构对齐本机执行日志二级页。
12. Worker 客户端安装包出厂必须是未绑定状态，不得包含 Worker Token、`worker_id`、`client_instance_id` 或本机绑定缓存；首次启动展示绑定页，绑定后只允许保存在本机，重新发包绝不能带入当前机器缓存。

## 3. 前端实现规则

1. 如果已有静态稿或可运行原型，必须先判断是否能作为 Vite/TypeScript 正式工程迁移来源。
2. 不允许先做一套静态页面，再另起一套 Vite 页面，除非用户明确要求两套产物。
3. 设计还原和工程化实现应尽量在正式前端工程内完成。
4. 临时静态稿必须提前说明“不是正式工程”，并给出迁移计划。
5. 开发前必须回答：最终用户会用哪个入口，测试会测哪个入口，上线会部署哪个入口。

## 4. UI 还原规则

1. 当前按本地设计稿/本地静态稿还原，不以 Figma 作为当前最终基准。
2. 给前端的修改必须有可执行来源：文件、截图、组件名、页面路径或 CSS token。
3. 弹窗、抽屉、表格、分页、提示条必须检查无重叠、无遮挡、可读、可点。
4. 修销售管理和 Worker 管理时，不能破坏已通过的线索管理、销售轮询、操作日志、手机号审计等既有能力。
5. 新增 P1a 页面必须覆盖空态、加载态、错误态、成功态和接口失败提示。
6. Worker 客户端正式主流程必须围绕 RPA 自动执行 add_friend 任务，不得把人工传值做成正常业务主入口。

## 5. 前端自测交付

前端提交“完成/自测说明”必须包含：

1. 开发范围。
2. 运行入口。
3. `npm run build` 结果。
4. `npm run test` 结果。
5. 联调接口清单。
6. 浏览器验收结果。
7. 已知问题。
8. 不包含范围。

## 6. 禁止事项

1. 禁止把“元素存在”当作“功能通过”。
2. 禁止把“接口返回成功”当作“页面通过”。
3. 禁止只修 happy path，不处理重复、异常、失败、空态。
4. 禁止在设计基准不清时宣称“已复刻”“一比一”“和设计稿一致”。
5. 禁止把移动端兼容偷偷写成 P1a，除非项目经理明确纳入。
