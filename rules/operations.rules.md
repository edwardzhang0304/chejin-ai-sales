# 运维与发布约束

版本：v0.1.0

日期：2026-09-07

适用范围：部署、正式发包、客户端升级、生产变更、故障止血及运维结论。执行前同时读取根目录 `rules.md`、测试规则和四份权威文档的当前状态。本文件是运维角色执行约束；具体版本、包哈希、事故状态和执行记录仍写入版本更新记录。

## 1. 先判断可行性，再决定执行路径

1. 开始前确认业务影响、故障时间线、当前运行状态、最近变更及数据风险；缺失项标注【待确认】，不得凭用户想要的体验补齐技术事实。
2. 运维必须给出自己的结论和依据：可执行、需更换实施路径，或阻断待验证。用户希望“一键升级”不能代替兼容性证明；授权执行也不等于技术条件通过。
3. 发现旧版本能力不支持、关键证据缺失或实机失败，必须先明确说明“本轮不能继续采用该自动升级路径”，给出已知限制和可验证的替代路径。不能先承诺能升级，再临时拼接兼容逻辑让生产用户试错。
4. “没有证明兼容”足以阻断生产自动升级，但不能据此编造“所有环境永远无法兼容”的根因结论。根因分析继续以日志、进程、数据差异和变更证据为准。

## 2. 第一次升级必须按旧客户端真实能力评估

1. 先固定起点和终点：原始已发布客户端及其内置 Updater 的版本、来源、哈希、信任配置，目标正式包的来源、签名、哈希、协议、最低 Updater 要求和数据格式。
2. 明确第一次实际运行哪个更新器、谁生成更新计划与数据摘要、谁等待退出和恢复结果。新包里的修复不能提前改变旧客户端和旧 Updater 的行为。
3. 旧端退出收尾、残留写入、快照时序、恢复状态或协议不满足目标包要求时，禁止仅降低最低 Updater 版本、忽略时间戳/数据差异、重拍基线、替换可信公钥或绕过校验来宣称兼容。
4. 兼容桥接属于需要完整验证的新实现。模拟场景成功只能使它进入隔离验证，不能直接开放生产更新。

## 3. 自动升级的发布阻断条件

必须在开放生产自动更新之前，完成目标升级起点的完整验证；任一项缺失或失败即阻断：

| 必须核验的事项 | 合格证据 | 不足以放行的证据 |
|---|---|---|
| 真实起点 | 原始已发布 Worker + 它实际内置的 Updater | 用受控进程模拟旧 Worker，或重编译/替换旧 Updater |
| 用户入口 | 从原客户端“检查更新”进入，贯通生产协调器、下载、校验、退出、替换、启动、结果对账 | 直接构造计划或调用新 Worker 启动接口 |
| 实际终点 | 本次不可变正式包，记录来源和包哈希 | 另一个测试包、相同版本号的不同构建 |
| 已有状态 | 带绑定、配置和有代表性业务状态的隔离数据，覆盖暂停、退出收尾和恢复路径 | 只有空数据库、新装客户端或简单存活标记 |
| 数据与故障 | 按约定时点核验受保护数据、必要初始化、失败恢复及暂停/故障状态保持 | 只核对版本号、行数或进程能启动 |

实机可以由自动化操作，但必须运行真实旧客户端及真实用户入口；“在 Windows runner 上运行”不自动等于完整实机链路通过。允许在隔离环境提供与生产等价的更新接口，必须注明环境和未覆盖部分，禁止借验证先向全部生产客户端登记开放。发布后的用户现场复核用于确认现场环境，不能替代发布前兼容准入。

## 4. 实机失败立即改变发布判断

1. 收到真实用户升级失败反馈，立即将该起点到目标的路径标为“不通过/停止推荐”，停止扩大该路径的发布；保留已有自动化通过记录，但不得拿测试数量否认现场失败。
2. 根因尚未明确也必须先阻断风险扩大。按已有授权范围评估并处理生产更新入口；撤回、限制或保持现状都要记录实际动作和验证结果。未执行不得写成“已关闭入口”。
3. 保存错误时间、版本、包哈希、日志和数据差异摘要，不输出密钥、客户内容或绑定原值；禁止要求用户反复点击更新来试错。
4. 修复后复测真实失败路径及受影响恢复场景，证据绑定新的实际构建；不能沿用失败前的成功报告重新放行，也不得覆盖已发布的同版本包。

## 5. 保留数据的强制安装升级

1. 自动路径不合格时，运维应选择保留数据的安装升级方案，并先验证该方案；不得仅改口称“强升”就让用户直接覆盖目录。
2. 执行前查清程序目录、实际数据目录、启动方式、相关进程、绑定/配置存储位置、目标包身份及需要保留的业务文件。目录或停机状态不明时，禁止给出覆盖命令。
3. “强升”指绕过不合格的旧自动更新入口，通过受控安装更换程序；不等于强杀仍在处理业务的进程、关闭验签、删除数据库、清空绑定或重置配置。
4. 排空任务并正常退出所有相关写入者；验证目标包和数据保留边界后再更换程序，启动后核验版本、绑定、配置、业务数据、心跳及受影响业务，最后恢复接单。
5. 先说明失败时的停止条件、程序恢复能力与限制；备份/恢复按本次明确授权执行并记录例外。免备份授权不能抵消兼容和数据保护门禁，也不能据此承诺无风险。

## 6. 运维汇报与流程边界

1. 分别报告：构建、验签、传输、更新登记、下载、真实旧客户端升级、业务验收。每项只能标记“通过/失败/待验证/未执行”，不得合并成一句“发布成功，可以升级”。
2. 只有对应起点的真实升级链路通过，才能告诉用户“该版本可以点击更新完成升级”；否则应直接说明当前不支持本轮自动升级、阻断原因和下一实施路径。
3. 每个生产方案必须写清检查、执行、验证、故障处理及恢复限制。用户提出失败时，先纠正当前结论并止血，再分析根因；不为维护此前承诺降低门禁。
4. 正式包继续 GitHub → 生产隔离目录直传；Fast UAT 继续 GitHub ZIP → Mac → 原 ZIP + 命令行流程。用户另行要求下载正式包到 Mac，不等于改变正式发布传输流程。
5. 写入约束文档不等于流水线已经实现自动阻断，也不等于生产入口已经撤回；必须分别记录规则、代码门禁和实际生产状态。
