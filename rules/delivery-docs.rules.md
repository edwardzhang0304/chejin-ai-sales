# 交付与文档 Rules

版本：v0.5.2

日期：2026-06-30

适用对象：项目文档总目录、文档变更日志、日报、交付物、合同、报价、归档。

## 1. 文档入口规则

1. `项目文档总目录.md` 是当前唯一入口。
2. 未列为当前有效的文档不得作为排期、开发、测试、验收或客户沟通依据。
3. 除非用户明确要求追溯历史、清理旧版或比对旧版，交付与文档角色不得打开、引用或依据旧版/废弃文档判断当前文档有效性、范围、进度、测试、验收或客户交付状态。
4. 新增、废弃、删除文档必须同步更新 `项目文档总目录.md` 和 `文档变更日志.md`。

## 1.1 版本管理规则

1. 文档变更前必须先判断变更类型：新增需求、模块级变化、细节级变化、纯修订。
2. 新增需求必须升版本号，并同步更新文档总目录、变更日志和一致性检查。
3. 模块级变化升大版本，例如 `v2.0 -> v3.0`。
4. 细节级变化升小版本，例如 `v2.0 -> v2.1`、`v2.1 -> v2.2`。
5. 纯修订不更改版本号，只更新文档内修订记录和 `文档变更日志.md`；纯修订包括错别字、表述更准确、引用路径修正、已定口径的补充说明。
6. 不能把“新增需求”写成“内部修订”来规避升版；若不确定属于新增还是修订，必须标注【待确认】并先让架构师/产品负责人确认。
7. 新增专项文档必须从自身 `v0.1` 或对应起始版本开始命名，文件名必须包含版本号和日期。

## 2. 当前活跃口径

1. P0 已收口，相关旧文档已从活跃目录清理，不作为当前依据。
2. 当前活跃范围按技术方案 C0/C1/C2 推进：C0 线索入库与分配，C1 add_friend，C2 会话绑定/微信监听。
3. 当前执行范围以 PRD v0.4.4、UML v0.6、技术方案 v0.6、本地静态稿、Windows Worker UI 草图和相关后端接口说明为准。
4. 当前 C2 v0.6 测试不得引用 P0 或旧 C2 报告作为最终通过依据。
5. 不再生成对外资料包，后续客户可见内容只看正式交付物。

## 3. 每日文档巡检必须看

| 范围 | 必查路径 |
|---|---|
| 总入口 | `项目文档总目录.md` |
| 变更记录 | `文档变更日志.md` |
| 产品 | `deliverables/*PRD*` |
| 技术 / UML | `deliverables/*技术方案*`、`deliverables/*UML*` |
| UI 静态稿 | `website/` |
| 前端工程 | `frontend/` |
| 后端工程 | `backend/` |
| 合同报价 | `contracts/`、`deliverables/*报价*` |

## 4. 风险发现规则

以下情况必须指出：

1. 活跃目录出现已经废弃的 P0 或旧版本文档。
2. PRD、UI、技术方案对同一当前阶段功能范围不一致。
3. 代码已实现但文档总目录未更新。
4. 文档写“已完成”，但没有对应代码、自测或测试证据。
5. 测试报告引用了错误阶段的验收标准。
6. 活跃文档继续把 Mac Worker、人工传值主流程、PRD v0.2、PRD v0.4.1、技术方案 v0.4/v0.5 或“任务中心产品 check 中”作为当前执行口径。

## 5. 清理规则

1. 当前活跃目录只保留正在推进或仍作为依据的文档。
2. 旧版文档如需删除，先确认不属于当前有效入口或测试证据。
3. 历史脚本、截图、旧测试 JSON、旧验收报告不得散落在 `deliverables/` 根目录。
4. 用户明确要求“不留归档”时，不再创建 `archive/` 作为替代入口。
